이 섹션은 생명주기를 설명합니다.[튼튼한 목표](/durable-objects/concepts/what-are-durable-objects/).

당신이 만들 필요가 튼튼한 개체를 사용하려면[튼튼한 목표 Stub](/durable-objects/api/stub/)·
튼튼한 Object Stub를 만드는 것은 튼튼한 개체에 요청을 보내지 않으며, 따라서 튼튼한 Object는 아직 즉시 되지 않습니다.
요청은 내구성 객체와 그 수명주기에 전송됩니다. 한 번의 방법은 튼튼한 Object Stub에서 호출됩니다.

```js
const stub = env.MY_DURABLE_OBJECT.getByName("foo");
//이제 요청은 원격 내구성 개체로 전송됩니다.
const rpcResponse = await stub.sayHello();
```

## 튼튼한 목표 Lifecycle 국가 전환

튼튼한 개체는 다음 주 중 하나에 있을 수 있습니다:

| 주요 특징                            | 이름 \*                                                                                                |
| -------------------------------- | ---------------------------------------------------------------------------------------------------- |
| **활동, in-memory**                | 튼튼한 객체는 메모리에서 실행되며 수신 요청을 처리합니다.                                                                     |
| **아이들, in-memory 비 난연성**         | 튼튼한 목표는 다음 들어오는 요청/출구를 기다립니다, 그러나 hibernation를 위한 기준을 만족하지 않습니다.                                     |
| **아이들, in-memory hibernateable** | 튼튼한 목표는 다음 들어오는 요청/출구를 기다립니다. 튼튼한 개체를 hibernate 할 때 결정하는 런타임까지입니다. 현재, 이 상태에서 10 초의 inactivity 후입니다. |
| **채용 정보**                        | 튼튼한 개체는 메모리에서 제거됩니다. Hibernated WebSocket 연결은 연결됩니다.                                                 |
| **관련 기사**                        | 튼튼한 목표는 주인 과정에서 완전하게 제거되고 찬 시작을 필요로 할지도 모릅니다. 이것은 모든 Durable Objects의 처음 상태입니다.                      |

이 주 중의 튼튼한 목표 전환은 어떻게 (각 국가는 둥근 직사각형에 있습니다).

![튼튼한 목표의 수명주기](~/assets/images/durable-objects/lifecycle-of-a-do.png)

튼튼한 개체가 실행되지 않습니다, 첫 수신 요청 또는 이벤트 (예 : 알람과 같은) 실행`constructor()`튼튼한 목표 종류의, 그 후에 대응 함수를 실행합니다.

이 시점에서 튼튼한 개체는**활동 in-memory 상태**.

모든 들어오는 요청 또는 이벤트가 처리되면, 튼튼한 개체는 hibernateable 상태 또는 non-hibernateable 상태에서 몇 초 동안 유휴 in-memory 남아 있습니다.

Hibernation는 경우에만 일어날 수 있습니다**모든 것**아래의 조건은 true:

- 이름 \*`setTimeout`/`setInterval`예약된 콜백은 설정되어, hibernating 후 콜백을 다시 만들 수 없습니다.
- 자주 묻는 질문`fetch()`존재, 그것은 I / O를 기다리고 있기 때문에.
- WebSocket 표준 API가 없습니다.
- 요청/event는 여전히 처리되지 않습니다. hibernating는 그 요청에 응답을 반환하기 위해 결국 async 함수의 트랙을 잃게됩니다.

들어오는 요구 또는 사건의 10 초 후에, 전부 만족된 조건은, 튼튼한 목표 전환할 것입니다**이름 \***&#xAD6D;가.

:::카트로션
hibernated 때, in-memory 상태는 discarded, 그래서 당신은 튼튼한 목표의 저장에 있는 모든 중요한 정보를 주장합니다.
주요 특징

위의 조건 중 하나가 거짓이라면, 튼튼한 개체는 in-memory에 남아 있습니다.**idle, in-memory, 비 난연성**국가.

수신 요청 또는 이벤트의 경우**이름 \***&#xAD6D;가,`constructor()`다시 실행하고, 튼튼한 목표는 전환 할 것입니다**활동, in-memory**state와 invoked 함수를 실행합니다.

동안에**idle, in-memory, 비 난연성**상태, inactivity의 70-140 초 후에 ( 들어오는 요구 또는 사건 없음), 튼튼한 목표는 Cloudflare 주인에서 전적으로 evicted이고 전환합니다**관련 제품**국가.

목표에**이름 \***&#xC0C1;태는 Websocket 클라이언트가 연결되고, 런타임은 객체를 전환 할 때 결정합니다.**관련 제품**state (예를 들어 객체를 다른 호스트로 이동) 따라서 Lifecycle을 다시 시작합니다.

다음 수신 요청 또는 이벤트는 다시 사이클을 시작합니다.

:::노트\[Lifecycle state incurring period Charge]
튼튼한 Object incurs는 때만 청구됩니다**in-memory에 대해**, 또는 때**idle in-memory와 비 난연성**(도표에 녹색 직사각형으로 사용).

## Shutdown 동작

Durable Objects는 때때로 닫히고 물체는 당신의 튼튼한 목표 종류 constructor를 달릴 것입니다. 다음과 같은 다양한 이유로 발생할 수 있습니다:

- 새로운 노동자[설치하기](/workers/configuration/versions-and-deployments/)코드 업데이트
- 위의 상태 전환을 따르는 객체에 대한 요청의 부족
- Cloudflare 업데이트 Workers 런타임 시스템
- Workers 런타임은 객체를 호스트하는 곳의 결정

튼튼한 개체가 종료되면 객체 인스턴스가 자동으로 재시작되고 새로운 요청이 새로운 인스턴스로 경로를 지정합니다. In-flight 요청은 다음과 같이 처리됩니다.

- **HTTP 요청**: In-flight 요청은 최대 30 초 동안 마무리 할 수 있습니다. 그러나 요청이 우아한 기간 동안 튼튼한 개체의 저장에 액세스하려고 시도하면 Durable Objects 글로벌 고유 특성을 유지하기 위해 즉시 중지됩니다.
- **WebSocket 연결**: WebSocket 요청은 종료 중에 자동으로 종료됩니다. 이것은 새로운 인스턴스가 가능한 한 빨리 연결을 취할 수 있도록.
- **기타 직업 (이메일, cron)**: 다른 invocations는 HTTP 요청과 유사하게 처리됩니다.

Durable ObjectsXQ를 사용하여 어떤 서비스가 중단되는 튼튼한 목표의 가능성을 처리하도록 설계되었습니다.

### Code 업데이트

튼튼한 개체 코드가 업데이트되면 Worker 및 Durable Objects는 결국 일관된 방식으로 글로벌 출시됩니다. 이것은 위에 설명 된 행동과 함께 종료 할 수있는 튼튼한 개체를 일으킬 것입니다. 업데이트는 또한 요청이 한 위치에 작업자의 새로운 버전을 도달 할 수있는 상황을 만들 수 있으며, 다른 곳에서도 기존 버전을 실행하는 튼튼한 개체에 전화합니다. 더 알아보기[Code 업데이트](/durable-objects/platform/known-issues/#code-updates)이 시나리오를 처리하는 방법에 대한 자세한 내용은.
