Cloudflare는 각 가치 조합을 위한 비율 제한 규칙을 위한 분리 비율 카운터를 지킵니다<GlossaryTooltip term="rule characteristics">규칙 특성</GlossaryTooltip>.

다음 특성으로 구성된 규칙을 고려하십시오:

- IP 주소
- HTTP 헤더`x-api-key`

이 경우, HTTP 헤더에 대한 동일한 값을 가진 두 수신 요청`X-API-Key`하지만 다른 IP 주소는 값 조합이 다르기 때문에 별도로 계산됩니다. 또한, 카운터는 데이터 센터를 통해 공유되지 않습니다.

이 비율 제한 규칙의 계산 모델은 들어오는 요청의 수를 기반으로합니다. 고급 비율 제한을 가진 기업 고객은 또한 모델이 들어오는 요청의 복잡성을 기반으로하는 규칙을 구성할 수 있습니다. 더 알아보기[복잡한 비율 제한](#complexity-based-rate-limiting)더 많은 정보.

:::note\[중요한 노트]

- Cloudflare는 현재 전체 네트워크에서 카운터를 제한하는 글로벌 속도를 지원하지 않습니다 - 카운터는 데이터 센터를 통해 공유되지 않습니다. 이 사실은 특히 IP 주소를 하나의 비율 제한 특성으로 추가하지 않는 고객에 대한 관련입니다. Cloudflare는 해당 지리적 위치와 관련된 여러 데이터 센터를 보유하고 있습니다. 이 경우, 제한 카운터의 비율은 해당 특정 데이터 센터 사이에 공유됩니다.

- Cloudflare 데이터 센터 ID (`cf.colo.id`)는 데이터 센터를 통해 카운터가 공유되지 않도록 모든 비율 제한 규칙의 필수 특성입니다. 이 특성은 대시보드의 규칙 구성에 나타나지 않지만 필요할 때[API를 통한 제한 규칙 생성](/waf/rate-limiting-rules/create-api/).

- 유효한 특성은 Cloudflare 계획에 달려 있습니다. 더 알아보기[적용분야](/waf/rate-limiting-rules/#availability)더 많은 정보.

- 일부 상황에서 Workers subrequests는 동일한 영역으로 계산됩니다. 이는 예상보다 더 빨리 방아쇠하는 비율 제한 규칙을 일으킬 것입니다. 더 알아보기[문제 해결](/waf/rate-limiting-rules/troubleshooting/#some-workers-subrequests-are-counted-as-separate-requests)상세 정보

:::

## 예제 A

제한 규칙의 비율에 대한 다음 구성을 고려:

<Example>
  ***비율 제한 규칙 #1***

  **수신 요청 일치**:<br />
  `http.request.uri.path eq "/form" and any(http.request.headers["content-type"][*] eq "application/x-www-form-urlencoded")`

  **자주 묻는 질문**: *제품정보*

  **이름 \***(송금 시간):*10 분*

  **제품정보**: `1`

  **기간 :**: *10 초*

  **동일한 특성으로**:

  - *데이터 센터 ID*(대시보드의 규칙을 만들 때 기본적으로 포함)
  - *IP 정보*
  - *헤더 값* > `x-api-key`
</Example>

다음 다이어그램은 Cloudflare가 위의 비율 제한 규칙의 상황에 4 개의 들어오는 요청을 처리하는 방법을 보여줍니다.

![요청 중 하나가 제한되는 4개의 요청을 가진 비율. 세부사항을 위해, 독서를 지킵니다.](~/assets/images/waf/custom-rules/rate-limiting-example.png)

요청 이후 1 규칙 표현, 제한 규칙은 평가됩니다. Cloudflare는 비율 제한 규칙의 상황에 있는 특성의 값에 대한 요청 카운터를 정의하고 카운터를 설정`1`. 카운터 값이 설치된 제한 안에 있기 때문에**제품정보**, 요청은 허용됩니다.

요청 2 규칙 표현과 따라서 Cloudflare는 제한 규칙을 평가합니다. 특성의 값은 기존 카운터와 일치하지 않습니다 (값의 값`X-API-Key`헤더는 다릅니다. 따라서 Cloudflare는 이 규칙의 상황에 별도의 카운터를 정의하고 그것을 설정한다.`1`. 카운터 값은 요청 제한 내에서 설치됩니다.**제품정보**, 그래서이 요청은 허용됩니다.

요청 3 규칙식을 일치하고 규칙 특성에 대한 동일한 값을 요청 1. 따라서 Cloudflare는 기존 카운터의 값을 증가시켜 설정하여`2`. 카운터 값은 이제 제한 위에 정의되어 있습니다.**제품정보**, 그래서 요청 3 블록.

요청 4 규칙 표현과 일치하지 않습니다.`Content-Type`헤더는 표현의 값과 일치하지 않습니다. 따라서 Cloudflare는 이 요청에 대한 새로운 규칙 카운터를 만들지 않습니다. 요청 4 이 비율 제한 규칙의 컨텍스트에서 평가되지 않고 요청 평가 워크플로우의 후속 규칙에 전달됩니다.

  ***비율 제한 규칙 #2***

  **수신 요청 일치**:<br />

![비율 제한 예와 4 개의 요청으로 제한 속도 제한 규칙은 응답 필드 (HTTP 응답 코드) 계산 표현에서. 세부사항을 위해, 독서를 지킵니다.](~/assets/images/waf/custom-rules/rate-limiting-example-response-field.png)

요청 이후 1 규칙 표현, 제한 규칙은 평가됩니다. 이 요청은, 어떤 캐시 된 내용을 건너, 비율 제한 규칙은 응답 필드를 포함하기 때문에 (이)`http.response.code`) 계산 표현에서. 기원은 응답`400`상태 코드. 계산 표현에 대한 일치가 있기 때문에 Cloudflare는 제한 규칙의 맥락의 특성에 대한 요청 카운터를 만들고이 카운터를 설정`1`.

요청 2 규칙 표현과 따라서 Cloudflare는 제한 규칙을 평가합니다. 특성 값에 대한 요청 카운터는 여전히 정의 된 최대 번호 내에서**제품정보**. 기원은 응답`200`상태 코드. 응답은 계산 표현과 일치하지 않습니다, 카운터는 증가하지 않습니다, 그것의 가치를 유지 (`1`).

요청 3 규칙 표현과 따라서 Cloudflare는 제한 규칙을 평가합니다. 요청은 여전히 정의된 최대 번호 내에서**제품정보**. 기원은 응답`400`상태 코드. 카운터를 설정하는 카운트 표현의 일치가 있습니다.`2`.

요청 4 규칙 표현과 따라서 Cloudflare는 제한 규칙을 평가합니다. 요청에 정의된 최대 번호 내에서 더 이상 없다**제품정보**( 카운터에는 값이 있습니다.`2`그리고 최대 요청 수는`1`). Cloudflare는 규칙 윤곽을 제한하는 비율에서 정의된 활동을, 차단하는 요구 4 그리고 10 분 동안 제한 규칙과 일치하는 어떤 나중에 요구 적용합니다.

## 복잡한 비율 제한

:::참조
Advanced Rate Limiting으로 Enterprise 고객에게만 사용할 수 있습니다.
주요 특징

규칙을 제한하는 복잡성 기반 비율은 같은 기간에 요청의 수 대신 주어진 기간 동안 복잡성 또는 비용에 따라 제한 비율을 수행합니다.

일반적인 사용 사례는 해당 요청을 제공하기 위해 필요한 비용 (또는 복잡성)의 견적으로 각 요청을 점수하는 것입니다. 각 클라이언트가 주어진 기간 동안 신청에 넣을 수 있는 전체 복잡성에 제한을 시행할 수 있습니다. 즉, 클라이언트가 보낸 요청의 총 수에 관계없이.

복잡한 비율 제한 규칙을 구성할 때, Origin 서버는 복잡성 점수와 HTTP 헤더를 포함해야 합니다. 이 점수는 현재 요청을 제공하는 복잡성 (또는 비용)에 해당합니다. 점수 값은 1과 1,000,000 사이이어야 합니다.

복잡한 비율 제한 규칙은 다음과 같은 속성을 포함해야합니다:

- [기간별 점수](/waf/rate-limiting-rules/parameters/#when-rate-exceeds--score-per-period): 기간 당 최대 점수. 이 값이 초과되면 규칙 동작이 실행됩니다.
- [기간 :](/waf/rate-limiting-rules/parameters/#when-rate-exceeds--period): 요청률을 평가할 때 고려할 시간의 기간.
- [응답 헤더 이름](/waf/rate-limiting-rules/parameters/#when-rate-exceeds--response-header-name): 응답의 HTTP 헤더의 이름, 원래 서버로 설정, 현재의 요청에 대한 점수.

Cloudflare는 규칙 표현과 일치하는 규칙 특성에 대한 동일한 값과 모든 요청의 총 점수와 카운터를 유지합니다. 점수는 응답의 근원에 의해 제공된 값에 의해 증가합니다 (기본적으로, 그것은 규칙 표식과 동일하) 계산 표식에 대한 일치가 있을 때. 총 점수가 설정된 최대 점수보다 크면, 규칙 동작이 적용됩니다.

소스 서버가 HTTP 응답 헤더를 점수 값으로 제공하지 않거나, 점수 값이 허용 범위 밖에 있는 경우, 해당 비율 제한 카운터가 업데이트되지 않습니다.

### 예제 C

제한 규칙의 비율에 대한 다음 구성을 고려하십시오. 규칙 일치가있을 때, 복잡성 점수 카운터는 값에 따라 증가합니다.`x-score`Origin 서버에서 제공하는 응답 헤더.

<Example>
  ***비율 제한 규칙 #3***

  **수신 요청 일치**:<br />
  `(http.request.uri.path eq "/graphql")`

  **동일한 특성으로**:

  - *데이터 센터 ID*(대시보드의 규칙을 만들 때 기본적으로 포함)
  - *헤더 값* > `x-api-key`

  **비율 초과시**: *회사연혁*

  - 기간 당 점수:`400`
  - 기간:*1 분*
  - 응답 헤더 이름:`x-score`

  **자주 묻는 질문**: *제품정보*

  **다음 행동으로**: *선택한 기간 동안 블록*

  **이름 \***(송금 시간):*10 분*
</Example>

다음 다이어그램은 Cloudflare가 위의 비율 제한 규칙의 맥락에서 1 분 기간 동안받은 4 개의 들어오는 요청을 처리하는 방법을 보여줍니다.

![제한율은 4개의 요청으로, 제한율은 "x-score" HTTP 헤더에서 제공하는 복잡성 점수를 고려해야 합니다. 세부사항을 위해, 독서를 지킵니다.](~/assets/images/waf/custom-rules/rate-limiting-example-complexity-based.png)

요청 이후 1 규칙 표현, 제한 규칙은 평가됩니다. 기원은 응답`200`상태 코드와 복잡성 점수의`100`내 계정`x-score`HTTP 응답 헤더. Cloudflare는 비율 제한 규칙의 상황에 있는 특성의 가치를 위한 요청 카운터를 만들고, 이 카운터를`100`.

요청 2 규칙 표현과 따라서 Cloudflare는 제한 규칙을 평가합니다. 특성 값에 대한 요청 카운터는 기간 당 최대 점수 내에서 여전히됩니다. 기원은 응답`200`상태 코드 및 요청 카운터가 증가`200`. 요청의 현재 복잡성 점수는 이제`300`.

요청 3 규칙 표현과 따라서 Cloudflare는 제한 규칙을 평가합니다. 특성 값에 대한 요청 카운터는 기간 당 최대 점수 내에서 여전히됩니다. 기원은 응답`200`상태 코드 및 요청 카운터가 증가`150`. 요청의 현재 복잡성 점수는 이제`450`.

요청 4 규칙 표현과 따라서 Cloudflare는 제한 규칙을 평가합니다. 요청은 규칙에 정의 된 기간 당 최대 점수 내에서 더 이상 없습니다 ( 카운터에는 값이 있습니다.`450`그리고 최대 점수는`400`). Cloudflare는 규칙 윤곽을 제한하는 비율에서 정의된 활동을, 차단하는 요구 4 그리고 10 분 동안 제한 규칙과 일치하는 어떤 나중에 요구 적용합니다.
