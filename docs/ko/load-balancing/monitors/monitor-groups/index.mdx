여러 헬스 모니터를 함께 그룹화하여 애플리케이션을 위한 정교한 헬스 체크를 만들고, 더 지능적이고 복원력 있는 트래픽 스티어링을 구현하세요.

여러 헬스 모니터를 그룹화하면 애플리케이션의 실제 상태를 더 정확하게 반영하는 정교한 헬스 체크를 만들 수 있습니다. Monitor Group을 사용하면 여러 개의 독립적인 모니터를 결합하고, 집계 로직을 정의한 뒤, 그 집합 결과를 사용해 오리진 풀의 상태를 판단할 수 있습니다.

여러 헬스 모니터를 그룹화하면 더 지능적이고 복원력 있는 페일오버가 가능해집니다. 예를 들어 일반적인 API 게이트웨이 모니터와 특정 로그인 서비스 모니터가 모두 정상일 때만 풀이 트래픽을 받도록 요구할 수 있습니다.

## 사용 가능 여부

Monitor Groups는 Load Balancing 구독이 포함된 Enterprise 플랜 고객만 사용할 수 있습니다.

구성은 [API](/api/resources/load_balancers/subresources/monitor_groups/methods/create/)를 통해서만 가능합니다.

:::note
API를 통해 monitor group에 할당된 풀은 대시보드에서 **Not monitored**로 표시됩니다.
:::

## 동작 방식

풀에 Monitor Group을 연결하면, 해당 풀의 상태는 그룹 내에서 활성화된 모든 모니터의 결과를 집계해 결정됩니다.

아래 섹션에서는 monitor group이 상태, 지연 시간, 결과 처리에 어떤 영향을 미치는지 설명합니다.

## Monitor Groups를 사용할 때의 엔드포인트 상태

Monitor Group은 critical monitor override와 quorum 기반 합의를 결합해 엔드포인트 상태를 결정합니다.

**Critical Monitor Override** (`must_be_healthy`): `"must_be_healthy": true`로 설정하면 해당 모니터를 중요 모니터로 지정할 수 있습니다. 이 설정이 적용된 모니터가 어떤 엔드포인트에 대한 헬스 체크에 실패하면, 같은 그룹의 다른 모니터가 어떤 상태를 보고하든 상관없이 그 엔드포인트는 즉시 비정상으로 표시됩니다. 이는 핵심 서비스에 대해 결정적인 우선 적용 규칙을 제공합니다.

**Quorum-Based Health**: `must_be_healthy` 모니터의 실패가 없는 경우, 엔드포인트 상태는 나머지 모든 활성 모니터의 정족수(quorum)에 따라 결정됩니다.

- 엔드포인트는 할당된 모니터 중 50%를 초과하는 수가 비정상이라고 보고할 때만 비정상으로 간주됩니다.
- `"monitoring_only": true`로 표시된 모니터는 정족수 계산에서 제외됩니다. 이런 모니터도 계속 실행되고 알림을 트리거할 수는 있지만, 엔드포인트 상태 판정에는 표를 행사하지 않습니다.
- `disabled`로 표시된 모니터는 연결된 어떤 풀에도 모니터링 요청을 보내지 않습니다. 이들 역시 정족수 계산에서 제외됩니다.

이 정족수 시스템은 중요하지 않은 단일 모니터의 일시적 실패 때문에 엔드포인트가 너무 일찍 비정상으로 표시되는 일을 방지합니다.

## 스티어링을 위한 지연 시간

Dynamic Steering을 사용하는 풀에서는, 풀의 지연 시간이 활성화되어 있고 monitoring-only가 아닌 모든 모니터의 평균 지연 시간으로 계산됩니다. 이렇게 집계된 RTT(Round Trip Time) 값은 오리진 성능을 더 전체적으로 보여 주며, 스티어링 결정을 내리는 데 사용됩니다.

## 서로 다른 interval의 결과 처리

그룹 내 모니터들이 서로 다른 검사 interval을 가지면, 그룹은 각 모니터의 다음 결과가 갱신될 때까지 마지막으로 उपलब्ध한 결과를 사용합니다. 예를 들어 한 모니터는 10초마다, 다른 모니터는 30초마다 실행된다면, 30초 주기 모니터의 결과는 다음 실행이 완료될 때까지 30초 전체 동안 유효한 것으로 간주됩니다.
