Privacy Proxy는 두 개의 배포 아키텍처를 지원합니다: 단일 채팅 및 이중 채팅. 올바른 선택은 개인 정보 보호 요구 사항 및 운영 preferences에 따라 다릅니다.

## 단 하나 호

단일 채팅 배포에서 Cloudflare는 전체 프록시 인프라를 운영합니다. 클라이언트는 Cloudflare의 개인 정보 보호 프록시에 직접 연결하여 인증, 프록시 및 egress를 처리합니다.

```
┌────────┐      ┌─────────────────┐      ┌─────────────┐
│ Client │ ───▶ │  Privacy Proxy  │ ───▶ │ Destination │
│        │      │  (Cloudflare)   │      │   Server    │
└────────┘      └─────────────────┘      └─────────────┘
```

### 어떻게 작동합니까?

1. 클라이언트는 Cloudflare 프록시 엔드포인트에 HTTP / 2 또는 HTTP / 3 연결을 설정합니다.
2. Privacy Pass 토큰 또는 사전 공유 키를 사용하여 클라이언트 인증.
3. 클라이언트는 CONNECT 요청을 보내 대상 서버에 터널을 설치합니다.
4. Cloudflare 프록시 트래픽을 선택하고 클라이언트 Geolocation에 따라 egress IP 주소를 선택하십시오.

### 사용 사례

Single-hop 배포가 잘 작동 할 때:

- Cloudflare를 원하면 완전한 프록시 인프라를 관리할 수 있습니다.
- 귀하의 개인 정보 보호 모델은 목적지에서 클라이언트 IP 주소를 숨기고, 하지만 프록시 연산자에서 아닙니다.
- 최소 클라이언트 측과의 통합이 필요합니다.

#### 예: Microsoft Edge 보안 네트워크

[Microsoft Edge 보안 네트워크](https://blog.cloudflare.com/cloudflare-now-powering-microsoft-edge-secure-network/)Single-hop 배포를 사용합니다. Edge 브라우저는 Cloudflare의 개인 정보 보호 프록시에 직접 연결하여 개인 정보 보호 패스 및 프록시 트래픽을 대상 서버에 처리합니다. 사용자는 추가 인프라를 구성하지 않고 네트워크 관찰자 및 대상 서버에서 보호를받습니다.

## 더블 홉

더블 홉 배포에서 먼저 프록시 (Proxy A) 및 Cloudflare는 두 번째 프록시 (Proxy B)를 운영하고 있습니다. 단일 파티가 사용자 정체성 및 목적지를 모두 볼 수 없기 때문에 더 강한 프라이버시 분리를 만듭니다.

```
┌────────┐      ┌─────────────┐      ┌─────────────────┐      ┌─────────────┐
│ Client │ ───▶ │   Proxy A   │ ───▶ │    Proxy B      │ ───▶ │ Destination │
│        │      │    (You)    │      │  (Cloudflare)   │      │   Server    │
└────────┘      └─────────────┘      └─────────────────┘      └─────────────┘
```

### 어떻게 작동합니까?

1. 클라이언트는 Proxy A에 연결, 당신이 작동.
2. 다운로드 사용자를 인증하고 서비스를 사용할 수 있습니다.
3. 다운로드 Cloudflare의 프록시 B에 터널을 설치하여 클라이언트의 CONNECT 요청을 전달합니다.
4. 프록시 B는 목적지와 프록시 트래픽에 연결됩니다.
5. 프록시 B는 프록시 A에 의해 제공된 지리적 위치에 근거를 둔 IP를 선택합니다.

### 공급 업체

Double-hop 아키텍처는 다음과 같습니다.

| - 연혁        | 프록시 A (you) | 프록시 B (Cloudflare) |
| ----------- | ----------- | ------------------ |
| 클라이언트 IP 주소 | 이름 \*       | 이름 \*              |
| 사용자 계정      | 이름 \*       | 이름 \*              |
| 대상 서버       | 암호화 된       | 이름 \*              |
| 자주 묻는 질문    | 암호화 된       | 암호화 된              |

Proxy A는 사용자가 누구인지 알고 있지만 그들이가는 곳을 볼 수 없습니다 ( 대상은 암호화됩니다). 프록시 B는 목적지를 알고 있지만 요청을하지 않습니다. Neither 파티에는 완전한 그림이 있습니다.

### 사용 사례

Double-hop 배포가 잘 작동 할 때:

- 단일 연산자가 정체성 및 목적지를 모두 볼 수있는 더 강한 개인 정보 보호 보장이 필요합니다.
- 사용자 인증 및 계정 관리에 대한 제어를 유지하고 싶습니다.
- 규제 또는 준수 요구 사항 사용자 데이터의 위임 분리.

#### 예: iCloud 전용 릴레이

[iCloud 전용 릴레이](https://blog.cloudflare.com/icloud-private-relay/)Double-hop 배포를 사용합니다. Apple은 Apple ID로 사용자를 인증하고 목적지를 암호화하는 최초의 hop 프록시를 운영합니다. Cloudflare는 목적지를 해독하고 서버에 연결합니다 두 번째 홉 프록시를 작동합니다. Apple은 사용자가 누구인지 알지 못합니다. Cloudflare는 목적지를 알고 있지만 검색하지 않습니다.

## 배포 모델 선택

배포 모델을 선택할 때 이러한 질문을 고려:

1. 누가 사용자 인증을 관리해야합니까?

Cloudflare를 원하는 경우 인증을 처리하고 단일 채팅을 사용합니다. 사용자 계정에서 제어해야하는 경우, 더블 홉을 사용합니다.

2. 귀하의 개인 정보 보호 요구 사항은 무엇입니까?

귀하의 위협 모델이 단일 파티가 사용자 정체성과 검색 활동을 모두 볼 필요가 있다면, 이중 채팅을 사용합니다.

3. 어떤 작업 능력이 있습니까?

Double-hop는 프록시를 작동하고 유지해야 합니다. 완전 관리 솔루션을 선호하는 경우 단일 채팅을 사용합니다.
