[DNS records](/dns/manage-dns-records/)는 웹사이트나 애플리케이션을 방문자 및 다른 웹 서비스에 노출하는 역할을 하지만, DNS 레코드의 프록시 상태는 해당 레코드로 들어오는 DNS 쿼리를 Cloudflare가 어떻게 처리할지를 정의합니다.

Cloudflare를 통해 프록시할 수 있는 레코드는 [IP 주소 해석에 사용되는 레코드](/dns/manage-dns-records/reference/dns-record-types/#ip-address-resolution)이며, 즉 A, AAAA, CNAME 레코드입니다.

Cloudflare는 웹 트래픽을 제공하는 데 사용되는 모든 A, AAAA, CNAME 레코드를 프록시 상태로 설정할 것을 권장합니다. 예를 들어 타사 서비스에서 도메인을 검증하는 데 쓰이는 CNAME 레코드는 프록시하지 않아야 합니다.

:::note
대시보드로 도메인을 온보딩하면 기본적으로 프록시가 켜져 있습니다.
:::

### 이점

DNS 레코드를 **Proxied**(오렌지 구름 표시)로 설정하면 Cloudflare는 다음을 수행할 수 있습니다.

- [DDoS 공격](https://www.cloudflare.com/learning/ddos/what-is-a-ddos-attack/)으로부터 오리진 서버를 보호합니다.
- 애플리케이션에 대한 모든 요청을 [최적화하고, 캐시하고, 보호](/fundamentals/manage-domains/add-site/)합니다.
- 다양한 Cloudflare 제품에 대한 구성을 적용합니다.

:::caution
[도메인을 Cloudflare에 추가](/fundamentals/manage-domains/add-site/)하면 소유권을 확인할 수 있을 때까지 Cloudflare 보호는 [pending 상태](/dns/zone-setups/reference/domain-status/)가 됩니다. 이 과정은 완료까지 최대 24시간이 걸릴 수 있습니다. 자세한 내용은 [제한 사항](/dns/proxy-status/limitations/#pending-domains)을 참고하세요.
:::

### 예시

이는 다음을 의미합니다.

- 프록시된 레코드 `blog.example.com`에 대한 DNS 쿼리는 `192.0.2.1` 대신 Cloudflare [애니캐스트 IP 주소](/fundamentals/concepts/cloudflare-ip-addresses/)로 응답됩니다. 이를 통해 해당 이름에 대한 HTTP/HTTPS 요청이 Cloudflare 네트워크로 전송되어 프록시될 수 있으며, [위에 나열한 이점](#benefits)을 누릴 수 있습니다.
- DNS-only 레코드 `shop.example.com`에 대한 DNS 쿼리는 실제 오리진 IP 주소인 `192.0.2.2`로 응답됩니다. 이 경우 오리진 IP 주소가 노출되고 여러 기능의 이점을 받지 못할 뿐 아니라, Cloudflare는 해당 요청에 대해 HTTP/HTTPS 분석을 제공할 수 없습니다(DNS 분석만 가능).

자세한 맥락은 [How Cloudflare works](/fundamentals/concepts/how-cloudflare-works/)를 참고하세요.

## 프록시된 레코드

아래 섹션은 DNS 레코드가 <GlossaryTooltip term="proxy status">프록시됨</GlossaryTooltip>으로 설정되어 있을 때의 구체적인 동작과 예상 결과를 설명합니다. 특정 시나리오에서는 [제한 사항](/dns/proxy-status/limitations/)도 있을 수 있습니다.

### 미리 정의된 Time to Live

기본적으로 모든 프록시된 레코드는 Time to Live(TTL) 값이 **Auto**이며, 300초로 설정됩니다. 이 값은 수정할 수 없습니다.

[IP 주소 해석에 사용되는 레코드](/dns/manage-dns-records/reference/dns-record-types/#ip-address-resolution)만 프록시할 수 있으므로, 이 설정은 할당된 [애니캐스트 IP 주소](/fundamentals/concepts/cloudflare-ip-addresses/)가 바뀌더라도 재귀 리졸버가 300초(5분)를 넘겨 캐시하지 않도록 하여 빠르게 반영되게 합니다.

:::note
로컬 DNS 캐시가 업데이트되는 데 더 오래 걸릴 수 있으므로, 실제로 레코드 변경을 체감하는 데는 5분 이상 걸릴 수 있습니다.
:::

### 프록시된 레코드와 프록시되지 않은 레코드 혼합

같은 이름에 여러 개의 A 또는 AAAA 레코드가 있고 그중 하나라도 프록시되어 있다면, Cloudflare는 해당 이름의 모든 A 또는 AAAA 레코드를 프록시된 것으로 취급합니다.

<Details header="예시">

<Example>

**example.com**의 DNS 관리:

| Type | Name   | Content     | Proxy status | TTL  |
| ---- | ------ | ----------- | ------------ | ---- |
| A    | `blog` | `192.0.2.1` | Proxied      | Auto |
| A    | `blog` | `192.0.2.5` | DNS only     | Auto |

</Example>

이 예시에서는 `blog.example.com`으로 향하는 모든 트래픽이 두 레코드 모두 **Proxied**인 것처럼 처리됩니다.

</Details>

Cloudflare는 CNAME 체인 상의 호스트 이름이 프록시된 경우에도 요청을 프록시합니다.

<Details header="예시">

같은 Cloudflare 계정에 `example.com`과 `example.net`이라는 두 개의 서로 다른 Zone이 있다고 가정합니다.

<Example>

**example.com**의 DNS 관리:

| Type | Name   | Content     | Proxy status | TTL  |
| ---- | ------ | ----------- | ------------ | ---- |
| CNAME   | `example.com` | `origin.example.net` | DNS only     | Auto |

</Example>

<Example>

**example.net**의 DNS 관리:

| Type | Name   | Content     | Proxy status | TTL  |
| ---- | ------ | ----------- | ------------ | ---- |
| CNAME   | `origin.example.net` | `<origin>` | Proxied     | Auto |

</Example>

이 예시에서는 `example.com`으로 향하는 모든 트래픽이 **Proxied**로 처리됩니다.

:::note
다른 Cloudflare 계정으로의 CNAME은 허용되지 않으며 [Error 1014 (CNAME Cross-User Banned)](/support/troubleshooting/http-status-codes/cloudflare-1xxx-errors/error-1014/)가 발생합니다.
:::

</Details>

### CNAME 레코드

프록시된 [CNAME 레코드](/dns/manage-dns-records/reference/dns-record-types/#cname)는 Cloudflare 애니캐스트 IP를 반환하므로 기본적으로 flatten됩니다. CNAME flattening에서는 Cloudflare가 CNAME이 가리키는 IP 주소를 찾아 DNS 쿼리가 더 빠르게 해석되도록 합니다. 자세한 내용은 [CNAME flattening](/dns/cname-flattening/)을 참고하세요.

경우에 따라 Cloudflare가 경고 메시지를 표시하거나 CNAME 레코드 프록시를 [막을](/dns/proxy-status/limitations/#proxy-eligibility) 수 있습니다. 이는 잘못된 구성을 방지하기 위한 것으로, 일반적으로 다른 CDN 제공업체나 DKIM 검증에 사용되는 특정 레코드와 관련이 있습니다.

:::note
Cloudflare를 통해 트래픽이 프록시되는 특정 CNAME 레코드 값은 Shopify SaaS 제공업체를 위한 Orange-to-Orange(O2O) 라우팅을 활성화합니다. 자세한 내용은 [Shopify provider guide](/cloudflare-for-platforms/cloudflare-for-saas/saas-customers/provider-guides/shopify/)를 참고하세요.
:::

### 프로토콜 최적화

프록시된 레코드의 경우, 도메인에 [HTTP/2 또는 HTTP/3](/speed/optimization/protocol/)가 활성화되어 있고 [Universal SSL](/ssl/edge-certificates/universal-ssl/)도 사용 중이라면, Cloudflare는 해당하는 [HTTPS Service (HTTPS) records](/dns/manage-dns-records/reference/dns-record-types/#svcb-and-https)를 즉시 자동 생성합니다. HTTPS 레코드를 사용하면 초기 평문 HTTP 연결 없이도 클라이언트에 서버 연결 방법 정보를 미리 제공할 수 있습니다.

:::note
HTTP/2와 HTTP/3 설정 모두 Cloudflare가 제공하는 SSL/TLS 인증서가 있어야 합니다. 예를 들어 [Universal SSL](/ssl/edge-certificates/universal-ssl/)을 비활성화하면 이 동작에 영향을 줄 수 있습니다.
:::

## DNS-only 레코드

A, AAAA, 또는 CNAME 레코드가 **DNS-only**(회색 구름 표시)인 경우, [예시](#example)에서 설명했듯이 DNS 쿼리는 해당 레코드의 오리진 IP 주소로 해석됩니다.

이 경우 오리진 IP 주소가 악의적 행위자와 [DDoS 공격](https://www.cloudflare.com/learning/ddos/what-is-a-ddos-attack/)에 노출될 수 있을 뿐 아니라, Cloudflare가 애플리케이션 요청을 [최적화, 캐시, 보호](/fundamentals/concepts/how-cloudflare-works/)하거나 해당 요청에 대한 분석을 제공할 수 없습니다.
