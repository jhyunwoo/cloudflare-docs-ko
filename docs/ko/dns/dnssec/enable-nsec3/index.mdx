[블로그](https://blog.cloudflare.com/black-lies/)에서 설명했듯이, Cloudflare의 NSEC 기반 부정 응답 구현은 zone walking[^1]으로부터 보호됩니다. 이 구현은 Compact Denial of Existance([RFC 9824](https://www.rfc-editor.org/rfc/rfc9824.html))라고도 하며, NSEC3의 필요성을 없애고 훨씬 더 효율적으로 동작합니다.

하지만 규정 준수 등의 이유로 반드시 NSEC3를 사용해야 한다면 아래 설명대로 활성화할 수 있습니다.

## NSEC3 활성화

[Edit DNSSEC Status endpoint](/api/resources/dns/subresources/dnssec/methods/edit/)를 사용하고 `status`를 `active`, `dnssec_use_nsec3`를 `true`로 설정하세요. `$`로 시작하는 값은 영역 ID와 인증 자격 증명으로 바꿔야 합니다. Cloudflare API 사용법에 대한 자세한 내용은 [Fundamentals](/fundamentals/api/get-started/)를 참고하세요.

<APIRequest
	path="/zones/{zone_id}/dnssec"
	method="PATCH"
	json={{
		"dnssec_use_nsec3": true,
		"status": "active"
	}}
/>

### 사전 서명된 DNSSEC

Cloudflare를 [사전 서명된 DNSSEC](/dns/zone-setups/zone-transfers/cloudflare-as-secondary/dnssec-for-secondary/)를 사용하는 보조 DNS 공급자로 이용하는 경우, `dnssec_use_nsec3`를 `true`로 설정하면 Cloudflare는 기본 DNS 공급자에게서 전송된 NSEC3 레코드를 그대로 사용합니다.

그 외의 경우에는 NSEC3 레코드가 요청 시점에 생성되고 서명됩니다.

## NSEC3 사용 여부 확인

NSEC3가 사용 중인지 검증하려면 다음 시나리오를 고려하세요.

### 존재하지 않는 영역 이름

다음과 같은 명령은 존재하지 않음을 증명하기 위해 NSEC3를 사용한 서명된 부정 응답을 발생시킵니다. 응답의 `Authority Section` 아래에서 NSEC3 레코드를 찾으세요.

```sh
dig +dnssec doesnotexist.example.com
```

### 존재하는 이름에서 존재하지 않는 레코드 유형

이름 `www`는 존재하지만 TXT 유형이 없다면, 아래 예시는 NSEC3를 사용한 서명된 NODATA 응답을 발생시킵니다. 응답의 `Authority Section` 아래에서 NSEC3 레코드를 찾으세요.

```sh
dig +dnssec www.example.com TXT
```

## 제공 여부

NSEC3는 Enterprise 요금제의 영역에서만 사용할 수 있습니다.

[^1]: 공격자가 NSEC 부정 응답을 악용하여 특정 영역 안의 모든 이름을 알아내는 방법입니다. 이런 부정 응답이 체인 내 이전 이름과 다음 이름에 대한 정보를 제공할 때 가능합니다.
