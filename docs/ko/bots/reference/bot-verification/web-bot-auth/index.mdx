Web Bot Auth는 HTTP 메시지에서 암호화 서명을 활용하는 인증 방법입니다. Web Bot Auth는 검증 방법으로 사용됩니다.[검증된 봇](/bots/concepts/bot/verified-bots/)·[서명된 대리인](/bots/concepts/bot/signed-agents/).

그것은 두 활성 IETF 초안에 의존합니다 : a[디렉토리](https://datatracker.ietf.org/doc/html/draft-meunier-http-message-signatures-directory)크롤러가 공공 키를 공유하고,[프로토콜 초안](https://datatracker.ietf.org/doc/html/draft-meunier-web-bot-auth-architecture)이 키가 HTTP 요청에 크롤러의 정체성을 첨부하는 데 사용되어야하는 방법을 정의합니다.

이 문서는 Cloudflare에서 특정 통합을 진행합니다.

## 1. 유효한 서명 열쇠 생성

봇의 요청을 인증하는 데 사용되는 서명 키를 생성해야합니다.

{/* prettier-ignore */}

<Steps>
  1. 독특한 생성[에드25519](https://ed25519.cr.yp.to/)귀하의 요청에 서명하는 개인 키. 이 예제는[열린SSL](https://openssl-library.org/) `genpkey`명령:
     :::참조
     Cloudflare는 Ed25519 키 알고리즘을 지원합니다.
     주요 특징

     ```sh
     openssl genpkey -algorithm ed25519 -out private-key.pem
     ```
  2. 당신의 공중 열쇠를 추출하십시오.

     ```sh
     openssl pkey -in private-key.pem -pubout -out public-key.pem
     ```
  3. 선택 도구로 JSON Web Key (JWK)로 public key를 변환합니다. 이 예제는[`jwker`](https://github.com/jphastings/jwker)명령줄 신청.
     ```sh
     go install github.com/jphastings/jwker/cmd/jwker@latest
     jwker public-key.pem public-key.jwk
     ```
</Steps>

다음 단계로, 당신은 개인 키와 공공 키 생성, 다음 JWK에 공공 키를 변환.

:::참조
당신은 또한 할 수 있습니다[WebCrypto API를 사용하여 JavaScript키 생성](https://developer.mozilla.org/en-US/docs/Web/API/SubtleCrypto/generateKey)정확한 JWK 체재에 있는 열쇠를 생성할 것입니다.

현재 위치[JWK 라이브러리](https://jwt.io/libraries)JavaScript키 생성을 위한 WebCrypto API 지원

## 2. 키 디렉토리를 호스팅

'Cloudflare'에 요청을 인증하려면 봇의 방법을 생성하는 키 디렉토리를 호스트해야합니다.
이 디렉토리는 활성 IETF 초안에서 정의를 수행해야합니다.[초안-meunier-http-message-signatures-directory-01](https://datatracker.ietf.org/doc/html/draft-meunier-http-message-signatures-directory-01).

<Steps>
  1. 키 디렉토리를 호스트`/.well-known/http-message-signatures-directory`(이 요구 사항입니다). 이 키 디렉토리는 서명 키에서 파생 된 공개 키를 포함하여 JSON Web Key Set (JWKS)를 제공합니다.
  2. HTTPS를 통해 웹 페이지를 세울 (HTTP).
  3. [base64 URL 인코딩된 JWK 썸프린트 계산](https://www.rfc-editor.org/rfc/rfc8037.html#appendix-A.3)Ed25519 공공 키와 관련된.
  4. 키 디렉토리의 키 당 하나의 서명을 첨부하여 HTTP 메시지 서명 사양을 사용하여 HTTP 응답을 서명하십시오. 이 웹 사이트는 귀하가 웹 사이트를 탐색하는 동안 귀하의 경험을 향상시키기 위해 쿠키를 사용합니다. 귀하의 응답은 다음 헤더를 포함해야 합니다:

     - `Content-Type`: 이 헤더는 값이 있어야 합니다.`application/http-message-signatures-directory+json`.
     - `Signature`: 건설[`Signature`기타 제품](https://www.rfc-editor.org/rfc/rfc9421#name-the-signature-http-field)당신의 선택된 성분에.
     - `Signature-Input`: 건설[`Signature-Input`기타 제품](https://www.rfc-editor.org/rfc/rfc9421#name-the-signature-input-http-fi)당신의 선택된 성분에. 헤더는 다음과 같은 요구 사항을 충족해야합니다.
       | 필수품 / 모수     | 자주 묻는 질문                                                                                                                       |
       | ------------ | ------------------------------------------------------------------------------------------------------------------------------ |
       | `tag`        | 이것은 동등해야합니다.`http-message-signatures-directory`.                                                                               |
       | `keyid`      | JWK는 디렉토리에 해당 키의 축소.                                                                                                           |
       | `created`    | 이것은 동일해야합니다.`Unix`메시지가 응용 프로그램에 의해 전송되었을 때와 관련된 타임스탬프.                                                                         |
       | `expires`    | 이것은 동일해야합니다.`Unix`Cloudflare가 더 이상 메시지를 확인하려고 시도하지 않을 때와 관련된 타임스탬프.                                                            |
       | `@authority` | 요청에 의해 보낸 호스트 헤더의 값과 동일해야합니다. 당신은 설정해야[`req`부품 매개 변수](https://datatracker.ietf.org/doc/html/rfc9421#content-request-response). |

     다음 예제는 필수 헤더에 대한 할당 된 요청 및 응답을 보여줍니다.`https://example.com`. 값의`Signature`여기에는 illustrative 목적을 위해 순수하고 실제 생성 된 서명이 아닙니다.

     ```txt
     GET /.well-known/http-message-signatures-directory HTTP/1.1
     Host: example.com
     Accept: application/http-message-signatures-directory+json

     HTTP/1.1 200 OK
     Content-Type: application/http-message-signatures-directory+json
     Signature: sig1=:TD5arhV1ved6xtx63cUIFCMONT248cpDeVUAljLgkdozbjMNpJGr/WAx4PzHj+WeG0xMHQF1BOdFLDsfjdjvBA==:
     Signature-Input: sig1=("@authority";req);alg="ed25519";keyid="poqkLGiymh_W0uP6PZFw-dvez3QJT5SolqXBCW38r0U";nonce="ZO3/XMEZjrvSnLtAP9M7jK0WGQf3J+pbmQRUpKDhF9/jsNCWqUh2sq+TH4WTX3/GpNoSZUa8eNWMKqxWp2/c2g==";tag="http-message-signatures-directory";created=1750105829;expires=1750105839
     Cache-Control: max-age=86400
     {
       "keys": [{
         "kty": "OKP",
         "crv": "Ed25519",
         "x": "JrQLj5P_89iXES9-vFgrIy29clF9CC_oPPsw3c5D0bs", // Base64 URL-encoded public key, with no padding
       }]
     }
     ```
</Steps>

:::참조
이 URL은 표준 JSON Web Key Set를 제공합니다. 기타`x`, `crv`·`kty`, 당신은 다른 표준 JSON 웹 키 매개 변수를 포함 할 수 있으며, 비 Ed25519 키를 게시 할 수 있습니다. 다수 Ed25519 열쇠는 지원됩니다. 위의 형식의 서명을 제공 할 수있는 사람 만 사용됩니다.

Cloudflare는 다른 키 유형과 키 매개 변수를 무시합니다.`kty`, `crv`·`x`위의 형식. 개인 키를 유출하는 정보가 포함되지 않습니다.`d`모수.
주요 특징

Cloudflare-developed를 사용할 수 있습니다.[`http-signature-directory`CLI 도구](https://crates.io/crates/http-signature-directory)귀하의 디렉토리를 검증하는 데 도움을줍니다.

## 3. 봇 및 키 디렉토리 등록

봇과 키 디렉토리를 등록하면 확인된 봇 목록에 봇을 추가해야합니다.

<Steps>
  1. 로그인하기[‘Cloudflare’ ‘대시보드’](https://dash.cloudflare.com/), 귀하의 계정과 도메인을 선택합니다.
  2. 오시는 길**계정 관리** > **제품 설명**.
  3. 오시는 길**Bot 제출 양식**탭.
  4. 제품 정보**검증 방법**: 선택**자주 묻는 질문**.
  5. 제품 정보**유효성 검사**: 키 디렉토리의 URL을 입력합니다. 추가적으로 봇에 의해 전송 될 사용자 에이전트 값 (그리고 그들의 일치 패턴)을 공급할 수 있습니다.
  6. 제품정보**제출하기**.
</Steps>

Cloudflare는 키 디렉토리에서 발견 된 모든 유효 Ed25519 키를 허용합니다. 이벤트에서는 이미 'Cloudflare'의 등록 된 데이터베이스에 존재합니다. 'Cloudflare'는 새로운 키를 공급하거나 기존 키를 회전 할 수 있습니다.

성공적인 검증 후, 확인된 요청을 보낼 수 있습니다.

## 4. (확인 후) 자주 묻는 질문

봇이 성공적으로 확인 된 후, 봇은 요청을 서명 할 준비가되어 있습니다. 서명 프로토콜은 정의된다[초안-meunier-web-bot-auth-architecture-02](https://datatracker.ietf.org/doc/html/draft-meunier-web-bot-auth-architecture-02)

### 4.1. 표시할 부품 세트를 선택하십시오.

표시할 구성품의 집합을 선택하십시오.

구성 요소는 HTTP 헤더 또는[공급 업체](https://www.rfc-editor.org/rfc/rfc9421#name-derived-components)HTTP 메시지 서명 사양. Cloudflare는 다음을 권장합니다:

- 적어도 선택`@authority`도메인을 나타내는 파생 된 구성 요소는 요청을 전송하는 것입니다. 예를 들어, 요청`https://example.com`번역할 수 있습니다.`@authority`이름 \*`example.com`.
- ASCII 값을 포함 하는 구성 요소를 사용 합니다. HTTP 메시지 서명 사양은 봇의 요청을 검증하기 위해 실패로 인한 비 ASCII 문자를 용해합니다.

:::note\[ASCII 값만 사용]
Cloudflare는 현재 지원하지 않습니다.`bs`또는`sf`ASCII에 비 ASCII 값을 직렬화하도록 설계된 매개 변수.
주요 특징

:::카트로션\[`Content-Digest`헤드러
로그인하려면[메시지 내용](https://www.rfc-editor.org/rfc/rfc9421#name-message-content)사용 방법`Content-Digest`헤더는 'Cloudflare'로 변경되는 메시지의 0 위험이 있는 경우에만 해야 합니다.

예를 들어, 메시지가 암호화되지 않은 경우, Cloudflare에 proxied, 당신은 사용하지 않아야합니다`Content-Digest`.
:::

### 4.3. 필요한 헤더를 구성

Web Bot Auth를 위한 3개의 필수 헤더를 건설하십시오.

#### `Signature-Input`기타 제품

회사연혁[`Signature-Input`기타 제품](https://www.rfc-editor.org/rfc/rfc9421#name-the-signature-input-http-fi)당신의 선택된 성분에. 헤더는 다음과 같은 요구 사항을 충족해야합니다.

| 필수 구성품 모수 | 자주 묻는 질문                                                                                                                                            |
| --------- | --------------------------------------------------------------------------------------------------------------------------------------------------- |
| `tag`     | 이것은 동등해야합니다.`web-bot-auth`.                                                                                                                         |
| `keyid`   | 이것은 단계 2에서 엄지 인쇄와 동일해야합니다.                                                                                                                          |
| `created` | 이것은 동일해야합니다.`Unix`메시지가 응용 프로그램에 의해 전송되었을 때와 관련된 타임스탬프.                                                                                              |
| `expires` | 이것은 동일해야합니다.`Unix`Cloudflare가 더 이상 메시지를 확인하려고 시도하지 않을 때와 관련된 타임스탬프. 짧은 시간`expires`재생 공격의 likelihood를 감소시키고, Cloudflare는 적당한 짧은 생존 간격을 선택하는 것이 좋습니다. |

:::가격\[`nonce`·
더 보기`nonce`매개변수를 사용하면 공급할 수 있습니다.`nonce`서버의 과거 메시지 재생에서 공격자를 방지하기 위해.

"Cloudflare"는 그것을 포함하여 권장하지만, 현재는 없습니다`nonce`유효성 검사, 또는 'Cloudflare'는 검색 데이터베이스를 사용하여 재생 공격에 대한 보호`nonces`.

대신, Cloudflare는 짧은 것이 좋습니다.`expires`재생 공격에 대한 보호로. 1 분은 종종 충분합니다.
주요 특징

#### `Signature`기타 제품

회사연혁[`Signature`기타 제품](https://www.rfc-editor.org/rfc/rfc9421#name-the-signature-http-field)당신의 선택된 성분에.

#### `Signature-Agent`기타 제품

회사연혁[`Signature-Agent`기타 제품](https://www.ietf.org/archive/id/draft-meunier-http-message-signatures-directory-01.html#name-header-field-definition)키 디렉토리에 점. Cloudflare는 메시지가 확인되지 않습니다.

- 메시지는 포함`Signature-Agent`머리가 아닌`https://`.
- 메시지는 유효한 URI를 포함하고 그러나 두 배 인용에서 그것을 둘러싸지 않습니다. 시그니처-Agent는 구조화 된 필드로 인해 발생합니다.
- 메시지는 유효하다`Signature-Agent`헤더는 있지만 구성 요소 목록에 포함되지 않습니다.`Signature-Input`.

## 제한 사항

Cloudflare는 Web Bot Auth의 구현은 IETF RFC 9421에서 정의된 모든 구성 요소와 매개 변수를 지원하지 않습니다. 요청의 서명 입력 헤더에서 다음을 포함하는 경우, 검증은 실패합니다.

- `@query-params`:Cloudflare는 전체 쿼리에 서명하는 것이 좋습니다.`@query`대신 개별 매개 변수를 서명합니다.
- `@status`: 요청 경로에 포함 할 수 없습니다.

IETF RFC 9421에서 정의된 다음 구성 요소 매개 변수는 지원되지 않으며, Cloudflare는 포함되는 경우 메시지를 확인하지 못합니다.

- `sf`(HTTP 헤더 필드의 경우)
- `bs`(HTTP 헤더 필드의 경우)
- `key`(HTTP 헤더 필드의 경우)
- `req`(HTTP 헤더 필드 또는 파생 된 구성 요소)
- `name`(대략)`@query-param`지원 -이 필요`@query-param`지원)

### 실패 메시지 유효성

메시지가 유효성 검사를 실패하면 원인(s)가 포함될 수 있습니다.

- 당신을 확신[`Signature-Agent`기타 제품](/bots/reference/bot-verification/web-bot-auth/#signature-agent-header), 그리고 그것의 가치는 두 배 인용에서 입니다.
- 자주 묻는 질문`signature-agent`구성 요소 목록에서[`Signature-Input`기타 제품](/bots/reference/bot-verification/web-bot-auth/#signature-agent-header).
- 감사합니다.`expires`timestamp는 너무 짧지 않습니다. 그런 다음 "Cloudflare" 서버에서 도착하면 이미 만료되었습니다. 1 분은 종종 충분합니다.
- 비-ASCII 값, 또는 지원되지 않은 목록에 포함 된 구성 요소를 표시하지 않습니다.

### HTTP 메시지 서명 / 웹 Bot Auth를 사용하여 Cloudflare의 검증없이 영역에서

HTTP Message Signatures (Web Bot Auth)를 사용하려는 경우 자신의 원산지 처리에 대해 'Cloudflare'의 검증을 intervene 또는 populate하지 마십시오.`cf.bot_management.verified_bot`필드, 'Cloudflare' 검증 기능은 영역에서 비활성화 될 수 있습니다.

웹 Bot Auth 검증을 비활성화하려면 연락처[Cloudflare 지원](/support/contacting-cloudflare-support/).

이 기능을 비활성화하면 Cloudflare는 들어오는 서명을 유효하지 않습니다. 인증된 봇은 다른 방법 (역방향 DNS 유효성 검사와 같은)으로 돌아갑니다.
