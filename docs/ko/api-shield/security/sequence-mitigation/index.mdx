Sequence mitigation은 API와 통신하는 인증된 클라이언트에 대해 요청 패턴을 강제할 수 있게 해 줍니다.

sequence rules를 사용해 API 클라이언트의 알려진 정상 동작 집합을 정의하거나, 악성 동작을 탐지하고 완화할 수 있습니다.

예를 들어 은행 자금 이체 중 API 요청이 시간상 다음 순서를 따라야 한다고 예상할 수 있습니다.

| Order | Method | Path | Description |
| ----- | ------ | --------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------- |
| 1     | `GET`  | `/api/v1/users/{user_id}/accounts`      | `user_id`는 활성 사용자입니다. |
| 2     | `GET`  | `/api/v1/accounts/{account_id}/balance` | `account_id`는 사용자의 계정 중 하나입니다. |
| 3     | `GET`  | `/api/v1/accounts/{account_id}/balance` | `account_id`는 사용자에게 속한 다른 계정입니다. |
| 4     | `POST` | `/api/v1/transferFunds`                 | 이 요청에는 자금을 출금할 계좌, 입금할 계좌, 이체 금액을 설명하는 요청 본문이 포함됩니다. |

예를 들어 API 사용자가 `GET /api/v1/accounts/{account_id}/balance`보다 먼저 `GET /api/v1/users/{user_id}/accounts`를 요청해야 하며, `POST /api/v1/transferFunds`보다 먼저 `GET /api/v1/accounts/{account_id}/balance`를 요청해야 한다고 강제하고 싶을 수 있습니다.

sequence mitigation을 사용하면 두 개의 새로운 sequence mitigation rules로 이러한 요청 패턴을 강제할 수 있습니다.

:::note

시퀀스가 [Sequence Analytics](/api-shield/security/sequence-analytics/)에 표시되지 않더라도 해당 시퀀스에 대한 sequence mitigation rules를 만들 수 있습니다.
:::

## 프로세스

시간에 따른 API 동작을 강제하기 위해 [sequence rule을 생성](/api-shield/security/sequence-mitigation/manage-sequence-rules/)하는 방법은 두 가지입니다. sequence rules는 알려진 특정 API 호출 시퀀스를 수행하는 사용자로부터 엔드포인트를 보호하는 방식(negative security model)이나, 예상 범위를 벗어난 API 요청을 수행하는 사용자로부터 보호하는 방식(positive security model)으로 사용할 수 있습니다.

API Shield rules를 사용해 Cloudflare dashboard에서 만든 sequence rules는 lookback window를 사용해 시퀀스 안의 엔드포인트를 매칭합니다. 두 엔드포인트가 서로 [10 requests](/api-shield/security/sequence-mitigation/#request-limitations) 이내(Endpoint Management에 있는 엔드포인트 기준)에서 발견되고, [10 minutes](/api-shield/security/sequence-mitigation/#time-limitations) 이내에 요청되었다면 규칙이 매치됩니다.

:::note

기본 lookback window가 충분하지 않다면 계정 팀에 문의하세요.
:::

여러 엔드포인트를 추가하고, lookback window를 무시하며, 시간 기반 제약을 직접 구성하려면 [Sequence mitigation custom rules](/api-shield/security/sequence-mitigation/custom-rules/)를 참고하세요.

은행 자금 이체 예시에서, 사용자가 `POST /api/v1/transferFunds` 전에 반드시 `GET /api/v1/accounts/{account_id}/balance`를 요청해야 한다고 강제하는 것은 positive security model로 간주됩니다. 사용자는 계좌 잔액을 조회한 뒤에만 자금 이체를 수행할 수 있기 때문입니다.

negative security model은 애플리케이션의 일반적인 동작 범위를 벗어난 악성 행위가 보이고, 올바른 positive security model을 연구하는 동안 우선 요청을 중단해야 할 때 유용할 수 있습니다.

예를 들어 권한 버그 때문에 사용자가 `GET /api/v1/users/{var1}/profile`을 통해 계좌 번호가 포함된 다른 사용자의 프로필을 반복 조회할 수 있고, 그 뒤에 사기성 자금 이체를 시도한다면, `GET /api/v1/users/{var1}/profile`에서 `POST /api/v1/transferFunds`로 이어지는 시퀀스를 차단하거나 기록하는 규칙을 만들 수 있습니다.


## 제한 사항

### Endpoint Management

<GlossaryTooltip term="API endpoint">API endpoints</GlossaryTooltip>에 대한 요청을 추적하려면, 해당 엔드포인트가 [Endpoint Management](/api-shield/management-and-monitoring/)에 추가되어 있어야 합니다. Cloudflare dashboard를 통해 [API Discovery](/api-shield/security/api-discovery/), [Schema validation](/api-shield/security/schema-validation/), 또는 [수동 추가](/api-shield/management-and-monitoring/#add-endpoints-manually) 방식으로 엔드포인트를 추가하세요.

### Session Identifiers

API Shield는 구성한 <GlossaryTooltip term="session identifier">session identifier</GlossaryTooltip>를 사용해 세션을 추적합니다. sequence mitigation이 예상대로 동작하려면 API 최종 사용자마다 고유한 session identifier를 구성해야 합니다.

<div id="request-limitations"></div>

### Request limitations

기본적으로 API Shield는 session identifier로 식별된 각 개별 API 사용자에 대해 현재 요청과 직전 9개의 요청 엔드포인트를 저장합니다. 기본 lookback window가 충분하지 않다면 계정 팀에 문의하세요.

sequence mitigation은 시퀀스를 구성할 때 동일한 엔드포인트에 대한 중복 요청을 추가로 제거합니다.

이를 설명하기 위해 위의 원래 [sequence example](/api-shield/security/sequence-mitigation/)을 보면, sequence mitigation은 다음 시퀀스를 저장합니다.

1. `GET /api/v1/users/{user_id}/accounts`
2. `GET /api/v1/accounts/{account_id}/balance`
3. `POST /api/v1/transferFunds`

sequence mitigation은 `GET /api/v1/accounts/{account_id}/balance`에 대한 두 요청을 중복 제거하여 하나의 요청으로 저장했습니다.

<div id="time-limitations"></div>

### Time limitations

sequence mitigation rules의 lookback period는 10분입니다. 즉 동일한 session identifier를 사용하는 두 요청이 10분 이내에 발생하면 기존 시퀀스를 연장합니다. 마지막 요청 이후 10분이 지나 발생한 요청은 새 시퀀스 기록을 시작합니다. 예를 들어 어떤 엔드포인트보다 다른 엔드포인트가 먼저 요청되어야 한다는 규칙을 만들었는데, 사용자가 두 엔드포인트를 요청하는 사이에 10분이 넘게 경과하면 해당 규칙은 매치되지 않습니다.
