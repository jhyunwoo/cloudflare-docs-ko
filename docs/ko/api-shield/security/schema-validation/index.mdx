<GlossaryDefinition term="API schema" />

Schema validation은 들어오는 트래픽이 이전에 제공된 API schema를 준수하는지 확인할 수 있게 해 줍니다. API schema를 제공하거나 학습된 schema 목록에서 선택하면, API Shield는 schema 정의를 바탕으로 들어오는 트래픽에 대한 규칙을 생성합니다. 이 규칙은 어떤 트래픽이 허용되고 어떤 트래픽이 기록되거나 차단되는지를 정의합니다.

Cloudflare는 Schema validation 2.0을 출시했습니다. dashboard를 사용해 하나 이상의 host에 대해 이전 버전의 Schema validation을 구성하려면 [Configure Classic Schema validation](/api-shield/reference/classic-schema-validation/)을 참고하세요. 기존 Classic Schema validation 설정은 변경할 수 있지만, 새로운 schema는 추가할 수 없습니다.

새 시스템에 schema를 업로드하여 수동으로 Schema validation 2.0으로 마이그레이션할 수 있습니다.

### Fallthrough rule 추가로 validation 추가

fallthrough rule은 [Endpoint Management](/api-shield/management-and-monitoring/endpoint-management/)의 엔드포인트와 일치하지 않는 요청에 대한 catch-all 역할을 합니다.

schema에 있는 모든 엔드포인트가 Endpoint Management에 추가되도록 하면, fallthrough action이 팀이 알지 못하는 legacy 또는 zombie endpoints로부터의 요청을 보호하는 데 도움이 됩니다.

fallthrough action을 설정하려면 다음 단계를 따르세요.

{/* prettier-ignore-start */}

<Tabs syncKey="dashNewNav">
   <TabItem label="New dashboard" icon="rocket">
      <Steps>
         1. In the Cloudflare dashboard, go to the **Security rules** page.

               <DashButton url="/?to=/:account/:zone/security/security-rules" />
         3. Select **Templates**.
         4. Search for the template named `Mitigate API requests to unidentified endpoints` and select **Preview template**.
         5. Give your rule a descriptive name.
         6. Choose one or more hostnames from the dropdown menu and select your action.
         7. Select **Save as draft** to deploy later, or **Deploy** to deploy now.
      </Steps>

      현재 fallthrough rules는 security rules 목록에서 볼 수 있습니다.

   </TabItem>
   <TabItem label="Old dashboard">
      <Steps>
         1. Log in to the [Cloudflare dashboard](https://dash.cloudflare.com/), and select your account and domain.
         2. Go to **Security** > **API Shield**.
         3. Under **Settings**, go to **Fallthrough settings**.
         4. Select **Use Template**.
         5. Choose one or more hostnames from the drop down menu. The fallthrough rule will act on all traffic that does not match an existing endpoint in Endpoint Management to the selected hostnames.
         6. Select **Continue to custom rule**.
         7. Name your rule and select your action.
         8. Select **Save as draft** to deploy later, or **Deploy** to deploy now.
      </Steps>

      현재 fallthrough rules는 custom rules 목록에서 볼 수 있습니다.

   </TabItem>
</Tabs>

{/* prettier-ignore-end */}

:::note
더 사용자 지정된 논리 검사를 위해 자신의 custom rule에서 `cf.api_gateway.fallthrough_triggered` 문법을 사용할 수 있습니다. 이 탐지는 요청이 Endpoint Management의 엔드포인트와 일치하지 않을 때 `true`로 평가되므로, zone의 비 API 트래픽을 차단하지 않도록 API의 호스트명이나 루트 경로와 함께 검사하는 것이 중요합니다.
:::

### Schema validation의 전역 기본 action 변경

Schema validation의 기본 action은 main Schema validation 페이지에서 확인할 수 있습니다. 이 action은 action이 `Default`로 설정된 모든 엔드포인트에 적용됩니다.

- `Log` action: 이벤트를 [Firewall Events](/firewall/)에 기록합니다.
- `Block` action: 엔드포인트의 schema를 위반한 요청을 차단하고 이벤트를 [Firewall Events](/firewall/)에 기록합니다.
- `None` action: 비정상 요청을 기록도 차단도 하지 않습니다.

기본 action을 변경하려면 다음 단계를 따르세요.

{/* prettier-ignore-start */}

<Tabs syncKey="dashNewNav">
   <TabItem label="New dashboard" icon="rocket">
      <Steps>
          1. In the Cloudflare dashboard, go to the **Security Settings** page.

               <DashButton url="/?to=/:account/:zone/security/settings" />
         2. Filter by **API abuse**.
         3. Under **Schema validation** > **Configurations**, select the edit icon next to **Default action**.
         4. Choose a new action from the dropdown menu.
         5. Select **Save**.
      </Steps>
   </TabItem>
   <TabItem label="Old dashboard">
      <Steps>
         1. Log in to the [Cloudflare dashboard](https://dash.cloudflare.com/), and select your account and domain.
         2. Go to **Security** > **API Shield**.
         3. Select **Schema validation**.
         4. Under the default `Log` action, select **Change**.

         6. Observe the current action and accept the change by selecting **Change default action** in the popup window.
      </Steps>
      Alternatively, you can modify the global action via **Security** > **API Shield** > **Settings**.
   </TabItem>
</Tabs>

### 단일 엔드포인트의 action 변경

Schema validation에서는 기본 action과 별도로 개별 엔드포인트 action을 변경할 수 있습니다.

## 사양

Cloudflare는 현재 [OpenAPI v3 schemas](https://spec.openapis.org/oas/v3.0.3.html)만 허용합니다. 허용되는 파일 형식은 YAML(`.yml` 또는 `.yaml`)과 JSON(`.json`)입니다.

서로 다른 도구로 생성된 OpenAPI schemas는 Schema validation으로 가져오기에는 충분히 구체적이지 않을 수 있습니다. schema가 OpenAPI specification을 준수하는지 확인하려면 [Swagger Editor](https://swagger.io/tools/swagger-editor/) 같은 서드파티 도구를 사용하는 것을 권장합니다.

## 제한 사항

Cloudflare API Shield의 Schema validation(import)과 [Schema learning](/api-shield/management-and-monitoring/endpoint-management/schema-learning/)(export)은 [OpenAPI Specification (OAS) v3.0](https://spec.openapis.org/oas/v3.0.3)에 의존합니다.

이 지원에는 OAS v3.0.x 같은 모든 patch 버전이 포함됩니다. 현재 OAS v3.1은 지원하지 않으며 OpenAPI 2.0까지 지원을 확장할 계획도 없습니다.

:::note
Cloudflare는 업로드 전에 모든 schema가 OAS v3.0 사양을 완전히 준수하는지 확인하기 위해 [Swagger Editor](https://editor.swagger.io/) 같은 서드파티 도구를 사용할 것을 권장합니다.
:::

현재 API Shield는 다음과 같은 API schema 기능 일부를 지원하지 않습니다: 모든 responses, external references, non-basic path templating, unique items.

[API Shield](/api-shield/)를 구독한 Enterprise 고객은 활성화된 schema에 대해 총 10,000개의 operation 한도가 있습니다. 이 한도를 높이려면 계정 팀에 문의하세요.

Free, Pro, Business, 또는 API Shield를 구독하지 않은 Enterprise 고객의 한도는 [Plans](/api-shield/plans/)를 참고하세요.

### 필수 필드

OpenAPI specification에서 엄격히 요구되지는 않지만, Schema validation에서는 다음 필드를 엄격히 요구합니다.

#### `schema`

- [`type`](https://spec.openapis.org/oas/v3.0.3#schema-object)
  - 모든 schema는 type이 설정되어 있어야 합니다. 특정 type이 Schema validation에서 지원되지 않는다면 보통 `string`으로 설정하는 것이 가장 좋습니다.

#### `parameter`

- [`schema`](https://spec.openapis.org/oas/v3.0.3#schema-object)
  - Schema validation은 parameters에서 content 필드를 지원하지 않습니다. 자세한 내용은 아래 [validated and supported fields notes](#notes-on-validated-and-supported-fields)를 참고하세요. 대신 모든 parameters objects에 schema가 반드시 필요합니다.

<div id="notes-on-validated-and-supported-fields"></div>

### 검증 및 지원 필드에 대한 참고 사항

아래 정보는 다양한 OpenAPI specification(OAS) objects 및 fields에 대한 Schema validation의 현재 지원 범위를 설명합니다.

#### `servers`

- [`url`](https://spec.openapis.org/oas/v3.0.3#server-object)
  - Schema validation은 relative URLs를 지원하지 않습니다.
- [`variables`](https://spec.openapis.org/oas/v3.0.3#server-variable-object)
  - Server variables는 검증되지 않습니다.

#### `parameter`

- [`style`](https://spec.openapis.org/oas/v3.0.3#parameter-object)
  - 기본값만 지원합니다: `"simple"`(path 또는 header parameters)와 `"form"`(query 또는 cookie parameters)
- [`explode`](https://spec.openapis.org/oas/v3.0.3#parameter-object)
  - 기본값만 지원합니다: `true`(form용)와 `false`(simple용)
- [`content`](https://spec.openapis.org/oas/v3.0.3#parameter-object)
  - parameters에서는 content field가 지원되지 않습니다. 대신 schema field를 사용하세요.
- [`type`](https://spec.openapis.org/oas/v3.0.3#parameter-object)
  - Cloudflare는 현재 object type parameters를 검증하지 않습니다.

#### `reference`

- [`$ref`](https://spec.openapis.org/oas/v3.0.3#reference-object)
  - External 또는 relative references는 지원되지 않습니다.

#### `requestBody`

- `content`
  - [Request Body Object](https://spec.openapis.org/oas/v3.0.3#request-body-object)
  - [Media Type Object](https://spec.openapis.org/oas/v3.0.3#media-type-object)
    - Schema validation은 `application/json` 문서를 검증할 수 있습니다. schema가 다른 content type도 허용한다면, Schema validation은 그런 요청을 검증 없이 허용합니다.

#### `parameter/schema`

- `anyOf`
  - [Parameter Object](https://spec.openapis.org/oas/v3.0.3#parameter-object)
  - [Schema Object](https://spec.openapis.org/oas/v3.0.3#schema-object)
    - parameter schemas에서 `anyOf` schemas는 현재 지원되지 않습니다.

#### `schema`

- [`format`](https://spec.openapis.org/oas/v3.0.3#schema-object)
  - 검증되는 format:
    - `date-time`
    - `time`
    - `date`
    - `email`
    - `hostname`
    - `ipv4`
    - `ipv6`
    - `uri`
    - `uri-reference`
    - `iri`
    - `iri-reference`
    - `int32`
    - `int64`
    - `float`
    - `double`
    - `password`
    - `uuid`
    - `byte`
    - `uint64`

- [`uniqueItems`](https://spec.openapis.org/oas/v3.0.3#schema-object)
  - 이 필드는 현재 Schema validation에서 검증되지 않습니다.

## Body inspection

API Shield는 업로드된 schema에 포함된 body specifications를 식별하고, 들어오는 API 요청 데이터가 이를 준수하는지 검증할 수 있습니다.

현재 Schema validation은 content-type `application/json`을 사용하는 요청 검증을 지원합니다.

OpenAPI specification에서 request body schemas는 `application/*`, `application/xml`, `application/json` 같은 media-ranges와 연결됩니다.

Cloudflare가 들어오는 요청을 검증할 때는 요청의 `content-type`이 OpenAPI에 지정된 media-range와 일치하는지 확인합니다.

예를 들어 OpenAPI 파일이 request body content map의 일부로 `application/*`를 지정한다면, Cloudflare는 `application/xml`과 `application/json` content-type을 가진 요청을 모두 허용합니다. 하지만 제공된 schema로 실제 검증되는 것은 `application/json` 본문뿐입니다.

Cloudflare는 일반적으로 media-ranges를 가능한 한 엄격하게 유지할 것을 권장합니다. 개별 media-type으로 설정하는 것이 좋습니다. 한 API 엔드포인트에서 여러 content-types를 지원해야 한다면 wildcard media-ranges를 활용할 수 있습니다.

origin이 [MIME sniffing](https://mimesniff.spec.whatwg.org/)을 수행하도록 구성된 경우에도 주의가 필요합니다. 예를 들어 JSON body를 담고 있으면서도 의도적으로 `application/malicous` content-type을 가진 요청에 대해, Cloudflare가 `application/*` media-ranges를 허용하도록 구성되어 있다면, 이 요청은 JSON body 내용을 검증하지 않은 채 origin으로 전달됩니다. 하지만 content-type을 무시하고 시도적 역직렬화나 MIME type sniffing을 수행하는 origin은, schema body validation을 통과했다고 잘못 가정한 채 JSON body를 역직렬화할 수 있습니다.

따라서 동일한 엔드포인트에서 `application/json`과 `application/xml`을 모두 지원해야 한다면 `application/*`를 사용할 수 있습니다. Cloudflare는 content-type이 `application/json`으로 설정된 request bodies에 대해서만 제공된 schema를 검증합니다. content-type이 `application/xml`인 요청(및 `application/*`에 매치되는 다른 요청)은 통과됩니다. 그렇더라도 origin에서 content-type sniffing은 비활성화하는 것을 강력히 권장합니다.

Cloudflare는 OpenAPI request body content map에서 다음 media-ranges를 지정할 수 있도록 허용합니다.

- `*/*`
- `application/*`
- `application/json`.

media-ranges는 `charset` parameter를 강제하도록 구성할 수도 있습니다. 이 경우 Cloudflare는 media-range specification의 일부로 정적인 `utf-8` 값의 `charset` parameter만 허용하며, 이를 구성하면 요청의 content-type에도 동일한 charset이 포함되어야 합니다.

## 문제 해결

이 섹션은 schema validation 사용 중 마주칠 수 있는 일반적인 문제를 다룹니다.

### Security Events의 `OneOf` constraint error schema violation

`OneOf` constraint error는 API 요청 본문이 업로드한 schema의 [`oneOf`](https://swagger.io/docs/specification/v3_0/data-models/oneof-anyof-allof-not/) 목록에 정의된 옵션 중 정확히 하나와만 일치하지 않아 schema validation에 실패했음을 의미합니다.

요청이 잘못된 이유는 다음 두 가지 중 하나입니다.

- **Matches Zero**: payload가 사용 가능한 어느 subschema와도 올바르게 일치하지 않았습니다. 일반적으로 discriminator field는 설정되어 있지만 해당 타입에 필요한 다른 필수 필드가 빠져 있을 때 발생합니다.
- **Matches Multiple**: payload가 모호하여 둘 이상의 subschema와 일치했습니다. 이는 schema가 너무 일반적일 때 발생합니다. 예를 들어 payload에 `email`과 `phone` 필드가 모두 들어 있다면, `email` schema 정의와 `phone` schema 정의 모두에 일치해 "정확히 하나" 규칙을 위반할 수 있습니다.

이 문제를 해결하려면 실패한 request body를 API schema 정의와 비교해 보세요. 의도된 타입에 필요한 필수 필드가 누락되었거나, 여러 서로 다른 충돌하는 타입의 속성이 함께 포함되어 payload를 모호하게 만들고 있을 것입니다.
