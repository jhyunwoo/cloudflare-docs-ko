인덱스는 D1를 활성화하여 일반적인 (popular) 쿼리에 대한 색인 된 열에 대한 쿼리 성능을 개선하기 위해 데이터 (열 수)의 양을 줄이기 위해 데이터베이스는 쿼리를 실행할 때 스캔해야합니다.

## 인덱스가 유용할 때?

인덱스는 유용하다:

- 일반적으로 predicates에서 사용 되는 열에 읽기 성능 향상을 원할 때 - 예를 들어,`WHERE email_address = ?`또는`WHERE user_id = 'a793b483-df87-43a8-a057-e5286d3537c5'`- 이메일 주소, 사용자 이름, 사용자 ID 및 / 또는 날짜는 일반적인 웹 응용 프로그램 또는 서비스에 색인하기 위해 열에 좋은 선택입니다.
- 열 또는 열에 고유 한 제약을 촉진하기 위해 - 예를 들어, 이메일 주소 또는 사용자 ID를 통해`CREATE UNIQUE INDEX`.
- 여러 열을 함께 쿼리하는 경우 -`(customer_id, transaction_date)`.

인덱스는 테이블과 열(s)가 참고 자료를 삽입, 업데이트 또는 삭제할 때 자동으로 업데이트됩니다. 당신은 수동으로 테이블에 쓰기 후 인덱스를 업데이트 할 필요가 없습니다 참고 자료s.

## 인덱스 보기

:::참조

기본 키(an)를 사용하는 테이블`INTEGER`제품정보`ROWID`), 또는 그 자신의 정의`INTEGER PRIMARY KEY`, 그 열에 대한 인덱스를 만들 필요가 없습니다.
주요 특징

D1 테이블에 인덱스를 생성하려면`CREATE INDEX`SQL 명령을 지정하고 테이블과 열을 지정합니다.

예를 들어, 다음을 주었다.`orders`테이블, 인덱스를 만들려면`customer_id`. 그 테이블 필터에 대한 거의 모든 쿼리`customer_id`, 당신은 그것을 위해 색인을 창조해서 성과 개선을 볼 것입니다.

```sql
CREATE TABLE IF NOT EXISTS orders (
    order_id INTEGER PRIMARY KEY,
    customer_id STRING NOT NULL, -- for example, a unique ID aba0e360-1e04-41b3-91a0-1f2263e1e0fb
    order_date STRING NOT NULL,
    status INTEGER NOT NULL,
    last_updated_date STRING NOT NULL
)
```

인덱스를 만들려면`customer_id`열, 데이터베이스에 대한 아래의 진술을 실행:

:::참조

색인을 위한 일반적인 naming 체재는 입니다`idx_TABLE_NAME_COLUMN_NAMES`, 그래서 당신은 테이블과 열을 식별 할 수 있습니다 (s) 당신의 인덱스는 데이터베이스를 관리 할 때.
주요 특징

```sql
CREATE INDEX IF NOT EXISTS idx_orders_customer_id ON orders(customer_id)
```

참고 자료를 쿼리`customer_id`열은 이제 인덱스의 이점을 제공합니다:

```sql
-- Uses the index: the indexed column is referenced by the query.
SELECT * FROM orders WHERE customer_id = ?

-- Does not use the index: customer_id is not in the query.
SELECT * FROM orders WHERE order_date = '2023-05-01'
```

더 복잡한 경우에, 당신은 색인이 D1에 의해 사용되는지 확인할 수 있습니다[자주 묻는 질문](#test-an-index)직접.

### 지원하다`PRAGMA optimize`

인덱스 생성 후, 실행`PRAGMA optimize`데이터베이스 성능 향상 명령.

`PRAGMA optimize`지원하다`ANALYZE`데이터베이스의 각 테이블에 명령, 테이블과 인덱스의 통계를 수집합니다. 이 통계는<GlossaryTooltip term="query planner">질문 planner</GlossaryTooltip>사용자 쿼리를 실행할 때 가장 효율적인 쿼리 계획을 생성합니다.

더 많은 정보를 원하시면, 참조[`PRAGMA optimize`](/d1/sql-api/sql-statements/#pragma-optimize).

## 목록 색인

데이터베이스에 색인을 나열하고 SQL 정의뿐만 아니라 쿼리하여`sqlite_schema`시스템 테이블:

```sql
SELECT name, type, sql FROM sqlite_schema WHERE type IN ('index');
```

이것은 아래에 닮은 산출을 돌려보낼 것입니다:

```txt
┌──────────────────────────────────┬───────┬────────────────────────────────────────┐
│ name                             │ type  │ sql                                    │
├──────────────────────────────────┼───────┼────────────────────────────────────────┤
│ idx_users_id                     │ index │ CREATE INDEX idx_users_id ON users(id) │
└──────────────────────────────────┴───────┴────────────────────────────────────────┘
```

이 표 또는 기존 인덱스를 수정할 수 없습니다. 인덱스를 수정하려면[첫 번째 삭제](#remove-indexes)·[새 인덱스 생성](#create-an-index)업데이트된 정의로.

## 인덱스 테스트

index가 쿼리를 prepending에 의해 쿼리에 사용되었는지 검증[`EXPLAIN QUERY PLAN`](https://www.sqlite.org/eqp.html). 이것은 성공 진술을 위한 쿼리 계획을 출력할 것입니다, 어느 것 (if any) 색인은 사용되었습니다.

예를 들어, 당신이 가정하는 경우`users`테이블에는`email_address TEXT`열과 당신은 인덱스를 만들었습니다`CREATE UNIQUE INDEX idx_email_address ON users(email_address)`, predicate에 어떤 조회든지`email_address`인덱스를 사용해야 합니다.

```sql
EXPLAIN QUERY PLAN SELECT * FROM users WHERE email_address = 'foo@example.com';
QUERY PLAN
`--SEARCH users USING INDEX idx_email_address (email_address=?)
```

자주 묻는 질문`USING INDEX <INDEX_NAME>`쿼리 플래너에서 출력, 인덱스를 확인합니다.

이것은 색인을 위한 상당히 일반적인 use-case입니다. 이메일 주소에 근거한 사용자를 찾아내는 것은 수시로 로그인 (authentication) 체계를 위한 아주 일반적인 질문 유형입니다.

인덱스를 사용하여 쿼리에 의해 읽는 행 수를 줄일 수 있습니다. 사용 방법`meta`당신의 사용법을 견적하는 목표. 더 알아보기["문서에 의해 읽는 행 수를 줄이기 위해 인덱스를 사용할 수 있습니까?"](/d1/platform/pricing/#can-i-use-an-index-to-reduce-the-number-of-rows-read-by-a-query)·["나는 어떻게 내 (동기) 청구서를 인용 할 수 있습니까?"](/d1/platform/pricing/#how-can-i-estimate-my-eventual-bill).

## 멀티 열 색인

다중 열 색인 (다중 열을 지정하는 색인)를 위해, 쿼리는 단지 색인을 사용할 것입니다*모든 것*열의, 또는 열의 subset는 "왼쪽"에 모든 열을 쿼리 내에서 제공합니다.

의 인덱스를`CREATE INDEX idx_customer_id_transaction_date ON transactions(customer_id, transaction_date)`, 색인이 사용될 때 뒤에 오는 테이블 쇼:

| 글쓰기                                                                                         | 인덱스 사용?                                                        |
| ------------------------------------------------------------------------------------------- | -------------------------------------------------------------- |
| `SELECT * FROM transactions WHERE customer_id = '1234' AND transaction_date = '2023-03-25'` | 예: 인덱스의 열을 모두 지정합니다.                                           |
| `SELECT * FROM transactions WHERE transaction_date = '2023-03-28'`                          | 아니오: 단지 specifies`transaction_date`, 인덱스에서 다른 왼쪽 열을 포함하지 않습니다. |
| `SELECT * FROM transactions WHERE customer_id = '56789'`                                    | 예: 지정`customer_id`색인에 있는 leftmost 란인 .                         |

참고 :

- 대신 3개의 열에 색인을 만들면 —`customer_id`, `transaction_date`·`shipping_status`— 모두 사용하는 쿼리`customer_id`·`transaction_date`인덱스를 사용 하 여 모든 열을 포함 하 여 "왼쪽에".
- 같은 인덱스로, 단지 사용하는 쿼리`transaction_date`·`shipping_status`(주)*아니다.*&#xC0AC;용되지 않은 것처럼 인덱스를 사용`customer_id`(왼쪽 열) 쿼리에.

## Partial 색인

Partial 색인은 테이블에 있는 행의 subset에 색인 입니다. Partial 색인은 사용으로 정의됩니다.`WHERE`인덱스를 만들 때 항목. 일부 인덱스는 값이 있는 것과 같은 특정 행을 omit에 유용할 수 있습니다.`NULL`또는 특정 값의 행은 쿼리에 따라 존재합니다.

- 부분 색인의 구체적인 예는 테이블에 있을 것입니다`order_status INTEGER`열, 어디`6`현재 위치`"order complete"`앱 코드에서.
- 이것은 아직 성취되고 배송되거나 가장 일반적인 사용자 (사용자는 주문 상태를 검사)의 일부가 될 가능성이있는 주문에 대해 쿼리 할 수 있습니다.
- Partial 색인은 또한 시간이 지남에 따라 상승하는 색인을 지킵니다. 인덱스는 모든 완료된 순서를 위한 행을 유지해야 하지 않으며, 완료된 순서는 in-progress 순서 보다는 훨씬 더 많은 시간이라고 queried 가능성이 있습니다.

인덱스에서 완성 된 주문을 필터링하는 부분 색인은 다음과 같습니다.

```sql
CREATE INDEX idx_order_status_not_complete ON orders(order_status) WHERE order_status != 6
```

Partial 색인은 읽기 시간에 더 빠를 수 있습니다 (지수에 있는 더 적은 줄) 그리고 쓰기 시간 (지수는 색인에 쓰기) 가득 차있는 색인 보다는. 부분 인덱스도 결합할 수 있습니다.[Multi-column 색인](#multi-column-indexes).

## 인덱스 제거

제품 정보`DROP INDEX`인덱스를 제거하십시오. 삭제 된 인덱스는 복원 할 수 없습니다.

## 관련 기사

인덱스를 만들 때 다음과 같은 고려 사항들을 주의하십시오:

- 인덱스는 항상 무료 성능 향상입니다. 가장 정해진 열을 반영하는 열에만 인덱스를 작성해야 합니다. 유지해야합니다. 인덱스 열에 쓸 때, 데이터베이스는 테이블과 인덱스에 쓰기해야 합니다. 열에 색인과 감소의 성능 이점은 거의 모든 경우에, 이 추가 쓰기를 상쇄할 것입니다.
- 참고 자료 다른 테이블 또는 인덱스가 안정되지 않기 때문에 색인을 만들 수 없습니다.
- 인덱스는 업데이트할 수 없습니다. 인덱스에서 열을 추가하거나 제거하려면[기타 제품](#remove-indexes)색인과 그 후에[새 인덱스 생성](#create-an-index)새로운 열으로.
- Indexes는 데이터베이스에 의해 요구되는 전체 저장소에 기여: 인덱스는 효과적으로 테이블 자체.
