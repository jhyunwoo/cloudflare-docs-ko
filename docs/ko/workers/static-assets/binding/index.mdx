Configuring the Worker with Asset 를 지정해야 합니다.[이름 \*](/workers/static-assets/binding/#directory)그리고, 선택적으로,[자산 바인딩](/workers/static-assets/binding/), 당신의 노동자의 Wrangler 파일에서. 더 보기[자산 바인딩](/workers/static-assets/binding/)작업자 스크립트 내의 역동적으로 fetch 자산을 허용 (e.g.`env.ASSETS.fetch()`), 당신이 만드는 방법과 유사하게`fetch()`전화 번호[서비스 바인딩](/workers/runtime-apis/bindings/service-bindings/http/).

정적 자산의 한 컬렉션은 각 노동자에서 구성 할 수 있습니다.

## `directory`

정적 자산의 폴더가 제공됩니다. 많은 프레임 워크의 경우, 이것은`./public/`, `./dist/`, 또는`./build/`폴더.

<WranglerConfig>
  ```jsonc
  {
  	"$schema": "./node_modules/wrangler/config-schema.json",
  	"name": "my-worker",
  	"compatibility_date": "$today",
  	"assets": {
  		"directory": "./public/",
  	},
  }
  ```
</WranglerConfig>

### 자산을 무시

몇몇에는 업로드하지 않아야 하는 자산 디렉토리에 파일이 있습니다.

이 경우,`.assetsignore`자산 디렉토리의 루트에 파일.
이 파일은 같은 형식을 가지고`.gitignore`.

Wrangler는 이 파일에 있는 선을 일치하는 자산 파일을 업로드하지 않을 것입니다.

**이름 \***

자산 디렉토리가 있는 Pages 프로젝트에서 마이그레이션`dist`·
서버 측 Worker 코드 또는 Pages 구성 파일을 공개 클라이언트 측 자산으로 업로드하고 싶지 않습니다.
다음을 추가`.assetsignore`파일 :

```txt
_worker.js
_redirects
_headers
```

이제 Wrangler는 Worker를 배포할 때 클라이언트 측 자산으로 이러한 파일을 업로드하지 않습니다.

## `run_worker_first`

그렇지 않으면 자산을 일치시키는 요청에 관계없이 Worker 스크립트를 호출하는지 여부를 제어합니다.`run_worker_first = false`(과태)는 요청을 일치하는 정적 자산을 봉사합니다.`run_worker_first = true`무조건[당신의 Worker 스크립트를 호출](/workers/static-assets/routing/worker-script/#run-your-worker-script-first).

<WranglerConfig>
  ```jsonc
  {
  	"$schema": "./node_modules/wrangler/config-schema.json",
  	"name": "my-worker",
  	"compatibility_date": "$today",
  	"main": "src/index.ts",
  	//다음 구성 unconditionally에서 Worker 스크립트를 호출
  	//`src/index.ts`, ASSETS 바인딩을 통해 프로그래밍적으로 fetch 자산 할 수
  	"assets": {
  		"directory": "./public/",
  		"binding": "ASSETS",
  		"run_worker_first": true,
  	},
  }
  ```
</WranglerConfig>

지정할 수 있습니다.`run_worker_first`선택적으로 Worker 스크립트를 실행하는 경로 패턴의 배열은 특정 경로에만 사용됩니다.

배열은 glob 패턴을 지원합니다.`*`깊은 일치와 부정적인 본을 위해`!`연락처

부정적인 본은 비 부정 본에 전진했습니다. 노동자는 부정적인 본 경기의 비 부정적인 본 경기 및 아무도 때 첫째로 달릴 것입니다.

본이 나열된 순서는 중요하지 않습니다.

`run_worker_first`자주 쌍[`not_found_handling = "single-page-application"`설치하기](/workers/static-assets/routing/single-page-application/#advanced-routing-control):

<WranglerConfig>
  ```json
  {
  	"name": "my-spa-worker",
  	"compatibility_date": "$today",
  	"main": "./src/index.ts",
  	"assets": {
  		"directory": "./dist/",
  		"not_found_handling": "single-page-application",
  		"binding": "ASSETS",
  		"run_worker_first": ["/api/*", "!/api/docs/*"]
  	}
  }
  ```
</WranglerConfig>

이 설정에서 요청`/api/*`routes는 worker 스크립트를 먼저 호출합니다.`/api/docs/*`기본 자산 첫 번째 라우팅 동작을 따를 것입니다.

일반 용도`run_worker_first`인증 체크, A/B 테스트 및[당신의 SPA 쉘에 부트 스트랩 데이터를 주사](/workers/examples/spa-shell/).

## `binding`

선택 사항[관련 제품](/workers/runtime-apis/bindings)Worker 스크립트 내에서 자산 수집에 대한 액세스를 제공합니다.

<WranglerConfig>
  ```jsonc
  {
  	"$schema": "./node_modules/wrangler/config-schema.json",
  	"name": "my-worker",
  	"main": "./src/index.js",
  	"compatibility_date": "$today",
  	"assets": {
  		"directory": "./public/",
  		"binding": "ASSETS",
  	},
  }
  ```
</WranglerConfig>

위의 예에서, 자산은 통해 사용할 수 있습니다`env.ASSETS`.

### Runtime API 참조

#### `fetch()`

**매개 변수**

- `request: Request | URL | string`패스워드[자주 묻는 질문](/workers/runtime-apis/request/), URL 객체 또는 URL 문자열. 이 방법을 통해 만든 요청은`html_handling`·`not_found_handling`그들에 적용된 윤곽.

**관련 기사**

- `Promise<Response>`지정된 요청에 대한 정적 자산 응답을 반환합니다.

**이름 \***

동적 코드는 자산 바인딩을 사용하여 프로젝트의 정적 자산에 새로운, 또는 앞으로 들어오는 요청을 만들 수 있습니다. 예를 들어,`env.ASSETS.fetch(request)`, `env.ASSETS.fetch(new URL('https://assets.local/my-file'))`또는`env.ASSETS.fetch('https://assets.local/my-file')`. URL에 사용되는 호스트명(예를 들어,`assets.local`)는 의미가 없습니다 - 유효한 hostname은 작동합니다. URL 경로만 사용할 수 있습니다.

:::참조
자산을 채우려면[RPC 방법](/workers/runtime-apis/rpc/#fetching-static-assets)(무엇이 없다)`request`), 어떤 hostname을 사용하여 URL을 생성 — 예를 들어,`this.env.ASSETS.fetch(new Request('https://assets.local/path/to/asset'))`.
:::

Worker 스크립트를 구성하는 다음 예제를 사용하여 모든 요청에서 응답을 반환합니다.`/api/`. 그렇지 않으면 Worker 스크립트는 자산 바인딩을 통해 들어오는 요청을 전달합니다. 이 경우, Worker 스크립트가 요청한 경로가 일치하지 않은 경우, 이것은 항상 평가됩니다[`not_found_handling`](/workers/static-assets/#routing-behavior)행동.

## 스마트 배치

[스마트 배치](/workers/configuration/placement/)Worker의 코드를 백엔드 인프라에 가까이 배치할 수 있습니다. Smart Placement는 당신이 지정한 경우에만 효력이 있을 것입니다`main`, 당신의 노동자 부호에 지적.

### Smart Placement 와 Worker Code 처음으로

당신이 뛰고 싶은 경우에[자산의 앞에 Worker 코드](/workers/static-assets/routing/worker-script/#run-your-worker-script-first)으로 설정`run_worker_first=true`, 모든 요청은 Smart-Placed Worker에 처음 여행해야합니다. 결과적으로, 당신은 자산 요청에 대한 지연 시간을 경험할 수 있습니다.

Smart Placement 사용`run_worker_first=true`다른 백엔드 서비스와 통합 할 때, 모든 자산을 봉사하기 전에 정통 요청, 또는 당신이 그들을 봉사하기 전에 당신의 자산에 수정을 만들려면.

사용자가 가능한 한 빨리 제공 한 일부 자산을 원하는 경우, 그러나 다른 사람은 스마트 대체 노동자 뒤에 제공, 여러 Workers로 앱을 분할 고려[서비스 바인딩을 사용하여 연결](/workers/configuration/placement/#multiple-workers).

### 자산과 스마트 배치 First

Smart Placement 활성화`run_worker_first=false`(또는 지정하지 않음) 당신은 사용자에게 가능한 한 가까이에서 자산을 제공 할 수 있지만, 가장 효율적으로 실행하기 위해 작업자 논리를 이동합니다 (예 : 데이터베이스 근처).

Smart Placement 사용`run_worker_first=false`(또는 지정하지 않음) 빠른 자산 배달을 우선화 할 때.

이것은 영향을 미치지 않습니다.[기본 routing 동작](/workers/static-assets/#routing-behavior).
