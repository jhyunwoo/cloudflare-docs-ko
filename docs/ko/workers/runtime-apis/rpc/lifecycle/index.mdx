## 일생, 기억 및 자원 관리

서비스 바인딩을 사용하여 RPC에 다른 노동자를 호출 할 때, 당신은 당신이 호출하는 노동자에 메모리를 사용합니다. 다음 예제를 고려:

```js
let user = await env.USER_SERVICE.findUser(id);
```

관련 기사`findUser()`서버 측에서 객체 확장을 반환합니다.`RpcTarget`, 이렇게`user`클라이언트 측은 그 먼 목표에 기인한 stub입니다.

stub가 여전히 클라이언트에 존재함에 따라 서버의 대응 객체는 수집 할 수 없습니다. 그러나, 각 isolate는 다른 고립으로 볼 수없는 자체 쓰레기 수집기를 가지고 있습니다. 그래서, 서버의 isolate에 대한 순서는 객체가 수집 될 수 있다는 것을 알고, 호출 isolate는 "disposing"라는 명시적 신호를 보내야한다.

많은 경우에 (아래로 구독해), 체계는 더 이상 필요로 하지 않을 때 자동적으로 깨닫고, 그것을 자동적으로 분해할 것입니다. 그러나, 최고의 성능을 위해, 당신의 코드는 그와 함께 수행 될 때 명시적으로 stubs를 분해해야합니다.

## Explicit 자원 관리

자원이 제대로 분해되도록하려면 사용해야합니다.[Explicit 자원 관리](https://github.com/tc39/proposal-explicit-resource-management), 새로운 JavaScript 언어 기능은 자원이 분해 될 때 명시적으로 신호 할 수 있습니다. Explicit Resource Management는 단계 3 TC39 제안입니다.[곧 V8에 오는](https://bugs.chromium.org/p/v8/issues/detail?id=13559).

Explicit Resource Management는 다음과 같은 언어 기능을 추가합니다.

- 더 보기[`using`관련 기사](https://github.com/tc39/proposal-explicit-resource-management?tab=readme-ov-file#using-declarations)
- [`Symbol.dispose`·`Symbol.asyncDispose`](https://github.com/tc39/proposal-explicit-resource-management?tab=readme-ov-file#additions-to-symbol)

변수가 선언된 경우`using`, 변수가 더 이상 범위가 없을 때, 변수의 disposer는 호출됩니다. 예를 들면:

```js
function sendEmail(id, message) {
  using user = await env.USER_SERVICE.findUser(id);
  await user.sendEmail(message);

  //user[Symbol.dispose]()는 범위의 끝에 불용하게 불립니다.
}
```

`using`선언은 예외로 인해 코드가 중단되는 경우에도 stubs를 분해하는 것을 잊지 못할 것입니다.

### 이용 방법`using`당신의 노동자의 선언

[모델 번호: Wrangler](/workers/wrangler/)v4+ 지원`using`기본적으로 키워드. Wrangler의 이전 버전을 사용하는 경우 대신 리소스를 수동으로 분해해야합니다.

다음 코드:

```js
{
	using counter = await env.COUNTER_SERVICE.newCounter();
	await counter.increment(2);
	await counter.increment(4);
}
```

...와 동등한 것:

```js
{
	const counter = await env.COUNTER_SERVICE.newCounter();
	try {
		await counter.increment(2);
		await counter.increment(4);
	} finally {
		counter[Symbol.dispose]();
	}
}
```

## 자동 처리 및 실행 상황

RPC 시스템은 다음과 같은 경우 stubs를 자동으로 분배합니다.

### 이벤트 핸들러 / 실행 상황

이벤트 핸들러가 "done"일 때, 이벤트의 일부로 생성 된 모든 스텁은 자동으로 분해됩니다.

예를 들어, 고려[`fetch()`회사 소개](/workers/runtime-apis/handlers/fetch)HTTP 이벤트를 처리한다. 핸들러는 이벤트를 처리하는 일부로 RPC를 나가고, 그 중에는 텁을 반환 할 수 있습니다. 최종 HTTP 응답이 전송되면 핸들러는 "done"이며 모든 스텁은 즉시 처분됩니다.

더 정확하게, 이벤트는 "execution context"를 가지고 있으며 핸들러가 처음 호출되면 HTTP 응답이 전송되면 종료됩니다. 실행 컨텍스트는 클라이언트가 응답을 받기 전에 차단하면 일찍 종료 될 수도 있습니다. 또는 호출하여 정상적인 엔드 포인트에서 확장 될 수 있습니다.[`ctx.waitUntil()`](/workers/runtime-apis/context).

예를 들어, 아래 작업자는 사용하지 않습니다.`using`선언,하지만 스텁은 한 번의 처분 될 것이다`fetch()`핸들러는 응답을 반환합니다:

```js
export default {
	async fetch(request, env, ctx) {
		let authResult = await env.AUTH_SERVICE.checkCookie(
			req.headers.get("Cookie"),
		);
		if (!authResult.authorized) {
			return new Response("Not authorized", { status: 403 });
		}
		let profile = await authResult.user.getProfile();

		return new Response(`Hello, ${profile.name}!`);
	},
};
```

RPC를 통해 Worker는 실행 컨텍스트가 있습니다. 컨텍스트가 RPC 방식이 시작될 때`WorkerEntrypoint`뚱 베어 이 RPC의 매개 변수 또는 결과에서 stubs가 전달되지 않은 경우, RPC가 반환되면 컨텍스트 엔드 (이벤트는 "done")입니다. 그러나, 어떤 스텁이 통과되면, 실행 상황은 그러한 스텁이 분해 될 때까지 임의로 연장됩니다 (그들 모두 반환). HTTP와 마찬가지로 클라이언트가 차단되면 서버의 실행 컨텍스트는 여전히 존재 여부에 관계없이 즉시 취소됩니다. 다른 노동자는 자체 실행 상황에 따라 분리 된 것으로 간주됩니다. 다시, context는 확장될 수 있습니다[`ctx.waitUntil()`](/workers/runtime-apis/context).

### Stubs는 RPC 통화의 매개 변수로 수신

stubs가 RPC의 매개 변수에서 수신되면, 해당 stubs는 호출이 반환될 때 자동으로 분해됩니다. 그보다 더 긴 스텁을 유지하려면 전화를해야합니다.`dup()`그들에 대한 방법.

### RPC 객체를 처리하는 것은 그 객체의 일부인 stubs를 disposes

RPC가 어떤 종류의 객체를 반환할 때, 그 객체는 시스템에 의해 추가 된 disposer가있을 것입니다. 호출에 의해 반환된 모든 stubs를 분배합니다. 예를 들어, RPC가 4 개의 스텁의 배열을 반환하면 배열 자체는 모든 4 개의 스텁을 분배하는 분산 장치가 있습니다. RPC에 의해 반환된 값은 정수기가 숫자나 문자열과 같은 원시값이 있을 때는 안 됩니다. 이 유형은 그들에 추가된 disposers가 있을 수 없습니다, 그러나 이 유형은 그(것)들을 포함할 수 없기 때문에, 이 경우에 있는 disposer를 위한 아무 필요도 없습니다.

이것은 당신이 거의 항상 RPC의 결과를 저장해야한다는 것을 의미합니다`using`선언 :

```js
using result = stub.foo();
```

이 방법, 결과가 어떤 스텁을 포함하면, 그들은 처분 될 것입니다. RPC를 반환하지 않더라도, 객체의 어떤 종류를 반환하면, 그것은 저장하는 좋은 아이디어입니다`using`공지사항 이 방법, RPC가 미래에 확장되면, 당신의 코드가 준비됩니다.

반환된 스텁을 유지하려는 경우`using`선언, 당신은 호출 할 수`dup()`범위의 끝 전에 스텁에. (자세한 내용은 나중에 복제합니다.)

## 처분 및`RpcTarget`한국어

확장 된 클래스[`RpcTarget`](/workers/runtime-apis/rpc/)선택적으로 disposer를 실행할 수 있습니다:

```js
class Foo extends RpcTarget {
	[Symbol.dispose]() {
		//· ...
	}
}
```

RpcTarget의 disposer는 마지막 stub가 분해 된 후 실행됩니다. stub의 disposer에 클라이언트 측 호출은 서버 측 disposer를 호출하지 않습니다; 서버의 disposer는 나중에 호출됩니다. 이 때문에, 사기꾼에 의해 던지는 어떤 예외든지 클라이언트에게 전파하지 않습니다; 대신, 그들은 uncaught 예외로 보고됩니다. 주의사항`RpcTarget`'s disposer'는 선언해야 합니다.`Symbol.dispose`. `Symbol.asyncDispose`지원되지 않습니다.

## 더 보기`dup()`제품 설명

때때로, 당신은 stub를 함수에 전달해야 할 때 그것은 완료 될 때, 그러나 당신은 또한 나중에 사용을 위해 stub를 유지하고 싶습니다. 이 문제를 해결하기 위해, 당신은 "dup"스텁을 할 수 있습니다:

```js
let stub = await env.SOME_SERVICE.getThing();

//중복 만들기.
let stub2 = stub.dup();

//몇 가지 함수를 호출합니다.
await func(stub);

//stub2는 여전히 유효합니다
```

당신은 생각할 수 있습니다`dup()`이름 \*[유닉스 시스템 같은 이름의 호출](https://man7.org/linux/man-pages/man2/dup.2.html): 독립적으로 닫아야하는 동일한 대상에서 새로운 핸들 포인팅을 만듭니다.

인스턴스의 경우[`RpcTarget`한국어](/workers/runtime-apis/rpc/)의 붓기 포인트는 붓기, 붓기는 모든 중복이 처분되었을 때 붓기 만 호출됩니다. 그러나, 이것은 단지 같은 스텁에서 시작 중복에 적용. 같은 경우의`RpcTarget`RPC를 여러 번 이상 통과, 새로운 스텁은 각 시간을 생성하고, 이들은 서로 중복으로 간주되지 않습니다. 따라서, disposer는 각 시간 동안 한 번 호출됩니다`RpcTarget`견적 요청

이 상황을 피하기 위해, 당신은 수동으로 stub를 로컬로 만들고, 그 후에 RPC 다수 시간의 맞은편을 통과할 수 있습니다. RPC를 통해 스텁을 전달할 때, 스텁의 소유권은 수신자에게 전송합니다.`dup()`당신이 그것을 보낼 때마다:

```js
import { RpcTarget, RpcStub } from "cloudflare:workers";

class Foo extends RpcTarget {
	//· ...
}

let obj = new Foo();
let stub = new RpcStub(obj);
await rpc1(stub.dup()); //`stub`의 dup을 보냅니다
await rpc2(stub.dup()); //`stub`의 다른 dup을 보냅니다
stub[Symbol.dispose](); //원래 스텁을 분배

//obj's disposer는 다른 2개의 stubs 때 호출될 것입니다
//원격으로 처분됩니다.
```
