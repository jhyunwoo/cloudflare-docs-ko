gradual 배포를 사용하여, 당신은 할 수 있습니다:

## gradual 배포 사용

다음 섹션에서는 gradual 배포의 예를 통해 안내합니다. 당신은 하나를 사용할 수 있습니다[Wrangler](/workers/configuration/versions-and-deployments/gradual-deployments/#via-wrangler)또는 Cloudflare dashboard에:

- 새로운 노동자를 만듭니다.
- 배포하지 않고 작업자의 새로운 버전을 게시.
- 두 가지 버전 사이의 점차적인 배포를 만듭니다.
- 새로운 버전의 배포를 100% 트래픽으로 진행합니다.

### Wrangler

:::참조

최소 필요한 Wrangler 버전: 3.40.0. 3.73.0 이전 버전이 필요한 경우`--x-versions`플래그.

:::

#### 1. 새 노동자를 만들고 배치

새로운 기능`"Hello World"`작업자 사용[`create-cloudflare`클립 (C3)](/pages/get-started/c3/)그리고 그것을 배치합니다.

```sh
npm create cloudflare@latest <NAME> -- --type=hello-world
```

이름 \*`yes`또는`no`TypeScript를 사용하기 위하여. 이름 \*`yes`응용 프로그램을 배포합니다. 이것은 당신의 노동자의 첫 번째 버전입니다.

#### 2. Worker의 새로운 버전 만들기

Worker의 새로운 버전을 만들려면 Worker 코드를 변경하여 편집하십시오.`Response`원하는 텍스트에 콘텐츠 및 Worker를 사용하여 업로드[`wrangler versions upload`](/workers/wrangler/commands/#versions-upload)명령.

```sh
npx wrangler versions upload
```

이것은 자동으로 배포되지 않는 Worker의 새로운 버전을 만들 것입니다.

#### 3. 새 배포 만들기

사용 방법[`wrangler versions deploy`](/workers/wrangler/commands/#versions-deploy)명령을
Worker의 두 버전 사이의 트래픽을 나누는 새로운 배포를 만듭니다. 대화 형 프롬프트를 따르고 버전이 업로드되었습니다.[단계 #1](/workers/configuration/versions-and-deployments/gradual-deployments/#1-create-and-deploy-a-new-worker)·[단계 #2](/workers/configuration/versions-and-deployments/gradual-deployments/#2-create-a-new-version-of-the-worker). 각 버전의 원하는 비율을 선택하십시오.

```sh
npx wrangler versions deploy
```

#### 4. 분할 배포를 테스트

작업자의 cURL 명령을 실행하여 분할 배포를 테스트합니다.

```bash
for j in {0..10}
do
    curl -s https://$WORKER_NAME.$SUBDOMAIN.workers.dev
done
```

당신은 10 응답을 볼 수 있습니다. 응답은 배포판의 버전에 의해 반환된 콘텐츠를 반영합니다. 응답은 구성된 비율에 따라 다를 것입니다[단계 #3](/workers/configuration/versions-and-deployments/gradual-deployments/#3-create-a-new-deployment).

특정 버전을 사용할 수 있습니다.[버전 overrides](#version-overrides).

#### 5. 새 버전 설정 100% 배포

지원하다`wrangler versions deploy`다시 대화 형 프롬프트를 따르십시오. 버전 선택[단계 2](/workers/configuration/versions-and-deployments/gradual-deployments/#2-create-a-new-version-of-the-worker)그리고 설정 100% 배포.

```sh
npx wrangler versions deploy
```

## 버전 친화

기본적으로, gradual 배포를 사용할 때 구성 된 비율은 per-request 기초에서 작동합니다. 요청에는 Worker의 두 가지 버전 중 하나 인 X % 확률이 있습니다.[설치하기](/workers/configuration/versions-and-deployments/#deployments).

특정 식별자 (사용자, 세션 또는 고유 ID와 같은)와 관련된 요청을 원할 수 있습니다. 작업자의 일관된 버전에 의해 처리됩니다. 버전 skew는 여러 버전의 응용 프로그램이 배포 될 때 발생합니다. Worker의 버전을 변경하고 per-request 기초에 나타날 것을 방지하기 위해 버전 친화성을 구성할 수 있습니다.

이 작업을 수행 할 수 있습니다.`Cloudflare-Workers-Version-Key`당신의 노동자에 들어오는 요구에 머리. 예를 들면:

```sh
curl -s https://example.com -H 'Cloudflare-Workers-Version-Key: foo'
```

견적 요청[설치하기](/workers/configuration/versions-and-deployments/#deployments), 버전 열쇠 세트를 가진 모든 요구`foo`당신의 노동자의 동일한 버전에 의해 취급될 것입니다. 당신의 노동자의 특정 버전은 버전 열쇠입니다`foo`각 작업자 버전에 대해 설정한 비율에 의해 결정됩니다.

설정할 수 있습니다.`Cloudflare-Workers-Version-Key`인터넷에서 직장인에게 외부 요청을 할 때 두 사람뿐만 아니라 한 직장인에서 다른 노동자에게 잠수함을 만들 때[서비스 바인딩](/workers/runtime-apis/bindings/service-bindings/).

### 설치하기`Cloudflare-Workers-Version-Key`Ruleset Engine 사용

URL, 헤더 또는 쿠키와 같은 요청의 특정 속성에서 버전 키를 추출 할 수 있습니다. 구성할 수 있습니다.[Ruleset 엔진](/ruleset-engine/)이 지역을 규칙. 이 옵션을 지정할 수 있습니다. 외부 클라이언트를 수정하지 않고 이러한 속성에 따라 버전 친화성을 지정할 수 있습니다.

예를 들어, 노동자가 URI 경로 아래 비디오 자산을 봉사하는 경우`/assets/`그리고 당신은 일관된 버전에 의해 처리 될 각 독특한 자산에 요청을 원, 당신은 다음을 정의 할 수[요청 헤더 변형 규칙](/rules/transform/request-header-modification/):

<Example>
  본문 바로가기**Expression 편집기**:

  ```txt
  starts_with(http.request.uri.path, "/asset/")
  ```

  선택된 작업**요청 헤더를 수정**: *동적 설정*

  **헤더 이름**: `Cloudflare-Workers-Version-Key`

  **제품정보**: `regex_replace(http.request.uri.path, "/asset/(.*)", "${1}")`
</Example>

## 버전 overrides

gradual 배포에서 작업자의 특정 버전을 보낼 수 있습니다.

귀하의 요청에 버전 override를 지정하려면 설정할 수 있습니다.`Cloudflare-Workers-Version-Overrides`당신의 노동자에 요청에 헤더. 예를 들면:

```sh
curl -s https://example.com -H 'Cloudflare-Workers-Version-Overrides: my-worker-name="dc8dcd28-271b-4367-9840-6c244f84cb40"'
```

`Cloudflare-Workers-Version-Overrides`한국어[사전 구조 Header](https://www.rfc-editor.org/rfc/rfc8941#name-dictionaries).

사전은 여러 키 값 쌍을 포함 할 수 있습니다. 각 열쇠는 노동자의 이름을 과도하게 적용되어야 합니다 나타냅니다. 값은 사용해야 하는 버전 ID를 나타냅니다.[스트레이트](https://www.rfc-editor.org/rfc/rfc8941#name-strings).

지정된 버전이 현재 배포중인 경우 버전 오버라이드만 적용됩니다. 현재 배포판의 버전은 사용할 수 있습니다.[`wrangler deployments list`](/workers/wrangler/commands/#deployments-list)명령 또는 명령**Workers & Pages**Cloudflare QXdashboard의 페이지 > Workers > 배포 > Active Deployment를 선택하십시오.

:::note\[버전의 중복이 적용되었음]

요청의 버전 오버라이드가 적용되지 않은 이유의 수가 있습니다. 예를 들면:

- 지정된 버전을 포함하는 배포는 아직 전파되지 않을 수 있습니다.
- 헤더 값은 유효하지 않을 수 있습니다.[한국어](https://www.rfc-editor.org/rfc/rfc8941#name-dictionaries).

요청의 버전 오버라이드가 적용되지 않은 경우, 요청은 gradual 배포 설정에서 설정된 백분율에 따라 처리됩니다.

요청의 버전 오버라이드가 올바르게 적용되었는지 확인하려면,[관련 기사](#observability)당신의 노동자의 버전은 invoked. 이 체크를 사용하여 자동화 할 수 있습니다.[runtime 바인딩](#runtime-binding)Worker의 응답에서 버전을 반환합니다.

:::

## Durable Objects를 위한 Gradual 배치

제품정보[글로벌 독창성](/durable-objects/platform/known-issues/#global-uniqueness), 각의 1개의 버전만[튼튼한 목표](/durable-objects/)시간에 실행할 수 있습니다. 이것은 gradual 배치가 Durable Objects를 위해 약간 다르게 작동한다는 것을 의미합니다.

Durable Objects로 Worker를 위한 새로운 gradual 배포를 만들 때, 각 튼튼한 개체는 구성된 비율에 따라 Worker 버전을 할당합니다.[설치하기](/workers/configuration/versions-and-deployments/#deployments). 이 버전은 새로운 배포를 만들 때까지 변경하지 않습니다.

![Gradual 배포 Durable Objects](~/assets/images/workers/platform/versions-and-deployments/durable-objects.png)

### 이름 \*

이 예제는 이전에 "foo", "bar"및 "baz"라는 이름으로 3 개의 튼튼한 객체 인스턴스를 만들었습니다.

작업자는 현재 버전 "A"을 호출하고 점차적으로 작업자의 새로운 버전 "B"을 배치 할 버전에 있습니다.

Durable Objects의 버전이 어떻게 진행되는지 알 수 있습니다.

|           배포 설정          |  "후" |  "바" | "바즈" |
| :----------------------: | :--: | :--: | :--: |
|     버전 A: 100%<br />     |   ·  |   ·  |   ·  |
| 버전 B: 20%<br />번역 A: 80% | 사이트맵 |   ·  |   ·  |
| 버전 B: 50%<br />번역 A: 50% | 사이트맵 | 사이트맵 |   ·  |
|     버전 B: 100%<br />     | 사이트맵 | 사이트맵 | 사이트맵 |

이것은 단지 예이므로 Durable Objects에 할당 된 버전은 다를 수 있습니다. 그러나 다음은 보장됩니다 :

- 주어진 배치를 위해, 각 튼튼한 목표에 요구는 항상 동일한 노동자 버전을 사용합니다.
- 이전 배포와 같은 순서에 각 버전을 지정할 때 버전의 비율을 증가, 이전에 할당 된 Durable Objects는 다른 버전을 할당되지 않습니다. 이 예제에서, 튼튼한 개체 "foo"는 버전 "B"에서 버전 "A"로 뒤지지 않을 것입니다.
- 튼튼한 개체는 단지 일 것입니다[지원하다](/durable-objects/observability/troubleshooting/#durable-object-reset-because-its-code-was-updated)다른 버전을 할당할 때, 그래서 각 튼튼한 목표는이 예에서 한 번만 재설정됩니다.

:::참조
일반적으로, 노동자 번들은 모두 튼튼한 개체 클래스와 그와 상호 작용하는 노동자를 정의합니다. 이 경우에, 당신은 당신의 튼튼한 목표 및 노동자에 자주적으로 변화할 수 없습니다.

당신은 당신의 튼튼한 목표와 그것의 노동자 사이 API 변화가 있다는 것을 보증해야 합니다[앞으로와 뒤로 호환](/durable-objects/platform/known-issues/#code-updates)gradual 배포 또는 사용하지 않는 경우. 그러나, gradual 배포를 사용하면 Durable Objects의 다른 버전이 서로 상호 작용할 수 있습니다.
주요 특징

### 이름 \*

새로운 튼튼한 개체 마이그레이션을 포함하는 Worker 번들의 버전은 업로드 할 수 없습니다. 이것은 튼튼한 목표 마이그레이션이 원자 작업이기 때문에. 튼튼한 개체 마이그레이션은 다음과 같은 명령으로 배포 될 수 있습니다:

```sh
npx wrangler versions deploy
```

튼튼한 개체 마이그레이션 배포의 폭발 반경을 제한하려면 마이그레이션은 다른 코드 변경의 독립적으로 배포해야합니다.

왜 튼튼한 개체 마이그레이션이 원자 작업인지 이해하기 위해, 점차적으로 삭제 마이그레이션을 배치의 hypothetical 예제를 고려. 삭제 마이그레이션이 튼튼한 개체 인스턴스의 50 %에 적용되면 WorkersXQ는 그들이 삭제되었기 때문에 내구성 객체 인스턴스를 요청합니다.

오류를 일으키지 않고이 작업을 수행하려면, 어떤 튼튼한 개체 인스턴스에 의존하지 않는 노동자의 버전은 이미 구출되었습니다. 그런 다음 트래픽에 영향을받지 않고 삭제 마이그레이션을 배포 할 수 있으며 점차적으로 할 이유가 없습니다.

## 옵션 정보

gradual 배포를 사용할 때 Workers invocations를 새로운 버전 배포의 영향으로 가시성을 얻을 수 있습니다.

### 다운로드

새로운`ScriptVersion`객체는[Workers 다운로드](/workers/observability/logs/logpush/). `ScriptVersion`지금 Logpush API를 통해서만 추가될 수 있습니다. 샘플 API 호출:

```bash
curl -X POST 'https://api.cloudflare.com/client/v4/accounts/<ACCOUNT_ID>/logpush/jobs' \
-H 'Authorization: Bearer <TOKEN>' \
-H 'Content-Type: application/json' \
-d '{
"name": "workers-logpush",
"output_options": {
    "field_names": ["Event", "EventTimestampMs", "Outcome", "Logs", "ScriptName", "ScriptVersion"],
},
"destination_conf": "<DESTINATION_URL>",
"dataset": "workers_trace_events",
"enabled": true
}'| jq .
```

`ScriptVersion`다음 구조와 객체입니다:

```json
scriptVersion: {
    id: "<UUID>",
    message: "<MESSAGE>",
    tag: "<TAG>"
}
```

### Runtime 바인딩

사용 방법[버전 metadata 바인딩](/workers/runtime-apis/bindings/version-metadata/)에 액세스 버전 ID 또는 버전 태그 당신의 노동자에.

## 제한 사항

### 설정 제한

작업자의 마지막 100 업로드 버전으로 새로운 배포만 만들 수 있습니다.
