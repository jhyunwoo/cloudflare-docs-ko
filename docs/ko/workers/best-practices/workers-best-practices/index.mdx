생산 패턴을 기반으로 Workers에 대한 모범 사례, Cloudflare의 자체 내부 사용 및 개발자 커뮤니티에서 볼 수있는 일반적인 문제.

## 제품 설명

### 당신의 호환성 날짜 현재를 지키십시오

더 보기[`compatibility_date`](/workers/configuration/compatibility-dates/)런타임 기능 및 버그 수정이 작업자에게 제공됩니다. 새 프로젝트에서 오늘 날짜로 설정하면 최신 행동을 얻을 수 있습니다. 기존 프로젝트에서 지속적으로 업데이트하는 것은 새로운 API에 액세스하고 코드를 변경하지 않고 수정합니다.

<WranglerConfig>
  ```jsonc
  {
  	"name": "my-worker",
  	"main": "src/index.ts",
  	"compatibility_date": "$today",
  	"compatibility_flags": ["nodejs_compat"],
  }
  ```
</WranglerConfig>

더 많은 정보를 원하시면, 참조[호환성 날짜](/workers/configuration/compatibility-dates/).

### nodejs compat 사용

더 보기[`nodejs_compat`](/workers/runtime-apis/nodejs/)호환성 깃발은 Node.js 붙박이 단위에 당신의 노동자 접근을 좋아합니다`node:crypto`, `node:buffer`, `node:stream`, 다른 사람. 많은 라이브러리는 이러한 모듈에 의존하고, 이 플래그는 cryptic import errors를 runtime에 방지합니다.

<WranglerConfig>
  ```jsonc
  {
  	"name": "my-worker",
  	"main": "src/index.ts",
  	"compatibility_date": "$today",
  	"compatibility_flags": ["nodejs_compat"],
  }
  ```
</WranglerConfig>

더 많은 정보를 원하시면, 참조[Node.js 호환성](/workers/runtime-apis/nodejs/).

### wrangler 유형의 바인딩 유형 생성

손을 덮지 마십시오.`Env`인터페이스. 지원하다[`wrangler types`](/workers/wrangler/commands/#types)실제 Wrangler 구성과 일치하는 유형 정의 파일을 생성합니다. config와 code 사이의 mismatches를 배치하여 배포 시간 대신 컴파일된 시간에 잡습니다.

재 실행`wrangler types`바인딩을 추가하거나 변경할 때.

<PackageManagers type="exec" pkg="wrangler" args="types" />

<TypeScriptExample filename="src/index.ts">
  ```ts
  //✅ 좋은: Env는 wrangler 유형에 의해 생성되고 항상 당신의 config를 일치합니다
  //Env를 수동으로 정의하지 마십시오 - 실제적인 바인딩에서 무서운

  export default {
  	async fetch(request: Request, env: Env): Promise<Response> {
  		//env.MY KV, env.MY BUCKET, 등은 모두 정확하게 입력됩니다
  		const value = await env.MY_KV.get("key");
  		return new Response(value);
  	},
  } satisfies ExportedHandler<Env>;
  ```
</TypeScriptExample>

더 많은 정보를 원하시면, 참조[wrangler 유형](/workers/wrangler/commands/#types).

### 소스에 wrangler 비밀과 비밀을 저장

비밀 (API 키, 토큰, 데이터베이스 자격)는 Wrangler 구성 또는 소스 코드에 나타나지 않아야합니다. 제품 정보[`wrangler secret put`](/workers/configuration/secrets/)그것을 안전하게 저장하고, 그들을 통해 접근`env`런타임에. 현지 발전을 위해, 사용`.env`파일 (그리고 그것을 확인합니다.`.gitignore`). 더 많은 정보를 원하시면, 참조[환경 변수](/workers/configuration/environment-variables/).

<WranglerConfig>
  ```jsonc
  {
  	"name": "my-worker",
  	"main": "src/index.ts",
  	"compatibility_date": "$today",
  	"compatibility_flags": ["nodejs_compat"],

  	//✅ 좋은: 버전 통제에 있는 non-secret 윤곽 생활
  	"vars": {
  		"API_BASE_URL": "https://api.example.com",
  	},

  	//✓ 나쁜 : 여기에 비밀을 넣지 마십시오.
  	//"API KEY": "sk-live-abc123..."
  }
  ```
</WranglerConfig>

비밀을 추가하려면 다음 명령을 실행하고 즉시 비밀을 제공합니다.

<PackageManagers type="exec" pkg="wrangler" args="secret put API_KEY" />

다른 도구 또는 환경 변수에서 관 비밀을 할 수 있습니다:

```bash
#다른 CLI 도구에서 파이프
npx some-cli-tool --get-secret | npx wrangler secret put API_KEY
#환경변수 또는 .env 파일에서 파이프
echo "$API_KEY" | npx wrangler secret put API_KEY
```

더 많은 정보를 원하시면, 참조[계정 관리](/workers/configuration/secrets/).

### 환경 deliberately 구성

[Wrangler 환경](/workers/wrangler/environments/)생산, staging 및 개발을 위해 WorkersXQ를 분리하는 동일한 코드를 배포할 수 있습니다. 각 환경은 지정된 노동자를 만듭니다`{name}-{env}`(예:`my-api-production`·`my-api-staging`).

각 환경은 따로따로 대우됩니다. Bindings와 vars는 환경 당 선언되고 상속되지 않습니다. 더 알아보기[비 inheritable 열쇠](/workers/wrangler/configuration/#non-inheritable-keys). 루트 노동자 (환경 suffix 없이)는 별도의 배포입니다. 사용하지 않으려면 환경 지정 없이 배포하지 마십시오.`--env`.

<WranglerConfig>
  ```jsonc
  {
  	"name": "my-api",
  	"main": "src/index.ts",
  	"compatibility_date": "$today",
  	"compatibility_flags": ["nodejs_compat"],

  	//이 바인딩은 root Worker에만 적용됩니다.
  	"kv_namespaces": [{ "binding": "CACHE", "id": "dev-kv-id" }],

  	"env": {
  		//생산 환경 : "my-api-production"로 배포
  		"production": {
  			"kv_namespaces": [{ "binding": "CACHE", "id": "prod-kv-id" }],
  			"routes": [
  				{ "pattern": "api.example.com/*", "zone_name": "example.com" },
  			],
  		},
  		//노화 환경 : "my-api-staging"로 배포
  		"staging": {
  			"kv_namespaces": [{ "binding": "CACHE", "id": "staging-kv-id" }],
  			"routes": [
  				{ "pattern": "api-staging.example.com/*", "zone_name": "example.com" },
  			],
  		},
  	},
  }
  ```
</WranglerConfig>

이 구성 파일로, staging에 배포:

<PackageManagers type="exec" pkg="wrangler" args="deploy --env staging" />

더 많은 정보를 원하시면, 참조[환경분야](/workers/wrangler/environments/).

### 사용자 정의 도메인 또는 경로 설정

Workers는 2개의 여정 기계장치를 지원하고, 그들은 다른 목적을 봉사합니다:

- **[주문 영역](/workers/configuration/routing/custom-domains/)**: 노동자**이름 \***&#xC774;름. Cloudflare는 DNS 레코드와 SSL 인증서를 자동으로 생성합니다. 작업자가 호스트 이름에 대한 모든 트래픽을 처리 할 때 이것을 사용하십시오.
- **[오시는 길](/workers/configuration/routing/routes/)**: 노동자 실행**앞**기존의 Origin 서버. 경로 추가하기 전에 hostname에 대한 Cloudflare proxied (orange-clouded) DNS 레코드가 있어야합니다.

경로와 가장 일반적인 실수는 DNS 레코드가 누락됩니다. DNS 레코드없이, hostname 반환에 요청`ERR_NAME_NOT_RESOLVED`그리고 당신의 노동자를 결코 도달하지 마십시오. 진짜 근원이 없는 경우, proxied를 추가하십시오`AAAA`관련 기사`100::`회사연혁

<WranglerConfig>
  ```jsonc
  {
  	"name": "my-worker",
  	"main": "src/index.ts",
  	"compatibility_date": "$today",
  	"compatibility_flags": ["nodejs_compat"],

  	//옵션 1 : 사용자 정의 도메인 - 노동자는 기원이며 DNS는 자동으로 관리됩니다.
  	"routes": [{ "pattern": "api.example.com", "custom_domain": true }],

  	//옵션 2: 경로 — 노동자는 기존의 기원의 앞에 실행
  	//shop.example.com에 대한 proxied DNS 레코드가 필요합니다.
  	//"루트": [
  	//{ "pattern": "shop.example.com/*", "zone name": "example.com" }
  	//·
  }
  ```
</WranglerConfig>

더 많은 정보를 원하시면, 참조[로그아웃](/workers/configuration/routing/).

## 요청 및 응답 처리

### 스트림 요청 및 응답 몸

메모리 제한에 관계없이 큰 요청과 응답을 스트리밍하는 것은 모든 언어에서 최고의 연습입니다. 피크 메모리 사용량을 감소시키고 시간 첫 번째 바이트를 향상시킵니다. Workers에는[128 MB 메모리 제한](/workers/platform/limits/), 그래서 전체 몸을 버퍼`await response.text()`또는`await request.arrayBuffer()`큰 페이로드에서 노동자를 충돌합니다.

전적으로 소비하는 요청 신체 (JSON 탑재량, 파일 업로드), 읽기 전에 최대 크기를 적용합니다. 이 데이터 전송에서 클라이언트가 프로세스를 원하지 않습니다.

Worker를 통해 데이터 스트림`TransformStream`소스에서 모든 메모리에 보관하지 않고 목적지까지 파이프.

<TypeScriptExample filename="src/index.ts">
  ```ts
  //✓ 나쁜 : 메모리에서 전체 응답 몸 버퍼
  const badHandler = {
  	async fetch(request: Request, env: Env): Promise<Response> {
  		const response = await fetch("https://api.example.com/large-dataset");
  		const text = await response.text();
  		return new Response(text);
  	},
  } satisfies ExportedHandler<Env>;

  //✅ 좋은: 완충기 없이 응답 몸을 흐릅니다
  export default {
  	async fetch(request: Request, env: Env): Promise<Response> {
  		const response = await fetch("https://api.example.com/large-dataset");
  		return new Response(response.body, response);
  	},
  } satisfies ExportedHandler<Env>;
  ```
</TypeScriptExample>

여러 응답 (예를 들어, 여러 업스트림 API에서 데이터를 fetching)을 concatenate 할 때, 각 신체가 단일 쓰기 가능한 스트림으로 순차적으로 파이프. 이것은 메모리의 응답의 모든 버퍼를 피합니다.

<TypeScriptExample filename="src/concat.ts">
  ```ts
  export default {
  	async fetch(request: Request, env: Env): Promise<Response> {
  		const urls = [
  			"https://api.example.com/part-1",
  			"https://api.example.com/part-2",
  			"https://api.example.com/part-3",
  		];

  		const { readable, writable } = new TransformStream();

  		//✅ 좋은: 완충기 없이 각 응답 몸 순차적으로 관
  		const pipeline = (async () => {
  			for (const url of urls) {
  				const response = await fetch(url);
  				if (response.body) {
  					//pipeTo with PreventionClose 다음 응답을 위해 writable open 유지
  					await response.body.pipeTo(writable, {
  						preventClose: true,
  					});
  				}
  			}
  			await writable.close();
  		})();

  		//즉시 읽기 가능한 측면을 반환 — 데이터 스트림으로 도착
  		return new Response(readable, {
  			headers: { "Content-Type": "application/octet-stream" },
  		});
  	},
  } satisfies ExportedHandler<Env>;
  ```
</TypeScriptExample>

더 많은 정보를 원하시면, 참조[사이트 맵](/workers/runtime-apis/streams/).

### 응답 후에 일을 위해 waitUntil를 사용하십시오

[`ctx.waitUntil()`](/workers/runtime-apis/context/)응답 후에 작업을 수행 할 수 있습니다 분석, 캐시 쓰기, 비 크리티컬 로깅, 또는 webhook 알림과 같은 클라이언트에 전송됩니다. 이것은 여전히 배경 작업을 완료하면서 빠른 응답을 유지합니다.

두 개의 일반적인 pitfalls가 있습니다. 파괴`ctx`(그것은 잃습니다)`this`30초를 초과하는 "Illegal invocation"을 바인딩하고 던져`waitUntil`응답 후에 시간 제한은 보내집니다.

<TypeScriptExample filename="src/index.ts">
  ```ts
  //✓ 나쁜 : ctx가 `this` 바인딩을 파괴
  const badHandler = {
  	async fetch(
  		request: Request,
  		env: Env,
  		ctx: ExecutionContext,
  	): Promise<Response> {
  		const { waitUntil } = ctx; //runtime에서 "Illegal invocation"
  		waitUntil(fetch("https://analytics.example.com/events"));
  		return new Response("OK");
  	},
  } satisfies ExportedHandler<Env>;

  //✅ 좋은: 즉시 응답을 보내고, 후에 배경 일을 합니다
  export default {
  	async fetch(
  		request: Request,
  		env: Env,
  		ctx: ExecutionContext,
  	): Promise<Response> {
  		const data = await processRequest(request);

  		ctx.waitUntil(logToAnalytics(env, data));
  		ctx.waitUntil(updateCache(env, data));

  		return Response.json(data);
  	},
  } satisfies ExportedHandler<Env>;

  async function logToAnalytics(env: Env, data: unknown): Promise<void> {
  	await fetch("https://analytics.example.com/events", {
  		method: "POST",
  		body: JSON.stringify(data),
  	});
  }

  async function updateCache(env: Env, data: unknown): Promise<void> {
  	await env.CACHE.put("latest", JSON.stringify(data));
  }
  ```
</TypeScriptExample>

더 많은 정보를 원하시면, 참조[사이트맵](/workers/runtime-apis/context/).

## 회사연혁

### Cloudflare 서비스에 대한 바인딩을 사용하여 REST APIs

Cloudflare 서비스 R2, KV, D1, Queues, WorkflowsXQ는 유효합니다[관련 제품](/workers/runtime-apis/bindings/). 바인딩은 네트워크 홉, 인증 및 추가 대기 시간을 필요로하지 않는, 직접, 처리 referenceS입니다. 작업자가 폐기물 시간 내에 REST API를 사용하여 불필요한 복잡성을 추가합니다.

<TypeScriptExample filename="src/index.ts">
  ```ts
  //✓ 나쁜 : 노동자에서 REST API 호출
  const badHandler = {
  	async fetch(request: Request, env: Env): Promise<Response> {
  		const response = await fetch(
  			"https://api.cloudflare.com/client/v4/accounts/ACCOUNT_ID/r2/buckets/BUCKET_NAME/objects/my-file",
  			{ headers: { Authorization: `Bearer ${env.CF_API_TOKEN}` } },
  		);
  		return new Response(response.body);
  	},
  } satisfies ExportedHandler<Env>;

  //✅ 좋은: 직접 바인딩을 사용하십시오 — 아무 네트워크 hop, 필요 없음
  export default {
  	async fetch(request: Request, env: Env): Promise<Response> {
  		const object = await env.MY_BUCKET.get("my-file");

  		if (!object) {
  			return new Response("Not found", { status: 404 });
  		}

  		return new Response(object.body, {
  			headers: {
  				"Content-Type":
  					object.httpMetadata?.contentType ?? "application/octet-stream",
  			},
  		});
  	},
  } satisfies ExportedHandler<Env>;
  ```
</TypeScriptExample>

### 동기화 및 배경 작업을 위한 Queues 및 WorkflowsXQ를 사용하십시오

긴 실행, retryable, 또는 비 긴급 작업은 요청을 차단하지 않아야합니다. 제품 정보[Queues](/queues/)·[모델 번호: Workflows](/workflows/)중요한 경로에서 작업을 이동합니다. 그들은 다른 목적을 봉사합니다:

**Queues를 사용할 때**당신은 소비자로부터 생산자를 분리해야합니다. Queues는 메시지 중개인입니다: 1명의 노동자는 메시지, 다른 노동자 과정을 나중에 보냅니다. 그들은 팬 아웃을위한 올바른 선택입니다 (하나의 이벤트 트리거 많은 소비자), 버퍼링 및 배치 (아래 스트림 서비스로 작성하기 전에 집계 메시지), 간단한 단일 단계 배경 작업 (이메일을 보내, 웹 후크, 로그를 작성). Queues는 메시지 당 configurable retries로 at-least-once 납품을 제공합니다.

**사용 Workflows 때**배경 작업은 서로에 따라 여러 단계가 있습니다. Workflows는 튼튼한 실행 엔진입니다: 각 단계 반환 가치는 지속되고, 단계가 실패한 경우에, 그 단계는 전체적인 일 아닙니다 -입니다. 그들은 다중 단계 프로세스에 적합한 선택입니다 (카드를 충전 한 다음 선적을 생성 한 다음 확인을 보내), 일시 중지 및 재시작해야하는 긴 실행 작업 (외부 이벤트 또는 인간 승인을위한 시간 또는 일)`step.waitForEvent()`), 그리고 나중에 단계가 이전 결과에 달려있는 복잡한 조건 논리. Workflows는 시간, 일, 또는 주 동안 달릴 수 있습니다.

**모두 사용**높은 처리량 입력점이 복잡한 처리로 공급될 때. 예를 들어, Queue는 들어오는 주문을 버퍼 할 수 있으며, 소비자는 다중 단계 성취를 필요로하는 각 주문에 대해 Workflow 인스턴스를 만들 수 있습니다.

<TypeScriptExample filename="src/index.ts">
  ```ts
  export default {
  	async fetch(request: Request, env: Env): Promise<Response> {
  		const order = await request.json<{ id: string; type: string }>();

  		if (order.type === "simple") {
  			//✅ Queue: 단일 단계 배경 작업 — 동기화 처리를 위한 메시지를 보냅니다
  			await env.ORDER_QUEUE.send({
  				orderId: order.id,
  				action: "send-confirmation-email",
  			});
  		} else {
  			//✅ 워크플로우: 다중단계 내구성 프로세스 — 결제, 완료, 알림
  			const instance = await env.FULFILLMENT_WORKFLOW.create({
  				params: { orderId: order.id },
  			});
  		}

  		return Response.json({ status: "accepted" }, { status: 202 });
  	},
  } satisfies ExportedHandler<Env>;
  ```
</TypeScriptExample>

### Worker-to-Worker 커뮤니케이션을 위한 서비스 바인딩

1명의 노동자가 다른 전화를 필요로 할 때, 사용[서비스 바인딩](/workers/runtime-apis/bindings/service-bindings/)HTTP 요청을 public URL로 만드는 대신. 서비스 바인딩은 공공 인터넷을 우회하고, 유형 안전한 RPC를 지원합니다.

<TypeScriptExample filename="src/index.ts">
  ```ts
  import { WorkerEntrypoint } from "cloudflare:workers";

  //"auth" 노동자는 RPC 방법을 노출
  export class AuthService extends WorkerEntrypoint {
  	async verifyToken(
  		token: string,
  	): Promise<{ userId: string; valid: boolean }> {
  		//토큰 검증 논리
  		return { userId: "user-123", valid: true };
  	}
  }

  //"api" Worker는 서비스 바인딩을 통해 auth Worker를 호출
  export default {
  	async fetch(request: Request, env: Env): Promise<Response> {
  		const token = request.headers.get("Authorization")?.replace("Bearer ", "");

  		if (!token) {
  			return new Response("Unauthorized", { status: 401 });
  		}

  		//✅ 좋은: 서비스 바인딩 RPC를 통해 다른 노동자에게 부르십시오 — 네트워크 hop 없음
  		const auth = await env.AUTH_SERVICE.verifyToken(token);

  		if (!auth.valid) {
  			return new Response("Invalid token", { status: 403 });
  		}

  		return Response.json({ userId: auth.userId });
  	},
  } satisfies ExportedHandler<Env>;
  ```
</TypeScriptExample>

### WebSockets의 Durable Objects

일반 Workers는 WebSocket에 HTTP 연결을 업그레이드 할 수 있지만 지속적인 상태와 고용이 부족합니다. 이슬레이트가 evicted 경우, 연결은 영구적인 배우가 없기 때문에 손실됩니다. 믿을 수 있는, 오래 살아남는 WebSocket 연결을 위해, 사용[Durable Objects](/durable-objects/)이름 \*[Hibernation API 정보](/durable-objects/best-practices/websockets/). Durable Objects는 객체가 메모리에서 evicted 동안 WebSocket 연결이 열리고, 메시지가 도착했을 때 자동으로 깨어납니다.

제품 정보`this.ctx.acceptWebSocket()`대신에`ws.accept()`hibernation를 사용할 수 있습니다. 제품 정보`setWebSocketAutoResponse`객체를 깨지지 않는 ping/pong heartbeats를 위해.

<TypeScriptExample filename="src/index.ts">
  ```ts
  import { DurableObject } from "cloudflare:workers";

  //부모 노동자: WebSocket에 HTTP를 업그레이드하고 튼튼한 개체로 경로
  export default {
  	async fetch(request: Request, env: Env): Promise<Response> {
  		if (request.headers.get("Upgrade") !== "websocket") {
  			return new Response("Expected WebSocket", { status: 426 });
  		}

  		const stub = env.CHAT_ROOM.getByName("default-room");
  		return stub.fetch(request);
  	},
  } satisfies ExportedHandler<Env>;

  //내구재 목표: hibernation를 가진 WebSocket 연결 관리
  export class ChatRoom extends DurableObject {
  	constructor(ctx: DurableObjectState, env: Env) {
  		super(ctx, env);
  		//객체를 waking 없이 자동 ping/pong
  		this.ctx.setWebSocketAutoResponse(
  			new WebSocketRequestResponsePair("ping", "pong"),
  		);
  	}

  	async fetch(request: Request): Promise<Response> {
  		const pair = new WebSocketPair();
  		const [client, server] = Object.values(pair);

  		//✅ 좋은: acceptWebSocket는 hibernation를 가능하게 합니다
  		this.ctx.acceptWebSocket(server);

  		return new Response(null, { status: 101, webSocket: client });
  	}

  	//메시지가 도착했을 때 호출됨 — 필요한 경우 hibernation에서 객체가 깨집니다.
  	async webSocketMessage(ws: WebSocket, message: string | ArrayBuffer) {
  		for (const conn of this.ctx.getWebSockets()) {
  			conn.send(typeof message === "string" ? message : "binary");
  		}
  	}

  	async webSocketClose(
  		ws: WebSocket,
  		code: number,
  		reason: string,
  		wasClean: boolean,
  	) {
  		ws.close(code, reason);
  	}
  }
  ```
</TypeScriptExample>

## Code 패턴

### 글로벌 범위에서 request-scoped 상태를 저장하지 마십시오.

Workers 재사용은 요청에 따라 달라집니다. 하나의 요청에 대한 변수 설정은 여전히 다음 중에 존재합니다. 이 원인은 cross-request data leaks, stale state, 그리고 "다른 요청을 대신하여 I/O를 수행 할 수 없습니다" 오류.

함수 인자를 통해 state를 통과하거나 위에 저장하십시오`env`바인딩. 모듈 레벨 변수에 절대.

<TypeScriptExample filename="src/index.ts">
  ```ts
  //✓ 나쁜 : 요청 간의 글로벌 mutable 상태 누출
  let currentUser: string | null = null;

  const badHandler = {
  	async fetch(
  		request: Request,
  		env: Env,
  		ctx: ExecutionContext,
  	): Promise<Response> {
  		//Storing request-scoped data globally 의미 다음 요청은 stale 데이터를 볼
  		currentUser = request.headers.get("X-User-Id");
  		const result = await handleRequest(currentUser, env);
  		return Response.json(result);
  	},
  } satisfies ExportedHandler<Env>;

  //✅ 좋은: 함수 인수를 통해 request-scoped 데이터를 전달합니다.
  export default {
  	async fetch(
  		request: Request,
  		env: Env,
  		ctx: ExecutionContext,
  	): Promise<Response> {
  		const userId = request.headers.get("X-User-Id");
  		const result = await handleRequest(userId, env);

  		return Response.json(result);
  	},
  } satisfies ExportedHandler<Env>;

  async function handleRequest(userId: string | null, env: Env): Promise<object> {
  	return { userId };
  }
  ```
</TypeScriptExample>

### 항상 기다립니다 또는 당신의 약속

·`Promise`그것은 없다`await`칫`return`ed, 또는 통과`ctx.waitUntil()`부동 약속입니다. 부동 약속은 침묵 버그를 발생: 결과, 삼키는 오류, 그리고 unfinished 일. Workers 런타임은 뜨 약속의 앞에 당신의 고립을 종결할지도 모릅니다.

이름 \*`no-floating-promises`lint 규칙은 개발 시간에 이것을 붙잡기. ESLint를 사용하는 경우, 활성화[`@typescript-eslint/no-floating-promises`](https://typescript-eslint.io/rules/no-floating-promises/). oxlint를 사용하는 경우, 활성화[`typescript/no-floating-promises`](https://oxc.rs/docs/guide/usage/linter/rules/typescript/no-floating-promises.html).

```bash
#ESLint (typescript-eslint)
npx eslint --rule '{"@typescript-eslint/no-floating-promises": "error"}' src/

#채용정보
npx oxlint --deny typescript/no-floating-promises src/
```

<TypeScriptExample filename="src/index.ts">
  ```ts
  export default {
  	async fetch(
  		request: Request,
  		env: Env,
  		ctx: ExecutionContext,
  	): Promise<Response> {
  		const data = await request.json();

  		//✓ 나쁜 : 부동 약속 - 결과는 떨어졌다, 오류는 삼키다
  		fetch("https://api.example.com/webhook", {
  			method: "POST",
  			body: JSON.stringify(data),
  		});

  		//✅ 좋은: 당신이 응답하기 전에 결과를 필요로 하는 경우에 기다립니다
  		const response = await fetch("https://api.example.com/process", {
  			method: "POST",
  			body: JSON.stringify(data),
  		});

  		//✅ 좋은 : 응답하기 전에 결과를 필요로하지 않으면 waitUntil
  		ctx.waitUntil(
  			fetch("https://api.example.com/webhook", {
  				method: "POST",
  				body: JSON.stringify(data),
  			}),
  		);

  		return new Response("OK");
  	},
  } satisfies ExportedHandler<Env>;
  ```
</TypeScriptExample>

### 안전한 토큰 생성을 위한 Web Crypto 사용

Workers 런타임은[웹 암호화 API](/workers/runtime-apis/web-crypto/)암호화 작업. 제품 정보`crypto.randomUUID()`고유 식별자 및`crypto.getRandomValues()`임의 바이트를 위해. 이용안내`Math.random()`모든 보안 감지. 그것은 암호화되지 않습니다.

Node.js[`node:crypto`](/workers/runtime-apis/nodejs/crypto/)또한 완전히 지원될 때`nodejs_compat`활성화되므로 API 또는 라이브러리가 선호하는 것을 사용할 수 있습니다.

<TypeScriptExample filename="src/index.ts">
  ```ts
  export default {
  	async fetch(request: Request, env: Env): Promise<Response> {
  		//✓ 나쁜 : Math.random ()는 예측할 수 있으며 보안에 적합하지 않습니다.
  		const badToken = Math.random().toString(36).substring(2);

  		//✅ 좋은: cryptographically 안전한 무작위 UUID
  		const sessionId = crypto.randomUUID();

  		//✅ 좋은: 토큰을 위한 암호로 고쳐진 안전한 무작위 바이트
  		const tokenBytes = new Uint8Array(32);
  		crypto.getRandomValues(tokenBytes);
  		const token = Array.from(tokenBytes)
  			.map((b) => b.toString(16).padStart(2, "0"))
  			.join("");

  		return Response.json({ sessionId, token });
  	},
  } satisfies ExportedHandler<Env>;
  ```
</TypeScriptExample>

비밀 값 (API 키, 토큰, HMAC 서명)을 비교하면 사용`crypto.subtle.timingSafeEqual()`타이밍 측 채널 공격을 방지하기 위해. 길이 mismatch에 단락하지 마십시오. 고정 크기의 해시에 두 값을 먼저 인코딩합니다.

<TypeScriptExample filename="src/verify.ts">
  ```ts
  async function verifyToken(
  	provided: string,
  	expected: string,
  ): Promise<boolean> {
  	const encoder = new TextEncoder();

  	//✅ 좋은: 고정 크기에 가치를 둘 다, 그 후에 일정한 시간에 비교하십시오
  	//이것은 예상 값의 길이를 새는 것을 피합니다
  	const [providedHash, expectedHash] = await Promise.all([
  		crypto.subtle.digest("SHA-256", encoder.encode(provided)),
  		crypto.subtle.digest("SHA-256", encoder.encode(expected)),
  	]);

  	return crypto.subtle.timingSafeEqual(providedHash, expectedHash);
  }

  //✓ Bad : 직접 문자열 비교 누출 타이밍 정보
  function verifyTokenInsecure(provided: string, expected: string): boolean {
  	return provided === expected;
  }
  ```
</TypeScriptExample>

### passThroughOnException을 오류 처리로 사용하지 마십시오.

`passThroughOnException()`당신의 노동자가 불쾌한 예외를 던질 때 당신의 근원에 요구를 보내는 실패 열려있는 기계장치입니다. 원래 서버에서 마이그레이션 중에 유용 할 수 있지만 버그를 숨기고 어려운 문제를 해결합니다. 대신 구조 오류 응답을 가진 명시된 시험/캐치 블록을 사용하십시오.

<TypeScriptExample filename="src/index.ts">
  ```ts
  //✓ 나쁜 : 근원을 통해 떨어지는 오류를 숨깁니다
  const badHandler = {
  	async fetch(
  		request: Request,
  		env: Env,
  		ctx: ExecutionContext,
  	): Promise<Response> {
  		ctx.passThroughOnException();
  		const result = await handleRequest(request, env);
  		return Response.json(result);
  	},
  } satisfies ExportedHandler<Env>;

  //✅ 좋은: 구조화된 응답을 가진 명확한 과실 취급
  export default {
  	async fetch(
  		request: Request,
  		env: Env,
  		ctx: ExecutionContext,
  	): Promise<Response> {
  		try {
  			const result = await handleRequest(request, env);
  			return Response.json(result);
  		} catch (error) {
  			const message = error instanceof Error ? error.message : "Unknown error";

  			console.error(
  				JSON.stringify({
  					message: "unhandled error",
  					error: message,
  					path: new URL(request.url).pathname,
  				}),
  			);

  			return Response.json({ error: "Internal server error" }, { status: 500 });
  		}
  	},
  } satisfies ExportedHandler<Env>;

  async function handleRequest(request: Request, env: Env): Promise<object> {
  	return { status: "ok" };
  }
  ```
</TypeScriptExample>
