이 문서는 overview의 QXCloudflare 보안 아키텍처를 포함 하 여 두 자주 문제에 대 한 요청: V8 버그 및 스펙트럼.

Workers 프로젝트의 시작부터 보안은 높은 우선 순위였습니다. 공유 인프라의 많은 10개 업체를 호스팅할 때, 다양한 종류의 측면 채널이 위협을 낼 것입니다. Cloudflare Workers 런타임은 측 수로 공격에 방어하기 위해 신중하게 설계되었습니다.

이 끝에 Workers는 코드가 로컬로 실행 시간을 측정 할 수 있도록 불가능하도록 설계되었습니다. 예를 들어, 반환된 값`Date.now()`코드가 실행되는 동안 장소에 잠겨 있습니다. 다른 타이머가 제공되지 않습니다. 또한, Cloudflare는 concurrency (예를 들면, 다 보행)에 접근할 수 없기 때문에, 공격자는 광고 hoc 타이머를 건설할 수 있었습니다. 이 디자인 선택은 웹 브라우저와 같은 다른 플랫폼으로 개조 할 수 없습니다. 기존 애플리케이션이 의존하는 API를 제거하기 때문에. Workers는 시작에서 런타임 디자인 선택 때문에만 가능합니다.

이러한 초기 설계 결정은 효과적인 입증되었지만, Cloudflare는 WorkersXQ를 재개하여 공격을 중단하는 기술을 포함한 방어형 심층을 추가하는 데 계속되고 의심스러운 WorkersXQ 및 고가치 WorkersXQXQXQXQ.

Workers 접근법은 업계에서 가장 중요한 접근법과 매우 다릅니다. 그것은 전체 범위에 저항[Spectre 작풍 공격](https://www.cloudflare.com/learning/security/threats/meltdown-spectre/), 특별한 주의를 요구하지 않고 각 하나에 지불하고 일반에 있는 speculation를 막기 없이. 그러나, Workers의 접근이 다르기 때문에, 그것은 주의깊은 학문을 요구합니다. Cloudflare는 현재 Graz University of Technology (TU Graz)의 연구원과 협력하여 수행 된 것을 연구합니다. 이 연구자들은 원래 스펙트럼을 발견 한 사람들의 일부를 포함한다. Cloudflare는 이 연구의 결과를 유효하게 됩니다.

더 자세한 내용은 참조[이 이야기](https://www.infoq.com/presentations/cloudflare-v8/)작성자: Kenton Varda, 건축가 Cloudflare Workers. Spectre는 끝의 가까이에 덮습니다.

### 절연성

먼저, 보안 실행 환경에 필요한 코드를 액세스할 수 없습니다.

이것을 위해, 1 차적인 공구는 크롬에 있는 사용을 위한 구글에 의해 개발된 JavaScript 엔진입니다. V8은 isolates 내부 코드를 실행합니다. 이슬레이트 이외의 메모리에 액세스하여 코드를 방지합니다. 중요하게, 이것은 Cloudflare가 단 하나 과정 안에 많은 고립을 달릴 수 있다는 것을 의미합니다. 이것은 WorkersXQ와 같은 가장자리 compute 플랫폼에 필수적입니다. Cloudflare는 모든 기계에 수천 명의 게스트 애플리케이션을 호스팅해야하며 최소 오버 헤드와 초당 수천 개의 시간을 신속하게 전환해야합니다. Cloudflare는 각 손님을 위한 별도의 과정을 실행해야 하는 경우에, 10ants CloudflareXQ의 수는 drastically 감소될 수 있고, CloudflareXQ는 큰 기업 고객의 작은 수에 가장자리 compute를 제한해야 할 것입니다. 고립 기술로, Cloudflare는 모두에 유효한 가장자리 compute를 만들 수 있습니다.

때로는 Cloudflare는 자체 개인 프로세스에서 노동자를 일정으로 결정합니다. Cloudflare는 노동자가 고립의 여분 층을 필요로 하는 특정 특징을 이용하는 경우에 이것을 합니다. 예를 들어, 개발자가 자신의 노동자를 검사하기 위해 devtools debugger를 사용했을 때 CloudflareXQ는 별도의 프로세스에서 노동자를 실행합니다. 브라우저에서 실제로, 검사기 프로토콜은 브라우저의 신뢰할 수있는 연산자에 의해 사용되었으므로 V8의 나머지만큼 많은 보안 scrutiny로 수신되지 않습니다. 검사기 의정서에 있는 버그의 증가한 위험에 대하여 hedge에, Cloudflare는 가공 수준 샌드박스를 가진 분리되는 과정에 Workers를 검열했습니다. Cloudflare는 또한 Spectre에 대하여 여분 방위로 가공 고립을 이용합니다.

또한, 다른 isolates와 공유 프로세스에서 실행하는 isolates, CloudflareXQ는 각 기계에 전체 실행 시간의 여러 인스턴스를 실행, 코드라고. Workers는 각 노동자에게 신뢰의 수준을 할당해서 코슨 사이에서 배부되고 그들에서 낮은 위탁된 WorkersXQXQ를 더 높게 신뢰했습니다. 이 작업의 예로 : 무료 계획에 가입하는 고객은 엔터프라이즈 고객과 동일한 프로세스에서 예약되지 않습니다. V8에서 제로데이 보안 취약점이 발견되면 방어 심층을 제공합니다.

전체 공정 수준에서, Cloudflare는 깊이에 방어를 위해 샌드 박스의 다른 층을 적용합니다. 레이어 2 샌드박스는 Linux 네임스페이스를 사용하고`seccomp`filesystem 및 네트워크에 대한 모든 액세스를 금지합니다. 네임스페이스 및`seccomp`콘테이너를 실행하기 위하여 통용됩니다. 그러나, Cloudflare의 이러한 기술의 사용은 컨테이너 엔진에서 일반적으로 가능한 것보다 훨씬 엄격합니다. Cloudflare는 네임스페이스를 구성하고`seccomp`프로세스가 시작되었지만 어떤 것이 로드되기 전에. 즉, 예를 들어, Cloudflare는 완전히 빈 파일 시스템 (mount namespace)을 사용하며 사용`seccomp`모든 파일시스템 관련 시스템 호출을 차단합니다. 컨테이너 엔진은 일반적으로 모든 파일 시스템 액세스를 금지하므로 사용 불가능하게 만들 수 없습니다.`exec()`디스크에서 게스트 프로그램을 시작합니다. Workers 케이스에서, Cloudflare의 손님 프로그램은 본래 궤적 및 Workers런타임 자체가 이미 CloudflareXQ 구획 파일 시스템 접근의 앞에 선적을 완료하지 않습니다.

레이어 2 sandbox 또한 완전히 prohibits 네트워크 액세스. 대신, 프로세스는 로컬 UNIX 도메인 소켓에서만 동일한 시스템에 다른 프로세스에 대해 이야기 할 수 있습니다. 외부 세계에 대한 모든 통신은 sandbox 밖에 다른 로컬 프로세스에 의해 중재해야합니다.

특히 슈퍼바이저라고 불리는 이러한 과정 중 하나는 디스크 또는 기타 내부 서비스에서 작업자 코드 및 구성을 fetching하는 역할을 담당합니다. 슈퍼바이저는 샌드박스 프로세스가 실행해야 하는 WorkersXQ와 관련된 모든 구성을 읽을 수 없다는 것을 보증합니다.

예를 들어, 샌드박스 프로세스가 Worker에 대한 요청을 수신하면 이전에 볼 수 없습니다. 그 요청은 해당 작업자의 코드에 대한 암호화 키가 포함되어 있습니다. sandbox는 코드를 요청하기 위해 supervisor에 열쇠를 전달할 수 있습니다. sandbox는 적절한 키를받지 않은 작업자를 요청할 수 없습니다. 그것은 알려진 Workers를 enumerate 할 수 없습니다. 설정은 필요하지 않습니다. 예를 들어, 작업자에게 HTTPS 트래픽에 사용되는 TLS 키를 요청할 수 없습니다.

읽기 설정 외에도 샌드 박스에 대한 다른 이유는 시스템에 다른 프로세스에 대해 이야기하는 것은 Workers에 노출 된 API를 구현하는 것입니다.

### API 디자인

말하기가 있다: 나무가 숲에 떨어졌을 때, 아무도 그것을 듣고, 소리를 만들 수 있습니까? Cloudflare는 말하기: 노동자가 외부 세계에 communicating에서 완전히 막힌 환경에서 실행하는 경우에, 실제로 실행합니까?

완전한 부호 고립은, 실제로, useless 입니다. Workers에 대한 주문은 유용 할 수 있으며 사용자에게 통신 할 수 있습니다. 매우 적어도, 노동자는 요청을 받고 그들에 응답 할 수 있어야합니다. Workers에 대한 요청을 안전하게 보내려면 API가 필요합니다.

샌드박스의 컨텍스트에서 API 디자인은 새로운 수준의 책임감을 가지고 있습니다. 모델 번호: Cloudflare API는 작업자가 할 수 있고 할 수 없다는 것을 정확히 정의합니다. Cloudflare는 각 API를 디자인하기 위하여 아주 주의해야 합니다 그래서 그것은 허용한 가동 및 더 많은 것만 할 수 있습니다. 예를 들어, Cloudflare는 Workers를 허용하고 HTTP 요청을 수신하고 싶지만 로컬 파일 시스템 또는 내부 네트워크 서비스에 액세스 할 수 있습니다.

현재 Workers는 로컬 파일 시스템에 대한 액세스를 허용하지 않습니다. 따라서 Cloudflare는 모든 파일 시스템 API를 노출하지 않습니다. API가 접근하지 않습니다.

그러나 Workers가 미래의 로컬 파일 시스템 액세스를 지원하려는 경우 상상해보십시오. 어떻게 할 수 있습니까? Workers는 전체적인 파일 시스템을 볼 수 없습니다. Imagine, 비록, 각 노동자가 원하는 모든 것을 저장할 수있는 파일 시스템에 자신의 개인 디렉토리를했다.

이렇게하려면, Workers는 디자인에 기초를 두어 사용할 것입니다[기능 기반 보안](https://en.wikipedia.org/wiki/Capability-based_security). 능력은 큰 주제이지만이 경우 Cloudflare는 노동자에게 유형의 객체를 줄 것입니다`Directory`, filesystem에 디렉토리를 나타냅니다. 이 객체는 파일과 하위 디렉토리를 생성하고 열 수 있는 API를 가지고 있지만, 부모 디렉토리를 실행할 수 없습니다. 효과적인, 각 노동자는 그것의 개인을 볼 것입니다`Directory`자신의 파일 시스템의 뿌리가 있다면.

API는 어떻게 구현됩니까? 위에서 설명한 대로 샌드박스 프로세스는 실제 파일 시스템에 접근할 수 없습니다. 대신, 파일 액세스는 supervisor 프로세스에 의해 중재 될 것입니다. sandbox는 supervisor에 대해 이야기합니다.[모자'n Proto RPC](https://capnproto.org/rpc.html), 기능 기반 RPC 프로토콜. (Cap'n Proto는 현재 QXQX0600XQQ Workers 팀에 의해 유지되는 오픈 소스 프로젝트입니다.) 이 프로토콜은 CloudflareXQ는 Workers에 속한 파일만 접근하기 위하여 sandbox를 엄격히 제한할 수 있다 그래야 기능을 근거한 APIs를 실행하기 위하여 아주 쉽습니다.

이제 네트워크 액세스에 대해? 오늘, Workers는 HTTP를 통해 세계의 나머지에 대해 이야기 할 수 있습니다 - 들어오고 나가기. 네트워크 액세스의 다른 형태에 대한 API가 없기 때문에 금지됩니다. 그러나 Cloudflare는 향후 다른 프로토콜을 지원할 계획입니다.

이전에 언급했듯이, sandbox 프로세스는 네트워크에 직접 연결할 수 없습니다. 대신, 모든 아웃 바운드 HTTP 요청은 로컬 프록시 서비스에 UNIX 도메인 소켓을 통해 전송됩니다. 그 서비스는 요청에 대한 제한을 구현합니다. 예를 들어, 이 요청은 공용 인터넷 서비스 또는 Worker의 영역 자체 소스 서버에 주소되어 로컬 기계 또는 네트워크에 볼 수 있는 내부 서비스에 접근할 수 없습니다. 그것은 또한 그들이 시작된 노동자를 식별하는 모든 요청에 헤더를 추가, 그래서 abusive 요청 추적 및 차단 될 수 있습니다. 모든 것이 순서대로되면, 요청은 Cloudflare 네트워크의 HTTP 캐싱 레이어로 보내지고 인터넷에 있습니다.

마찬가지로, inbound HTTP 요청은 Workers 런타임에 직접 이동하지 않습니다. 그들은 inbound 프록시 서비스에 의해 첫 번째 수신. 이 서비스는 TLS 종료 (Workers 런타임은 TLS 키를 볼 수 없습니다)뿐만 아니라 특정 요청 URL을 실행하기 위해 올바른 작업자 스크립트를 식별합니다. 모든 것이 순서대로되면, 요청은 샌드박스 프로세스에 UNIX 도메인 소켓을 통해 전달됩니다.

## V8 버그 및 패치 간격

소프트웨어의 모든 비-trivial 조각은 버그 및 샌드 박스 기술 예외가 없습니다. 가상 머신, 컨테이너 및 isolates - Workers 사용 - 또한 버그가 있습니다.

Workers는 크롬에서 사용을 위해 구글에 의해 건축된 JavaScript 엔진에 의해 제공된 고립에 크게 의존합니다. 이것은 pros와 cons를 가지고 있습니다. 한 손으로 V8은 가상 머신보다 더 넓은 공격 표면을 만드는 기술의 extraordinarily 복잡한 조각입니다. 더 복잡성은 무언가에 대한 더 많은 기회를 잘못합니다. 그러나 특별한 노력은 V8 버그를 발견하고 수정하기 위해 간다, 세계에서 가장 인기있는 샌드 박스 기술로 위치에 빚지고. Google은 정기적으로 V8 샌드박스 탈출을 발견하는 사람에게 5 개의 현상을 지불합니다. Google은 자동적으로 대부분의 인간보다 버그를 빠르게 찾을 수 있도록 fuzzing 인프라를 운영합니다. Google의 투자는 V8 Zero-days의 위험을 최소화하기 위해 많은 것을 사용합니다. 악성 행위자가 발견 된 버그와 Google에 알려지지 않았습니다.

그러나 버그가 발견되고보고 된 후 어떻게됩니까? V8는 오픈 소스이므로 보안 버그에 대한 수정은 개방적이고 동시에 출시됩니다. 그것은 어떤 패치가 가능한 한 빨리 생산에 구르는 것이 중요합니다, 악의 행위자 전에 악의적으로 악의적으로 개발할 수 있습니다.

수정과 배포 사이의 시간은 패치 간격으로 알려져 있습니다. Google 이전에[크롬의 패치 간격이 33 일에서 15 일로 감소했다고 발표했다.](https://www.zdnet.com/article/google-cuts-chrome-patch-gap-in-half-from-33-to-15-days/).

다행히, CloudflareXQ는 직접 Workers 런타임이 작동되는 기계를 통제합니다. 거의 전체 빌드 및 릴리스 프로세스가 자동화되었으므로 V8 패치가 게시 된 순간, Cloudflare 시스템 자동적으로 Workers 런타임의 새로운 릴리스를 구축하고 필요한 (human) 검토자에서 한 번 클릭 한 후 자동으로 생산에 출시됩니다.

결과적으로 Workers 패치 간격은 현재 24 시간 이내에 있습니다. 작업 일 동안 뮌헨 V8의 팀에 의해 출판 패치는 일반적으로 미국 작업 일의 끝 앞에 생산 될 것입니다.

## Spectre: 소개

Google의 V8 팀은 다음과 같이 말했습니다.[V8 자체는 스펙트럼에 대한 방어 할 수 없습니다](https://arxiv.org/abs/1902.05178). Workers는 이것을 위한 V8에 의존하지 않습니다. Workers 환경은 투과 스펙트럼에 대한 많은 대안 접근 방식을 제시합니다.

### 그것은 무엇입니까?

Spectre는 악의적 인 프로그램이 CPU를 추측적으로 수행 할 수있는 공격의 클래스입니다. CPU는 결국 문제를 깨닫고 speculative 계산의 결과를 볼 수있는 프로그램을 허용하지 않습니다. 그러나이 프로그램은 캐시의 효과와 같은 계산의 미묘한 부작용을 찾는 비밀 데이터의 파생 비트를 할 수 있습니다.

Spectre에 대한 자세한 내용은 참조[학습 센터 주제에 페이지](https://www.cloudflare.com/learning/security/threats/meltdown-spectre/).

### Workers는 왜 중요합니까?

Spectre는 현대 CPU에서 다양한 취약점을 우회합니다. 특정 취약점은 건축 및 모델에 따라 다를 수 있으며 아직 발견되지 않은 많은 취약점이 존재합니다.

이 취약점은 모든 클라우드 컴퓨팅 플랫폼에 대한 문제입니다. 동시에 동일한 기계에 1 개 이상의 테넌트 실행 코드를 가지고, Spectre 공격이 가능합니다. 그러나, 점점 더 어렵게 특정 취약점을 완화 할 수 있습니다. 알려진 문제의 대부분은 커널 레벨 (각 다른 각에서 프로세스를 보호) 또는 하이퍼 바이저 레벨 (VM을 보호)에서 mitigated 수 있습니다, 종종 CPU 마이크로 코드 업데이트 및 다양한 방어의 도움으로 (그의 심각한 성능 영향으로 올 수 있음).

Cloudflare Workers의 임계인은 V8 isolates를 사용하여 서로 격리되어 있으며 프로세스나 VM을 처리하지 않습니다. 즉, Workers는 반드시 OS 또는 하이퍼 바이저 패치에서 스펙트럼을 방지 할 수 없습니다. Workers는 그것의 자신의 전략을 필요로 합니다.

### 왜 과정 고립을 사용하지 않습니까?

Cloudflare Workers는 각 단 하나 Cloudflare 위치에 있는 당신의 코드를 실행하기 위하여 디자인됩니다.

Workers는 모든 사람에게 접근 가능한 플랫폼이기 위하여 디자인됩니다. 그것은 많은 tenants가 매우 작은 트래픽을 얻을 수있는 총수의 엄청난 수를 처리해야합니다.

이 두 가지 점을 결합하고 계획은 어렵습니다.

전형적인 비 edge serverless 공급자는 단 하나 기계에 그것의 tenant의 소통량의 모두를 보내서 낮은 traffic tenant를 취급할 수 있었습니다, 그래서 신청의 1개의 사본만 적재될 필요가 있습니다. 기계가 취급할 수 있는 경우에, 말하십시오, 수십개의 tenants, 그것 많습니다. 그 기계는 가늠자의 수백만을 달성하는 기계의 다량 자료 센터에서, 호스팅될 수 있습니다. 그러나,이 중앙화 incurs latency 및 전세계 대역폭 비용 사용자가 근처에 있지 않을 때.

Workers로, 다른 한편으로, 트래픽 수준에 관계없이, 현재 모든 Cloudflare 위치에 실행됩니다. 그리고 가능한 한 최종 사용자에 가까운 퀘스트에서, CloudflareXQ는 때때로 제한된 수의 기계만 있는 위치를 선택합니다. 그물 결과는 Cloudflare가 기계 당 수천을, 급속하게 비활동성 것을 주문하기 위하여 급속하게 회전할 수 있는 능력과 더불어 체재할 수 있어야 합니다. 즉, 각 게스트는 메모리의 두 개 메가 바이트보다 더 걸릴 수 없다는 것을 의미합니다. 즉, 통화 스택의 충분한 공간, 프로세스가 필요로하는 다른 모든 것이 훨씬 적습니다.

또한, Cloudflare는 적절하게 능률적일 것이다 맥락을 필요로 합니다. 많은 Workers 메모리에 거주하는 것은 이제 이벤트를 처리하고, 많은 WorkersXQ는 특정 이벤트에서 밀리 초의 분수보다 덜 지출합니다. 이 환경에서 단일 코어는 수천 개의 다른 10 종 사이의 전환을 쉽게 찾을 수 있습니다. 1개의 사건을 처리하기 위하여, 손님 신청과 그것의 주인 사이에서 일어나는 중요한 양은, 아직도 전환하고 커뮤니케이션 overhead를 표현합니다. 각 임차인이 자신의 과정에서 살고 있다면, 모든 이 오버 헤드는 하나의 프로세스에 살고있는 많은 10ants보다 더 큰 크기의 주문입니다. Workers에서 엄격한 공정 고립을 사용할 때, CPU 비용은 공유 공정으로 10x 일 수 있습니다.

Workers 싼, 빠르고, 그리고 모든 사람에게 접근하기 위하여는, Cloudflare는 단 하나 과정에 있는 다수 tenants를 호스트하는 방법을 찾아내기 위하여 필요로 했습니다.

### Spectre에 대한 수정이 없습니다.

Spectre는 공식적인 해결책이 없습니다. 헤비급 가상 머신을 사용할 때도 없습니다. 모두가 여전히 취약합니다.

업계는 새로운 스펙트럼 공격을 보여줍니다. 모든 몇 달, 연구원은 새로운 스펙트럼 취약점, CPU 공급 업체는 새로운 마이크로 코드 및 OS 공급 업체가 커널 패치를 해제합니다. 모두 계속 업데이트해야합니다.

그러나 그것은 단지 최신 패치를 배포하는 것이 충분합니까?

더 취약점이 존재하지만 아직 공개되지 않았습니다. Spectre에 대한 방어하기 위해 Cloudflare는 다른 접근 방식을 취해야합니다. 개인 알려진 취약점을 차단하는 것은 충분하지 않습니다. 대신, 취약점의 전체 수업은 한 번에 해결되어야 합니다.

### 방어 구축

Spectre를 위한 all-encompassing fix가 발견될 것입니다. 그러나 다음과 같은 생각 실험은 고려해야 할 점을 제기 :

Fundamentally, 모든 스펙트럼 취약점은 숨겨지은 가공업자 국가를 검출하기 위하여 측 수로를 이용합니다. 정의에 의해 측면 채널, 시스템의 일부 비 결정적인 행동을 관찰. 편리하고, 대부분의 소프트웨어 실행 환경은 non-determinism을 제거하기 위해 열심히 노력합니다. non-deterministic 실행은 응용 프로그램을 믿을 수 없게 만듭니다.

그러나 여전히 일반적 인 비 결정체의 몇 가지 종류가 있습니다. 이 중 가장 명백한 타이밍입니다. 업계는 오래 전에 프로그램이 실행되는 시간의 동일한 양을 가지고 있어야한다는 아이디어에 포기했습니다. deterministic 타이밍은 치열한 성과 최적화를 가진 확률에 근본적으로 입니다. 대부분의 Spectre 공격은 CPU의 숨겨진 미생물 상태를 감지하는 방법으로 타이밍에 초점을 맞춥니다.

몇몇은 이 타이머 inaccurate를 만들고 무작위 소음을 추가해서 해결될 수 있다는 것을 제안했습니다. 그러나,이 공격을 멈추지 않는다는 것을 밝혀; 그것은 단지 그들을 느리게한다. 타이머가 모든 시간에 실제 시간을 추적하는 경우, 당신이 그것을 inaccurate 할 수있는 것은 공격을 여러 번 실행하고 통계를 사용하여 의도치를 필터링 할 수 있습니다.

많은 보안 연구자들은이 이야기의 끝으로 볼 수 있습니다. 공격이 여전히 가능한 경우 공격을 낮추는 것은 무엇입니까?

### Cascading 느린 다운

그러나 공격을 느리게하는 것은 강력합니다.

중요한 통찰력은 다음과 같습니다. 공격이 느리게되면 새로운 기술은 여전히 더 느리게 만들 수 있습니다. 목표, 다음, 공격이 너무 느리게되지 않도록 충분한 기술을 함께 체인에있다.

암호화의 많은, 모든 후, 기술적으로 강제 공격에 취약 - 기술적으로, 충분한 시간으로, 당신은 그것을 깰 수 있습니다. 그러나 필요한 시간은 수천 (또는 수십억)입니다.

Spectre가 의미없는 점으로 공격을 느리게 할 수 있습니까?

## Spectre 공격을 해방

### 단계 0: 기본 코드를 허용하지 마십시오

Workers는 Cloudflare 네트워크에서만 실행하기 위하여 본래 부호 궤양을 업로드하기 위하여 우리의 고객을 허용하지 않습니다 — JavaScript 및 WebAssembly만. Python, Rust, 또는 Cobol와 같은 다른 많은 언어는, 이 2개의 체재 중 하나에 컴파일되거나 transpiled 할 수 있습니다. 둘 다 V8를 통해 이 형식을 true 네이티브 코드로 변환합니다.

이 자체에서는 반드시 Spectre가 더 열심히 공격하지 않습니다. 그러나, 이것은 다음과 같은 단계를 가능하게하는 기본이기 때문에 단계 0로 표시됩니다.

네이티브 코드 프로그램을 받아들이는 것은 기존의 CPU 아키텍처 (일반적으로, x86)에 속한다. 합리적인 성능으로 코드를 실행하려면 실제 하드웨어에서 코드를 직접 실행하는 것이 필요합니다. 그 실행 방법은 호스트의 제어를 심각하게 제한합니다. 예를 들어, 커널 또는 하이퍼바이저에는 호출에서 prohibit 애플리케이션이 없습니다.`CLFLUSH`교육, 교육[측면 채널 공격에 유용합니다](https://gruss.cc/files/flushflush.pdf)그리고 거의 아무것도 다른.

또한, 기본 코드를 지원 일반적으로 전체 기존 운영 체제 및 소프트웨어 스택 지원, 아키텍처가 어떻게 작동 하는지에 대 한 기대의 수십 년. 예를 들어, x86 CPU는 높은 정밀도 타이머를 읽는 RDTSC 지시를 비활성화하는 커널 또는 하이퍼바이저를 허용합니다. 현실적으로, 비록, 그들은 현재 시간을 알고 싶은 RDTSC를 사용 하 여 실행 하기 때문에 많은 프로그램을 깰 것 이다.

지원 기본 코드는 향후 완화 기술에서 선택을 제한 할 것입니다. 요약 중간 형식을 사용하여 더 큰 자유가있다.

### 단계 1: 타이머와 다 보행을 허용

Workers에서 JavaScript 날짜 API를 사용하여 현재 시간을 얻을 수 있습니다`Date.now()`. 그러나, 반환된 시간 가치는 현재 시간 아닙니다.`Date.now()`마지막 I/O의 시간을 반환합니다. 코드 실행 중에 미리는 없습니다. 예를 들어, 공격자가 쓴 경우:

```js
let start = Date.now();
for (let i = 0; i < 1e6; i++) {
  doSpectreAttack();
}
let end = Date.now();
```

가치의`start`·`end`항상 동일합니다. 공격자는 사용할 수 없습니다`Date`그들의 코드의 실행 시간을 측정하기 위해, 그들은 공격을 수행해야합니다.

:::참조

이 측정은 Spectre가 발표되기 전에 Mid-2017에서 구현되었습니다. 이 측정은 Cloudflare가 이미 사이드 채널 타이밍 공격에 대해 우려했기 때문에 구현되었습니다. Workers 팀은 마음에 있는 옆 수로를 가진 체계를 디자인했습니다.
주요 특징

마찬가지로 멀티 스레드 및 공유 메모리는 Workers에서 허용되지 않습니다. 하나의 이벤트의 처리와 관련된 모든 것은 동일한 스레드에 발생합니다. 그렇지 않으면, 하나는 추측하기 위하여 실을 경주하고 underlying 타이머를 검사할 수 있을 것입니다. 다중 Workers는 동시에 동일한 요청에 작동할 수 없습니다. 예를 들어, Cloudflare를 설치한 경우 Workers를 사용하여 구현되는 영역에서 앱과 영역 자체는 Workers를 사용하고, 해당 영역의 요청은 실제로 시퀀스에서 2 WorkersXQ에 의해 처리 될 수 있습니다. 이 같은 스레드에서 실행.

이 시점에서, 로컬로 측정 코드 실행 시간은 예방됩니다. 그러나, 그것은 아직도 원격으로 측정될 수 있습니다. 예를 들어, Worker의 실행을 트리거 할 수있는 HTTP 클라이언트는 Worker가 응답하는 데 얼마나 걸리는지 측정 할 수 있습니다. 이러한 측정은 매우 noisy 될 가능성이, 그것은 인터넷과 incur 일반 네트워킹 비용을 가로 질러해야합니다. 이러한 소음이 극복 될 수 있습니다, 이론에서, 공격을 여러 번 실행하고 평균을 복용.

:::참조

WorkersXQ가 각 요청에 따라 실행 환경을 재설정하는 경우 WorkersXQ는 타이밍 공격에 대한 훨씬 더 안전한 위치에있을 것입니다. 불행히도, 그것은 너무 간단합니다. 실행 상태는 클라이언트에서 저장 될 수 있습니다 — 노동자 자체가 아닌 — 작업자가 모든 새로운 요청에 이전 상태를 재개 할 수 있습니다.
주요 특징

선도적인 스펙트럼 전문가로부터의 도움을 받아 Cloudflare는 생산에서 작동하는 원격 타이밍 공격을 개발할 수 없습니다. 그러나 작업 공격의 부족은 Workers가 방어를 중지해야한다는 것을 의미하지 않습니다. 대신 Workers 팀은 현재 몇 가지 고급 조치를 테스트하고 있습니다.

### 단계 2: 동적인 과정 고립

공격이 가능한 경우, 그것은 실행하는 긴 시간을 걸릴 것입니다 - 적어도 시간, 아마 몇 주. 그러나 공격이 두 번째로도 실행되면 더 많은 측정을 트리거하기 위해 사용할 수있는 새로운 데이터의 큰 양이 있습니다.

스펙트럼 공격은 일반적으로 일반 프로그램에 볼 수없는 이상한 행동을 전시합니다. 이러한 공격은 의도적으로 미생물 효과를 증폭하기 위해 병리적 성능 시나리오를 만들려고합니다. 이것은 특히 사실 공격이 이미 위에 논의 된 것과 같은 다른 완화를 극복하기 위해 반복에서 수십억 번의 시간을 실행 할 때. CPU 성능 카운터와 같은 메트릭에서 보여줍니다.

이제 Spectre 공격을 감지하는 성능 메트릭을 사용하는 일반적인 문제는 때때로 false 긍정적 인 것입니다. 때때로, 합법적 인 프로그램은 가난한 행동. 런타임은 성능이 좋지 않은 모든 응용 프로그램을 차단할 수 없습니다.

대신, 런타임은 자신의 프로세스로 suspicious 성능 메트릭으로 어떤 노동자를 재조정하는 것을 선택합니다. 위에서 설명한대로, 런타임은 오버헤드가 너무 높기 때문에 모든 노동자와 함께 할 수 없습니다. 그러나, 그것은 방위 기계장치로 몇몇 노동자 과정을 고립시키기 위하여 수락가능합니다. 노동자가 합법적 인 경우, 그것은 운영을 유지하고, 조금 더 오버 헤드. 다행히, Cloudflare는 기본적으로 어떤 시간에 그것의 자신의 과정에 노동자를 찾아낼 수 있습니다.

실제로, elaborate performance-counter 기반 트리거는 여기에 필요하지 않을 수 있습니다. 노동자가 사건 당 CPU 시간의 큰 양을 이용하면, 그 자체 과정에서 고립의 머리가 더 적은 때문에 더 적은입니다. 따라서, 런타임은 CPU-hungry인 어떤 노동자든지를 위한 과정 고립을 사용할지도 모릅니다.

노동자가 격리되면 Cloudflare는 대부분의 데스크탑 웹 브라우저로 운영 체제의 스펙트럼 방어에 의존 할 수 있습니다.

Cloudflare는 Graz 기술 대학의 전문가와 협력하여이 접근법을 개발합니다. TU Graz의 팀 공동 발견 된 Spectre 자체와 그 이후로 후속 발견의 거대한 수에 대한 책임이 있습니다. Cloudflare는 동적인 Workers를 고립시키는 기능을 개발하고 공격을 믿을 수 있는 식별한 미터가 있습니다.

이전에 언급했듯이 Process isolation은 완전한 방어가 아닙니다. 시간이 지남에 따라 Spectre 공격은 Cloudflare가 악의적인 행동을 추측하고 식별 할 수있는 능력을 가지고 있음을 의미합니다. 프로세스를 더 느리고 잠재적 인 공격.

### 단계 3: 정기적인 전체 메모리 shuffling

이 시점에서 알려진 모든 공격이 예방되었습니다. 이 잎 Workers는 다른 모든 CPU 근거한 체계로 미래에 알 수없는 공격에 취약합니다. 그러나, 모든 새로운 공격은 일반적으로 매우 느리고, 일 또는 더 긴, 방어를 준비하는 시간으로 Cloudflare를 떠나.

예를 들어, 전체 Workers 런타임을 일일 기준으로 재시작하는 이유가 있습니다. 이 메모리의 모든 위치를 재설정, 공격을 강제로 비밀의 위치를 발견의 과정을 재시작. Cloudflare는 또한 육체적인 기계 또는 cordons의 맞은편에 WorkersXQXQ를 reschedule 할 수 있습니다, 그래서 어떤 특정 이웃을 공격하는 창은 제한됩니다.

일반적으로, Workers는 근본적으로 preemptible (컨테이너 또는 VMs와는 달리), Cloudflare는 가짜 공격에 많은 자유가 있습니다.

Cloudflare는 지속적인 투자로 이 것을 볼 수 있습니다 — 그 어느 것이 수행되지 않습니다.
