이 페이지 세부 정보 R2의 일관성 모델, 여기서 R2는 강력하고 전 세계적으로 일관성이 있으며, 이는 이를 위해 적용된다.

R2는 다른 배부된 목표 저장 체계에 비교에서 “강하게 일관된”로 특히 설명될 수 있습니다. 이 강한 견실함은 R2에 대하여 가동이 최신 (accurate) 국가를 보십시오: 클라이언트는 어떤 쓰기, 갱신 및/또는 즉시 가동의 효력을 관찰할 수 있어야 합니다.

## 용어 정의

R2의 상황에,*큰 가슴*일관성과*행사일정*일관성은 다음과 같은 의미가 있습니다:

- **강한 일관되게**- 가동의 효력은 전 세계, 즉시, 모든 클라이언트에 의해 관찰될 것입니다. 클라이언트는 'stale'(inconsistent) 상태를 관찰하지 않습니다.
- **자주 묻는 질문**- 고객은 즉시 가동의 효력을 볼 수 없습니다. 국가는 전 세계적으로 propagate에 몇 번 (일반적으로 초) 걸릴 수 있습니다.

## 운영 및 책임

R2 물통과 목표에 대하여 가동은 뒤에 오는 견실함 보증에 따릅니다:

<table-wrap>
  | - 연혁                                    | 관련 제품                                                                                                    |
  | --------------------------------------- | -------------------------------------------------------------------------------------------------------- |
  | read-after-write: 쓰기 (upload) 객체, 다음 읽기 | 강력하게 일관되게: 독자는 즉각 최신 목표를 세계적으로 볼 것입니다                                                                    |
  | Metadata: 객체의 메타데이터 업데이트                | 강력하게 일관성 : 독자는 즉시 업데이트 된 메타 데이터를 볼 수 있습니다.                                                               |
  | 삭제: 객체 삭제                               | 강력하게 일관되게: 그 객체에 대한 읽기는 즉시 "가 존재하지 않는" 오류를 반환합니다.                                                        |
  | Object listing: 버킷의 개체 목록               | 강력하게 일관되게: 목록 가동은 시간에 있는 그 점에 모든 목표를 나열할 것입니다                                                            |
  | IAM: 추가/제거 R2 저장 권한                     | 지속적으로 일관되게: A[새로운 업데이트 API 키](/fundamentals/api/get-started/create-token/)세계적으로 반영된 권한이 있는 분까지 갈 수 있습니다. |
</table-wrap>

추가 노트:

- 이벤트에서 두 클라이언트는 쓰기 (`PUT`또는`DELETE`) 같은 열쇠에, 마지막 작가는 "wins"를 완료합니다.
- Multipart 업로드를 수행 할 때, read-after-write 일관성은 모든 부품이 성공적으로 업로드되면 계속 적용됩니다. 같은 부분이 업로드 된 경우 ( 오류) 여러 작가에서 마지막 쓰기가 승리합니다.
- 같은 버킷 내에서 객체를 복사하는 것은 새로운 객체를 작성하는 동일한 read-after-write 일관성을 따릅니다. "copied" 객체는 복사 작업이 완료되면 모든 클라이언트가 즉시 읽을 수 있습니다.
- R2 버킷을 삭제하려면 삭제 전에 완전히 비어 있어야합니다. 여전히 객체가 포함 된 버킷을 삭제하려고하면 다음과 같은 오류를 받게됩니다.`The bucket you tried to delete (X) is not empty (account Y)`또는`Bucket X cannot be deleted because it isn’t empty.`"

## 뚱 베어

:::참조

기본적으로 Cloudflare의 캐시가 일반 캐시 상태 코드가 자동으로 캐시됩니다.[우리의 캐시 문서](/cache/how-to/configure-cache-status-code/#edge-ttl).

:::

연결하기[사용자 정의 도메인](/r2/buckets/public-buckets/#custom-domains)R2 버킷과 같은 버킷에서 제공되는 개체를 캐싱 할 수 있도록, 일관성 모델은 반드시 캐싱 활성화 도메인을 통해 콘텐츠에 액세스 할 때 편안합니다.

구체적으로, 당신은 예상해야 합니다:

- R2에서 삭제하는 객체는 여전히 캐시되어 있지만 여전히 사용할 수 있습니다. 당신은[캐시를 제거](/cache/how-to/purge-cache/)당신이 반사되는 삭제를 필요로 하는 경우에 삭제 물체 후에.
- 기본적으로 Cloudflare의 캐시가[캐시 HTTP 404 (찾지 않음) 응답](/cache/how-to/configure-cache-status-code/#edge-ttl)자동. 같은 경로에 객체를 업로드하면 캐시가 캐시 TTL (Time to Live)가 만료될 때까지 HTTP 404s를 반환하고 새로운 객체는 R2 또는[캐시는 Purged](/cache/how-to/purge-cache/).
- 주어진 열쇠를 위한 목표는 새로운 목표에 overwritten입니다: 오래된 (이전) 목표는 캐시 TTL가 만료될 때까지 클라이언트에 계속될 것입니다 (또는 목표는 evicted) 또는 캐시는 순화됩니다.

캐시는 접근에 영향을 미치지 않습니다.[Worker API 바인딩](/r2/api/workers/)또는[사이트맵](/r2/api/s3/), 이 가동은 물통에 대하여 직접 만들고 캐시를 통해서 transit하지 않습니다.
