## 오류

### 웹사이트에 beacon을 추가하고 웹페이지를 로드하면 `is not allowed by Access-Control-Allow-Origin` (CORS)이 포함된 오류가 보입니다. 무슨 일이 일어나고 있나요?

이 오류는 대개 analytics를 로드하는 사이트의 호스트명이 대시보드에 구성한 analytics 사이트 이름과 일치하지 않을 때 발생합니다. 두 값이 완전히 동일한지 다시 확인하세요.

Cloudflare는 postfix를 기준으로 호스트명을 일치시킵니다. 예를 들어 `example.com`에 대해 analytics를 설정했다면 `www.example.com`, `blog.staging.example.com`, `fooexample.com`에서 오는 analytics는 허용됩니다. 하지만 `example.com.br`에서 오는 analytics는 허용되지 않습니다.

사이트가 `Referer` 또는 `Origin` 헤더를 보내지 않는 경우에도 이 오류가 나타날 수 있습니다. `Referer` 헤더는 필수입니다(`Referrer-policy` 헤더로 대체하려고 하지 마세요). 현재는 앞으로 `Origin` 헤더만 필요하도록 변경 작업이 진행 중이며, Cloudflare는 브라우저에서 이를 비활성화하는 방법이 없다고 보고 있습니다.

### analytics beacon이 ad-blocker(adblockplus, Brave, DuckDuckGo extension 등)에 의해 차단됩니다. 왜 그런가요?

Cloudflare는 analytics beacon이 이러한 서비스에 의해 차단된다는 점을 인지하고 있습니다.

Cloudflare Web Analytics는 JavaScript beacon을 사용하지만, Cloudflare의 edge analytics는 수신되는 모든 요청을 측정할 수 있기 때문에 차단될 수 없습니다. Edge analytics는 트래픽을 Cloudflare를 통해 프록시하는 모든 고객에게 제공됩니다. 현재 Pro, Business, Enterprise 요금제 사용자는 Cloudflare edge 로그를 기반으로 하는 고급 웹 analytics를 사용할 수 있습니다.

### Single-page application(SPA) 또는 multiple-page application(MPA)에서 모든 지표가 보이지 않는 이유는 무엇인가요?

single-page app에서 발생하는 각 route 변경은 route가 변경되기 전에 그 route의 측정값을 beacon endpoint로 전송합니다. 마지막 route 변경에 대한 측정값은 사용자가 탭을 떠나거나 브라우저 창을 닫을 때 전송됩니다. 이때 `visibilityState`가 hidden 상태가 됩니다. 이런 상황이 발생하면 Beacon JS는 [Navigator.sendBeacon method](https://developer.mozilla.org/en-US/docs/Web/API/Navigator/sendBeacon)를 사용해 payload를 전송하며, 이 방식은 브라우저 창이 닫혀도 취소되지 않아야 합니다. 그러나 호환성 때문에 오래된 브라우저에서는 AJAX(`XmlHttpRequest`) 방식으로 대체되는데, 이 경우 브라우저 창이 닫힐 때 요청이 취소될 수 있어 beacon endpoint로 전송되는 마지막 payload가 유실될 수 있습니다. 또한 다양한 네트워크 상태로 인해 beacon endpoint로 payload를 보내는 과정에서 데이터 손실이 발생할 수도 있습니다.

### 같은 사이트인데 자동 설정을 사용했을 때 데이터가 더 많이 보이는 이유는 무엇인가요?

측정할 페이지를 제어하기 위해 Rules를 사용하지 않는 한, [automatic setup](/web-analytics/get-started/#sites-proxied-through-cloudflare)은 zone 아래의 모든 페이지(서브도메인 포함)에 JS 스니펫을 삽입합니다.

반대로 [manual setup](/web-analytics/get-started/#sites-not-proxied-through-cloudflare)을 사용했다면, JS 스니펫을 실제로 렌더링한 페이지에서만 데이터가 보고됩니다.

:::note

페이지당 렌더링 및 사용할 수 있는 JS 스니펫은 하나뿐이므로, 같은 페이지에 여러 개의 스니펫을 둘 수는 없습니다.

:::

### 내 웹사이트는 Cloudflare를 통해 프록시되는데, Web Analytics의 자동 설정이 동작하지 않습니다.

`Cache-Control` 헤더가 `public, no-transform`으로 설정되어 있으면 Cloudflare 프록시는 웹사이트의 원본 payload를 수정할 수 없습니다. 따라서 Beacon 스크립트가 사이트에 자동으로 삽입되지 않으며 Web Analytics가 동작하지 않습니다. 자세한 내용은 [Origin cache control](/cache/concepts/cache-control/)을 참고하세요.

## 설정

### 내 사이트를 Cloudflare를 통해 프록시하고 있습니다. JS beacon을 수동으로 추가해야 하나요?

추가할 수는 있지만, 꼭 그럴 필요는 없습니다. Cloudflare Web Analytics는 원래 Cloudflare 프록시를 사용하지 않는 고객이 자신의 웹 트래픽을 측정할 수 있도록 주로 설계되었습니다.

기존 Cloudflare 고객은 대시보드의 **Analytics** 탭에서 Cloudflare edge가 수집한 analytics에 접근할 수 있습니다. 또한 JavaScript를 사용해 성능을 측정하도록 Web Analytics를 활성화할 수도 있습니다.

[automatic setup](/web-analytics/get-started/#sites-proxied-through-cloudflare)이 적용된 Cloudflare 프록시 도메인을 사용하면 통계가 해당 도메인의 `/cdn-cgi/rum` endpoint로 보고됩니다. 반면 JS 스니펫을 직접 설치한 경우([manual setup](/web-analytics/get-started/#sites-not-proxied-through-cloudflare)), `cloudflareinsights.com/cdn-cgi/rum` endpoint로 보고됩니다.

### Google Tag Manager(GTM) 같은 태그 매니저를 사용해 사이트에 Web Analytics를 추가할 수 있나요?

예. 다음과 같이 태그 매니저로 스크립트를 삽입하는 대신:

```html
<script
	defer
	src="https://static.cloudflareinsights.com/beacon.min.js"
	data-cf-beacon='{"token": "$SITE_TOKEN"}'
></script>
```

아래 스크립트를 추가하세요.

```html
<script
	defer
	src="https://static.cloudflareinsights.com/beacon.min.js?token=$SITE_TOKEN"
></script>
```

### 다른 도메인에서도 같은 JS Snippet을 사용할 수 있나요?

아니요. 다만 apex domain(즉 "root domain" 또는 "naked domain")이 같다면 같은 site tag를 사용할 수 있습니다. 예를 들어 사이트 등록 시 `example.com` 호스트명을 제공했다면, `abc.example.com`과 `def.example.com`에서도 같은 JS snippet을 사용할 수 있습니다. 두 도메인이 같은 apex domain을 사용하기 때문입니다. payload가 beacon endpoint로 전송될 때 Cloudflare는 postfix matching으로 호스트명을 검증하므로, 같은 apex domain을 공유하면 동작합니다.

### DNS-only 도메인(CNAME setup)에서 automatic setup을 사용할 수 있나요?

아니요. JS snippet 삽입을 포함한 [automatic setup](/web-analytics/get-started/#sites-proxied-through-cloudflare)은 도메인 트래픽이 Cloudflare를 통해 프록시될 때(오렌지 클라우드)만 사용할 수 있습니다.

DNS-only 도메인을 사용하는 경우에는 [manual setup](/web-analytics/get-started/#sites-not-proxied-through-cloudflare)을 사용해야 합니다.

## 기능

### URL 기준으로 서버 측 analytics를 볼 수 있나요?

Web Analytics는 클라이언트 측 analytics만 표시합니다. 트래픽을 Cloudflare를 통해 프록시하는 모든 고객은 edge 트래픽 기반 analytics도 함께 받습니다.

현재 Pro, Business, Enterprise 요금제 사용자는 고급 HTTP 트래픽 analytics를 사용할 수 있으며, 이는 URL별 서버 측 analytics 세부 분해를 볼 수 있는 유일한 방법입니다.

### Web Analytics에서 데이터에 접근할 수 있는 기간은 얼마나 되나요?

현재 이전 6개월의 데이터에 접근할 수 있습니다.

### Cloudflare Web Analytics는 UTM 파라미터를 지원하나요?

아직은 아닙니다. UTM 파라미터는 트래픽의 유입 출처를 추적하는 데 도움이 되는 특별한 query string 파라미터입니다.
현재 Cloudflare Web Analytics는 잠재적으로 민감한 데이터를 수집하지 않기 위해 query string을 기록하지 않지만, 앞으로 지원이 추가될 수 있습니다.

### Web Analytics는 custom events를 지원하나요?

아직은 아니지만, 앞으로 지원이 추가될 수 있습니다.

### Web Analytics로 하나 이상의 웹사이트를 추적할 수 있나요?

예. 현재는 계정당 10개 사이트라는 소프트 제한이 있지만, Cloudflare 지원팀에 문의하면 조정할 수 있습니다.

### beacon은 언제 `/cdn-cgi/rum/` endpoint로 지표를 전송하나요?

전통적인 웹사이트, 즉 Single Page Application(SPA)이 아닌 경우 Web Analytics beacon은 페이지 로드가 완료되었을 때(load event)와 사용자가 페이지를 떠날 때 `/cdn-cgi/rum/` endpoint로 보고합니다. Single Page Application의 경우 페이지 로드 이벤트를 포착하기 위해 모든 route 변경마다 추가 지표가 전송됩니다.
