3xx 코드는 HTTP 클라이언트가 요청한 리소스를 얻기 위해 다른 작업을 수행해야한다는 것을 나타내는 응답의 클래스입니다.

리디렉션 위치는 다음과 같은 방법으로 지정되어야 합니다:

- 내 계정`Location`자동 리디렉션에 유용합니다 응답의 헤더 필드.
- 응답의 페이로드에서, 선택적으로 정확한 위치에 하이퍼 링크 포함.

## 300의 다수 선택

300 Multiple Choices 상태는 요청된 리소스를 사용할 수 있는 여러 옵션을 나타냅니다. 클라이언트는 하나를 선택할 수 있습니다.

더 많은 정보를 원하시면, 참조[RFC 7231의](https://tools.ietf.org/html/rfc7231).

### 일반적인 사용 사례

자원이 여러 표현이나 형식에서 사용할 때 일반적으로 사용됩니다. 예를 들면:

- 다양한 형식의 비디오의 여러 버전을 제공합니다 (예 : MP4, AVI).
- 다른 파일 목록 제공[관련 상품](https://en.wikipedia.org/wiki/File_extensions)또는 압축 유형.
- 현재 위치[단어감 장애](https://en.wikipedia.org/wiki/Word_sense_disambiguation)여러 의미의 용어에 대한 옵션.

응답은 포함될 수 있습니다`Location`선호하는 옵션으로 향하거나 가능한 선택에 하이퍼 링크로 페이로드를 제공 할 때 클라이언트가 결정할 수 있습니다.

### Cloudflare-특징 정보

Cloudflare는 일반적으로 자동화된 리디렉션을 위한 300의 다중 선택 응답을 우회하여 최적의 성능과 사용자 경험을 보장합니다.

## 301 영구적으로 이동

301 Moved 영구 상태는 요청된 리소스가 새로운 영구 URI를 할당한 것을 나타냅니다. 모든 미래 참고 자료s는 동봉 된 URI 중 하나를 사용해야합니다.

더 많은 정보를 원하시면, 참조[RFC 7231의](https://tools.ietf.org/html/rfc7231).

### 일반적인 사용 사례

이 상태는 일반적으로 클라이언트에게 알리기 위하여 이용됩니다:

- 자원은 영구적으로 새로운 URI로 이전되었습니다.
- 검색 엔진은 새로운 URI를 반영하기 위해 인덱스를 업데이트해야합니다.
- 책갈피 또는 다른 저장된 참고 자료s는 개정되어야 합니다.

응답은 일반적으로 포함`Location`새로운 URI를 지정하는 헤더. 이것은 대부분의 User-Agents의 자동 리디렉션을 가능하게 합니다.

### Cloudflare-특징 정보

Cloudflare는 근원 서버에게 조회하기 위하여 필요 없이 301 Moved 영구적으로 응답을 생성할 수 있습니다. 더 많은 정보를 원하시면, 참조[Redirect 규칙](/rules/url-forwarding/).

## 302 발견

302 건의 상태, 또한 임시 리디렉션으로 언급, 요청 된 자원이 다른 URI에 일시적으로 위치한다는 것을 나타냅니다. 영구적으로 301개의 공격 상태와 달리, 302개의 발견 상태는 임시 사용을 위해 특히 예정됩니다.

User-Agent는 다음과 같이 할 수 있습니다.`Location`리소스를 검색하는 헤더는 301 Moved 영구적으로 현재 URI를 대체하지 않아야합니다.

더 많은 정보를 원하시면, 참조[RFC 7231의](https://tools.ietf.org/html/rfc7231).

### 일반적인 사용 사례

이 상태는 일반적으로 사용됩니다:

- 유지 보수 또는 업그레이드 중에 Temporarily 리디렉션 트래픽.
- 저장된 참고 자료S를 변경하지 않고 대체 자원에 직접 사용자.
- A/B는 영원한 변화를 만들기 없이 자원의 다른 버전을 시험합니다.

### Cloudflare-특징 정보

Cloudflare는 이 응답을 생성할 수 있고, 근원 봉사에 요구에 보내기 위하여 필요를 삭제합니다. CloudflareXQ가 리디렉션을 생성하는 방법에 대해 자세히 알아보기[Redirect 규칙](/rules/url-forwarding/).

## 303 참조 기타 (HTTPS / 1.1 이후)

303 다른 상태는 클라이언트가 다른 URI에 리소스를 검색해야한다는 것을 나타냅니다`GET`이름 \* 301 Moved 영구적으로 리디렉션과는 달리 리디렉션 위치의 리소스는 원래 요청된 리소스와 동일하지 않습니다.

더 많은 정보를 원하시면, 참조[RFC 7231의](https://tools.ietf.org/html/rfc7231).

### 일반적인 사용 사례

303 상태는 일반적으로 응답에서 사용됩니다.`POST`또는`DELETE`Origin 서버가 성공적으로 데이터를 처리하고 적절한 캐싱 동작을 지원하기 위해 요청합니다.

초기 303 응답은 캐시 할 수 없지만, 이후의 응답`GET`요청은 별도의 URI에 묶여 있기 때문에 캐시 될 수 있습니다.

### Cloudflare-특징 정보

Cloudflare는 303의 구성을 통해 리디렉션을 허용합니다[Redirect 규칙](/rules/url-forwarding/), 이 응답의 이음새가 없는 취급을 가장자리에 직접 가능하게 합니다. 이 접근은 Origin 서버에 불필요한 요청을 피함으로써 성능을 향상시킵니다.

## 304 변경되지 않음

304 변경되지 않은 상태는 요청된 리소스가 사용 가능하고 클라이언트의 캐시에서 유효하다는 것을 나타냅니다. 클라이언트의 마지막 요청 이후 리소스를 수정하지 않은 경우, 클라이언트가 원래 서버에 연결하지 않고 캐시 된 리소스를 사용할 수 있도록 허용. 304 응답을 받기 위한 요구는 안으로 정의됩니다[RFC 7234의 단면도 4.3.4](https://tools.ietf.org/html/rfc7234#section-4.3.4).

더 많은 정보를 원하시면, 참조[RFC 7232의](https://tools.ietf.org/html/rfc7232).

### 일반적인 사용 사례

A 304 변경된 응답은 클라이언트가 조건부를 보낼 때 사용됩니다`GET`또는`HEAD`캐시 된 리소스를 검증하는 요청. 서버는 캐시 된 버전이 현재까지 계속되어 클라이언트가 리소스를 다시 다운로드하지 않고 사용할 수 있다는 것을 확인합니다. 이 도움은 불필요한 자료 전송을 감소시키고 효율성을 개량합니다.

304 응답은 포함합니다:

- 아니 메시지 몸: 304 응답 자체는 실제적인 자원 (이미지 또는 웹 페이지 내용과 같은) 포함하지 않습니다. 대신, 그것은 단지 캐시 된 버전이 유효하다는 것을 확인합니다.
- 필수 헤더: 응답은 중요한 metadata (와 같은)를 포함합니다`Cache-Control`, `Content-Location`, `Date`, `ETag`, `Expires`, 또는`Vary`) 클라이언트에게 캐시 된 리소스를 관리하는 방법을 알려줍니다. 이 헤더는 200 OK 응답으로 전송 된 경우 리소스를 동반하는 것과 동일합니다.

### Cloudflare-특징 정보

stale 요청이 원산지에서 다시 유효해야 할 때 Cloudflare는 캐시 된 버전이 원래 버전 일치한다는 것을 확인하기 위해 304 응답을 보냅니다. 응답은 포함`CF-Cache-Status: REVALIDATED`헤더 및 Cloudflare는 버전을 사용하여 검증`If-Modified-Since`헤더. 더 많은 정보를 원하시면, 참조[ETag 헤더](/cache/reference/etag-headers/).

## 305 사용 프록시 (사전)

이 상태 코드는 요청이 프록시를 통해 전달되어야한다는 것을 나타냅니다.`Location`원래 서버로 직접 전송되는 대신 헤더. 그러나 보안 문제로 인해 305 사용 프록시 상태 코드가 중단되었습니다.

## 306 스위치 프록시 (deprecated)

이 상태 코드는 지정된 프록시를 통해 나중에 요청이 전송되어야한다는 것을 나타냅니다. 그러나 306 스위치 프록시 상태 코드가 deprecated이고 더 이상 사용하지 않습니다.

## 307 임시 간접

307 임시 간접 상태는 요청한 자원이 다른 URI로 일시적으로 이동되었음을 나타냅니다.`Location`헤더. 302 리디렉션과는 달리, 원래 요청 방법 (예를 들어,`GET`또는`POST`)는 리디렉션이 자동적으로 이어질 때 변하지 않아야 합니다. 이것은 자원의 위치에 임시 변경이 요청의 의도 된 행동을 방해하지 않습니다. 사용자 에이전트는 자동으로 리디렉션을 따라갈 수 있습니다.`Location`헤더, 그러나 미래의 요청에 대한 원래 URI를 대체하지 않아야합니다.

더 많은 정보를 원하시면, 참조[RFC 7231의](https://tools.ietf.org/html/rfc7231).

### 일반적인 사용 사례

307 상태는 서버 유지 보수 또는 업그레이드 중에 일시적으로 재배 자원에 유용하며 원래 요청 방법을 보존합니다. 그것은 또한 일반적으로 향후 요청에 대한 원래 URI를 변경하지 않고 프로모션, 캠페인, 또는 특별 이벤트에 대한 임시 URL에 직접 트래픽에 사용됩니다.

### Cloudflare-특징 정보

Cloudflare는 307 임시 간접 응답을 능률적으로 처리할 수 있고, 근원 서버에서 변화 없이 임시 리디렉션을 가능하게 합니다. 설정할 수 있습니다.[Redirect 규칙](/rules/url-forwarding/).

## 308 영구 Redirect

308 영구 Redirect 상태는 요청된 리소스가 영구적으로 새로운 URI로 이전되었음을 나타냅니다.`Location`헤더. 301 리디렉션과는 달리, 원래 요청 방법 (예를 들어,`GET`, `POST`)는 리디렉션을 따라 자동으로 변경되지 않습니다. 사용자 에이전트는 리디렉션을 따라야 합니다.`Location`헤더 및 원래 URI를 대체하는 새로운 하나에 대한 후속 요청.

더 많은 정보를 원하시면, 참조[RFC 7538년](https://tools.ietf.org/html/rfc7538#section-3).

### 일반적인 사용 사례

308 영구 Redirect 상태는 영구 자원 이전, API 버전 업그레이드, 도메인 또는 경로 마이그레이션 및 리디렉션에 대한 무결성 유지에 사용됩니다. 또한, 그것은 새로운 URI에 링크를 전송하여 SEO에 도움이됩니다.

### Cloudflare-특징 정보

Cloudflare는 308의 영원한 Redirects를 능률적으로 취급할 수 있고, 리디렉션을 지키고, 요청 무결성을 유지하고 있습니다. 이 리디렉션을 사용하여 구성할 수 있습니다.[Redirect 규칙](/rules/url-forwarding/).
