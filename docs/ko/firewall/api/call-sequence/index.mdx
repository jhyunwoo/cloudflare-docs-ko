아래 이미지는 생성 및 편집 규칙에 적용할 수 있는 이 순서들을 묘사합니다. 역은 삭제 작업에 적용됩니다.

!['Cloudflare' 필터 API 및 방화벽 규칙 API를 호출하여 규칙을 작성하거나 편집 할 때 권장 유량](~/assets/images/firewall/recommended-flow.png)

Cloudflare는 필터 재사용을 촉진하고 독립적으로 API로 작업 할 수 있기 때문에이 순서를 권장합니다. 'Cloudflare' 필터의 독립 자연 덕분에 동일한 필터는 여러 방화벽 규칙과 다른 미래 'Cloudflare' 제품 및 기능에서 공유 할 수 있습니다.

예를 들어, API에 대한 모든 트래픽을 일치 필터 (즉,`http.request.uri.path matches "^/api/.*$"`)는 캐싱을 비활성화 할 수있다, 인간 CAPTCHA를 비활성화, JSON 사용자 정의 오류를 구성, 방화벽 규칙에 나타납니다. 위의 권장 시퀀스를 사용하면 각 "Cloudflare"기능을 반복하여 1-2 단계로 생성 된 동일한 필터에 대해 구성 할 수 있습니다.

그러나,`POST`가동,**simplified 순서**— 아래에 표시된 — 필터와 같은 통화의 규칙을 모두 만들 수 있습니다. 이 경우, 필터 및 규칙은 서로를 참조합니다.

![방화벽 규칙 API를 호출하기위한 기본 흐름은 필터와 단일 통화의 규칙을 만들 수](~/assets/images/firewall/simple-flow.png)

이 순서에서, 단일`POST`요청하기`/firewall/rules`endpoint는 JSON의 필터 객체를 사용하여 Filters API에 필터를 생성합니다.`POST`요청). 성공하면 방화벽 규칙이 생성됩니다.

아래는 이 방법을 사용하여 예 통화 및 응답입니다.

```bash title="Request"
curl "https://api.cloudflare.com/client/v4/zones/{zone_id}/firewall/rules" \
--header "X-Auth-Email: <EMAIL>" \
--header "X-Auth-Key: <API_KEY>" \
--header "Content-Type: application/json" \
--data '[
  {
    "filter": {
      "expression": "http.request.uri.path contains \"/api/\" and ip.src eq 93.184.216.34"
    },
    "action": "block"
  }
]'
```

```json title="Response"
{
	"result": [
		{
			"id": "<RULE_ID>",
			"paused": false,
			"action": "block",
			"priority": null,
			"filter": {
				"id": "<FILTER_ID>",
				"expression": "http.request.uri.path contains \"/api/\" and ip.src eq 93.184.216.34",
				"paused": false
			}
		}
	],
	"success": true,
	"errors": [],
	"messages": []
}
```

그러나이 접근법은 다음과 같습니다.

- 방화벽 규칙 클라이언트는 방화벽 규칙과 필터 API 모두에서 발생하는 모든 잠재적 실패에 대한 오류 및 예외 처리를 구현해야 합니다.
- 실수로 수정하거나 다른 'Cloudflare' 기능에 의해 사용되는 필터 삭제에 대한 보호`PUT`또는`DELETE`작업은 허용되지 않습니다.

기본적으로 필터 또는 규칙이 유효하지 않은 경우, 생성되지 않습니다.

그러나 예외는 적용됩니다. 규칙 할당량을 초과하는 경우, Cloudflare는 필터를 만들 수 있지만 방화벽 규칙이 아닙니다. 이 규칙은 순서도에 있는 여과기 후에만 창조되기 때문에 일어납니다.

쿼타를 초과하거나 지역을 사용할 수없는 기능을 요청하는 문제를 해결 한 후, '참고 자료' 필터가 규칙을 만드는 것이 좋습니다.
