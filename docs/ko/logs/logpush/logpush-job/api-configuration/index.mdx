R2, S3, 등. 또한, 일반적인 사용 사례`https`또한 커버:

- `r2`,
- `gs`,
- `s3`,
- `sumo`,
- `https`,

더 보기`destination-address`자주 묻는 질문
회사 소개 그러나 특정 공급자를 위해, 우리는 요구합니다`destination-address`특정 형식을 따르기 위해:

- **Cloudflare R2**(체계)`r2`): 물통 경로 + 계정 ID + R2 접근 열쇠 ID + R2 비밀 접근 열쇠; 예를 들면:`r2://<BUCKET_PATH>?account-id=<ACCOUNT_ID>&access-key-id=<R2_ACCESS_KEY_ID>&secret-access-key=<R2_SECRET_ACCESS_KEY>`
- **사이트맵**(체계)`s3`) : 버킷 + 옵션 디렉토리 + 지역 + 옵션 암호화 매개 변수 (당신의 정책에 따라 필요한 경우); 예를 들면 :`s3://bucket/[dir]?region=<REGION>[&sse=AES256]`
- **데이터 독**(체계)`datadog`): Datadog 엔드포인트 URL + Datadog API 열쇠 + 선택적인 모수; 예를 들면:`datadog://<DATADOG_ENDPOINT_URL>?header_DD-API-KEY=<DATADOG_API_KEY>&ddsource=cloudflare&service=<SERVICE>&host=<HOST>&ddtags=<TAGS>`
- **Google 클라우드 스토리지**(체계)`gs`): 물통 + 선택적인 지시; 예를 들면:`gs://bucket/[dir]`
- **마이크로 소프트 Azure**(체계)`azure`): 서비스 수준 SAS URL과`https`에 의해 대체`azure`+ 쿼리 문자열 전에 추가 된 옵션 디렉토리; 예를 들어:`azure://<BLOB_CONTAINER_PATH>/[dir]?<QUERY_STRING>`
- **새로운 Relic**(사용 계획`https`): 새로운 Relic 엔드포인트 URL은`https://log-api.newrelic.com/log/v1`미국 또는`https://log-api.eu.newrelic.com/log/v1`EU + 라이센스 키 + 형식; 예를 들어: 미국`"https://log-api.newrelic.com/log/v1?Api-Key=<NR_LICENSE_KEY>&format=cloudflare"`유럽 연합`"https://log-api.eu.newrelic.com/log/v1?Api-Key=<NR_LICENSE_KEY>&format=cloudflare"`
- **스플리크**(체계)`splunk`): Splunk 엔드포인트 URL + Splunk 채널 ID + insecure-skip-verify 플래그 + Splunk sourcetype + Splunk authorization 토큰; 예를 들면:`splunk://<SPLUNK_ENDPOINT_URL>?channel=<SPLUNK_CHANNEL_ID>&insecure-skip-verify=<INSECURE_SKIP_VERIFY>&sourcetype=<SOURCE_TYPE>&header_Authorization=<SPLUNK_AUTH_TOKEN>`
- **스모 로직**(체계)`sumo`): HTTP 소스 주소 URL과`https`에 의해 대체`sumo`; 예를 들면:`sumo://<SUMO_ENDPOINT_URL>/receiver/v1/http/<UNIQUE_HTTP_COLLECTOR_CODE>`
- **센티넬원**(체계)`sentinelone`): SentinelOne 엔드포인트 URL + SentinelOne Sourcetype + SentinelOne Authorization 토큰; 예를 들면:`sentinelone://<SENTINELONE_ENDPOINT_URL>?sourcetype=<SOURCE_TYPE>&header_Authorization=<SENTINELONE_AUTH_TOKEN>`

제품 정보**모델 번호: R2**, **사이트맵**, **Google 클라우드 스토리지**·**Azure 클라우드**, 당신은 특별한 placeholder를 포함하여 매일 subdirectories로 로그를 구성할 수 있습니다`{DATE}`URL 경로에서. 이 위주자는 자동으로 날짜로 대체됩니다.`YYYYMMDD`형식 (예를 들면,`20180523`).

logpull options를 사용하는 경우, 여기에 당신이 사용자 정의 할 수있는 옵션입니다:

2. **Timestamp 형식**(선택): 타임스탬프 필드가 반환됩니다. 가치 선택권:`unixnano`(nanoseconds 단위 - 과태),`unix`(초 단위),`rfc3339`(초 단위).

## 구성 변경 타이밍

Logpush 작업 구성을 수정할 때, 변경은 즉시 영향을받지 않습니다.

### 여행 일정

새로운 목적지를 사용하기 위해 일을 재구성하는 경우, 로그는 전환 기간 동안 약 10-15 분 동안 오래된 목적지로 보내질 수 있습니다. 이 지연은 Cloudflare의 네트워크를 통해 새로운 구성을 완료하는 시스템을 허용합니다.

### 현장 변경

기존 Logpush 작업에 새로운 필드를 추가하면 새로운 필드는 약 10-15 분 이내에 로그에 표시됩니다. 이 타이밍은 추정이며 시스템 부하에 따라 달라질 수 있습니다.

:::참조
이 시간표는 견적입니다. 변경 사항을 확인해야 하는 경우, 업데이트 로그 형식의 목적지를 모니터링하거나 확인해야 합니다.[건강 대시보드](/logs/logpush/logpush-health/)최근 업로드.
주요 특징

## 샘플링 비율

가치는 범위에서 할 수 있습니다`0.0`(exclusive)에`1.0`(포함).`sample=0.1`반환 10% (1 에 10) 모든 레코드. 기본값은`1`, 의미 로그는 unsampled.

### sample rate 및 SampleInterval 이해

더 보기`sample_rate`매개 변수 및`SampleInterval`필드는 로깅 파이프라인의 다른 단계에서 작동하는 독립적 인 메커니즘입니다.

- **`sample_rate`**: Logpush 작업에 설정된 구성 매개 변수는 로그의 비율이 목적지 (0.0-1.0)에 전달되는 것을 제어하는 것입니다. 예를 들어, 설정`sample_rate: 0.1`약 10%의 로그를 제공합니다.

- **`SampleInterval`**: 특정 데이터셋에 나타나는 데이터 필드(particularly)[Network Analytics 로그](/logs/logpush/logpush-job/datasets/account/network_analytics_logs/)) 데이터 수집에 적용되는 업스트림 샘플링을 나타냅니다. ·`SampleInterval`1000의 로그 입력은 1000 패킷에 1을 나타냅니다.

더 보기`sample_rate`sampling 의 상단에 적용할 수 있습니다. 이미 데이터가 있는 경우`SampleInterval: 1000`그리고 당신은`sample_rate: 0.1`, 원래 이벤트의 10,000에서 약 1을받습니다 (1000 × 10).

:::참조
고객 구성 샘플링이 적용되면`SampleInterval`로그의 필드 값은 수정되지 않습니다. 내부 샘플링이 없다면,`SampleInterval`항상 구성에 관계없이 1 일 것입니다.`sample_rate`.
:::

## 최대 업로드 매개 변수

이 매개 변수는 각 업로드 일괄의 크기를 제어 - 빠른 데이터가 전달되지 않습니다. 해당 이용 후기에 달린 코멘트가 없습니다.

| 제품 설명                         | 이름 \*                                      | 기본 정보   |
| ----------------------------- | ------------------------------------------ | ------- |
| `max_upload_bytes`            | 로그의 배치의 최대 압축 파일 크기.                       | 여행 일정   |
| `max_upload_records`          | 일괄 처리 당 로그 라인의 최대 번호.                      | 100,000 |
| `max_upload_interval_seconds` | 일괄 처리 당 로그 데이터의 최대 시간 수명 (캐치 업 시나리오에서 사용). | 여행 일정   |

:::참조
이 설정은 업로드 크기, 배달 대기 시간. Logpush 프로세스 데이터는 이 매개 변수 값에 관계없이 분 당 약 한 번. 이 설정은 메모리 또는 요청 크기 제약이있는 목적지를 과부하시키는 데 도움이되는 배치 당 작거나 더 큰 업로드에 결과를 조정합니다.
주요 특징

### 이 매개 변수를 조정할 때

- 이름 \*`max_upload_records`목적지가 큰 페이로드로 투쟁하거나 큰 배치를 처리 메모리를 실행하는 경우.
- 더 보기`max_upload_records`만약 당신이 몇몇을 원하면, 더 큰 파일 (예를 들면, R2 또는 S3) 같이 물건 저장을 밀어낼 때.
- 엄격한 페이로드 제한이있는 Datadog와 같은 목적지를 위해, Logpush는 자동으로 작은 배치 크기를 사용합니다 (예 : 1,000 행).

:::가격
비용 계획 (예를 들면, R2 쓰기 가동)를 위해 생성된 파일의 수를 견적하는 경우에, 대표자 기간을 위한 Logpush를 실행하고 실제적인 산출을 측정하십시오. 업로드의 수는 데이터 볼륨에 달려 있으며 사전에 정확하게 계산할 수 없습니다.

HTTP 요청 헤더, HTTP 응답 헤더 및 쿠키 형태로 HTTP 요청 로그 항목을 추가할 수 있습니다. Custom 필드 구성은 HTTP 요청 데이터셋을 사용하는 영역에서 Logpush 작업에 적용됩니다. 더 알아보기[회사 소개](/logs/logpush/logpush-job/custom-fields/).
