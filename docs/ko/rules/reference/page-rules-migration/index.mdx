Cloudflare는 지속적으로 당신의 윤곽을 관리하기를 위한 강력한 확장 가능한 공구를 전달하기 위하여 그것의 플랫폼을 개량합니다. 이 개선의 전체 이점을 돕기 위해, 우리는 사용하는 것을 추천합니다[현대 규칙 특징](/rules/)새로운 구현. 이 제품은 더 큰 유연성, 확장성 및 사용 편의성을 제공하면서 페이지 규칙의 제한을 해결합니다.

빠른 시작을 위해 Cloudflare 대시보드에서 사용할 수있는 한 클릭 템플릿을 살펴보십시오.**이름 \*** > **제품정보**. 이 템플릿은 리디렉션, 리디렉션 및 헤더 수정과 같은 일반적인 구성을 단순화하여 설정이 빠르고 쉽게 만듭니다.

## 페이지 규칙 마이그레이션

전환을 원활히 만들기 위해 Cloudflare는 기존 페이지 규칙의 마이그레이션을 자동으로 처리합니다. 이 과정은 늦은 2025 또는 그 이상으로 계획되어 귀하의 부분에 필요한 작업이 없습니다. 변경 전에 미리 알림을 받게 됩니다.

현대 규칙의 혜택을 탐험하려는 경우, 오늘 그들을 채택 시작할 수 있습니다. 이렇게 할 수 있도록:

- 현대 기능과 기능을 빨리 활용하십시오.
- 당신의 진화 요구에 맞게 규칙을 사용자 정의하고 정제합니다.

이 과정을 지원하려면 페이지 규칙 설정과 현대 규칙 제품 사이의 포괄적 인 매핑을 제공합니다.

## 왜 전환?

모델 번호: Cloudflare 페이지 규칙에는 URL 패턴을 기반으로 트리거와 같은 몇 가지 기본 제한이 있으며 성능상의 이유로 지역 당 125 규칙으로 제한됩니다. 이 규칙은 여러 페이지 규칙이 동일한 수신 요청에 적용 할 때 디버그에 복잡합니다.

2022년에, 우리는 우리의 블로그 포스트에서 발표했습니다[페이지 규칙의 미래](https://blog.cloudflare.com/future-of-page-rules)그 페이지 규칙은 전용 제품의 스위트와 교체 될 것입니다, 각은 최상의-of-breed 및 우리의 사용자의 손에 더 많은 힘을 넣어 내장. 새로운 규칙 제품 —[구성 규칙](/rules/configuration-rules/), [압축 규칙](/rules/compression-rules/), [회사 소개](/rules/origin-rules/), [회사 소개](/rules/url-forwarding/)·[Transform 규칙](/rules/transform/)- 이제 일반적으로 사용할 수 있습니다 (GA) 이미 Cloudflare 고객의 수천에 의해 채택되었습니다.

현대 규칙 특징에 있는 개량은 다음을 포함합니다:

- **새로운 엔진**: 새로운 규칙은 다음과 같습니다.[Ruleset 엔진](/ruleset-engine/)많은 HTTP 요청 및 응답 필드를 지원하는 강력한 언어로 다양한 구성을 제공합니다.
- **향상된 확장성**: 개선된 확장성 덕분에 CloudflareXQ 계획은 이제 quotas를 증가시켰습니다.
- **Easier 문제 해결**: 규칙 실행은 더 예측할 수 있으므로 각 규칙이 독립적으로 작동하므로 문제 해결을 단순화합니다. 또한,[Cloudflare 추적](/rules/trace-request/)규칙 상호 작용을 이해하는 데 도움이됩니다.
- **향상된 일관성**: 새로운 규칙은 또한 일관성을 보장하고, 일반적인 필드와 기능으로 제품을 공유하고, 원활한 경험과 예측 가능한 Terraform 구성을 제공합니다.

## 키 차이

규칙의 평가 및 실행 명령은 페이지 규칙과 다릅니다.

- **규칙 일치 논리**: 페이지 규칙은 첫 번째 일치하는 규칙 (첫 번째 경기 승리)을 적용합니다. 대조적으로, 현대 규칙은 쌓을 수 있고, 다수 어울리는 규칙은 동일한 요구에 결합하고 적용합니다 (마지막 경기 승리). 예를 들어, 여러 캐시 규칙이 동일한 URL과 일치한다면, 이러한 규칙의 기능은 모두 순서대로 적용됩니다.
- **작업 분리**: 페이지 규칙은 페이지 규칙 자체 내에서 고객에 의해 선택된 순서에 적용되는 다른 제품에 대한 여러 작업을 포함 할 수 있습니다. 현대 규칙은 평가됩니다[고정 순서로](/rules/origin-rules/#execution-order), 고객과 제품 내에서 규칙 순서를 정의[단계별](/ruleset-engine/reference/phases-list/).
- **이름 \***: 현대 규칙은 페이지 규칙에 대한 우선권을 부여합니다. 예를 들어, 동일한 경로의 캐싱 설정을 정의하면 캐시 규칙은 페이지 규칙을 무시합니다.
- **충돌 행위**: 캐시 규칙에서, 선택**캐시에 대한 Eligible**자동 활성화**캐시 모든 것**기본적으로. 페이지 규칙의 정확한 동작을 유지하려면, 당신은해야합니다[설정 조정](/cache/how-to/cache-rules/page-rules-migration/).
- **Workers**: WorkersXQ에 의해 처리 된 요청은 페이지 규칙 작업을 억제하지만 현대 규칙 기능에서 동작을 억제하지 않습니다.

## 페이지를 변환 규칙 URL 필터 표현

현대 규칙은 URL 패턴 대신 필터 표현을 사용합니다. 규칙 언어에 내장 된이 표현은 레버리지로 더 큰 정밀도를 허용합니다.[주요연혁](/ruleset-engine/rules-language/fields/), [제품정보](/ruleset-engine/rules-language/functions/)·[채용 정보](/ruleset-engine/rules-language/operators/).

다음 예제는 사용의 설명[`http.request.full_uri`](/ruleset-engine/rules-language/fields/reference/http.request.full_uri/)분야 및`wildcard`채용 정보[wildcard 일치](/ruleset-engine/rules-language/operators/#wildcard-matching):

<Example>
  ·**페이지 규칙 URL**다음 것:

  `example.com/*/downloads/*.txt`

  계정 만들기**필터 표현**같은:

  `http.request.full_uri wildcard "http*://example.com/*/downloads/*.txt*"`
</Example>

[단일 Redirects](/rules/url-forwarding/single-redirects/create-dashboard/)·[URL Rewrite 규칙](/rules/transform/url-rewrite/create-dashboard/)또한 simplified 보기를 제공합니다**Wildcard 패턴**URL 패턴을 지정할 수 있습니다 (`http*://example.com/*/downloads/*.txt*`) 풀 필터 표현을 지정하지 않고 (`http.request.full_uri wildcard "http*://example.com/*/downloads/*.txt*"`).

### 중요한 고려사항

- **프로토콜 계획**: Page Rules URL 매칭은 URI 방식(예를 들어,`http://`또는`https://`) 규칙에 명시되지 않는 한. 필터 표현`http.request.full_uri`필드, 그러나, 프로토콜 계획을 포함하여 전체 URI를 일치해야합니다. 필터 표현 방식-agnostic을 만들기 위해 사용`http*://`모두를위한 와일드 카드`http://`·`https://`.
- **Query 문자열**: 페이지 규칙은 규칙 URL의 일부가 아닌 쿼리 문자열을 무시합니다. 필터 표현은 쿼리 문자열을 자동으로 포함, 일부로`http.request.full_uri`이름 \* 쿼리 문자열이 일치하지 않도록하려면, append`*`당신의 필터 표현의 끝에 wildcard, 같은`.txt*`.

    **어떻게 마이그레이션**:

    <Steps>
      1. [단일 리디렉션 만들기](/rules/url-forwarding/single-redirects/create-dashboard/)항상 HTTP 요청을 HTTPS로 리디렉션합니다. 선택할 수 있습니다.**HTTP에서 HTTPS로 이동**규칙 템플릿 또는 다음 규칙 구성을 입력:

         - **자주 묻는 질문**: 와일드카드 패턴
           - **URL 요청**: `http://*`
         - **다음 것**:
           - **대상 URL**: `https://${1}`

## 마이그레이션되지 않는 설정

다음 페이지 규칙 설정은 다른 유형의 규칙으로 마이그레이션되지 않습니다 :

- **사용 방법**(이 설정은 거부)
- **사용 방법**(이 설정은 더 이상 Railgun이 사용할 수 없기 때문에 deprecated입니다)
- **Disable 보안**(이 설정은 거부)
- **응답 버퍼링**(이 설정은 거부)
- **웹 애플리케이션 방화벽**(이 설정은 이전에 WAF 관리 규칙의 이전 버전부터 deprecated입니다)

다른 모든 페이지 규칙 설정은 2025 년 동안 마이그레이션됩니다.
