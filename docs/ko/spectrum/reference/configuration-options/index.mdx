Spectrum은 Cloudflare 엣지 노드에서 실행되는 전역 TCP 및 UDP 프록시입니다. 애플리케이션 계층 의미에서 연결을 종료하지는 않습니다. 하지만 Layer 4에서는 양방향의 TCP 및 UDP 소켓을 종료합니다. TCP 세그먼트와 UDP 데이터그램의 L4 payload는 수정 없이 원래 상태 그대로 양방향으로 전달됩니다.

:::note


이 기능 중 일부는 Enterprise 플랜이 필요합니다. 업그레이드하려면 계정 팀에 문의하세요.


:::

## 애플리케이션 유형

애플리케이션 유형은 데이터가 엣지에서 origin으로 이동할 때 사용하는 프로토콜을 결정합니다. origin으로 직접 프록시하려면 *TCP/UDP*를 선택하세요. CDN, Workers, Bot management 같은 제품을 설정하려면 *HTTP/HTTPS*를 선택해야 합니다. 이 경우 트래픽은 origin에 직접 연결되지 않고 Cloudflare 파이프라인을 통해 라우팅됩니다.

## IP 주소

Spectrum 애플리케이션을 생성하면 고유한 IPv4 및 IPv6 주소가 할당되며, 또는 애플리케이션을 IPv6 전용으로 프로비저닝할 수도 있습니다. 이 주소는 정적이지 않으며 시간이 지나면서 변경될 수 있습니다. 현재 주소를 확인하는 가장 좋은 방법은 DNS를 사용하는 것입니다. Spectrum 애플리케이션의 DNS 이름은 항상 해당 애플리케이션 전용으로 현재 할당된 IP를 반환합니다.

이 주소는 중국 데이터 센터를 제외한 모든 Cloudflare 데이터 센터에서 anycast됩니다.

## SMTP

Spectrum은 SMTP 서버 앞단에서 TCP 로드 밸런서로 동작할 수 있지만, 중간 메일 서버 역할은 하지 않습니다. 대신 데이터를 origin으로 그대로 전달합니다. 메일에 표시되는 클라이언트 IP는 Cloudflare 엣지 IP가 됩니다. 메일 서버가 실제 클라이언트 IP를 알아야 한다면 Proxy Protocol을 사용해 Cloudflare에서 원본 IP를 받아야 합니다. Cloudflare는 SMTP를 프록시하도록 구성한 애플리케이션에서 Proxy Protocol을 활성화할 것을 권장합니다.

SMTP 서버는 메시지를 전달하려는 서버에 대해 일련의 검사를 수행할 수 있습니다. 이러한 검사는 비정상 서버의 요청을 걸러내기 위한 것입니다.

다음과 같은 경우 메시지가 거부될 수 있습니다.

* 연결 중인 서버의 IP 주소에 대해 reverse DNS 조회를 수행했을 때 부정 응답이 반환되는 경우
* reverse DNS 조회 결과가 SMTP `HELO`/`EHLO` 메시지에서 보낸 hostname과 다른 경우
* reverse DNS 조회 결과가 SMTP 서버 배너에 광고된 hostname과 다른 경우
* reverse DNS 조회 결과가 대응되는 forward DNS 조회 결과와 일치하지 않는 경우

Spectrum 애플리케이션에는 reverse DNS 엔트리가 없습니다.

또한 SMTP 서버는 도메인의 MX 레코드를 찾기 위해 DNS 조회를 수행할 수 있습니다. 도메인의 MX 레코드가 Spectrum 애플리케이션에 연결되어 있다면 서버의 IP 주소가 Spectrum IP 주소와 일치하지 않으므로 서버에서 보낸 메시지가 거부될 수 있습니다.

## 포트

Cloudflare는 모든 TCP 포트를 지원합니다.

## 포트 범위

Spectrum 애플리케이션은 포트 범위에 대해 트래픽을 프록시하도록 구성할 수 있습니다.

직접 origin의 경우:

```json
{
  "protocol": "tcp/1000-2000",
  "dns": {
    "type": "CNAME",
    "name": "range.example.com"
  },
  "origin_direct": ["tcp://192.0.2.1:3000-4000"]
}
```

DNS origin의 경우:

```json
{
  "protocol": "tcp/1000-2000",
  "dns": {
    "type": "CNAME",
    "name": "range.example.com"
  },
  "origin_dns": {
    "name": "origin.example.com",
    "ttl": 1200
  },
  "origin_port": "3000-4000"
}
```

origin 포트 범위의 포트 수는 `protocol` 필드에 지정한 포트 수와 일치해야 합니다.
엣지의 포트 범위 안 특정 포트로 들어온 연결은 origin 범위에서 동일한 오프셋의 포트로 프록시됩니다.
예를 들어 위 구성에서 `range.example.com:1005`로 들어온 연결은 origin의 3005 포트로 프록시됩니다.

## IP Access rules

Spectrum 애플리케이션에 대해 IP Access rules가 활성화되어 있으면 Cloudflare는 해당 도메인에 대해 **Security** > **WAF** > **Tools** 아래에서 생성한 IP Access rules를 적용합니다. Cloudflare는 Spectrum 애플리케이션에 대해 특정 IP 주소, IP 블록, 국가 또는 ASN에 대해 만든 규칙만 존중합니다. 또한 Spectrum은 `allow` 또는 `block` 작업으로 생성한 규칙만 적용합니다.

:::note
Spectrum의 네트워크 분석 데이터에는 IP Access rules의 결과가 반영되지 않습니다. 대신 이러한 규칙에 따라 트래픽이 허용되었는지 차단되었는지 확인하려면 Spectrum 이벤트 로그를 확인하세요.
:::

## Argo Smart Routing

애플리케이션에 대해 Argo Smart Routing이 활성화되면 트래픽은 자동으로 가장 빠르고 가장 신뢰할 수 있는 네트워크 경로를 통해 라우팅됩니다. Argo Smart Routing은 TCP 및 UDP(beta) 애플리케이션에서 사용할 수 있습니다.

## Edge TLS 종료

Spectrum 애플리케이션에서 **Edge TLS Termination**을 활성화하면 Cloudflare는 엣지에서 해당 애플리케이션의 트래픽을 암호화합니다. Edge TLS Termination 토글은 TCP 애플리케이션에만 적용됩니다.

Spectrum은 TLS 종료 모드 세 가지를 제공합니다: 'Flexible', 'Full', 'Full (Strict)'.

'Flexible'은 엣지에서 클라이언트 연결을 종료할 수 있게 하지만, Cloudflare에서 origin으로의 TLS는 활성화하지 않습니다. 트래픽은 클라이언트에서 Cloudflare까지는 암호화되지만, Cloudflare에서 origin까지는 암호화되지 않습니다.

'Full'은 Cloudflare에서 origin까지의 트래픽도 암호화하되 인증서는 검증하지 않는다는 뜻입니다. 'Full (Strict)'로 설정하면 Cloudflare에서 origin까지의 트래픽도 암호화되며 origin 인증서를 엄격하게 검증합니다.

Spectrum이 지원하는 TLS 버전은 TLS 1.1, TLS 1.2, TLS 1.3입니다.

이는 Cloudflare dashboard의 Spectrum 앱이나 [Spectrum API endpoint](/api/resources/spectrum/subresources/apps/methods/update/)를 사용해 관리할 수 있습니다.

:::note[Note]

TLS termination 설정이 **off**로 구성되어 있으면 Spectrum은 복호화하지 않은 채 origin으로 연결을 프록시합니다. 이 경우 제시되는 인증서는 Cloudflare Edge Certificate이 아니라 origin 서버에 설치된 인증서입니다.

:::

## Origin TLS 종료

아래는 SSL/TLS 핸드셰이크 중 Cloudflare가 origin에 제시하는 cipher suites입니다. 엣지에서 지원되거나 브라우저 및 기타 user agent에 제시되는 cipher suites는 [Cipher suites](/ssl/edge-certificates/additional-options/cipher-suites/)를 참고하세요.

아래 cipher suites는 ClientHello에 나타나는 순서대로 정렬되어 있으며, 이를 통해 origin에 대한 Cloudflare의 선호를 전달합니다. 고객은 Spectrum에서 사용하는 cipher를 수정할 수 없습니다.

## 프로토콜별 지원되는 cipher suites

| OpenSSL Name                      | TLS 1.1 | TLS 1.2 | TLS 1.3 |
| --------------------------------- | ------- | ------- | ------- |
| AEAD-AES128-GCM-SHA256[^1]        | ❌       | ❌       | ✅       |
| AEAD-AES256-GCM-SHA384[^1]        | ❌       | ❌       | ✅       |
| AEAD-CHACHA20-POLY1305-SHA256[^1] | ❌       | ❌       | ✅       |
| ECDHE-ECDSA-AES128-GCM-SHA256     | ❌       | ✅       | ❌       |
| ECDHE-RSA-AES128-GCM-SHA256       | ❌       | ✅       | ❌       |
| ECDHE-RSA-AES128-SHA              | ✅       | ✅       | ❌       |
| AES128-GCM-SHA256                 | ❌       | ✅       | ❌       |
| AES128-SHA                        | ✅       | ✅       | ❌       |
| AES256-SHA                        | ✅       | ✅       | ❌       |

[^1]: TLS 1.3은 이전 TLS 버전과 동일한 cipher suite 공간을 사용하지만, TLS 1.3 cipher suites는 다르게 정의되어 대칭 cipher만 지정하며 TLS 1.2에서는 사용할 수 없습니다. 마찬가지로 TLS 1.2 이하의 cipher suites는 TLS 1.3에서 사용할 수 없습니다([RFC 8446](https://www.rfc-editor.org/rfc/rfc8446.html)). BoringSSL도 TLS 1.3에 대해 이 순서로 cipher 선호를 하드코딩합니다. 자세한 내용은 [TLS 1.3 cipher suites](/ssl/origin-configuration/cipher-suites/#tls-13-cipher-suites)를 참고하세요.
