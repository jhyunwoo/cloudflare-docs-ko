프로토콜은 장치 간 데이터 교환 또는 전송을 지배하는 규칙의 집합입니다. 애플리케이션이 네트워크 서비스에 접근할 수 있는 인간-컴퓨터 상호작용 계층에서 동작하는 가장 중요한 프로토콜 중 하나는 HTTP(Hypertext Transfer Protocol)입니다.

HTTP는 잘 정립된 프로토콜이며 여러 버전이 존재합니다. 각 버전은 이전 버전에 비해 성능을 개선하는 기능을 추가합니다. HTTP/1.1과 HTTP/2는 오늘날 인터넷에서 널리 배포되어 있습니다. HTTP/1.1은 10년이 넘는 기간 동안 사용되어 왔지만, 2015년에 IETF(Internet Engineering Task Force)가 HTTP/2를 도입했으며, HTTP/2는 페이지 로드 시간을 줄이기 위한 여러 기능을 제공합니다. HTTP/1.1과 HTTP/2의 차이점에 대해 더 자세히 알고 싶다면 [HTTP/2 versus HTTP/1.1](https://www.cloudflare.com/learning/performance/http2-vs-http1.1/)을 참고하세요.

## 오리진으로의 HTTP/2 비활성화

Cloudflare에서는 기본적으로 오리진으로의 HTTP/2 연결이 활성화되어 있습니다.

오리진으로의 HTTP/2를 비활성화하려면 다음 단계를 따르세요.

1. Cloudflare 대시보드에서 **Speed** > **Settings** 페이지로 이동합니다.

   <DashButton url="/?to=/:account/:zone/speed/optimization" />

2. **Protocol Optimization** 탭으로 이동한 다음 **HTTP/2 to Origin** 아래에서 토글을 **Off**로 설정합니다.

## 연결 멀티플렉싱

Cloudflare는 전 세계 엣지 네트워크에서 오리진 서버까지 HTTP/2 멀티플렉싱을 지원합니다. 들어오는 요청마다 새 TCP 연결을 여는 대신, 여러 HTTP/2 스트림이 하나의 장시간 유지되는 TCP 연결을 공유합니다. 이렇게 하면 연결 설정과 종료에 드는 비용이 크게 줄어들어 Cloudflare와 오리진 사이의 효율성과 성능이 향상됩니다.

많은 요청을 더 적은 수의 TCP 연결로 풀링함으로써, Cloudflare는 오리진이 유지해야 하는 활성 연결 수를 줄여 줍니다. 이는 특히 연결 오버헤드나 리소스 제한에 민감한 백엔드에서 더욱 큰 가치를 제공합니다.

### 작동 방식

새 요청이 도착하면 Cloudflare는 기존 HTTP/2 오리진 연결을 재사용하려고 시도합니다.

- 연결이 동시 스트림 한도에 도달하지 않았다면, Cloudflare는 동일한 연결 위로 해당 요청을 멀티플렉싱합니다.
- 스트림 한도에 도달했다면, Cloudflare는 필요에 따라 새 TCP 연결을 엽니다.

연결은 유휴 상태가 되거나 동시성 한도에 도달할 때까지 유지되고 재사용됩니다.

#### 연결 수명 주기

- **연결 재사용**: Cloudflare는 오리진에 대해 지속적(keep-alive) TCP 연결을 유지합니다. HTTP/2 스트림 한도에 도달하거나 연결이 유휴 상태가 될 때까지 재사용이 계속됩니다.

- **유휴 타임아웃(900초)**: 연결이 900초 동안 유휴 상태(활성 스트림 없음)로 유지되면 Cloudflare가 이를 닫습니다. 닫힌 연결을 재사용하려고 하면 `520` 오류가 발생할 수 있습니다.

- **Keep-alives**: Cloudflare는 응답하지 않는 오리진을 감지하기 위해 주기적으로 TCP keep-alive를 보냅니다. 두 번의 프로브에 응답하지 않으면 연결이 재설정됩니다.

	- 약 30초 동안 비활성 상태가 지속된 뒤 첫 번째 프로브 전송
	- 15초 후 두 번째 프로브 전송

- **연결 종료**: 다음과 같은 이유로도 연결이 닫힐 수 있습니다.

	- 로드 밸런싱 결정
	- 데이터 센터 또는 노드 유지 관리
	- 최대 동시성 한도 도달
	- 오리진 또는 중간 네트워크가 유휴 연결을 닫는 경우

### 장점

| 장점 | 설명 |
|------------------------|---------------------------------------------------------------------------------------------------|
| 더 적은 TCP 핸드셰이크 | 여러 요청이 하나의 장시간 유지되는 TCP 연결을 공유하므로 연결 생성과 종료가 최소화됩니다. |
| 더 낮은 지연 시간 | 반복적인 TCP/TLS 핸드셰이크를 제거해 새 요청의 왕복 지연 시간을 줄입니다. |
| 오리진 부하 감소 | 오리진이 관리해야 하는 동시 연결 수가 줄어들어 리소스가 제한된 시스템의 부담을 완화합니다. |
| 적응형 확장 | 급증 상황(예: 장애 조치)에서는 Cloudflare가 먼저 사용 가능한 스트림을 재사용한 뒤 필요에 따라 새 연결을 엽니다. |

### 플랜별 기본 동작

| 플랜 | 기본 상태 | 연결당 최대 동시 스트림 수 | 구성 가능 여부 |
|--------------------------|-----------------------------------------------|----------------------------------------|---------------|
| Free / Pro / Business | 기본적으로 활성화 | 200 | 아니요 |
| Enterprise | 기본적으로 비활성화(연결당 스트림 1개) | 1-200+ | 예 |

- **Free/Pro/Business**: 멀티플렉싱이 자동으로 활성화됩니다. 각 연결은 최대 200개의 동시 스트림을 지원합니다.
- **Enterprise**: 멀티플렉싱은 사실상 비활성화된 상태(스트림 1개)로 시작합니다. 대시보드나 API를 통해 zone별 동시성을 활성화하고 구성할 수 있습니다(최대 200개 이상의 동시 스트림).

### 구성

연결 멀티플렉싱은 Free, Pro, Business zone에서 기본적으로 활성화되어 있으며, 기본적으로 최대 100개의 동시 스트림을 사용합니다. Enterprise 플랜은 대시보드 또는 API에서 zone별 최대 동시 스트림 수(일반적으로 "멀티플렉싱 비율"이라고 부름)를 명시적으로 구성할 수 있습니다.

:::note
오리진이 멀티플렉싱을 지원하지 않으면 오리진으로의 HTTP/2를 활성화했을 때 5xx 오류, 특히 520 오류가 발생할 수 있습니다.

HTTP/2 핸드셰이크 중에 Cloudflare 엣지는 오리진이 광고하는 SETTINGS_MAX_CONCURRENT_STREAMS 값을 읽고, 오리진이 Cloudflare 설정보다 더 엄격한 동시성 상한을 구성한 경우 해당 더 낮은 한도를 존중합니다. 이를 통해 고객은 Cloudflare의 멀티플렉싱 프레임워크의 이점을 유지하면서 오리진별로 동시성을 제어할 수 있습니다.
:::

### 타임아웃과 오류 코드

| 조건 | 기본값 / 범위 | 오류 코드 | 설명 |
|-------------------------|----------------------------------------|------------|-------------------------------------------------------|
| Proxy Read Timeout | 100초 (Enterprise는 최대 6000초) | `524` | 오리진이 응답하는 데 너무 오래 걸렸습니다. |
| Proxy Idle Timeout | 900초 (고정) | `520` | 유휴 상태 때문에 연결이 닫혔습니다. |
| TCP Keep-Alive Interval | 최초 30초, 프로브 사이 15초 | `520` | 두 번의 프로브를 놓치면 Cloudflare가 연결을 재설정합니다. |
| TCP Handshake Timeout | 19초 | `522` | 오리진이 SYN 핸드셰이크를 완료하지 않았습니다. |
| TCP ACK Timeout | 90초 | `522` | 오리진이 데이터에 대한 확인 응답을 중단했습니다. |

### 일반적인 시나리오

**장애 조치 이벤트**

트래픽이 갑자기 이동할 때(예: 오리진 장애 조치 중) Cloudflare는 가능한 경우 활성 연결을 재사용합니다. 동시성 한도에 도달하면 새 연결을 엽니다. 활성 연결 수는 일시적으로 급증할 수 있지만, 전체 연결 수는 멀티플렉싱이 없을 때보다 전반적으로 더 낮게 유지됩니다.

**장시간 유지되거나 유휴 상태인 요청**

	- 요청이 100초를 초과하는 경우(예: 스트리밍), Proxy Read Timeout을 늘리세요(Enterprise 전용).
	- 900초보다 더 빨리 연결을 닫는 오리진은 연결 churn이 발생할 수 있지만, Cloudflare는 필요에 따라 자동으로 새 연결을 다시 설정합니다.

**잠재적 5xx 오류**

`520`이나 `522` 같은 일부 5xx 오류는 유휴 타임아웃 또는 도달할 수 없는 오리진과 관련될 수 있습니다. 동시성 값을 너무 높게 설정하면 성능이 낮은 오리진이 동시에 발생한 요청 burst를 감당하지 못해 스트림 재설정이나 일시적인 5xx 오류 급증이 발생할 수 있습니다. 이러한 문제를 겪는 Enterprise 고객은 Cloudflare 계정 팀이나 지원팀에 동시성 한도를 낮춰 달라고 요청할 수 있습니다. 그러면 동일한 시점에 오리진으로 전송되는 요청 수가 줄어들어 과부하를 방지하는 데 도움이 됩니다.

### FAQ

#### Cloudflare는 고정된 멀티플렉싱 비율을 사용하나요?

Free, Pro, Business 플랜은 연결당 200개의 동시 스트림을 사용합니다. Enterprise 사용자는 1~200개 이상의 스트림을 구성할 수 있습니다.

#### 급증이나 장애 조치 시 Cloudflare는 어떻게 연결을 확장하나요?

Cloudflare는 먼저 기존 keep-alive 연결을 재사용합니다. 이 연결들이 동시성 한도에 도달하면 필요에 따라 새 연결을 엽니다. 급증 중에도 전체 연결 수는 일반적으로 멀티플렉싱이 없을 때보다 낮습니다.

#### 백엔드가 병렬 요청에 민감하다면 어떻게 해야 하나요?

Enterprise 사용자는 동시성 한도를 낮출 수 있습니다. Cloudflare는 또한 오리진의 `SETTINGS_MAX_CONCURRENT_STREAMS`도 존중하므로, 서버가 더 엄격한 한도를 강제할 수 있습니다. Cloudflare CDN은 재검증 중 오리진으로 여러 병렬 요청이 가는 상황을 방지하는 Cache Locking 기능도 제공합니다. 자세한 내용은 [Revalidation](/cache/concepts/revalidation/)을 참고하세요.

#### 더 높은 동시성을 점진적으로 롤아웃할 수 있나요?

예. 오리진의 HTTP/2 설정이나 Cloudflare zone 설정을 점진적으로 조정하여 안전하게 동시성을 높일 수 있습니다.

#### Cloudflare는 어느 위치에서 오리진에 연결하나요?

Cloudflare는 평면형(anycast) 네트워크를 운영합니다. 어느 데이터 센터든 오리진에 직접 연결할 수 있으며, L1/L2 계층 구조는 없습니다. 오리진 연결은 전 세계 여러 데이터 센터에서 올 수 있습니다.

#### Cloudflare는 오리진 연결을 미리 예열(prewarm)하나요?

아니요. 연결은 필요할 때 생성되고 가능한 경우 재사용됩니다. 지속적으로 유휴 상태인 연결 풀은 존재하지 않습니다.

#### 유휴 연결은 어떻게 관리되나요?

유휴 연결은 900초 동안 비활성 상태가 지속되면 닫힙니다. 사전에 다시 열리지는 않으며, 트래픽이 재개되면 새 연결이 생성됩니다.

#### Cloudflare가 활성 TCP 연결을 닫을 수 있나요?

오리진이 연결을 닫거나 네트워크 오류가 발생하거나 Cloudflare가 유지 관리 또는 부하 재분산을 수행하는 경우에만 가능합니다. 활성 연결의 최대 수명에는 고정된 하드 한도가 없습니다.


## 프로토콜 호환성

오리진이 HTTP/2를 지원하지 않으면 Cloudflare는 HTTP/1.1 연결을 시작합니다.
Cloudflare는 [ALPN](https://blog.cloudflare.com/introducing-http2)을 통해 HTTP/2 연결 지원을 알리는 서버에 연결합니다.

서버가 HTTP/2를 지원하는지 확실하지 않다면, 오리진 서버 문서를 확인하거나 HTTP/2 구현 테스트 도구(예: [h2spec](https://github.com/summerwind/h2spec))를 사용하는 것을 권장합니다.
