## Zero Trust 도메인을 사용하여 WARP 클라이언트를 등록하려고했지만 다음 오류 메시지를 받았습니다.`Authentication Expired`·`Registration error. Please try again later`.

사용자가 조직으로 로그인할 때 WARP는 웹 페이지를 열고 Cloudflare Access를 통해 로그인할 수 있습니다. 액세스는 웹 페이지에서 WARP 클라이언트로 전달되는 JSON Web Token (JWT)을 생성하여 장치를 인증합니다. 이 JWT는 정확한 시간을 나타내는 타임 스탬프를 가지고 있으며, 타임 스탬프는 향후 50 초 동안 만료됩니다.

이 오류 메시지는 JWT가 마지막으로 WARP 클라이언트로 전달되면 이미 만료되었습니다. 두 가지 중 하나는 일어날 수 있습니다 :

1. (확대): 컴퓨터 시스템 시계는 네트워크 시간 의정서 (NTP)를 사용하여 제대로 동기화되지 않습니다. 기타[사이트맵](https://time.is)당신의 시계를 유효하게 하는 영향 받은 기계에 제대로 실제적인 시간의 20 초 안에 동기화됩니다.

2. Cloudflare WARP를 열려면 1 분 이상 기다리십시오. 즉시 WARP 클라이언트를 엽니다.

## 나는 웹 사이트를 차단하고, 그것은 할 수 없습니다.

도메인이 잘못 차단 된 것을 믿는 경우, 당신은 사용할 수 있습니다[이 양식](https://radar.cloudflare.com/categorization-feedback/)URL을 검토합니다.

## 나는 오류를보고`No Access-Control-Allow-Origin header is present on the requested resource`.

사이트맵 접근은 자격 증명을 요구합니다:`same-origin parameter`Fetch API를 사용할 때 JavaScript에 추가됩니다. AJAX 요청은 이 매개 변수 없이 실패합니다. 더 많은 정보를 원하시면, 우리의 문서 참조[CORS 설정](/cloudflare-one/access-controls/applications/http-apps/authorization-cookie/cors/).

## 나는 모든 페이지에 대한 신뢰할 수없는 인증서 경고를보고 인터넷을 검색 할 수 없습니다.

HTTPS 트래픽 검사를 포함한 고급 보안 기능은 사용자가 Cloudflare 루트 인증서를 설치하고 신뢰할 수 있습니다. 모든 장치에서 인증서를 수동으로 설치하면이 단계는 HTTP 필터링에 따라야합니다.
Cloudflare 루트 인증서를 설치하려면 다음을 따르십시오.[이 가이드](/cloudflare-one/team-and-resources/devices/user-side-certificates/).

## 웹 사이트에 탐색 할 때 오류 526을 참조하십시오.

Gateway는**HTTP 응답 코드: 526**다음 경우에는 오류 페이지:

- **위탁되지 않은 인증서는 Gateway의 기원에서 제시됩니다.**&#xAC8C;이트웨이는 이러한 조건이 true인 경우 인증서가 위탁되지 않습니다.
  - 서버 인증서 발급자는 알 수 없거나 서비스에 의해 신뢰할 수 없습니다.
  - 서버 인증서가 개정되고 CRL 체크가 실패합니다.
  - 서버 인증서에 대한 인증서 체인에 적어도 하나의 만료 된 인증서가 있습니다.
  - 인증서의 일반적인 이름은 도달하려고하는 URL과 일치하지 않습니다.
  - 인증서의 일반적인 이름은 잘못된 문자 (fromscores와 같은)를 포함합니다. Gateway 사용[보링SSL](https://csrc.nist.gov/projects/cryptographic-module-validation-program/validated-modules/search?SearchMode=Basic\&Vendor=Google\&CertificateStatus=Active\&ValidationYear=0)인증서를 검증합니다. 크롬의[검증 논리](https://chromium.googlesource.com/chromium/src/+/refs/heads/main/net/cert/x509_certificate.cc#429)WARP를 끄면 웹 사이트가 로드될 수 있는 이유가 아닌 RFC 1305 호환 인증서를 허용합니다.

- **Gateway의 연결은 insecure입니다.**&#x47;ateway는 다음과 같은 원산지를 신뢰하지 않습니다.
  - RC4, RC4-MD5 또는 3DES와 같은 insecure cipher 스위트 만 제공하십시오. 당신은 사용할 수 있습니다[SSL 서버 테스트 도구](https://www.ssllabs.com/ssltest/index.html)ciphers가 근원에 의해 지원되는 것을 확인하기 위하여.
  - 지원하지 않음[FIPS-compliant 수석](/cloudflare-one/traffic-policies/http-policies/tls-decryption/#cipher-suites)(당신이 활성화한 경우[FIPS 준수 모드](/cloudflare-one/traffic-policies/http-policies/tls-decryption/#fips-compliance)). 페이지를로드하려면 FIPS 모드를 비활성화하거나이 호스트에 대한 검사 정책을 만들 수 있습니다 (이 기원에 대한 FIPS 준수를 비활성화하는 효과).
  - HTTP에 모든 HTTPS 요청을 다시 시작합니다.

위의 시나리오가 적용되지 않은 경우, 다음 정보와 Cloudflare 지원을 접촉:

- 운영 체제 (Windows 10, macOS 10.x, iOS 14.x)
- 웹 브라우저 (Chrome, Firefox, Safari, Edge)
- 요청의 URL
- 오류 페이지의 내용의 스크린 샷 또는 복사 / 붙여 넣기

더 많은 문제 해결 정보, 참조[지원하다](/support/troubleshooting/http-status-codes/cloudflare-5xx-errors/error-526/).

## Gateway Overview 페이지의 오류를 보고 분석이 표시되지 않습니다.

![Analytics 대신 Gateway Overview 페이지에 표시된 오류.](~/assets/images/cloudflare-one/faq/gateway-dash-overview-empty.png)

당신은 다음과 같은 이유로 개요 페이지에서 분석을 볼 수 없습니다 :

- **DNS 쿼리를 Gateway로 전송하지 않습니다.**. DNS 쿼리를 전송하는 대상 IP 주소가 올바른지 확인합니다. DNS 위치에 대한 대상 IP 주소를 확인할 수 있습니다.**네트워크** > **해결사 및 Proxies** > **DNS 위치**그리고 그 후 위치를 확장.
- **다른 DNS 해결자를 사용하고 있습니다.**. DNS 설정에서 다른 DNS 해결자가 있는 경우, 기기는 게이트웨이의 일부가 아닌 해결자에게 IP 주소를 사용할 수 있습니다. DNS 설정에서 다른 모든 IP 주소를 제거하고 Gateway의 DNS 해결 IP 주소를 포함해야합니다.
- **DNS 위치에 대한 소스 IPv4 주소는 잘못**. 만약 IPv4를 사용한다면, 네트워크 소스 IPv4 주소와 일치하는 DNS 위치에 입력된 소스 IPv4 주소를 확인합니다.
- **Analytics는 아직 사용할 수 없습니다.**. Cloudflare Gateway에 대한 분석을 생성하는 데 시간이 걸립니다. 5 분 후에도 아무것도 볼 수없는 경우 지원 티켓을 제출하십시오.

## "Maximum Sessions Reached" 경고를 참조하십시오.

장치가 두 개 이상의 원격 브라우저 인스턴스에 연결을 설정하려고 시도하면 발생할 수 있습니다.
브라우저 고립 세션은 로컬 브라우저에서 원격 브라우저에 연결됩니다. 같은 브라우저 내에서 탭과 창은 단일 원격 브라우저 세션을 공유합니다. 실제로 Chrome과 Firefox를 모두 열 수 있지만 Opera와 같은 세 번째 브라우저를 열려고 시도는이 경고가 나타납니다. 브라우저 세션을 해제하려면 로컬 브라우저에서 모든 탭/창을 닫습니다. 원격 브라우저 세션은 15 분 안에 자동으로 종료됩니다.

## 나는`SAML Verify: Invalid SAML response, SAML Verify: No certificate selected to verify`SAML ID 공급자를 테스트할 때.

ID 공급자가 SAML 응답에 있는 표시 공공 열쇠를 포함하지 않은 경우 이 오류가 발생합니다. SAML 2.0 사양에 의해 요구되는 동안 Cloudflare 액세스는 항상 공개 키가 일치한다는 것을 확인합니다.**서명 인증서**Zero Trust에 업로드. 통합을 위해, 당신은 당신의 정체성 공급자를 구성해야 공공 키를 추가합니다.

## 나는`Error 0: Bad Request. Please create a ca for application.`SSH에 연결하려고 할 때 부족한 인증서.

이 오류는 액세스 응용 프로그램에 대한 인증서가 생성되지 않은 경우 나타납니다. Access Service Auth SSH 페이지의 응용 프로그램에 대한 인증서를 생성하는 방법에 대한 자세한 내용은 참조[이 지침](/cloudflare-one/access-controls/applications/non-http/short-lived-certificates-legacy/).

## 내 시스템에 Cloudflare 인증서를 설치하더라도 무효 인증서의 모바일 응용 프로그램은 경고.

이 모바일 애플리케이션은 사용할 수 있습니다.<GlossaryTooltip term="certificate pinning">인증 핀닝</GlossaryTooltip>사이트맵 Gateway dynamically는 HTTP 트래픽의 내용을 검사하기 위해 모든 암호화 된 연결을 위해 인증서를 생성합니다. 이 인증서는 인증서 핀닝을 사용하는 응용 프로그램에 의해 예상된 인증서와 일치하지 않습니다.
이 응용 프로그램을 정상적으로 기능할 수 있도록, 관리자는 방해 및 검사에서 응용 프로그램과 관련된 트래픽을 면제하는 우회 규칙을 구성 할 수 있습니다.

## Linux 쇼에서 WARP`DNS connectivity check failed`.

이 오류는`systemd-resolved`Linux의 서비스는 WARP가 DNS 요청을 해결할 수 없습니다. 이 문제를 확인할 수 있습니다.[`daemon.log`](/cloudflare-one/team-and-resources/devices/warp/troubleshooting/warp-logs/#warp-diag-logs)파일의`warp diag`로그인, 오류 메시지가 나타나는 곳`ERROR main_loop: warp::warp::connectivity_check: DNS connectivity check failed to resolve host="warp-svc."`.

문제를 해결하려면:

1. 다음 줄을 추가`/etc/systemd/resolved.conf`:

```txt
ResolveUnicastSingleLabel=yes
```

2. 다른 DNS 서버가 구성되지 않음`/etc/systemd/resolved.conf`. 예를 들어, 파일이 포함 된 경우`DNS=X.Y.Z.Q`, 선을 밖으로 의견.

3. 서비스 재시작:

```sh
sudo systemctl restart systemd-resolved.service
```

## Windows 잘못된 쇼`No Internet access`WARP가 활성화되면

[사이트맵](https://learn.microsoft.com/en-us/windows-server/networking/ncsi/ncsi-overview)네트워크 품질 및 연결을 결정하기위한 Windows 기능입니다. WARP가 활성화될 때, NCSI 체크는 때때로 실패할 수 있고 사용자가 장치가 아직도 가득 차있는 연결이더라도 인터넷이 없는 화장품 UI 오류를 일으키는 원인이 됩니다. 일부 앱 (Outlook, JumpCloud)는 Windows가 인터넷 연결이 없기 때문에 연결하지 않을 수 있습니다.

문제를 해결하려면 두 개의 Windows 레지스트리 키를 편집해야합니다.

1. WARP의 검출 NCSI 구성[로컬 DNS 프록시](/cloudflare-one/team-and-resources/devices/warp/configure-warp/route-traffic/warp-architecture/#dns-traffic).

   ```txt
   HKEY_LOCAL_MACHINE\SOFTWARE\POLICIES\MICROSOFT\Windows\NetworkConnectivityStatusIndicator
   Type: DWORD
   Value: UseGlobalDNS
   Data: 1
   ```

2. WARP로 활성 프로빙 모드를 사용하려면 NCSI를 구성하면 홉의 수를 고려할 수 있습니다.[수동 프로브](https://learn.microsoft.com/en-us/windows-server/networking/ncsi/ncsi-frequently-asked-questions#how-does-passive-probing-determine-connectivity).

   ```txt
   HKEY_LOCAL_MACHINE\SYSTEM\CurrentControlSet\Services\NlaSvc\Parameters\Internet
   Type: DWORD
   Value: EnableActiveProbing
   Data: 1
   ```

Microsoft 365 응용 프로그램에 문제가 계속되면 활성화하십시오.[**직접 경로 Microsoft 365 트래픽**](/cloudflare-one/team-and-resources/devices/warp/configure-warp/warp-settings/#directly-route-microsoft-365-traffic).

## 나는`WebGL Rendering Error`.

Cloudflare Browser Isolation는 네트워크 벡터 렌더링 (NVR) 기술을 활용합니다. 이것은 보안을 제공 할 수 있습니다, 기존 솔루션의 대역폭 제한없이 실행 된 원격 컴퓨팅 경험. WebGL (Web Graphics Library)와 같은 브라우저 기능과 웹 기술을 완벽하게 작동하려면 대부분의 웹 사이트를 기대합니다.

WebGL은 플러그 인의 사용없이 호환 웹 브라우저 내에서 고성능 대화 형 2D 및 3D 그래픽을 렌더링하기위한 JavaScript API입니다. WebGL은 모든 현대 브라우저에서 지원됩니다. 그러나 사용자의 장치는 또한 underlying에 접근해야 합니다[회사 소개](https://developer.mozilla.org/en-US/docs/Web/API/WebGL_API#browser_compatibility)이 기능을 지원합니다.

원격 브라우저가 가상화 환경에 미치는 영향을 실행할 때 사용자는 필요한 시스템 리소스에 액세스할 수 없습니다. 오류를 해결하려면, GPU에 의해 제공 된 하드웨어 가속을 사용하지 않고 소프트웨어를 통해 벡터 그래픽을 완전히 렌더링하는 브라우저를 구성 할 수 있습니다.

소프트웨어 rasterization를 가능하게 하기 위하여:

1. 오시는 길`chrome://flags/#override-software-rendering-list`.

## 나는`502 Bad Gateway`웹 사이트 탐색.

이 문제는 부분적으로 HTTP / 2를 지원하는 근원과 통신 할 때 발생할 수 있습니다. 이 시나리오에서 Gateway에서 웹 사이트로의 연결은 HTTP / 2를 사용하지만 일부 요청에 대한 HTTP / 1.1로의 다운 그레이드를 요청합니다. 예를 들어, 같은 서버[Microsoft 인터넷 정보 서비스 (IIS)](https://learn.microsoft.com/iis/get-started/whats-new-in-iis-10/http2-on-iis#when-is-http2-not-supported)HTTP/2에 인증이 지원되지 않습니다. 오류가 발생하면 웹 사이트를 다시 보낼 수 있습니다.`RST_STREAM`오류 코드와 프레임`HTTP_1_1_REQUIRED`브라우저가 HTTP/1.1에 요청을 다시 구해야 하는 것을 나타냅니다. Gateway는 수신된 업스트림을 번역합니다.`RST_STREAM`가짜 소켓 가까이에 프레임, 그래서이 나타납니다`502 Bad Gateway`예외 페이지. 브라우저가 실패한 이유를 나타내지 않습니다.

Gateway는 이 downgrade 기계장치를 지원하지 않습니다. 수신할 때`HTTP_1_1_REQUIRED`오류 코드, 게이트웨이는 HTTP/1.1에 재발행 요청이 없습니다. Gateway에서 웹 사이트에 연결하기 위해, 당신은 원래 HTTP / 2를 비활성화해야합니다.

API 액세스와 관련된 모든 denied 요청을 식별하기 위해 ID 공급자의 로그를 확인할 수 있습니다.

## WSL2는 WARP를 사용할 때 연결성을 잃습니다.

WSL2 환경이 WARP를 사용하여 연결성을 잃는 경우, 확인[분할 터널 구성](/cloudflare-one/team-and-resources/devices/warp/configure-warp/route-traffic/split-tunnels/).

문제는 WSL 환경이 호스트 장치와 통신하는 IP 범위가 분할 터널 구성에 포함되어 있기 때문에 발생 할 수 있습니다. WSL 환경의 IP 범위를 초과하면 연결성을 복원해야합니다.

호스트 장치는 WSL과 호스트 장치 사이의 연결 문제를 방지하기 위해 WSL 환경을 제외하고 WARP 터널에 포함되어 있어야 합니다.

이 문제를 디버그하려면:

1. WSL2 환경의 IP 주소를 검토하고 노트북의 IP와 비교하십시오.
2. WSL 네트워크가 있는지 확인[분할 터널 구성에 포함](/cloudflare-one/team-and-resources/devices/warp/configure-warp/route-traffic/split-tunnels/#change-split-tunnels-mode).
3. WSL 네트워크가 포함되어 있다면, 분할 터널에서 연결 문제를 방지합니다.

## Clientless Web Isolation는 Windows 장치에서 공백 스크린으로 적재됩니다.

이 문제는 브라우저 설정과 Windows 네트워크 구성 간의 충돌로 발생할 수 있습니다.

Chrome 및 Edge와 같은 Chromium 기반 브라우저에서**WebRTC에 의해 노출 된 지역 IP를 익명화**플래그 (`chrome://flags/#enable-webrtc-hide-local-ips-with-mdns`또는`edge://flags/#enable-webrtc-hide-local-ips-with-mdns`) — 설정할 때`Enabled`또는 왼쪽`Default`— mDNS hostnames로 대체하여 로컬 IP 주소를 숨깁니다. Multicast DNS (mDNS) 호스트명은 로컬 네트워크에서 제대로 해결되는 멀티캐스트 트래픽에 의존합니다.

더 보기[인터넷 그룹 관리 프로토콜 (IGMP)](https://www.cloudflare.com/learning/network-layer/what-is-igmp/)멀티캐스팅 그룹에 가입할 수 있습니다. Windows에서,`IGMPLevel`시스템가 멀티캐스트 그룹 멤버십에 참여 여부를 결정합니다. 시간 :`IGMPLevel`설정`0`, multicast 지원은 무능합니다.

이 오류를 해결하려면 다음 옵션을 검토하십시오.

| `IGMPLevel` | **WebRTC에 의해 노출 된 지역 IP를 익명화**설치하기 | Clientless Web Isolation의 결과     |
| ----------- | ---------------------------------- | -------------------------------- |
| `0`(장애)     | **/ 과태**                           | ❌ 빈 화면                           |
| `0`(장애)     | **지원하다**                           | ✅ Works - 브라우저는 로컬 IP 주소를 사용합니다. |
| `2`(유료)     | **/ 과태**                           | ✅ 작동 - mDNS는 성공적으로 해결            |

## 액세스 뒤에 Google Workspace를 입력 한 후 로그인 할 수 없습니다. 액세스와 Google 사이의 리디렉션을 유지하고 인증을 완료하지 않고.

액세스 뒤에 Google Workspace를 넣을 때 사용자는 ID 공급자로 Google 또는 Google Workspace를 사용하여 로그인 할 수 없습니다.

이 구성은 인증 루프를 만듭니다. 사이트맵 액세스는 Google을 통해 사용자를 인증하는 것입니다. 그러나 Google 자체는 Cloudflare를 ID 공급자로 취급하고 Cloudflare에서 인증을해야합니다. 각 시스템은 서로에 따라 로그인을 완료하기 위해 먼저, 사용자는 무한 리디렉션 사이클에 붙잡고 성공적으로 정통 할 수 있습니다.

## Windows에서 WARP를 설치하면 Setup Wizard가 조기 종료됩니다.

이 오류는 적절한 .NET Framework 버전 또는 기타 Dynamic Link Libraries (DLLs)와 같은 누락된 의존성을 포함하여 여러 가지 이유로 발생할 수 있습니다.`netstandard2.0`, 임명 도중 요구되는.

조사하려면 다음 명령을 실행하여 설치 로그를 생성합니다.

```powershell
msiexec /i <PATH_TO_WARP_MSI> /L*V <PATH_TO_OUTPUT_LOG>
```

누락된 DLLs (예를 들어,`netstandard2.0`), 누락되거나 .NET Framework의 버전이 나타날 수 있습니다.

한 가지 일반적인 원인은 누락 된 버전의[.NET Framework 실행 시간](/cloudflare-one/team-and-resources/devices/warp/download-warp/#windows:~:text=NET%20Framework%20version-,4.7.2%20or%20later,-HD%20space). Cloudflare WARP는 .NET Framework 버전을 요구합니다`4.7.2`또는 나중에.

일부 레거시 Windows 시스템 (Windows 10 Enterprise 1607 LTSB와 같은 .NET과 번들로`4.6`) 기본적으로 이 런타임을 포함하지 않으며 설치 중에 실패할 수 있습니다.`Setup Wizard ended prematurely`오류. 최근 Windows 버전에는 .NET이 포함됩니다.`4.7.2`또는 나중에 기본적으로이 오류를 발생하지 않습니다.

이 수정:

1. 다운로드 및 설치[.NET 프레임 워크 4.7.2 지원하다](https://dotnet.microsoft.com/en-us/download/dotnet-framework/net472)(설치해야 함)**지원하다**, 개발자 팩).
2. WARP 설치 프로그램을 다시 실행합니다.

문제가 계속되면, 실행 시도[.NET 수리 도구](https://www.microsoft.com/en-ca/download/details.aspx?id=30135), 또는 .NET 버전은 PowerShell의 다음 명령을 실행하여 설치됩니다:

```powershell
Get-ChildItem -Path "HKLM:\SOFTWARE\Microsoft\NET Framework Setup\NDP" -Recurse | ForEach-Object { $_.Name; Get-ItemProperty $_.PSPath; "" }
```

## 나는`Invalid session. Please try logging in again.`SSO를 통해 Cloudflare 대시보드에 로그인하려고 할 때 액세스 오류.

사이트맵 오시는 길[`CF_Session`제품 정보](/cloudflare-one/access-controls/applications/http-apps/authorization-cookie/#access-cookies)같은 브라우저가 시작되고 서명을 완료하는 것을 검증합니다. 더 보기`Invalid session`오류는 액세스가이 쿠키를 유효하지 못했습니다. 해당 기기 또는 네트워크에 소프트웨어 또는 방화벽이 없는 것을 보장하기 위해 요청을 통해 액세스할 수 있습니다.

## 긴 라이브 SSH 세션 자주 차단.

Cloudflare 게이트웨이를 통한 모든 연결[접근성 준수](/cloudflare-one/networks/connectors/cloudflare-tunnel/use-cases/ssh/ssh-infrastructure-access/)SSH 표적은 10 시간의 최대 보장한 기간이 있습니다. 10시간 이상 연결 가능 그러나 연결이 게이트웨이 릴리스의 시간에 활성화되면 게이트웨이가 나중에 연결 10 시간을 종료합니다. 릴리스는 예정되지 않으며 일주일에 여러 번 발생할 수 있습니다.

눈에 띄는 SSH 연결을 방지하기 위해 사전 정의 된 일정에 종료 세션을 권장합니다. 예를 들어, 8 시간 idle timeout을 설정할 수 있으므로 inactive sessions는 자동적으로 시간을 차단할 수 있습니다. idle timeout을 구성하려면`ChannelTimeout`SSH 서버 중 옵션 (`/etc/ssh/sshd_config`) 또는 클라이언트 구성 파일 (`~/.ssh/config`):

```txt
ChannelTimeout global=8h
```

회사연혁[`ChannelTimeout`클라이언트 측에](https://man.openbsd.org/ssh_config#ChannelTimeout)사용자가 그들을 위해 일하는 시간을 선택할 수 있습니다.[서버 측](https://man.openbsd.org/sshd_config#ChannelTimeout)최종 사용자의 구성 부담을 제거합니다.
