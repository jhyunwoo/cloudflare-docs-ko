## 관련 기사

행동은 특정 사용자 또는 사용자 그룹에 권한을 부여하거나 거부 할 수 있습니다. 당신은 정책 당 하나의 작업을 설정할 수 있습니다.

### 지원하다

허용 작업은 접근 뒤에 응용 프로그램에 도달 할 수있는 특정 기준을 충족 할 수 있습니다.

다음 예제는 사용자와 함께`@example.com`IdP에 대한 검증 된 이메일 주소, 응용 프로그램에 도달 :

| - 연혁 | 규칙 유형 | 옵션 정보 | 제품정보           |
| ---- | ----- | ----- | -------------- |
| 지원하다 | 이름 \* | 이메일:  | `@example.com` |

추가 체크를 시행하기 위해 동일한 정책 행동에 필요한 규칙을 추가 할 수 있습니다. 마지막으로, 정책이 예외적 인 규칙을 포함하면, 사용자 정의가 응용 프로그램에 도달에서 방지됩니다.

예를 들어,이 두 번째 구성은 포르투갈에서 모든 사용자를`@team.com`IdP에 대한 검증 된 이메일 주소, 응용 프로그램에 도달, 제외`user-1`·`user-2`:

| - 연혁 | 규칙 유형 | 옵션 정보      | 제품정보                                 |
| ---- | ----- | ---------- | ------------------------------------ |
| 지원하다 | 이름 \* | 이름 \*      | `Portugal`                           |
|      | 이름 \* | 이메일 Ending | `@team.com`                          |
|      | 이름 \* | 이름 \*      | `user-1@team.com`, `user-2@team.com` |

### 제품정보

Block action은 접근 뒤에 응용 프로그램에 도달하여 특정 critera를 충족하는 사용자를 방지합니다. 예를 들어, 다음 정책 블록은 러시아 소스 IPs에서 요청을 차단합니다.[승인 된 IP 목록](/cloudflare-one/reusable-components/lists/).

| - 연혁 | 규칙 유형 | 옵션 정보 | 제품정보                     |
| ---- | ----- | ----- | ------------------------ |
| 제품정보 | 이름 \* | 이름 \* | `Russian Federation`     |
|      | 이름 \* | IP 목록 | `Corporate IP allowlist` |

블록 정책과 함께 가장 잘 사용됩니다.[법적 고지](#allow)해당 이용 후기에 달린 코멘트가 없습니다. Access는 기본적으로 deny이므로 블록 정책과 일치하지 않는 사용자는 여전히 허용 정책과 일치하지 않는 한 액세스를 거부합니다.

### 비밀번호

:::카트로션\[Warning]

Bypass는 액세스 보안 제어 및 요청이 로그되지 않습니다. Bypass 정책은 생산에 배포하기 전에 테스트해야합니다. 자주 묻는 질문[서비스 Auth](/cloudflare-one/access-controls/policies/#service-auth)본 방침을 시행하고 사용자 인증을 요구하지 않고 로깅을 유지합니다.

Bypass는 액세스 보안 제어를 시행하지 않습니다. Bypass 정책은 ID 기반을 지원하지 않습니다.[규칙 유형](/cloudflare-one/access-controls/policies/#rule-types). Bypass 정책을 만들 때, 당신은 특정 정체성 기반을 적용 할 수 없습니다[회사 소개](/cloudflare-one/access-controls/policies/#selectors)(이메일 등).

:::

Bypass 행동은 정의된 규칙 기준을 충족하는 트래픽에 대한 액세스 집행을 비활성화합니다. Bypass는 일반적으로 특정 엔드포인트가 공개해야 하는 애플리케이션을 활성화하는 데 사용됩니다.

예를 들면, 몇몇 신청에는 아래에 endpoint가 있습니다`/admin`공개적으로 routable해야합니다 경로. 이 상황에서 도메인에 대한 액세스 응용 프로그램을 만들 수 있습니다`test.example.com/admin/<your-url>`그리고 다음 우회 정책을 추가:

| - 연혁 | 규칙 유형 | 옵션 정보 | 제품정보       |
| ---- | ----- | ----- | ---------- |
| 비밀번호 | 이름 \* | 한국어   | `Everyone` |

Zero Trust 보안 모델 구현의 일환으로 Cloudflare는 내부 애플리케이션에 직접 영구 액세스를 부여하는 우회를 사용하여 권장하지 않습니다. On-network 직원에 대한 원활하고 안전한 액세스를 가능하게하려면 Cloudflare Tunnel을 사용하십시오.[개인 네트워크 연결](/cloudflare-one/networks/connectors/cloudflare-tunnel/private-net/cloudflared/)WARP를 통해 사용자를 연결합니다.

:::참조

Bypass 동작을 적용할 때, 보안 설정은 영역과 구성된 페이지 규칙을 구성하는 기본으로 되돌아갑니다. 이름 \***항상 HTTPS를 사용**사이트가 활성화되어, 우회 대상에 대한 트래픽은 HTTPS에서 계속됩니다. 이름 \***항상 HTTPS를 사용**비활성화, 트래픽은 HTTP이다.

:::

## 규칙 유형

규칙은 논리 연산자처럼 작동합니다. 그들은 당신이 사용자의 정책의 범주를 정의하는 데 도움이됩니다. 모든 액세스 정책은 포함 규칙을 포함해야합니다. 이 응용 프로그램에 액세스 할 수있는 자격이 된 사용자의 초기 풀을 정의하는 것입니다. 당신은 그 사용자에게 특정 정책을 시행하기 위해 예외 및 요구 규칙을 추가 할 수 있습니다.

### 이름 \*

포함 규칙은 OR 논리 연산자와 유사합니다. 한 개 이상의 Include 규칙이 지정되어 있는 경우, 사용자는 한 가지 기준을 충족해야 합니다.

### 이름 \*

제외 규칙은 논리 연산자처럼 작동합니다. 모든 예외 기준을 충족하는 사용자는 신청서에 액세스 할 수 없습니다.

### 이름 \*

Require 규칙은 AND 논리 연산자와 같습니다. 모든 지정된 Require 규칙을 준수해야 합니다.

#### OR 연산자와 규칙을 요구

기본적으로 Require 규칙에 추가 된 값은 AND 연산자에 의해 요약됩니다. 예를 들어, 귀하는 풀 타임 직원과 계약자 모두에 응용 프로그램에 액세스 권한을 부여하고 특정 국가에서 근거를 둔 한 사람 - 포르투갈과 미국을 말한다. 다음 구성 규칙을 설정하면:

| - 연혁 | 규칙 유형 | 옵션 정보   | 제품정보                                  |
| ---- | ----- | ------- | ------------------------------------- |
| 지원하다 | 이름 \* | 이름 \*   | `United States`, `Portugal`           |
|      | 이름 \* | 이메일 보내기 | `@cloudflare.com`, `@contractors.com` |

이 정책은 미국과 포르투갈 모두에서 응용 프로그램에 도달하는 사람들에게만 권한을 부여하고, 이메일이 끝나는 것을 가지고`@cloudflare.com`이름 \*`@contractors.com`. 따라서, 아무도 신청에 접근할 것입니다.

1개의 국가 및 1개의 이메일 끝만 요구하십시오:

1. [규칙 그룹 만들기](/cloudflare-one/access-controls/policies/groups/)그것은 포르투갈 또는 미국에서 사용자를 포함:

   | 규칙 유형 | 옵션 정보 | 제품정보                        |
   | ----- | ----- | --------------------------- |
   | 이름 \* | 이름 \* | `United States`, `Portugal` |

2. 규칙 그룹을 필요로하는 정책을 작성하고, 또한 이메일이 끝나는 것을 포함`@cloudflare.com`이름 \*`@contractors.com`:

   | - 연혁 | 규칙 유형 | 옵션 정보   | 제품정보                                  |
   | ---- | ----- | ------- | ------------------------------------- |
   | 지원하다 | 이름 \* | 규칙 그룹   | `Country requirements`                |
   |      | 이름 \* | 이메일 보내기 | `@cloudflare.com`, `@contractors.com` |

## 연결 상황

Connection context 설정은 사용자가 액세스 권한을 부여 한 후 애플리케이션과 상호 작용하는 방법을 제어 할 수 있습니다. 한국어[회사 소개](#selectors)응용 프로그램에 액세스 할 수있는 사람을 결정, 연결 컨텍스트 설정은 작업 사용자가 세션 중에 취할 수있는 것을 결정합니다.

Connection context는 정책 당 구성되며 다른 사용자 그룹에 다른 권한을 부여 할 수 있습니다. 예를 들어, 원격 RDP 세션에서 데이터를 복사하기 위해 풀 타임 직원을 허용 할 수 있으며 계약자를 읽을 수 있습니다.

사용 가능한 연결 상황 설정은 애플리케이션 유형에 따라 다릅니다.

| 신청 유형                                                                                                              | 옵션 설정                       |
| ------------------------------------------------------------------------------------------------------------------ | --------------------------- |
| [인프라 (SSH)](/cloudflare-one/access-controls/applications/non-http/infrastructure-apps/)                            | UNIX 사용자 정의                 |
| [브라우저 기반 RDP](/cloudflare-one/networks/connectors/cloudflare-tunnel/use-cases/rdp/rdp-browser/#clipboard-controls) | 클립보드 컨트롤 (copy/pastestrict) |

## 실행의 순서

정책은 행동 유형과 주문에 따라 평가됩니다. 우회 및 서비스 Auth 정책은 UI에 표시된 것과 같이 정상에서 바닥까지 첫째로 평가됩니다. 그런 다음 블록 및 허용 정책은 주문에 따라 평가됩니다.

예를 들어, 다음과 같이 구성된 정책 목록을 가지고 있다면:

- 허용 A
- 블록 B
- 서비스 Auth C
- 우회 D
- 허용 E

정책은 이 순서에서 실행됩니다: 서비스 Auth C > Bypass D > 허용 A > 블록 B > 허용 E. 사용자가 허용하거나 블록 정책, 평가 정지 및 후속 정책은 결정을 내릴 수 있습니다.
