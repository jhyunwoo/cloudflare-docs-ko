이 가이드는 Cloudflare Gateway 정책을 사용하여 일반적인 문제를 해결하는 데 도움이됩니다. 문제는 가장 빈번한 문제로 주문됩니다.

## Egress 정책은 예상대로 작동하지 않습니다.

Egress 정책은 Gateway의 가장 일반적인 범주입니다. Symptoms는 전용 egress IP를 사용하지 않는 트래픽을 포함, 잘못된 실패 동작, 또는 먼 데이터 센터를 통해 게이트웨이 라우팅 트래픽으로 인해 높은 지연.

### 증상 : 트래픽은 전용 egress IP를 사용하지 않습니다.

활성 egress 정책에도 불구하고 트래픽이 전용 egress IP 대신 기본 Cloudflare IP 주소에서 egressing되는 것을 찾을 수 있습니다.

| 일반적인 원인                   | 제품정보                                                                                                                                                                                                                                                                                                              |
| ------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| CGNAT에 DNS 해결책 (차 등급 NAT) | egress 정책이 사용될 때*이름 \**&#xB610;는*이름 \**&#x73;elector, Gateway는 먼저 도메인을 해결해야 합니다. 트래픽은 Cloudflare를 통해 예상, 이것은 종종 CGNAT IP 주소로 해결`100.64.0.0/10`범위. 이 IP는 Cloudflare의 네트워크에 내부이므로 네트워크의 트래픽에 적용하는 egress 정책에 적용되지 않을 수 있습니다. egress 정책의 선택 변경*이름 \**&#xB610;는*이름 \**&#xC73C;로*대상 IP*. 서비스의 공공 IP 주소를 사용하여 도달하려고합니다. |
| 정책 precedence             | 더 높은 precedence (낮은 수)를 가진 다른 egress 정책은 첫번째 교통과 일치합니다. egress 정책이 동일한 첫 번째 매치 윈 논리를 따르는 것을 기억하십시오.                                                                                                                                                                                                               |
| Split Tunnel 구성           | 대상 IP 또는 도메인은 분할 터널 구성을 통해 WARP 터널에서 제외됩니다. 터널에서 제외되는 교통은 egress를 포함한 게이트웨이 정책에 적용되지 않습니다.                                                                                                                                                                                                                        |
| egress 로그인                | Egress logging은 Gateway Egress dataset과 Logpush를 통해 사용할 수 있습니다. 문제 해결에 필수적입니다. 시험 기기에서 egress IP를 확인할 수 있는 제3자 IP 검사 서비스를 사용할 수 있습니다.                                                                                                                                                                             |

### 증상: 장애가 작동하지 않거나 잘못된 IP 사용

기본 전용 egress IP는 사용할 수 없습니다. 그러나 구성 된 이차 전용 IP를 사용하는 대신 트래픽은 기본 Cloudflare 공유 IP로 실패합니다.

| 일반적인 원인                         | 제품정보                                                                                                                                           |
| ------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------- |
| Cloudflare 측에 Routing 또는 윤곽 문제점 | 문제의 시간을 문서하고 게이트웨이 HTTP 또는 DNS 로그에서 요청 ID를 수집합니다. 지원 티켓을 열고 이 정보를 제공합니다. Temporarily, 당신은 서비스를 복원하기 위해 1 차 IP를 설정하기 위해 egress 정책을 편집 할 수 있습니다. |

### Symptom: 사용자는 지리적으로 먼 위치에서 egressing

게이트웨이는 다른 지역 (독일과 같은)에 위치한 전용 egress IP를 통해 하나의 국가에서 사용자를 경로를 통해 높은 대기 시간 및 지역 제한 콘텐츠에 대한 액세스를 파괴합니다.

일반적인 원인과 해결책:

| 일반적인 원인      | 제품정보                                                                                                                                                                                                                                                                          |
| ------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 단일 egress 정책 | 해당 위치에 관계없이 모든 사용자에게 적용되는 하나의 넓은 egress 정책이 있습니다. 위치 인식 egress 정책을 작성합니다. 사용 방법*사용자 위치*특정 사용자 위치를 가장 가까운 전용 egress IP로 묶기 위해 정책의 선택자. 예를 들어, 한 번의 정책을 만들 때*사용자 위치*이름 \*`United Kingdom`, egress via London IP; 때를 위한 두번째 정책을 창조하십시오*사용자 위치*이름 \*`Australia`시드니 IP를 통해 egress. |
| 잘못된 위치 데이터   | 사용자의 ISP의 IP 주소가 올바르게 위치 할 수 없습니다. 게이트웨이 로그에 Cloudflare에 의해 본 사용자의 위치를 확인합니다. 잘못된 경우, Cloudflare 지원으로 보고할 수 있습니다.                                                                                                                                                             |

## Gateway는 정확한 순서에 있는 정책을 적용하지 않습니다

혼란의 일반적인 점은 Gateway가 다른 정책 유형과 규칙을 평가하는 방법이다.

### Symptom : 블록 정책은 더 구체적인 허용하거나 검사 정책이 적용되지 않습니다.

특정 응용 프로그램에 대한 검사 정책을 허용하거나 할 수 없습니다 (예 : Finance.example.com 등), 그러나 게이트웨이는 여전히 낮은 선행 블록 정책을 가진 트래픽을 차단합니다 (예 : Block All High-Risk Sites).

가장 중요한 개념은[Gateway 정책 우선](/cloudflare-one/traffic-policies/order-of-enforcement/)Gateway는 정책의 주문 번호를 기반으로 시행합니다. 목록에서 더 낮은 순서 수는 더 높은 precedence를 의미합니다. Gateway는 일치하는 첫 번째 규칙을 만날 때 추가 정책을 처리합니다.

Gateway 정책의 전진 문제를 해결하려면:

1. 내 계정[모델 번호: Cloudflare 한국어](https://one.dash.cloudflare.com), 이동**교통 정책** > **방화벽 정책**.
2. DNS, 네트워크 및 HTTP 정책의 순서를 검토하십시오.
3. 가장 특정한 허용, 검사하지 마십시오, 또는 정책을 검사하지 마십시오 당신의 일반적인 구획 정책 보다는 더 낮은 순서 수.
4. 자주 묻는 질문 자주 묻는 질문`teams.microsoft.com`모든 파일 공유 응용 프로그램에 대한 일반적인 블록 정책 전에 배치해야합니다.

## TLS 해독은 신청을 끊습니다

관련 기사[TLS 해독](/cloudflare-one/traffic-policies/http-policies/tls-decryption/)Data Loss Prevention (DLP), Browser Isolation 및 Application-aware HTTP 정책과 같은 게이트웨이 기능을 위해 필요합니다. 그러나 특정 유형의 소프트웨어로 문제를 일으킬 수 있습니다.

### Symptom : 명령행 도구 (CLI 도구) 또는 기본 응용 프로그램은 인증서 오류로 실패

TLS 해독 후, 명령 줄 도구 (예 :`git`, `aws`, `kubectl`·`terraform`) 또는 탁상용 신청 (ChatGPT 또는 Docker와 같은) 정지 일, 이것은 증명서 과실 때문에 일지도 모릅니다. 신청은 다음과 같은 오류를 반환할 수 있습니다.`SSL: CERTIFICATE_VERIFY_FAILED`, `self-signed certificate in certificate chain`, 또는 유사한 TLS 오류.

이 응용 프로그램은 운영 체제의 신뢰 저장소를 사용하지 않고 설치 한 Cloudflare 루트 인증서를 신뢰하지 않습니다. 그들은 종종 자신의 인증서 신뢰 저장소 또는 사용 인증서 핀닝, 이는 서버의 원래 인증서를 기대, Cloudflare에 의해 재 서명 되지.

이 문제를 해결하려면:

### 증상 : 사용자 정의 블록 페이지가 표시되지 않습니다.

HTTP 정책이 사용자의 요청을 차단하면 브라우저가 일반적인 오류를 반환합니다 (`ERR_SSL_PROTOCOL_ERROR`) 설정된 Gateway 블록 페이지 대신.

브라우저가 Cloudflare 루트 인증서에 의해 서명 된 블록 페이지에 의해 제시된 인증서를 신뢰하지 않기 때문에 발생합니다. 이 인증서는 사용자의 장치에 설치되지 않거나 신뢰할 수 없습니다.

이 문제를 해결하려면:

1. 견적 요청[Cloudflare 뿌리 증명서](/cloudflare-one/team-and-resources/devices/user-side-certificates/)장치에 설치됩니다.
2. 인증서가 올바른 시스템 수준의 신뢰 저장소에 배치됩니다 (예 : macOS의 키체인 시스템 저장소 또는 Windows의 로컬 컴퓨터를위한 신뢰할 수있는 루트 인증 권한).
3. MDM을 사용하는 경우 배포 스크립트가 올바르게 설치하고 인증서를 신뢰하는 것을 확인합니다.

## Private DNS 및 내부 리소스는 작동하지 않습니다.

내부 호스트명을 해결하기 위해 게이트웨이를 구성했지만 사용자는 액세스 할 수 없습니다. 예를 들어, WARP에 연결된 사용자는 내부 서비스에 접근하기 위해`jira.mycompany.local`, 하지만 DNS 쿼리 실패.

| 일반적인 원인                          | 제품정보                                                                                               |
| -------------------------------- | -------------------------------------------------------------------------------------------------- |
| Missing 또는 잘못된 해결자 정책            | 오시는 길**교통 정책** > **Resolver 정책**. 내부 도메인 suffix 및 내부 DNS 서버의 IP 주소로 전달되는 정책을 작성합니다.                |
| 분할 터널은 개인 IP 범위를 제외              | 내부 자원이 개인 IP 범위 (예 :`10.0.0.0/8`), 그 범위는 갱도에서 포함되어야 합니다. 분할 터널 구성의 목록을 제외하면 WARP는 트래픽을 프록시하지 않습니다. |
| 로컬 도메인 Fallback misconfiguration | 기업 DNS에 대한 해결 정책. 사용자의 즉각적인 물리적 네트워크에 특정 도메인의 Local Domain Fallback을 사용합니다.                        |
