규칙 또는 비율 제한의 스케일을 초과하는 per-hostname (customer) 설정을 구성 할 수 있습니다.

이 작업을 수행하려면 먼저 계정 팀에 도달하여 Custom Metadata에 액세스 할 수 있습니다. 사용자 정의 메타 데이터를 구성 한 후 다음 방법으로 사용할 수 있습니다.

- metadata JSON을 읽기[CloudflareWorkers](/workers/)(WorkersXQ)에 액세스하여 호스트 이름 동작을 정의합니다.
- 사용자 정의 메타데이터 값 사용[규칙 표현](/ruleset-engine/rules-language/expressions/)다른 Cloudflare 보안 제품의 규칙 범위를 정의합니다.

## 이름 \*

- Per-customer URL rewriting — 예를 들면, 서버 A, 10,001-20,000 서버 B, 등에서 클라이언트 1-10,000 fetch 자산.
- 사용자 정의 헤더 추가 — 예를 들어,`X-Customer-ID: $number`제공된 메타데이터를 기반으로
- HTTP Strict Transport Security (“HSTS”) 헤더 설정

추가 논리 및 요구 사항을 논의하기 위해 솔루션 엔지니어와 대화하십시오.

## 주문 메타데이터 제출

Custom Hostnames API를 통해 Cloudflare에 사용자 정의 메타 데이터를 추가 할 수 있습니다. 이 데이터는 추가할 수 있습니다.[`PATCH`이름 \*](/api/resources/custom_hostnames/methods/edit/)호스트명 ID에 대한 메타데이터를 설정하려면, 예를 들어:

<APIRequest
  path="/zones/{zone_id}/custom_hostnames/{custom_hostname_id}"
  method="PATCH"
  json={{
  	ssl: {
  		method: "http",
  		type: "dv",
  	},
  	custom_metadata: {
  		customer_id: "12345",
  		redirect_to_https: true,
  		security_tag: "low",
  	},
  }}
/>

metadata로 변경하면 30 초 이내에 Cloudflare의 가장자리를 통해 propagate됩니다.

***

## Cloudflare 작업자

metadata 객체는 각 요청에 접근할 수 있습니다.`request.cf.hostMetadata`호텔 위치 데이터를 읽고 작업자를 사용하여 행동을 사용자 정의 할 수 있습니다.

아래 예에서 API 호출을 사용하여 제출 된 Worker에서 user id를 사용합니다.`"custom_metadata":{"customer_id":"12345","redirect_to_https": true,"security_tag":"low"}`, 및 요청 헤더를 설정`customer_id`근원에:

<TypeScriptExample>
  ```ts
  export default {
  	/** 이름
  * Fetch는 hostname을 기준으로 X-Customer-Id 헤더를 추가합니다.
  * @param {Request} 요청*/
  	async fetch(request, env, ctx): Promise<Response> {
  		const customer_id = request.cf.hostMetadata.customer_id;
  		const newHeaders = new Headers(request.headers);
  		newHeaders.append("X-Customer-Id", customer_id);

  		const init = {
  			headers: newHeaders,
  			method: request.method,
  		};
  		return fetch(request.url, init);
  	},
  } satisfies ExportedHandler<Env>;
  ```
</TypeScriptExample>

## 규칙 표현에서 custom metadata 접근

사용 방법[`cf.hostname.metadata`](/ruleset-engine/rules-language/fields/reference/cf.hostname.metadata/)규칙 표현의 metadata 객체에 액세스 할 수있는 필드. JSON 객체의 다른 값을 얻으려면, 사용[`lookup_json_string`](/ruleset-engine/rules-language/functions/#lookup_json_string)기능.

다음 규칙 표현은 규칙 일치가되는 것을 정의합니다.`security_tag`custom metadata에 있는 가치는 가치를 포함합니다`low`:

```txt
lookup_json_string(cf.hostname.metadata, "security_tag") eq "low"
```

## 좋은 관행

- JSON schema가 수정되었는지 확인하십시오. 해당 Cloudflare QXQXWorkersXQ 변경이 잠재적으로 웹 사이트를 파괴하거나 정의 된 "기본" 행동으로 돌아갑니다.
- 플랫 JSON 구조를 Prefer
- 뱀의 문자열 키를 사용 케이스 ( camelCase 또는 PascalCase보다)
- 적당한 불린을 사용하십시오 (true/false 보다는 오히려`true`또는`1`또는`0`)
- 문자열 대신 정수를 나타내는 숫자를 사용합니다 (`1`또는`2`대신에`"1"`또는`"2"`)
- 메타데이터의 비영향에 있는 미들백 행동 정의
- 메타데이터의 키 또는 값이 알 수 없는 경우의 낙하 동작

일반 지도는 다음과 같습니다.[Google의 JSON 스타일 가이드](https://google.github.io/styleguide/jsoncstyleguide.xml)자주 묻는 질문

## 제한 사항

Cloudflare에 제공 될 수있는 메타 데이터에 대한 몇 가지 제한이 있습니다 :

- JSON을 유효해야 합니다.
- 어떤 근원 해결책 — 예를 들면, 특정한 백엔드에 주어진 hostname를 위한 지시 요구 — CloudflareQ's DNS 안에 존재하는 hostname로 제공되어야 합니다 (비 유해한 체제를 위해 조차). IP 주소를 직접 제공하면 오류 요청이 발생할 수 있습니다.
- 총 페이로드는 4 KB를 초과하지 않아야 합니다.
- Cloudflare 내용을 기반으로 스키마와 트리거 로직을 처리하는 방법을 알고 있습니다.

:::참조
schema를 수정할 때 주의하십시오. 추가, 제거, 또는 키 변경 및 가능한 값은 Cloudflare Worker는 데이터를 무시하거나 트리거 요청 오류를 반환합니다.
