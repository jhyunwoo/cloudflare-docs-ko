## AI 봇 및 크롤러 트래픽

AI assistant, AI data scraper, AI search crawler와 연관된 user agent의 HTTP request 활동입니다. 이 정보는 트래픽 볼륨 추세를 보여 주도록 정규화되어, 시간 경과에 따른 AI 기반 웹 상호작용의 활동 수준에 대한 인사이트를 제공합니다. 이 분석에 포함되는 user agent는 [ai.robots.txt](https://github.com/ai-robots-txt/ai.robots.txt) 저장소에 나열된 AI 중심 user agent에서 도출됩니다.

## 애플리케이션 수준 공격

완화된 요청을 기반으로 한 Layer 7 공격 정보로, 가장 자주 사용되는 완화 기법과 시간에 따른 완화된 요청 볼륨 추세를 포함합니다. "Application layer attack volume" 및 "Mitigated traffic sources" 그래프에서는 선택한 위치 또는 ASN이 완화된 요청의 source입니다. "Application layer attack distribution" 그래프에서는 Origin Location 그래프가 선택한 위치를 대상으로 한 공격이 어디서 오는지를 보여 주고, Target Location 그래프는 선택한 위치에서 출발한 공격의 목표 위치를 보여 줍니다. "Application layer attack distribution" 인사이트는 ASN 수준에서는 제공되지 않습니다.

## 인증 방법

[SPF](https://developers.cloudflare.com/dns/manage-dns-records/reference/dns-record-types/#spf), [DKIM](https://developers.cloudflare.com/dns/manage-dns-records/reference/dns-record-types/#dkim), [DMARC](https://developers.cloudflare.com/dns/manage-dns-records/reference/dns-record-types/#dmarc)는 정책 기반 이메일 인증 방법이며, 함께 사용하면 스패머, 피셔, 기타 무단 주체가 자신이 소유하지 않은 도메인을 대신해 이메일을 보내는 것을 방지하는 데 도움이 됩니다. PASS는 해당 검사를 통과한 처리된 메시지의 비율입니다. FAIL은 해당 검사를 통과하지 못한 처리된 메시지의 비율입니다. NONE은 관련 정책을 찾을 수 없었던 처리된 메시지의 비율입니다. 이 지표에 대한 데이터는 Cloudflare의 이메일 라우팅 서비스에서 가져옵니다.

## 자율 시스템

인터넷은 네트워크들의 네트워크이며, 자율 시스템은 인터넷을 구성하는 네트워크입니다. 보다 구체적으로 자율 시스템(AS)은 하나 이상의 네트워크를 통과하는 경로를 선택하는 과정인 통합된 라우팅 정책을 가진 대규모 네트워크 또는 네트워크 집합입니다.

데이터 패킷은 최종 목적지에 도달할 때까지 한 AS에서 다른 AS로 이동합니다. 인터넷에 연결되는 모든 컴퓨터나 장치는 AS에 연결됩니다. ISP는 하나 이상의 AS를 가지며, 각 AS에는 Border Gateway Protocol (BGP) 라우팅에 사용하기 위한 공식 Autonomous System Number (ASN)가 할당됩니다. 예를 들어 Cloudflare의 ASN은 AS13335입니다. 자세한 내용은 [Cloudflare Learning Center](https://www.cloudflare.com/learning/network-layer/what-is-an-autonomous-system/)를 참고하세요.

## Autonomous System Provider Authorization (ASPA)

[Autonomous System Provider Authorization (ASPA)](https://datatracker.ietf.org/doc/draft-ietf-sidrops-aspa-verification/)는 [Resource Public Key Infrastructure (RPKI)](https://en.wikipedia.org/wiki/Resource_Public_Key_Infrastructure) 내의 암호학적 객체로, route security를 origin validation 너머로 확장합니다. RPKI Route Origin Authorization (ROA)가 어떤 [Autonomous System (AS)](https://www.cloudflare.com/learning/network-layer/what-is-an-autonomous-system/)이 prefix를 originate할 권한이 있는지 검증하는 반면, ASPA는 AS가 허가된 upstream transit provider를 선언할 수 있게 함으로써 BGP `AS_PATH`를 검증하고, 위조된 path segment를 포함한 route leak 및 특정 BGP hijack을 탐지할 수 있게 합니다.

각 ASPA record는 **Customer AS (CAS)**가 생성하며, 자신의 route를 upstream으로 전파할 권한이 있는 **Set of Provider ASes (SPAS)**를 나열합니다. Router는 이러한 Customer-to-Provider 관계를 사용해 BGP `AS_PATH`가 합법적인 라우팅 토폴로지와 일치하는지를 평가하고, `Valid`, `Invalid`, `Unknown` 중 하나의 검증 결과를 생성합니다. IETF 명세는 아직 초안 상태이지만, [ARIN](https://www.arin.net/announcements/20260120/), [RIPE NCC](https://labs.ripe.net/author/tim_bruijnzeels/aspa-in-the-rpki-dashboard-a-new-layer-of-routing-security/) 같은 RIR 포털에서는 ASPA 객체 생성을 지원하며, [OpenBGPD](https://www.undeadly.org/cgi?action=article;sid=20231002135058), [BIRD](https://bird.network.cz/?get_doc&v=20&f=bird-5.html) 같은 라우팅 스택에는 검증 로직이 구현되어 있습니다.

## BGP announcement

Border Gateway Protocol (BGP)은 인터넷의 라우팅 프로토콜입니다. 우편 시스템이 우편물을 처리하는 것과 유사하게, BGP는 인터넷 트래픽을 전달하기 위한 가장 효율적인 경로를 선택합니다. BGP announcement는 한 AS가 다른 AS에게 "이 네트워크 prefix로 향하는 트래픽을 받으면 나에게 보내라"고 알리는 방법입니다. 이 메시지는 처리된 뒤 (가능하다면) 다른 AS로 전달되며, 경로상의 모든 AS가 해당 네트워크 prefix로 가는 트래픽을 어디로 보내야 하는지 학습할 수 있게 합니다. 자세한 내용은 [Cloudflare Learning Center](https://www.cloudflare.com/learning/security/glossary/what-is-bgp/)를 참고하세요.

Cloudflare Radar에서는 AS가 발표한 BGP message 양과 발표된 IP address 공간 전체 크기에 대한 시계열 차트를 제공합니다. BGP message 양은 특정 AS의 전체 라우팅 활동 수준을 보여 주고, 발표된 IP address 공간은 해당 AS가 시간에 따라 운영하는 네트워크의 크기를 나타냅니다. IP address 공간 크기는 최소 라우팅 가능 network prefix 크기의 개수로 표현하며, 이는 IPv4의 /24 prefix 수와 IPv6의 /48 수입니다. 이에 따라 /24 prefix는 256개의 IP address를 나타내고, /48은 2^80개의 IP address를 나타냅니다.

## BGP route leak

[BGP route leak](https://www.rfc-editor.org/rfc/rfc7908.html)은 의도된 범위를 넘어 라우팅 announcement가 전파되는 현상으로 정의됩니다.
Cloudflare Radar에서는 해당 autonomous system number (ASN) 페이지에서 탐지된 route leak event를 확인할 수 있습니다. 표의 열은 다음과 같이 정의됩니다.

- `From`: route를 학습한 autonomous system (AS)
- `By`: route를 leak한 AS, 즉 leaker
- `To`: leak된 route를 수신하고 전파한 AS
- `Start` 및 `End`: route leak event의 시작 및 종료 시각
- `BGP Msgs.`: leak된 route를 포함하는 BGP announcement 수
- `Prefixes`: route leak event가 영향을 준 IP prefix 수
- `Origins`: route leak event가 영향을 준 origin AS 수
- `Vantage Points`: route leak event를 관측한 route collector 수

자세한 설계와 활용 방식은 [How we detect route leaks and our new Cloudflare Radar route leak service](https://blog.cloudflare.com/route-leak-detection-with-cloudflare-radar/) 블로그 글을 참고하세요.

## BGP origin hijack

[BGP origin hijack](https://www.cloudflare.com/learning/security/glossary/bgp-hijacking/)은 네트워크가 자신이 소유하지도, 제어하지도, 라우팅하지도 않는 IP address 그룹(prefix)에 대한 소유권을 거짓으로 발표하는 BGP anomaly의 한 종류입니다. BGP origin hijack은 인터넷 트래픽을 정상 목적지에서 hijacker로 우회시켜 데이터 손실과 사적/기밀 정보 유출 가능성을 초래할 수 있습니다.

Cloudflare Radar에서는 "BGP Origin Hijacks" 표에서 탐지된 BGP origin hijack event를 확인할 수 있습니다. 표의 열은 다음과 같이 정의됩니다.

- `ID`: 클릭하면 event detail 페이지로 이동하는 event ID
- `Detected Origin`: 탐지 시점에 해당 prefix를 originate한 AS로, 잠재적인 BGP hijacker일 수 있음
- `Expected Origin(s)`: 다양한 근거에 따라 해당 prefix를 originate할 것으로 예상되는 AS
- `Start Time (UTC)` 및 `Duration`: UTC 기준 탐지 시각과 사람이 읽기 쉬운 지속 시간. 진행 중인 event는 `--`로 표시되며 duration 값이 없습니다.
- `BGP Messages`: 탐지된 anomaly를 포함하는 BGP message 수
- `Prefixes`: event 동안 hijack된 prefix. 표 공간 제약으로 인해 하나의 전체 prefix만 표시합니다.
- `Confidence`: 해당 event가 실제 hijack이라고 판단하는 confidence 수준. 값은 `High`, `Medium`, `Low`가 될 수 있습니다.
- `Tags`: RPKI validation 결과나 네트워크 관계와 같은 추가 데이터 소스를 통해 수집한 핵심 사실을 짧은 tag 형태로 표시한 관련 근거

탐지 결과는 [public API](/api/resources/radar/subresources/bgp/subresources/hijacks/subresources/events/methods/list/)를 통해 프로그래밍 방식으로도 접근할 수 있습니다([CC BY-NC 4.0](https://creativecommons.org/licenses/by-nc/4.0/) 라이선스).

## BGP real-time route

Cloudflare Radar의 prefix routing 페이지는 실시간 BGP route를 [Sankey diagram][sankey]으로 표시합니다. 이 시각화는 [RouteViews][route-views]와 [RIPE RIS][ripe-ris]의 MRT 데이터, 그리고 RouteViews의 Kafka 인스턴스와 [RIS Live][ris-live]의 실시간 stream을 결합해 구성됩니다.

기본적으로 route 시각화는 originating AS에서 [Tier-1 networks][tier-1]까지의 path를 보여 주며, 가독성을 위해 Tier-1 network에서 BGP route collector까지의 구간은 생략합니다. 사용자는 "Show full paths" 토글을 통해 전체 path를 볼 수 있습니다.

시각화 위의 표는 prefix origin에 대한 세부 정보를 제공하며, originating AS, route collector 전반에서의 visibility 비율, 그리고 [RPKI][rpki] validation 상태(`valid`, `invalid`, `unknown`)를 포함합니다.

## Certificates

암호화는 안전한 인터넷의 핵심 요소입니다. SSL/TLS는 client와 server 사이에 암호화된 연결을 설정하기 위한 표준 보안 기술입니다.

Cloudflare Radar에서는 신뢰할 수 있는 Certificate Authority가 발급하고 활성 certificate transparency log에 기록된 특정 domain의 모든 certificate를 확인할 수 있습니다.

도메인 이름에 대해 발급된 certificate를 검토해, 도메인과 연결된 certificate가 잘못되었거나 부정하게 발급된 경우가 없는지 확인할 수 있습니다. 또한 [Cloudflare Dashboard](https://dash.cloudflare.com/)의 certificate transparency monitor에서 alert를 받도록 등록할 수도 있습니다.

## Certificate Transparency

[Certificate Transparency (CT)](https://certificate.transparency.dev/)는 Certification Authority (CA)가 발급한 digital certificate 발급을 모니터링하고 감사하기 위한 인터넷 보안 표준입니다.
CT는 CA가 발급하는 모든 certificate를 append-only이면서 검증 가능한 log에 공개적으로 기록하도록 요구함으로써 잘못 발급되었거나 악의적인 certificate를 탐지하는 데 도움을 줍니다.
이 log는 transparency와 certificate 생태계에 대한 신뢰를 보장하기 위해 browser, 보안 연구자 등 여러 주체가 모니터링합니다.

CT의 핵심 구성 요소는 다음과 같습니다.

- **CAs:** certificate를 발급하는 조직
- **CT Logs:** 발급된 certificate가 기록되는 공개 append-only log
- **Monitors:** log의 정확성을 검사하는 주체

Cloudflare Radar에서 제공되는 데이터는 현재 Cloudflare가 모니터링하는 CT log에서 도출됩니다.
이를 통해 웹 전반의 certificate 발급 추세, 분포, 메타데이터에 대한 가시성을 확보할 수 있습니다.

## 연결 특성

지정된 특성을 가진 mail transfer agent에서 Cloudflare로 유입되는 연결의 비율입니다. “IP Version”은 IPv4와 IPv6로 이루어진 연결을 구분합니다. “Encryption”은 TLS를 사용한 암호화 연결과 평문 비암호화 연결을 구분합니다. 이 지표에 대한 데이터는 Cloudflare의 이메일 라우팅 서비스에서 가져옵니다.

## 연결 품질

연결 품질 지표에는 다운로드 및 업로드 속도, latency(round-trip time), latency jitter(round-trip time 안정성)가 포함되며, 특정 country나 ASN에서 기대할 수 있는 최상의 성능을 반영합니다. 이 지표는 [Cloudflare Speed Test website](https://speed.cloudflare.com/)에서 end user가 시작한 speed test를 기반으로 하며, 이전 90일 동안 집계됩니다. 기초 raw data는 [Measurement Lab's BigQuery](https://blog.cloudflare.com/aim-database-for-internet-quality/)를 통해 자유롭게 분석할 수 있습니다.

속도, latency, jitter ranking에는 사용자가 충분한 빈도로 speed test를 실행한 country만 포함됩니다. 따라서 일부 country는 Radar의 다른 섹션에 데이터가 존재하더라도 ranking에서는 제외될 수 있습니다.

Cloudflare Speed Test는 테스트 과정에서 latency를 여러 번 측정합니다. 다운로드나 업로드가 시작되기 전에 측정한 값은 idle latency와 jitter로 집계되고, 다운로드나 업로드가 진행 중일 때 측정한 값은 loaded latency와 jitter로 집계됩니다.

## 콘텐츠 카테고리

Cloudflare는 다양한 데이터 소스를 사용해 domain을 분류합니다. Cloudflare Radar를 사용하면 특정 domain과 연관된 콘텐츠 카테고리를 확인할 수 있습니다. [Cloudflare Gateway](/cloudflare-one/traffic-policies/domain-categories/) 또는 [1.1.1.1 for Families](/1.1.1.1/setup/#1111-for-families)를 사용하는 Cloudflare 고객은 malware, phishing 같은 보안 위협 외에도 "Adult Content" 같은 특정 카테고리를 차단하도록 결정할 수 있습니다.

경우에 따라 domain이 잘못 분류될 수 있습니다. 예를 들어 social media 사이트가 "Shopping & Auctions"로 분류될 수 있습니다. domain이 잘못 분류되었거나 아직 분류되지 않았다고 생각되면 [this form](https://radar.cloudflare.com/domains/feedback)을 통해 제안 카테고리를 보내 알려 주세요.

## DNS

[Domain Name System (DNS)](https://www.cloudflare.com/learning/dns/what-is-dns/)은 사람이 읽을 수 있는 domain name을 컴퓨터가 서로 통신하는 데 사용할 수 있는 숫자 IP address로 변환하는 데 가장 흔히 사용되는 네트워크 서비스입니다.
이는 필수적인 인터넷 서비스이며, 다른 네트워크 관련 정보를 조회하는 데에도 사용됩니다.

Radar에 표시되는 DNS 데이터는 Cloudflare의 [1.1.1.1](/1.1.1.1/) public resolver service에 대한 집계되고 익명화된 DNS lookup을 기반으로 합니다.

## DNS magnitude

DNS Magnitude는 인터넷에서 domain의 전반적인 가시성을 추정하기 위해 [nic.at](https://www.nic.at/media/files/pdf/dns-magnitude-paper-20200601.pdf) (PDF)이 처음 개발한 지표입니다.

DNS query 총량만 세는 대신, DNS Magnitude는 TLD 내 domain에 query를 보내는 고유 client 수에 대한 감각을 반영합니다. 이 접근 방식은 적은 수의 source가 대량의 query를 생성할 수 있기 때문에, TLD의 도달 범위를 보다 정확하게 보여 줍니다.
당사의 ranking은 Cloudflare의 [1.1.1.1](/1.1.1.1/) public resolver에서 관측한 query를 기반으로 합니다. 개별 client IP address는 여기서 "networks"라고 부르는 subnet으로 집계됩니다.

magnitude 값의 범위는 0에서 10이며, 값이 높을수록(10에 가까울수록) 해당 TLD가 더 넓은 범위의 network에서 query되고 있음을 의미합니다.

이는 더 큰 전 세계적 가시성과, 경우에 따라 서로 다른 시스템 간 name collision 가능성이 더 높다는 것을 반영합니다. [ICANN에 따르면](https://www.icann.org/resources/pages/name-collision-2013-12-06-en), name collision은 private namespace(예: 위임되지 않은 Top-Level Domain 아래)에서 사용되는 이름을 해석하려는 시도가 public DNS로 query를 보내는 경우 발생합니다. private namespace와 public namespace의 관리 경계가 겹치면 name resolution이 의도하지 않았거나 해로운 결과를 낳을 수 있습니다. 예를 들어 ICANN이 `.home`을 위임한다면, 현재 위임되지 않은 이 TLD를 로컬 네트워크에서 사용하는 취미 사용자들에게 상당한 문제를 일으킬 수 있습니다.

## Internet outages

인터넷 연결은 여러 요인으로 인해 outage 또는 disruption을 겪을 수 있습니다. 이러한 요인에는 정전, 광섬유 케이블 손상, 악천후, 자연재해, 정부 주도의 shutdown이 포함됩니다. outage는 지리적 범위가 국가 전체일 수도, 일부 지역일 수도 있으며, 하나 이상의 [ASN](https://www.cloudflare.com/en-gb/learning/network-layer/what-is-an-autonomous-system/)에 영향을 줄 수도 있습니다. 일부 outage는 몇 분 만에 끝나는 짧은 것이고, 다른 outage는 몇 달간 이어질 수도 있습니다. 지속 시간은 부분적으로 근본 원인과 관련이 있을 수 있습니다. Cloudflare Radar Outage Center에 나열된 Internet outage는 일반적으로 제3자 정보로 교차 확인된 주목할 만한 트래픽 급감을 의미하며, 여기에는 통신 사업자의 social media 또는 status page 게시물, 뉴스 기사, 업계/커뮤니티 메일링 리스트가 포함될 수 있습니다.

특정 네트워크나 country에서 Internet outage가 진행 중일 수 있음을 나타내는 조기 경고 신호는, 과거 트래픽 패턴과 추세에 비해 비정상적인 트래픽 감소입니다. Cloudflare Radar Outage Center에 나열되는 Internet anomaly는 해당 엔터티에 대해 알고리즘적으로 관측된 비정상적 트래픽 감소를 나타냅니다. 특정 항목이 verified로 표시되어 있다면, Cloudflare가 여러 Cloudflare 데이터 소스 및/또는 [IODA](https://ioda.inetintel.cc.gatech.edu/) 같은 제3자 소스, 또는 앞서 언급한 기타 정보 소스를 통해 해당 트래픽 감소를 수동으로 교차 검증했다는 뜻입니다. 후자의 경우에는 관련 Internet outage event가 열리며, 해당 event는 Internet Outages 표(및 API)에 나열됩니다.

## IQI

Internet Quality Index는 웹 브라우징과 같은 평균적 활용 상황에서의 연결 성능을 추정합니다. 이는 고정된 Cloudflare 및 제3자 target 집합에 대한 end user 측정값을 바탕으로 하며, 대륙, country, ASN별로 집계된 bandwidth, round-trip time(latency), DNS response time 수치를 제공합니다.

IQI 방법론은 추정치를 생성하기 위해 최소한의 측정 수를 요구합니다. 그 결과, 더 작은 country와 ASN의 그래프에서는 특히 야간에 간헐적 공백이 나타날 수 있습니다. 이러한 공백은 outage를 의미하지 않습니다. IQI의 기반이 되는 측정 수가 특정 country 또는 ASN에서 Cloudflare가 관측한 트래픽 양과 반드시 상관관계를 갖는 것은 아닙니다.

## IRR AS-SETs

IRR AS-SET은 Internet Routing Registry (IRR) 내의 Autonomous System Number (ASN)를 모아 BGP 라우팅 정책을 정의하고 관리하는 데 사용하는 이름 붙은 컬렉션입니다. 고객과 downstream peer 같은 관련 network를 하나의 식별자 아래 그룹화함으로써, 네트워크 운영자는 BGP filter 생성을 자동화할 수 있으며, 이는 BGP route leak 전파를 방지하는 데 필수적입니다. AS-SET은 다른 AS-SET을 멤버로 포함할 수 있는 계층적 구조를 가질 수 있어 확장성은 있지만 복잡성이 커집니다. 이 복잡성을 정량화하기 위해 "AS Cone"은 완전히 확장된 집합에 포함된 고유 ASN 총수(즉 downstream footprint)를 측정하고, "Upstreams"는 다른 AS-SET이 이를 직접 또는 간접적으로 얼마나 포함하는지를 측정해 전 세계 라우팅 시스템에서의 역할에 대한 인사이트를 제공합니다.

AS-SET은 본질적으로 소유자 network를 포함하지는 않습니다. Cloudflare Radar는 [PeeringDB](https://www.peeringdb.com/)에 있는 AS-SET 이름이나 이름 자체를 매칭해 소유자를 추론합니다. 두 방법 모두로 소유자를 추론할 수 있는 경우에는 PeeringDB 정보를 우선합니다.

## TCP resets and timeouts

Transmission Control Protocol (TCP)에서 client가 시작한 연결 reset(RST flag, 즉 TCP의 "panic button" 사용)은 비정상적인 현상이며, 즉시 연결을 닫아야 할 정도로 _무언가 잘못되었음_ 을 server에 알립니다. 마찬가지로 연결 timeout(server가 응답 없는 client 때문에 연결을 닫는 경우)도 일반적인 데이터 교환에서는 발생하지 않아야 합니다. 비교를 위해 설명하면, 일반적인 TCP 연결은 client가 server에 SYN packet을 보내 시작하는 3-way handshake, 그 다음 ACK 및 PSH flag로 조절되는 data packet 교환, 그리고 마지막으로 양쪽 중 한쪽이 시작하는 FIN packet 기반의 정상 종료로 구성됩니다. FIN 종료는 양쪽이 데이터 전송을 마친 뒤 연결을 닫는다는 점에서 정상적인 종료로 간주됩니다. 반면 timeout이나 RST flag는 전송 또는 확인을 기다리는 데이터가 있더라도 즉시 중단을 일으킵니다. TCP 프로토콜에 대한 자세한 내용은 [RFC 9293](https://datatracker.ietf.org/doc/html/rfc9293)를 참고하세요.

TCP server는 다양한 이유로 timeout되거나 reset된 연결을 볼 수 있습니다. 어떤 것은 연결을 잃거나 갑자기 종료된 client application(예: 닫힌 tab을 정리하는 browser, port scanner)처럼 양성적인 이유입니다. 다른 경우에는 [DoS attacks](https://www.cloudflare.com/learning/ddos/syn-flood-ddos-attack/)나 제3자 간섭처럼 더 우려스러울 수 있습니다. 어떤 경우에는 연결 내 packet을 자세히 살펴보면 종료 원인을 이해하는 데 도움이 됩니다. 예를 들어 [Global, Passive Detection of Connection Tampering](https://research.cloudflare.com/publications/SundaraRaman2023/)은 특정 packet pattern이 middlebox에 의한 연결 tampering과 연결될 수 있음을 보여 줍니다.

Cloudflare Radar의 [Security & Attacks page](https://radar.cloudflare.com/security-and-attacks)에서는 Cloudflare server로 향하는 TCP 연결 샘플에서 발생한 reset 및 timeout 통계를, 종료 전 연결이 어느 단계까지 진행되었는지 기준으로 나누어 볼 수 있습니다. plot line은 다음과 같이 정의됩니다.

- **Post-SYN (mid-handshake)**: server가 단 하나의 SYN packet만 받은 뒤 발생한 connection reset 또는 timeout
- **Post-ACK (immediately post-handshake)**: server가 SYN packet과 ACK packet을 모두 받아 연결이 성공적으로 수립된 뒤 발생한 connection reset 또는 timeout
- **Post-PSH (after first data packet)**: 연결이 수립된 뒤, PSH flag가 설정된 packet을 server가 받은 이후에 발생한 connection reset 또는 timeout. PSH flag는 해당 TCP packet이 application에 즉시 전달할 준비가 된 데이터(예: TLS Client Hello message)를 포함함을 의미합니다.
- **Later (after multiple data packets)**: client에서 보낸 처음 10개 packet 안에서 발생한 connection reset이지만, server가 이미 여러 data packet을 받은 이후의 경우
- **None**: 그 밖의 모든 연결

TCP resets and timeouts dataset에 대한 자세한 내용은 [blog post](https://blog.cloudflare.com/tcp-resets-timeouts)를 참고하세요.

## 위협 카테고리

공격자는 이메일 기반 공격을 수행할 때 여러 가지 기법을 사용합니다. 예를 들어 malware로 이어지는 링크나 첨부 파일, 신뢰할 수 있는 연락처에서 온 것처럼 보이게 만드는 신원 속임수, 신뢰할 수 있는 브랜드를 사칭하는 방식 등이 있습니다. 카테고리는 악성 이메일 메시지 분석 중 발견된 다양한 위협 유형에 부여되며, 하나의 메시지가 여러 카테고리를 동시에 가질 수 있습니다. 이 카테고리는 “Link”, “Attachment”, “Impersonation”, “Other” 그룹으로 집계됩니다. “Link”는 사용자가 무언가를 클릭하도록 유도하는 위협 유형을, “Attachment”는 공격자가 파일을 이메일에 첨부한 위협 유형을, “Impersonation”은 공격자가 신뢰할 수 있는 브랜드나 연락처를 사칭한 위협 유형을 묶습니다. “Other”는 앞선 세 그룹에 속하지 않는 나머지 위협 유형을 포함합니다. 퍼센트 값은 해당 위협 카테고리가 발견된 악성 이메일 메시지의 비율을 나타냅니다. 이 지표에 대한 데이터는 Cloudflare의 클라우드 이메일 보안 서비스에서 가져옵니다.

## 위협 분류

악성 이메일 메시지는 로그인 정보 같은 개인정보를 공유하도록 속이는 phishing 캠페인의 일부일 수 있으며, 내장된 이미지, 링크, 첨부 파일을 통해 malware를 퍼뜨리려는 시도일 수도 있습니다. 표시되는 퍼센트는 malicious로 분류된 처리된 메시지의 비율을 나타냅니다. 이 지표에 대한 데이터는 Cloudflare의 클라우드 이메일 보안 서비스에서 가져옵니다.

## 트래픽 유형 필터

- **Human Only Traffic**: 당사 알고리즘이 사람의 활동에 의해 생성되었다고 판단한 트래픽

- **Automated Only Traffic**: 당사 알고리즘이 봇 또는 자동화 스크립트 활동에 의해 생성되었다고 판단한 트래픽

- **All Traffic**: 사람의 활동과 자동화 활동을 모두 포함한 전체 트래픽 사용

## 추세

집계된 HTTP/s metadata를 기반으로 mobile device 대 desktop 트래픽 분포, 봇으로 탐지된 트래픽 비율, user agent/browser 분포 등 다양한 지표의 추세를 보여 줄 수 있습니다. 또한 HTTPS 및 IPv6 사용에 대한 인사이트도 제공합니다.

## Verified bots

봇 트래픽은 웹사이트나 앱으로 향하는 사람 이외의 모든 트래픽을 설명합니다. 일부 봇은 유용합니다. 예를 들어 검색 엔진 봇은 검색용으로 콘텐츠를 색인화하고, 고객 서비스 봇은 사용자를 돕습니다. 반면 일부 봇은 사용자 계정을 침해하거나 spam 발송을 위해 웹에서 연락처 정보를 수집하는 등 악의적인 활동에 사용될 수 있습니다.

검색 엔진 봇과 같은 verified bot은 일반적으로 자신이 누구인지 투명하게 밝힙니다. Cloudflare는 더 넓은 인터넷에 이익이 되고 robots.txt를 준수하는 서비스만 수동으로 승인합니다.

Verified Bots 목록의 각 항목은 지난 30일 동안 verified bot과 연관된 IP address가 관측되었기 때문에 존재합니다. verified bot이 반드시 좋거나 나쁘다는 뜻은 아닙니다.

## Visitor location

domain별 지리적 트래픽 패턴에 표시되는 데이터는 오로지 당사의 recursive DNS 서비스 데이터만을 기반으로 합니다. 표시되는 모든 데이터는 privacy policy와 약속을 준수합니다. 이 데이터에는 공격 트래픽과 cross-origin request가 포함될 수 있습니다.

## Web crawlers

[Web crawlers](https://www.cloudflare.com/learning/bots/what-is-a-web-crawler/)는 웹사이트 콘텐츠를 수집하고 색인화하기 위해 인터넷을 탐색하는 봇의 한 종류입니다. Google이나 Bing 같은 검색 엔진은 검색 결과에서 페이지를 발견할 수 있도록 하기 위해 이를 사용합니다.

또한 AI platform도 이를 사용합니다. 대규모 언어 모델 학습용 콘텐츠를 수집하거나, AI assistant를 위한 최신 정보를 가져오기 위해서입니다. 검색과 AI 모두에서 크롤러는 한 페이지에서 다른 페이지로 link를 따라가며 온라인 콘텐츠 지도를 만들어 작동합니다.

Radar의 crawl-to-refer ratio 지표는 먼저 `User-Agent` header를 기반으로 HTML 페이지에 대한 crawl request를, `Referer` header를 기반으로 HTML 페이지에 대한 referral request를 platform별로 매핑해 계산합니다(예: Google의 ratio는 Googlebot의 crawl request와 Google platform의 referral request를 기반으로 계산됩니다). Radar의 다른 트래픽 지표와 마찬가지로 ratio 데이터의 aggregation resolution은 선택한 timeframe 길이에 따라 달라집니다. 또한 native app에서 유입된 트래픽은 `Referer` header를 포함하지 않을 수 있다는 점에 유의하세요. referral count는 웹 기반 도구에서 온 트래픽만 포함하므로, 이러한 계산은 해당 ratio를 실제보다 높게 보이게 할 수 있지만 얼마나 과장되는지는 명확하지 않습니다.

## WHOIS

WHOIS는 등록된 모든 domain의 연락처 및 nameserver 정보를 공개하는 표준입니다. 각 registrar는 자체 WHOIS 서비스를 유지합니다. 누구나 registrar의 WHOIS 서비스에 query를 보내 특정 domain 뒤의 데이터를 확인할 수 있습니다.

## Workers AI

[Workers AI](/workers-ai/)를 사용하면 Workers, Pages 또는 Cloudflare API를 통해 어디에서든 Cloudflare 네트워크 위에서 machine learning model을 실행할 수 있습니다. Workers AI에 표시되는 데이터는 특정 시간 간격 동안 model을 사용한 Cloudflare account 수를 기반으로 합니다.
