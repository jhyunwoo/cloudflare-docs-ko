Workflow에는 1개 이상 단계가 포함되어 있습니다. 각 단계는 각자 달성된, 개별적으로 일류의 retryable 성분입니다. 단계는 네트워크 또는 인프라 문제로 인해 워크 플로우가 실패하더라도 그 단계에서 워크 플로우를 지속 할 수있는 (옵션) 상태를 방출 할 수 있습니다.

이것은 더 탄력적이고 정확한 WorkflowsXQ를 건설하는 방법에 작은 가이드북입니다.

### API/Binding 호출은 idempotent입니다

단계가 여러 번 재생 될 수 있기 때문에, 단계는 idempotent해야합니다. context의 경우, idempotency는 작업 (이 경우 단계),
초기 응용 프로그램을 넘어 결과를 변경하지 않고 여러 번 적용 할 수 있습니다.

예를 들어, 고객이 청구하는 워크 플로우가 있다고 가정하고 사고에 의해 두 번 청구하지 않으려는 것이 좋습니다. 그들을 충전하기 전에, 당신은해야합니다
그들은 이미 충전 된 경우 확인 :

<TypeScriptExample filename="index.ts">
  ```ts
  export class MyWorkflow extends WorkflowEntrypoint {
  	async run(event: WorkflowEvent<Params>, step: WorkflowStep) {
  		const customer_id = 123456;
  		//✅ 좋은: Non-idempotent API/Binding 호출은 항상 ** 가동이 있는 경우에 검사 **
  		//아직 필요.
  		await step.do(
  			`charge ${customer_id} for its monthly subscription`,
  			async () => {
  				//고객이 이미 위탁한 경우 확인하는 API 호출
  				const subscription = await fetch(
  					`https://payment.processor/subscriptions/${customer_id}`,
  				).then((res) => res.json());

  				//고객이 이미 위탁한 경우에 이른 반환, 이것은 목적지 서비스가 죽는 경우에 일어날 수 있습니다
  				//요청의 중간에 여전히 그것을 투입, 또는 Workflows 엔진 재시작.
  				if (subscription.charged) {
  					return;
  				}

  				//non-idempotent 전화, 이 가동은 실패하고 재발할 수 있고 그러나 아직도 지불에 투입합니다
  				//프로세서 - 즉, 재try에, 그것은 위의 체크가 다시 지불 할 것
  				//아니.
  				return await fetch(
  					`https://payment.processor/subscriptions/${customer_id}`,
  					{
  						method: "POST",
  						body: JSON.stringify({ amount: 10.0 }),
  					},
  				);
  			},
  		);
  	}
  }
  ```
</TypeScriptExample>

:::참조

보장 idempotency는 당신의 특정한 사용 케이스 및 실시에서 선택적일지도 모르지만, 우리는 당신이 그것을 보장하기 위하여 항상 시도하는 것을 추천합니다.

:::

### 당신의 단계 과립

단계는 가능한 한 자기 유지해야합니다. 이것은 자체 로직을 통해 타사 API, 네트워크 오류 등의 실패의 경우보다 내구성이 높을 수 있습니다.

거래 또는 작업 단위로 생각할 수도 있습니다.

- ✅ 단계별 API/binding 호출의 수를 최소화합니다. (idempotency를 증명하기 위해 여러 통화가 필요).

<TypeScriptExample filename="index.ts">
  ```ts
  export class MyWorkflow extends WorkflowEntrypoint {
  	async run(event: WorkflowEvent<Params>, step: WorkflowStep) {
  		//✅ 좋은: 관련 API/Binding 외침은 각자 달성됩니다, 그래서 그들 중 하나가 실패한 경우에
  		//그것은 그들을 개별적으로 구할 수 있습니다. 그것은 또한 여분 이점이 있습니다: 당신은 retry 또는 통제할 수 있습니다
  		//각 과립 단계에 대한 타임 아웃 정책 - 당신은 overload http.cat을 초과 할 수 없습니다
  		//그것이 내려가는 경우에.
  		const httpCat = await step.do("get cutest cat from KV", async () => {
  			return await this.env.KV.get("cutest-http-cat");
  		});

  		const image = await step.do("fetch cat image from http.cat", async () => {
  			return await fetch(`https://http.cat/${httpCat}`);
  		});
  	}
  }
  ```
</TypeScriptExample>

그렇지 않으면 전체 작업 흐름은 당신이 생각할 수만큼 내구성이 될 수 있으며, 당신은 일부 정의 된 행동을 발생할 수 있습니다. 아래 규칙에 따라 그들을 피할 수 있습니다.

- ✓ 한 단계에 전체 논리를 캡슐화하지 마십시오.
- ✓ 동일한 단계에 별도의 서비스를 호출하지 마십시오 (idempotency를 증명할 필요가 없습니다).
- ✓ 같은 단계에 너무 많은 서비스 통화를하지 마십시오 (당신은 불균형을 증명해야).
- ✓ 단일 단계에서 너무 많은 CPU 집중적 인 작업을하지 마십시오 - 때로는 엔진이 재시작 할 수 있으며 그 단계의 시작부터 시작합니다.

<TypeScriptExample filename="index.ts">
  ```ts
  export class MyWorkflow extends WorkflowEntrypoint {
  	async run(event: WorkflowEvent<Params>, step: WorkflowStep) {
  		//✓ 나쁜 : 동일한 단계에서 두 개의 별도의 서비스를 호출합니다. 이 원인
  		//일부 추가 호출 첫 번째 서비스에 대한 경우 두 번째 실패, 일부 경우에,
  		//단계 non-idempotent altogether
  		const image = await step.do("get cutest cat from KV", async () => {
  			const httpCat = await this.env.KV.get("cutest-http-cat");
  			return fetch(`https://http.cat/${httpCat}`);
  		});
  	}
  }
  ```
</TypeScriptExample>

### 단계 밖에 상태에 의존하지 마십시오

Workflows는 모든 in-memory 국가를 고용하고 잃을지도 모릅니다. 엔진이 고장없는 일이 없다는 것을 감지하고 깨지지 않도록 할 때까지 하이킹 할 수 있습니다 (잠, 리트리 또는 이벤트 때문에).

이것은 당신이 단계의 밖에 국가를 저장하지 않다는 것을 의미합니다:

<TypeScriptExample filename="index.ts">
  ```ts
  function getRandomInt(min, max) {
  	const minCeiled = Math.ceil(min);
  	const maxFloored = Math.floor(max);
  	return Math.floor(Math.random() * (maxFloored - minCeiled) + minCeiled); //최대는 독점이며 최소는 포함
  }

  export class MyWorkflow extends WorkflowEntrypoint {
  	async run(event: WorkflowEvent<Params>, step: WorkflowStep) {
  		//✓ 나쁜 : `imageList`는 엔진의 수명에 따라 지속되지 않습니다. 어떤 의미를 hibernation,
  		//`imageList`는 뒤에 오는 2개 단계가 이미 ran가더라도 다시 비어질 것입니다.
  		const imageList: string[] = [];

  		await step.do("get first cutest cat from KV", async () => {
  			const httpCat = await this.env.KV.get("cutest-http-cat-1");

  			imageList.push(httpCat);
  		});

  		await step.do("get second cutest cat from KV", async () => {
  			const httpCat = await this.env.KV.get("cutest-http-cat-2");

  			imageList.push(httpCat);
  		});

  		//긴 수면은 (그리고 아마) 엔진을 하이킹을 의미하는 첫 번째 엔진 수명이 여기에 끝납니다
  		await step.sleep("💤💤💤💤", "3 hours");

  		//이 실행할 때, 그것은 두 번째 엔진 수명에있을 것입니다 - 이는 `imageList`가 비어있을 것입니다.
  		await step.do(
  			"choose a random cat from the list and download it",
  			async () => {
  				const randomCat = imageList.at(getRandomInt(0, imageList.length));
  				//`randomCat`가 비어 있기 때문에 `imageList`가 비어있습니다
  				return await fetch(`https://http.cat/${randomCat}`);
  			},
  		);
  	}
  }
  ```
</TypeScriptExample>

### 부작용을 방지`step.do`

작업 흐름 엔진이 실행중인 동안 다시 시작할 수 있기 때문에 반복 될 수 없다면 단계 이외의 부작용으로 코드를 작성하는 것이 좋습니다. 엔진이 재시작하면 단계 논리가 보존되지만 단계 이외의 논리는 복제 될 수 있습니다.

예를 들어,`console.log()`작업 흐름 단계의 외부는 엔진 재시작시 두 번 인쇄 할 수 있습니다.

그러나 데이터베이스 연결과 같은 비 직렬 리소스를 포함하는 논리는 단계 밖에 실행되어야한다. 외부 운영`step.do`Workflows' 인스턴스 수명주기의 본질 때문에 한 번 이상 반복 될 수 있습니다.

<TypeScriptExample filename="index.ts">
  ```ts
  export class MyWorkflow extends WorkflowEntrypoint {
  	async run(event: WorkflowEvent<Params>, step: WorkflowStep) {
  		//✓ Bad : 단계 밖에서 인스턴스 생성
  		//예상보다 더 많은 인스턴스를 생성하는 것보다 더 많은 것을 얻을 수 있습니다.
  		const badInstance = await this.env.ANOTHER_WORKFLOW.create();

  		//✓ 나쁜 : 단계 이외의 비-deterministic 기능을 사용하여
  		//이 인스턴스가 재시작해야 할 경우 다른 결과를 생성합니다.
  		//다른 길을 따라 갈 수 있습니다.
  		const badRandom = Math.random();

  		if (badRandom > 0) {
  			//몇 가지 물건
  		}

  		//⚠️ 경고: 이 로그는 많은 시간이 발생할 수 있습니다.
  		console.log("This might be logged more than once");

  		await step.do("do some stuff and have a log for when it runs", async () => {
  			//몇 가지 물건

  			//이 로그는 한 번만 나타납니다
  			console.log("successfully did stuff");
  		});

  		//✅ 좋은: 단계에 있는 non-deterministic 기능 포장
  		//실행 후에 성공적으로 다시 실행하지 않을 것입니다
  		const goodRandom = await step.do("create a random number", async () => {
  			return Math.random();
  		});

  		//✅ 좋은: 부작용이 단계 밖에 행해질 수 없는 전화
  		const db = createDBConnection(this.env.DB_URL, this.env.DB_TOKEN);

  		//✅ 좋은: 단계의 안쪽에 부작용을 가진 기능을 달립니다
  		//실행 후에 성공적으로 다시 실행하지 않을 것입니다
  		const goodInstance = await step.do(
  			"good step that returns state",
  			async () => {
  				const instance = await this.env.ANOTHER_WORKFLOW.create();

  				return instance;
  			},
  		);
  	}
  }
  ```
</TypeScriptExample>

### 당신의 들어오는 사건을 mutate하지 마십시오

더 보기`event`작업 흐름에 전달`run`방법은 immutable입니다: 이벤트에 변경은 단계와 / 또는 Workflow 재시작을 통해 지속되지 않습니다.

<TypeScriptExample filename="index.ts">
  ```ts
  interface MyEvent {
  	user: string;
  	data: string;
  }

  export class MyWorkflow extends WorkflowEntrypoint {
  	async run(event: WorkflowEvent<MyEvent>, step: WorkflowStep) {
  		//✓ 나쁜 : 이벤트를 계산
  		//이것은 단계와 `event.payload`의 맞은편에 지속되지 않을 것입니다
  		//그것의 본래 가치에 가지고 가십시오.
  		await step.do("bad step that mutates the incoming event", async () => {
  			let userData = await this.env.KV.get(event.payload.user);
  			event.payload = userData;
  		});

  		//✅ 좋은: 당신의 단계에서 국가로 반환해서 persist 자료
  		//다음 단계의 상태 사용
  		let userData = await step.do("good step that returns state", async () => {
  			return await this.env.KV.get(event.payload.user);
  		});

  		let someOtherData = await step.do(
  			"following step that uses that state",
  			async () => {
  				//userData에 대한 액세스
  				//이 단계가 되면 항상 동일하게 될 것입니다.
  			},
  		);
  	}
  }
  ```
</TypeScriptExample>

### 이름 단계 deterministically

단계는 deterministically 지명되어야 합니다 (그, 현재 날짜/시간, 무작위, 등을 사용하지 않는). 이것은 그들의 국가가 캐시되고, 중단되지 않는 한 단계가 막습니다. 단계 이름은 작업 흐름에서 "cache key"로 작용합니다.

<TypeScriptExample filename="index.ts">
  ```ts
  export class MyWorkflow extends WorkflowEntrypoint {
  	async run(event: WorkflowEvent<Params>, step: WorkflowStep) {
  		//──────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────
  		//다음 단계가 실패하면 다시 실행되는 단계가 발생합니다.
  		await step.do(`step #1 running at: ${Date.now()}`, async () => {
  			let userData = await this.env.KV.get(event.payload.user);
  			//이벤트는 없습니다. 결제하기
  			event.payload = userData;
  		});

  		//✅ 좋은: deterministic 이름을 줍니다.
  		//상태의 동적 값을 반환하거나 대신 로그하십시오.
  		let state = await step.do("fetch user data from KV", async () => {
  			let userData = await this.env.KV.get(event.payload.user);
  			console.log(`fetched at ${Date.now()}`);
  			return userData;
  		});

  		//✅ 좋은: 역동적으로 지명되는 단계는 deterministic 방법에 건설합니다.
  		//이 경우에, `catList`는 안정되어 있는 단계 산출이고, `catList`는 입니다
  		//세례적인 패션에서 배운 (shuffles 또는 random accesses) 그래서,
  		//그것은 역동적으로 이름 단계 (예를 들면: 목록 입장 당 단계를 창조합니다).
  		let catList = await step.do("get cat list from KV", async () => {
  			return await this.env.KV.get("cat-list");
  		});

  		for (const cat of catList) {
  			await step.do(`get cat: ${cat}`, async () => {
  				return await this.env.KV.get(cat);
  			});
  		}
  	}
  }
  ```
</TypeScriptExample>

### 자주 묻는 질문`Promise.race()`·`Promise.any()`

Workflows는 사용법 단계를 안쪽으로 허용합니다`Promise.race()`또는`Promise.any()`concurrent 단계 실행을 달성하는 방법. 그러나 일부 고려사항이 취해야 합니다.

Workflows' 인스턴스 수명주기의 성격에 따라 Promise 내부의 단계가 완료 될 때까지 실행 될 수 있음을 주어진, 첫 번째 통과 동안 반환되는 단계는 실제 캐시 단계가 될 수 없습니다,[단계는 그들의 이름에 의해 캐시됩니다](#name-steps-deterministically).

<TypeScriptExample filename="index.ts">
  ```ts
  //helper 수면 방법
  const sleep = (ms: number) => new Promise((r) => setTimeout(r, ms));

  export class MyWorkflow extends WorkflowEntrypoint {
  	async run(event: WorkflowEvent<Params>, step: WorkflowStep) {
  		//✅ 나쁜: `Promise.race`는 `step.do`XQ에 의해 포위되지 않습니다, undeterministic 캐싱 행동을 일으킬 수 있습니다.
  		const race_return = await Promise.race([
  			step.do("Promise first race", async () => {
  				await sleep(1000);
  				return "first";
  			}),
  			step.do("Promise second race", async () => {
  				return "second";
  			}),
  		]);

  		await step.sleep("Sleep step", "2 hours");

  		return await step.do("Another step", async () => {
  			//이 단계는 QX`first`, 심지어 `Promise.race` 처음 반환 `second`를 반환합니다.
  			return race_return;
  		});
  	}
  }
  ```
</TypeScriptExample>

일관성을 보장하기 위해, 우리는 서라운드를 제안합니다`Promise.race()`또는`Promise.any()`내 계정`step.do()`, 이것은 다수 통행의 앞에 캐싱 견실함을 지킬 것입니다.

<TypeScriptExample filename="index.ts">
  ```ts
  //helper 수면 방법
  const sleep = (ms: number) => new Promise((r) => setTimeout(r, ms));

  export class MyWorkflow extends WorkflowEntrypoint {
  	async run(event: WorkflowEvent<Params>, step: WorkflowStep) {
  		//✅ 좋은: `Promise.race`는 `step.do`에 의해 포위되고, deterministic 캐싱 행동을 지키.
  		const race_return = await step.do("Promise step", async () => {
  			return await Promise.race([
  				step.do("Promise first race", async () => {
  					await sleep(1000);
  					return "first";
  				}),
  				step.do("Promise second race", async () => {
  					return "second";
  				}),
  			]);
  		});

  		await step.sleep("Sleep step", "2 hours");

  		return await step.do("Another step", async () => {
  			//이 단계는 QX`Promise.race`XQ가 `step.do` 방법의 서라운드이기 때문에 `second`XQ를 반환합니다.
  			return race_return;
  		});
  	}
  }
  ```
</TypeScriptExample>

### Instance ID는 고유합니다

작업 흐름[인스턴스 ID](/workflows/build/workers-api/#workflowinstance)Workflow의 장점 ID는 로그, 메트릭스, 상태 및 상태, 완료 후 특정 인스턴스로 실행되는 고유 식별자입니다. ID 재사용을 허용하면 작업 흐름 인스턴스 ID가 어제, 지난 주 또는 오늘 실행되는 인스턴스에 언급 한 경우 이해하기가 어렵습니다.

다른 여러 작업 흐름 인스턴스를 실행하려는 경우도 문제가 발생할 것입니다.[입력 모수](/workflows/build/events-and-parameters/)동일한 사용자 ID의 경우 즉시 새로운 ID 매핑을 결정해야합니다.

특정 사용자, 상인 또는 다른 "customer" ID와 함께 여러 인스턴스를 연결해야하는 경우 복합 ID를 사용하거나 무작위로 생성 된 ID를 사용하고 데이터베이스에서 매핑을 저장하십시오.[모델 번호: D1](/d1/).

<TypeScriptExample filename="index.ts">
  ```ts
  //이것은 당신의 Workflow 정의와 같은 파일에 있습니다.
  export default {
  	async fetch(req: Request, env: Env): Promise<Response> {
  		//✓ 나쁜 : 미래의 Workflow invocations에서 고유하지 않은 ID를 사용하십시오.
  		let userId = getUserId(req); //userId를 반환
  		let badInstance = await env.MY_WORKFLOW.create({
  			id: userId,
  			params: payload,
  		});

  		//✅ 좋은: 고유한 ID를 사용하십시오
  		//e.g. 거래 ID, 주문 ID 또는 작업 ID는 좋은 옵션입니다.
  		let instanceId = getTransactionId(); //e.g. assuming 거래 ID는 고유
  		//또는: 합성 ID를 구성하고 데이터베이스에 저장
  		//특정 사용자 또는 상인과 관련된 모든 인스턴스를 추적 할 수 있습니다.
  		instanceId = `${getUserId(req)}-${crypto.randomUUID().slice(0, 6)}`;
  		let { result } = await addNewInstanceToDB(userId, instanceId);
  		let goodInstance = await env.MY_WORKFLOW.create({
  			id: instanceId,
  			params: payload,
  		});

  		return Response.json({
  			id: goodInstance.id,
  			details: await goodInstance.status(),
  		});
  	},
  };
  ```
</TypeScriptExample>

### `await`당신의 단계

전화 번호`step.do`또는`step.sleep`, 사용`await`여러분의 Workflow 코드로 버그와 레이스 조건을 소개하는 것을 피하십시오.

전화 번호`await step.do`또는`await step.sleep`, 당신은 dangling Promise를 만듭니다. Promise가 생성되었지만 제대로 작동하지 않을 때 발생합니다.`await`ed, 잠재적 인 버그 및 인종 조건에 선도.

이것은 당신이 사용할 수없는 때 발생합니다`await`키워드 또는 체인에 실패`.then()`Promise의 결과를 처리하는 방법. 예를 들어, 호출`fetch(GITHUB_URL)`응답을 기다리지 않고 나중에 코드를 즉시 실행할 수 있습니다. 이것은 premature 로깅과 같은 문제를 일으킬 수 있습니다, 예외는 삼키지 않는 (작업 흐름을 종료하지 않음), 그리고 반환 값 (state).

<TypeScriptExample filename="index.ts">
  ```ts
  export class MyWorkflow extends WorkflowEntrypoint {
  	async run(event: WorkflowEvent<Params>, step: WorkflowStep) {
  		//✓ 나쁜 : 단계가 기다리고 있지 않으며 어떤 국가 또는 오류가 반환하기 전에 삼키지 않습니다.
  		const badIssues = step.do(`fetch issues from GitHub`, async () => {
  			//이 호출 전에 단계가 반환됩니다
  			let issues = await getIssues(event.payload.repoName);
  			return issues;
  		});

  		//✅ 좋은: 단계는 제대로 기다리고 있습니다.
  		const goodIssues = await step.do(`fetch issues from GitHub`, async () => {
  			let issues = await getIssues(event.payload.repoName);
  			return issues;
  		});

  		//작업 흐름의 나머지는 여기에 간다!
  	}
  }
  ```
</TypeScriptExample>

### 상태 논리를 주의깊게 사용하십시오

사용 가능`if`문, 루프 및 기타 제어 흐름 단계 밖에. 그러나 조건은 근거해야 합니다.**deterministic 가치**— 값에서`event.payload`또는 이전 단계에서 값 반환. Non-deterministic 상태 (와 같은`Math.random()`또는`Date.now()`) 단계의 외부는 Workflow 재시작시 예상치 못한 행동을 일으킬 수 있습니다.

<TypeScriptExample filename="index.ts">
  ```ts
  export class MyWorkflow extends WorkflowEntrypoint {
  	async run(event: WorkflowEvent<Params>, step: WorkflowStep) {
  		const config = await step.do("fetch config", async () => {
  			return await this.env.KV.get("feature-flags", { type: "json" });
  		});

  		//✅ 좋은: 단계 산출 (deterministic)에 근거를 둔 조건
  		if (config.enableEmailNotifications) {
  			await step.do("send email", async () => {
  				//이메일 logic
  			});
  		}

  		//✅ 좋은: 사건 탑재량 (deterministic)에 근거를 둔 조건
  		if (event.payload.userType === "premium") {
  			await step.do("premium processing", async () => {
  				//프리미엄 전용 로직
  			});
  		}

  		//✓ 나쁜 : 단계 이외의 비 결정적인 값에 따라 조건
  		//이것은 Workflow 재시작이 다르게 동작할 수 있었습니다.
  		if (Math.random() > 0.5) {
  			await step.do("maybe do something", async () => {});
  		}

  		//✅ 좋은: 단계에 있는 포장 non-deterministic 가치
  		const shouldProcess = await step.do("decide randomly", async () => {
  			return Math.random() > 0.5;
  		});
  		if (shouldProcess) {
  			await step.do("conditionally do something", async () => {});
  		}
  	}
  }
  ```
</TypeScriptExample>

### 일괄 다중 작업 흐름 invocations

여러 작업 흐름 인스턴스를 만들 때, 사용[`createBatch`](/workflows/build/workers-api/#createBatch)invocations를 함께 배치하는 방법. 이것은 Workflows API로 만든 요청의 수를 줄일 수있는 단일 요청에 여러 워크 플로우 인스턴스를 만들 수 있습니다. 그러나 일괄 처리의 각 개별 인스턴스는 여전히 계산됩니다.[생성 속도 제한](/workflows/reference/limits/). 싫어`create`, `createBatch`idempotent: 동일한 ID를 가진 기존 인스턴스가 아직도 있는 경우에[보유 제한](/workflows/reference/limits/), 반환된 배열에서 건너뛰고 제외될 것입니다.

<TypeScriptExample filename="index.ts">
  ```ts
  export default {
  	async fetch(req: Request, env: Env): Promise<Response> {
  		let instances = [
  			{ id: "user1", params: { name: "John" } },
  			{ id: "user2", params: { name: "Jane" } },
  			{ id: "user3", params: { name: "Alice" } },
  			{ id: "user4", params: { name: "Bob" } },
  		];

  		//✓ 나쁜 : 그들 하나씩 만들기, 더 많은 것은 생성 속도 제한을 명중 할 가능성이.
  		for (let instance of instances) {
  			await env.MY_WORKFLOW.create({
  				id: instance.id,
  				params: instance.params,
  			});
  		}

  		//✅ 좋은: 일괄 통화 함께
  		//이 향상 처리량.
  		let createdInstances = await env.MY_WORKFLOW.createBatch(instances);
  		return Response.json({ instances: createdInstances });
  	},
  };
  ```
</TypeScriptExample>

### 1 MiB 아래 단계 반환 값 유지

각 단계는 상태의 1 MiB (2^20 바이트)까지 persist 할 수 있습니다. 단계가 이 한계를 초과하는 데이터를 반환하면 단계가 실패합니다. 이것은 큰 API 응답을 fetching 또는 대형 파일을 처리 할 때 일반적인 문제입니다.

이 한계의 주위에 일하기 위하여, 외부로 큰 자료를 저장하십시오 (예를 들면, R2 또는 KV)와 반환 reference:

<TypeScriptExample filename="index.ts">
  ```ts
  export class MyWorkflow extends WorkflowEntrypoint {
  	async run(event: WorkflowEvent<Params>, step: WorkflowStep) {
  		//✓ 나쁜 : 1 MiB를 초과 할 수있는 큰 응답을 반환
  		const largeData = await step.do("fetch large dataset", async () => {
  			const response = await fetch("https://api.example.com/large-dataset");
  			return await response.json(); //1 MiB를 초과할 수 있었습니다
  		});

  		//✅ 좋은: 외부 저장 큰 자료 및 반환 reference
  		const dataRef = await step.do("fetch and store large dataset", async () => {
  			const response = await fetch("https://api.example.com/large-dataset");
  			const data = await response.json();
  			//R2에 저장하고 referenceXQ를 반환합니다
  			await this.env.MY_BUCKET.put("dataset-123", JSON.stringify(data));
  			return { key: "dataset-123" };
  		});

  		//필요한 경우 나중에 단계에 데이터를 검색
  		const data = await step.do("process dataset", async () => {
  			const stored = await this.env.MY_BUCKET.get(dataRef.key);
  			return processData(await stored.json());
  		});
  	}
  }
  ```
</TypeScriptExample>
