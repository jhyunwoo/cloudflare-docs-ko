## 제품정보

이 가이드는 건축가 및 개발자를 위한 포괄적인 층 7 (L7) 신청 성과 전략을 설명합니다. 오늘날의 경쟁력 있는 디지털 풍경에서**Application 성과는 중요한 사업 differentiator입니다**. 그러나, 궁극적인 목적은 성과 보안 평등점을 찾는다.

이 가이드는 최대화 속도와 사용자 경험 (UX)에 초점을 맞추고, 성능은 보안 비용에 올 수 없습니다. Architects는 DDoS 보호, WAF 및 Bot 관리와 같은 엄격한 보안 통제의 필요한 처리 오버 헤드에 대하여 대기시간 감소를 균형을 잡아야 합니다.

높은 위험 시나리오에서 보안은 이러한 성능 최적화에서 얻은 "경쟁 예산"이 전략적으로 전원 보호에 의존하는 반면 응용 프로그램은 사용자를 변환하고 비즈니스를 보호하기 위해 충분히 빠르게 남아있다.

:::참조
성능 최적화는 "right"metrics 및 개선이 각 조직 및 응용 프로그램에 고유 할 수있는 높은 컨텍스트 endeavor입니다.

이 아키텍처에 따라 조직은 다음을 기대할 수 있습니다.

- **핵심 웹 비틀림 개선 (CWV)**&#x4C;CP 및 INP와 같은, 이는 반송 속도와 드라이브 판매를 줄일 수 있습니다.
- Cache Hit Ratio를 극대화하고, 출발점에서 트래픽을 오프로드하고, 인프라 지출을 감소시키고, 전체**운영 비용 절감**.
- 높은 가동 시간/availability 및**사업 탄력**교통 스파이크 중에도.

## 성과 목표 및 미터

[측정 성능은 까다로운](https://blog.cloudflare.com/loving-performance-measurements/), 그리고 그것은 더 넓은 사업 상황에 대 한 보안 및[견적 요청](https://www.cloudflare.com/trust-hub/)종종 non-negotiable prerequisites입니다. 조직은 종종 자신의 아키텍처가 규제 기준을 충족한다는 것을 검증합니다 (예 :[자료 residency](https://www.cloudflare.com/learning/privacy/what-is-data-localization/)또는[암호화 프로토콜](/ssl/reference/protocols/), 등[포스트 시즌 암호화 (PQC)](/ssl/post-quantum-cryptography/)) 성능 기능을 잠금 해제 하기 전에.

이러한 보안 및 준수 기본은 보안되면 효과적인 최적화는 모두 약간 다릅니다. Untheless, 대부분의 사람들은 웹 사이트 성능에 대한 사용자 중심 미터에 초점을 맞추고, 사용[진단 기구로 TTFB](https://blog.cloudflare.com/ttfb-is-not-what-it-used-to-be/)서버 응답을 위해, 그러나 우선[핵심 웹 Vitals (CWV)](https://www.cloudflare.com/learning/performance/what-are-core-web-vitals/)측정 사용자 경험.

성공적인 구현은 이러한 미터에 의해 측정된다:

| 기본 정보                          | 대상 (75 % )    | 어떤 측정                                                                                                                                                                                  |
| :----------------------------- | :------------ | :------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **가장 큰 Contentful 페인트 (LCP)**  | \< 2.5 s="">  | 적재 성능 (hero image/text 가시성).                                                                                                                                                           |
| **Next Paint에 대한 상호 작용 (INP)** | \< 200 ms=""> | 입력에 상호 작용 및 응답.                                                                                                                                                                        |
| **Cumulative 배치 이동 (CLS)**     | \< 0.1        | 비주얼 안정성 (expected layout shifts).                                                                                                                                                      |
| **처음 바이트로 시간 (TTFB)**          | \< 800 ms=""> | 서버 응답 (network + 처리 시간). 연결 성능에 대한 깊은 가시성 확보[*cf.timings.origin ttfb msec의*](/ruleset-engine/rules-language/fields/reference/cf.timings.origin_ttfb_msec/)네트워크 오버헤드의 근원 지연을 고립시키기 위하여. |

75 %ile 표적은 입니다[이전 분석 기준](https://web.dev/articles/defining-core-web-vitals-thresholds)적당한 균형을 위해.

한국어[이전 분석](https://web.dev/articles/defining-core-web-vitals-thresholds)CWV, 서버 측 대기 시간 미터 (TTFB와 같이)를 위한 75 %ile에서 보는 추천은 99th 퍼센트 (P99) 또는 더 높은에 감시되어야 합니다. 단일 사용자 세션은 종종 수십 개의 요청을 포함합니다.[사용자의 확률이 늦은 스파이크를 경험하지](https://blog.cloudflare.com/loving-performance-measurements/)median (P50)의 위 0. ### 1. 사용자 (아이볼 클라이언트)

성능 여행은 고객의 장치에서 시작됩니다. 장치 하드웨어,[\* 이름](https://caniuse.com/), 네트워크 질 및 topology는 초기 응답을 결정합니다. 이 목표는 Cloudflare 네트워크에 가장 빠른 가능한 연결을 설정하는 것입니다.

- **DNS 해결책:**&#xD074;라이언트 장치는 도메인을 쿼리하고 공용 DNS 해결자와 궁극적으로, 권위있는 DNS 서버로 이동. Cloudflare의[글로벌 anycast 네트워크](https://www.cloudflare.com/network/)Presence (PoP)의 가장 가까운 지점에 대한 경로 요청[글로벌 DNS](https://www.dnsperf.com/)해결은 최소 보정 대기 시간을 보장, 확장 할 수있는 가능성을 포함하여[중국본토](/china-network/).
- **연결 설치:**&#xD074;라이언트는 IPv4/를 통해 연결을 설정[IPv6를](/network/ipv6-compatibility/)이름 \*[HTTP/3 (필수)](/speed/optimization/protocol/http3/)·[사이트맵](/ssl/edge-certificates/additional-options/tls-13/)- 이것은 또한 허용합니다[포스트 시즌 암호화 (PQC)](/ssl/post-quantum-cryptography/). 클라이언트가 전에 방문한 경우에,[0-RTT 연결 Resumption](/speed/optimization/protocol/0-rtt-connection-resumption/)Handhake 도중 둥근 지구를 삭제합니다. 또한,[HTTP 엄격한 운송 보안 (HSTS)](/ssl/edge-certificates/additional-options/http-strict-transport-security/)브라우저 측이 HTTPS로 리디렉션을 시행하고 불필요한 서버 왕복을 제거하십시오. 그것은 일반적으로 권장[HTTPS 연결](/ssl/edge-certificates/encrypt-visitor-traffic/). 게다가, 관련 레버리지로[TCP 필드](/changelog/2025-10-30-tcp-rtt-and-tcp-fields/), 당신은 적응 성능 전략을 실행할 수 있습니다.
- **브라우저 최적화:**&#xAC19;은 특징[속도 뇌](/speed/optimization/content/speed-brain/)(Speculation 규칙 API) proactively prefetch 자원, 동안[초기 힌트](/cache/advanced-configuration/early-hints/)링크 헤더를 브라우저에서 "서버는 시간을 생각", 속도 페이지 렌더링.
- **제 3 부 Offloading:** [스낵 바](/zaraz/)오프로드 타사 도구 (Google Analytics 4 또는 Mixpanel과 같은) 클라우드에. 이것은 장치에서 막는 주요 실을 감소시키고, 두드러지게 INP를 개량합니다.
- **웹 분석 (RUM):**&#xB808;버리지 Cloudflare[웹 분석](/web-analytics/)개인정보 수집 및 이용목적이 달성된 후에는 해당 정보를 지체없이 파기합니다. 이 경량 JavaScript 비콘은 사용자를 추적하거나 클라이언트 측 상태를 저장하지 않고 Core Web Vitals (LCP, INP, CLS)에 실제 통찰력을 제공합니다.

![그림 2: Argo Smart Routing, Tiered Cache, Cache Reserve, Connection Reuse, Dedicated Egress IPs, Load Balancing을 보여주는 Smart Shield 고급 네트워크 다이어그램.](~/assets/images/smart-shield/network-diagram.png "Figure 2: Smart Shield Advanced network diagram")

### 2. 네트워크와 최적화 (Cloudflare 가장자리)

요청이 네트워크 가장자리에 도달하면 Cloudflare 프로세스가 진행되거나 캐시에서 fetched 전에 콘텐츠를 최적화합니다.

- **교통 관리:**&#xC694;청은 검사됩니다.[URL 정상화](/rules/normalization/)일관성을 유지하면서[Redirect 규칙](/rules/url-forwarding/)또는[Transform 규칙](/rules/transform/)경로를 효율적으로 처리합니다.[대기실](/waiting-room/)동안 백엔드를 보호합니다.[큰 교통 수술](/learning-paths/surge-readiness/concepts/), 가용성 유지.
- **Programmatic 주문화:**&#xD45C;준 규칙이 부족한 고급 사용 사례[스니펫과 Workers](/rules/snippets/when-to-use/)programmatic 사용자 정의 허용. 이것은 헤더를 수정하기 위해 사용자 정의 코드 논리를 실행, URL을 다시 쓰기,[이미지 최적화](/images/transform-images/transform-via-workers/), 또는 가장자리에 독특한 캐싱 논리를 직접 구현. 기타 제품[서비스 바인딩](/workers/runtime-apis/bindings/service-bindings/)이 Workers 사이 저속, 제로 오버헤드 커뮤니케이션을 촉진하기 위하여.
- **공급 능력:**&#xD14D;스트 자산은 압축[압축 규칙](/rules/compression-rules/)(Brotli/Gzip). 이미지가 처리됩니다.[이미지 변환](/images/transform-images/)또는[담당자: Ms.](/images/polish/)그들은 최적의 형식으로 제공됩니다 (AVIF / WebP) 및 장치에 대한 크기, 크게 LCP 및 CLS를 개선.
- **글꼴 & 꼬리표 최적화:** [Cloudflare 글꼴](/speed/optimization/content/fonts/)DNS 조회 및 TLS 연결을 Google 글꼴에 제거하여 도메인에서 인라인으로 제공합니다.[Google 태그 게이트웨이](/google-tag-gateway/)광고 신호 측정 및 개인 정보 보호 향상.
- **Routing, 가용성 & 의정서 정보:**&#x43;loudflare는 가장 중 하나입니다[연결된 네트워크](https://blog.cloudflare.com/network-performance-update-birthday-week-2025/)세계에서 13,000 개 이상의 네트워크를 보유한 피어링[글로벌 백본](https://blog.cloudflare.com/backbone2024/), 주요 수에 참여[인터넷 교환 포인트 (IXPs)](https://bgp.he.net/report/exchanges#_participants)글로벌 우리는 레버리지[기업 정보](https://blog.cloudflare.com/how-cloudflare-uses-the-worlds-greatest-collection-of-performance-data/)이 대규모 데이터 세트에서 동적으로 Congestion Control(CC)을 프로토콜 수준에서 최적화하여 실시간 네트워크 조건을 기반으로 모든 연결에 적합한 최적의 알고리즘과 튜닝 적절한 매개 변수를 자동으로 선택합니다. 캐시 할 수없는 동적 요청을 위해,[Argo 스마트 여정](/argo-smart-routing/)네트워크를 통해 가장 빠른 경로 발견.[사용자 정의 오류](/rules/custom-errors/)실패 중에 일관된 브랜드 경험을 제공합니다.

### 3. 층계 캐시 및 저장 (Cloudflare 가장자리)

Cloudflare는 특정한 topology로 조직될 수 있습니다. 이 층은 내용 보유와 retrieval를 취급합니다. 그것은 기원과 고객을 위한 고속 상점을 위한 방패로 작동합니다.

- **캐시 논리:** [근원 캐시 통제 우두머리](/cache/concepts/cache-control/), [캐시 규칙](/cache/how-to/cache-rules/)·[캐싱 레벨](/cache/how-to/set-caching-levels/)TTL 및 쿼리 문자열 처리에 정확한 제어를 허용한다. Cache Normalization 전략을 구현하여 변수 URL을 사용하여 요청을 통합합니다.[캐시 키](/cache/how-to/cache-keys/), 두드러지게 개량하는 캐시 타격 비율.[Prefetch URL을](/speed/optimization/content/prefetch-urls/)캐쉬를 미리 팔 수 있습니다. 중요 한 자산을 통해 표시된 파일을 통해 더 늦게 감소. 이름 \*[기본 캐싱 동작과 한계](/cache/concepts/default-cache-behavior/#default-cached-file-extensions).
- **공급 능력:**&#xCF58;텐츠가 로컬 PoP가 아닌 경우, Cloudflare는 위층 캐시 토폴을 검사합니다.[Smart Tiered 캐싱](/cache/how-to/tiered-cache/)·[지역 계층 캐시](/cache/how-to/tiered-cache/#regional-tiered-cache)연결 중앙화, 캐시 히트 비율 증가 및 글로벌 소스로드 감소. 더 많은 사용자 정의 접근을 위해, 기업 고객은 선택할 수 있습니다[주문 Tiered 캐시](/cache/how-to/tiered-cache/#custom-tiered-cache)topology.
- **전용 장기 캐시:** [Cache 예약](/cache/advanced-configuration/cache-reserve/)대용량의 수명을 확장, 특히 접근 자산 (예를 들어, 이미지, 아카이브 비디오, 소프트웨어 업데이트, 또는 정적 AI 모델) 영구 객체 저장 백엔드 (R2에 의해 구동). 이로 인해 퇴치 방지[Least 최근 사용 (LRU)](/cache/concepts/retention-vs-freshness/)알고리즘 및 지연 발생 기원 fetches 방지, 동시에 스토리지 중복 및 탄력 요구 사항을 지원.
- **즉시 퍼지:**&#xB808;버리지 Cloudflare의[분산된 정화 건축](https://blog.cloudflare.com/instant-purge-for-all/)전 세계적으로 약 150ms의 콘텐츠를 유효성 검사합니다. 이름 \*[즉시 Purge](/cache/how-to/purge-cache/)기능은 URL, Tag, Prefix 또는 Hostname에 의해 Purge를 포함한 다양한 과립 접근 방식을 지원합니다. 사용자는 TTL 만료를 기다리지 않고 신선한 콘텐츠를 즉시받습니다.
- **클라우드 연결성:** [클라우드 커넥터 규칙](/rules/cloud-connector/)특정 객체 저장 또는 원산지 요구 사항에 대한 공공 클라우드 제공 업체 (AWS, Azure, GCP)에 트래픽을 라우팅합니다. 개인 인프라의 경우,[모델 번호: Workers VPC](/workers-vpc/)공공 인터넷에 배포하지 않고 공공 클라우드(예: AWS, Azure)의 프라이빗 스토리지 엔드포인트 또는 데이터베이스에 직접 연결 가능
- **정적 자산 호스팅:**&#xC751;용 프로그램의 전체 부품 (앞 자산, 대형 미디어 파일, 소프트웨어 패키지 포함 이미지) 직접 저장할 수 있습니다[R2 목표 저장](/r2/)또는[Workers 정체되는 자산](/workers/static-assets/), 전통적인 기원 서버를 타격하지 않고 가장자리에서 그들을 봉사. 기타 제품[저장 옵션](/workers/platform/storage-options/)있습니다.

### 4. 근원 서버

전체 경로 (즉, 동적 콘텐츠 또는 캐시 미스트)를 가로 질러야 할 요청을 위해, 기원 구성은 최종 대기 충격을 결정합니다. Architects는 다음과 같은 두 가지 주요 경로가 있습니다. performant, resilient serverless 모델을 채택하거나 기존 Origin Server의 연결 및 보안을 최적화하십시오.

**서버리스:**&#x43;loudflare의[개발자 플랫폼](/learning-paths/workers/devplat/intro-to-devplat/)"originless" 모델을 활성화하여 최적의 성능 계층을 달성합니다.[Fullstack 응용](/reference-architecture/diagrams/serverless/fullstack-application/)전 세계 글로벌 가장자리 네트워크에 직접 구축하고 배포, 먼 기원에 전체 경로 traversal 제거. 동적 요청은 가장 가까운 Cloudflare PoP에서 실행하고 통합에 원활한 액세스를 제공합니다.[Edge 스토리지 솔루션](/workers/platform/storage-options/)R2 개체 저장 및 D1 Serverless SQLite 데이터베이스와 같은. 이것은 TTFB를 감소시키고 공격적인 CWV 표적에 크게 공헌합니다. 또한,이 Originless 모델, 레버리지 Workers 및 R2, 고성능 파일 배포를위한 최적의 디자인이며 전통적인 백엔드 서버를 제거하여 대용량 데이터셋 및 미디어를 제공합니다.

**전통적인 근원 Optimization:**&#xD560; 수없는 응용[refactored 또는 현대화](https://www.cloudflare.com/modernize-applications/)원래 모델에, 다음과 같은 최적화는 전통적인 인프라의 결과로 대기 오염을 최소화해야합니다:

- **연결성:**&#x43;loudflare는 사용을 연결합니다[HTTP/2의 근원](/speed/optimization/protocol/http2-to-origin/), 사용[연결 재사용](/smart-shield/concepts/connection-reuse/)단일 지속 가능한 연결에 다중화 요청으로 TCP/TLS 오버 헤드를 줄입니다. 강화된 신뢰성 및 안전을 위해,[Cloudflare 네트워크 상호 연결 (CNI)](/network-interconnect/)Cloudflare에 직접 네트워크 인프라를 연결 할 수 있습니다 - 공공 인터넷을 우회 - 더 많은 수행 및 안전한 경험을 위해. 또한 레버리지[대역폭 얼라이언스](https://www.cloudflare.com/bandwidth-alliance/)(같은 파트너 포함)[Microsoft Azure 루팅 P참고 자료](https://www.cloudflare.com/en-gb/partners/technology-partners/microsoft/azure-routing-preference/))는 크게 감소하거나 waive 자료 egress 비용 할 수 있습니다.
- **개인 인프라:** [모델 번호: Workers VPC](/workers-vpc/)·[Cloudflare 갱도](/cloudflare-one/networks/connectors/cloudflare-tunnel/)개인 저장 엔드포인트 또는 데이터베이스에 직접 연결이 가능하여 반드시 공용 인터넷에 폭발하지 않고 공공 클라우드에.
- **짐 균형을 잡기:**&#xD2B8;래픽은 건강한 서버에서 배포됩니다.[Cloudflare 부하 균형](/load-balancing/understand-basics/proxy-modes/). 근원이 실패한 경우에, 교통은 즉시 건강한 서버 수영장에 rerouted. 대안으로,[라운드 로빈 DNS](/dns/manage-dns-records/how-to/round-robin-dns/)단순한 배포 전략을 위해 사용될 수 있습니다.

  - [즉시 로그인](/logs/instant-logs/): 즉시 디버깅을위한 실시간 트래픽 검사.
  - [네트워크 오류 로깅 (NEL)](/network-error-logging/): 서버가 결코 볼 수 없다는 클라이언트 측 연결 문제 캡처.
