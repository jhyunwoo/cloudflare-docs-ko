## 제품정보

오늘 조직은 점점 더 채택[Zero Trust 보안](https://www.cloudflare.com/learning/security/glossary/what-is-zero-trust/)끊임없이 진화하는 위협 환경에서 기업 자산 및 인프라를 보호하는 자세. 레거시 네트워크 설계와 관련된 전통적인 보안은 기업 네트워크 둘레 내에서 신뢰를 가정합니다. 대조적으로, Zero Trust는 "Never trust, 항상 확인합니다"의 원리에 작동하고 지속적인 구현[인증 및 엄격한 액세스 제어](https://www.cloudflare.com/learning/access-management/what-is-access-control/)모든 사용자, 장치, 응용 프로그램, 해당 위치 또는 네트워크에 관계없이.

일반적으로 두 개의 기술은 Zero Trust 아키텍처에서 역할을합니다. 첫째, a[보안 웹 게이트웨이 (SWG)](https://www.cloudflare.com/learning/access-management/what-is-a-secure-web-gateway/)인터넷을 위해 중단 된 아웃 바운드 트래픽을 필터링하고 피싱 캠페인과 관련된 높은 위험 웹 사이트에 액세스하는 차단 사용자. 그런 다음 SaaS 앱, 내부 호스팅 응용 프로그램 및 네트워크, Zero Trust 네트워크 액세스에 대한 원격 액세스를 가능하게합니다 ([사이트맵](https://www.cloudflare.com/learning/access-management/what-is-ztna/)) 서비스는 안전한 갱도를 창조하고 원격 사용자를 개인적인 신청으로 접근을 제공합니다.

이 가이드는 Cloudflare의 ZTNA 서비스를 배포하려는 고객을위한 것입니다 ([오시는 길](/cloudflare-one/access-controls/policies/)) 효과적으로 올바른 정책을 구축하는 방법에 대한 모범 사례 및 지침을 제공합니다. 이미 그렇게하지 않은 경우, 우리는 또한 Cloudflare의 읽는 것을 추천합니다[SASE 참고 자료 건축](/reference-architecture/architectures/sase/)Cloudflare를 Zero Trust 이니셔티브의 일부로 사용하는 방법의 모든 측면에 대한 세부 사항으로 간다.

### 이 문서는 누구입니까?

이 문서는 기존 VPN 서비스를 대체하거나 내부 리소스에 새로운 원격 액세스를 제공하도록 Cloudflare를 채택한 관리자를 대상으로합니다. 이것은 첫 번째 ZTNA 정책을 설계하고 지속적인 참고 자료로 시작하는 시점 역할을합니다. 이 가이드는 3개의 주요 단면도를 포함합니다:

- **기술 요구 사항**: 첫 번째 응용 프로그램에 액세스하고 액세스 정책을 정의하기 전에 어떤 장소에 있어야합니다.
- **건물 정책**: 액세스 정책의 주요 구성 요소와 결합 된 방법.
- **사용 사례**: 본 정책 디자인의 Blueprint로 제공 할 수있는 일반적인 사용 사례 및 정책.

이 디자인 가이드는 Cloudflare의 ZTNA 솔루션의 기본 이해가 있다고 가정합니다.[모델 번호: Cloudflare 오시는 길](/cloudflare-one/access-controls/). 따라서, 이 가이드는 효과적인 접근 정책을 디자인하고 당신이 이미 형성한 가정에 집중합니다[DNS 보호](/cloudflare-one/traffic-policies/get-started/dns/), [이름 \*](/cloudflare-one/integrations/identity-providers/)·[장치 자세 공급자](/cloudflare-one/integrations/service-providers/)뿐만 아니라[관련 링크](/cloudflare-one/networks/)자체 호스팅 응용 및 관련 네트워크.

이 가이드의 끝에 Zero Trust 원칙을 다양한 일반 기업 시나리오에서 시행하는 과립 액세스 정책을 구현할 수 있습니다.

### 네트워크 경로

Cloudflare를 위해 접근을 통제하기 위하여, 그것은 신청의 앞에 있어야 하고 성공적으로 정정된 사용자를 위한 안전한 믿을 수 있는 네트워크 경로가 있습니다. 응용 프로그램에 대한 요청은 Cloudflare 처음에 와서, 정책이 적용되고, 성공하면, 사용자 요청이 응용 프로그램에 경로.

Cloudflare는 신청의 뒤에 오는 유형에 접근을 지원합니다:

- SaaS 응용 프로그램
- Public hostname을 통해 액세스하는 셀프 호스팅 응용
- 개인 IP를 통해 액세스되는 자체 호스팅 응용

SaaS 및 기타 인터넷 기반 응용 프로그램에 대한, Cloudflare에서 액세스는 간단합니다 - 그것은 인터넷에 이미. 그러나 자체 호스팅 응용 프로그램을 위해 Cloudflare에서 응용 프로그램이 실행되는 개인 네트워크에 터널을 만듭니다. 이 작업을 위한 두 가지 방법이 있습니다:

- 자주 묻는 질문[소프트웨어 에이전트](/cloudflare-one/networks/connectors/cloudflare-tunnel/)등[구름 많음](/cloudflare-one/networks/connectors/cloudflare-tunnel/get-started/)또는[WARP 연결관](/cloudflare-one/networks/connectors/cloudflare-tunnel/private-net/warp-connector/). (주의, 현재 클라우드는 개인 응용 프로그램에 공개 호스트 이름의 프록시만 지원합니다.)
- 네트워크 기반 연결을 위해,[Cloudflare 대만](/cloudflare-wan/)(이전 매직 WAN)는 IPsec 또는 GRE 터널을 사용하여 Cloudflare를 개인 네트워크에 연결되는 기존 네트워크 기기에 연결하고,[네트워크 Interconnect](/network-interconnect/)데이터 센터 Cloudflare에서 서버에서 실행되는 경우 직접 연결성을 생성합니다. ( 기존의 레거시 VPN 솔루션에서 네트워크 기반 터널로 마이그레이션하려면, 찾을 수 있습니다.[이 가이드](/reference-architecture/design-guides/network-vpn-migration/)유용한.)

일단 우리가 당신의 신청에 연결성을 설치하면, 그것은 사용자 접근을 촉진하는 시간입니다. 귀하의 정책 요구 사항에 따라 (이 나중에 더 많은) 사용자는 공용 호스트 이름에 인터넷 연결에 직접 응용 프로그램에 액세스 할 수 있습니다, 또는 - 더 큰 보안 - 우리는 우리의 사용을 권장합니다[공급 업체](/cloudflare-one/team-and-resources/devices/warp/), Cloudflare WARP는, Cloudflare에 갱도를 직접 창조하고 또한 접근 정책에 있는 사용을 위한 그들의 장치에 관하여 정보를 제공합니다.

## 건물 정책

지금까지 기술 된 아키텍처를 신속하게 요약하려면 Cloudflare는 다음과 같습니다.

- 응용 프로그램에 네트워크 액세스의 앞에.
- ID 공급자와 통합.
- 장치 에이전트 또는 제3자 공급 업체를 사용하여 사용자에 대한 장치 자세 세부 정보를 알고 있습니다.

사용자가 응용 프로그램에 액세스 할 수있는 요청을 할 때, 그들은 먼저 인증해야, 다음, 액세스 권한을 부여하기 전에, 응용 프로그램에 대한 정책은 요청 사용자와 관련된 데이터를 기반으로 평가됩니다. Policies 및 기타 응용 프로그램 특정 설정은 액세스 응용 프로그램에 정의됩니다.

### 오시는 길

모델 번호: Cloudflare 접근은 4개의 주요 유형의 신청을 지원합니다:

- **셀프 호스팅**조직의 호스트 및 관리, 구내 또는 클라우드 중 하나를 나타냅니다. Cloudflare는 보안 터널을 응용 프로그램에 통해 프록시 트래픽을 사용하는 public hostname을 만듭니다. 서버가 인터넷에 공개적으로 직면하는 경우 공개 호스트 이름을 통해 액세스하는 동안, 우리는 당신이 사용하는 것이 좋습니다`cloudflared`Cloudflare의 가장자리에 응용 프로그램에서 보안, 아웃바운드 전용 연결을 만들려면. 일단 발생하면, Cloudflare는 그 후에 당신의 사용자에게 대상 응용 프로그램 / 내용을 반전합니다.
- **개인 IP**응용 프로그램은 비슷하게 개인적으로 호스팅되지만 완전 통합 된 공공 호스트 이름이 부족합니다. 오시는 길`cloudflared`, WARP 연결관, Cloudflare WAN, 또는 Cloudflare 네트워크 상호 연결. Cloudflare에 이미 연결된 네트워크에 연결되지 않는 원격 사용자는 개인 IP를 통해 애플리케이션에 액세스하고 IP 주소를 사용하여 IP 주소를 피하기 위해 장치 클라이언트를 사용해야합니다.[내부 DNS 서비스](/cloudflare-one/traffic-policies/resolver-policies/#use-cases)개인 IP 주소를 개인 IP 주소로 해결하기 위해. 그러나 우리의 Agentless를 사용하여 클라이언트에 배치된 소프트웨어 없이 접근을 제공할 수 있습니다[개인정보처리방침](/reference-architecture/diagrams/sase/sase-clientless-access-private-dns/).
- **SaaS 서비스**신청은 공중 인터넷에 접근되고, 그러므로 Cloudflare에 어떤 갱도 연결든지 요구하지 않습니다. 대신, 액세스는 사용자와 SaaS 애플리케이션 사이의 정체 프록시 역할을 합니다. 사용자가 SaaS 앱에 액세스하려고 시도할 때, 그들은 Cloudflare에 의해 처음 인증됩니다. SaaS 애플리케이션은 SAML 또는 OAuth를 통해 Cloudflare를 신뢰합니다. 이 조직은 추가 보안 레이어 (장치 자세 체크와 같은)를 구현하고 SaaS 애플리케이션에 대한 액세스 제어를 중앙화 할 수 있습니다. SaaS 또는 ID 공급자가 기본적으로 이러한 기능을 지원하지 않는 경우에도.
- **회사연혁**애플리케이션은 사용자가 개인 네트워크에서 개별 서버, 클러스터 또는 데이터베이스에 액세스할 수 있습니다. 'target'을 정의하여 인프라 앱 작업`cloudflared`, 그러나 사용자가 같은 대상에서 여러 기계를 그룹 할 수 있습니다 - 근본적으로, 사용자가 잠재적으로 인프라 리소스를 분산하는 일반적인 액세스 정책을 정의 할 수 있습니다. 내장 액세스 및 명령 로깅 기능은 조직은 준수 및 보안 조사 목적으로 상세한 감사 흔적을 유지할 수 있습니다.

:::노트북
Cloudflare에서만 접근할 수 있는 SaaS 애플리케이션을 구성할 수 있습니다. 이 모든 SaaS 애플리케이션 트래픽은 Cloudflare를 통해 발음되고 경로를 결정합니다. 게이트웨이는 SaaS 애플리케이션의 민감한 회사 데이터의 다운로드와 같은 보안 제어를 검사하고 필터 트래픽을 허용합니다. 아래 두 번째 사용 케이스는 이것을 달성하는 방법을 설명합니다.
주요 특징

액세스 응용 프로그램은 일반적으로 단일 응용 프로그램에지도. 그러나 액세스 응용 프로그램이 가능한 한, 그리고 그 관련 정책은 1 개 이상의 응용 프로그램 종료점 앞에 앉아. 일반적인 액세스 정책을 구현하고자하는 여러 Windows RDP 서버와 관련된 IP 범위가 될 수 있습니다. 같은 아이디어는 공공 호스트 이름에 적용 할 수 있습니다, 당신은 같은 정책을 가지고 싶어 몇 가지 응용 프로그램을 의미 하나의 호스트 이름보다 더있을 수 있습니다. 예를 들어, wiki.domain.com 및 wiki.domain.co.uk - 다른 응용 프로그램 인스턴스가 있지만 일반적인 액세스 정책 요구 사항이 있습니다.

다음, 우리는 효과적인 액세스 정책을 만들 필요가있는 ZTNA-protected 응용 프로그램의 주요 요소를 검사, 나중에 문서에서 우리는 그 특정 요소를 적용하는 일부 사용 사례를 검사합니다.

### 인증현황

사용자의 정체성을 인증하는 것은 Zero Trust 정책의 주요 구성 요소입니다. 응용 프로그램에 로그인하려고 할 때 사용자는 구성 된 정체성 공급자로 리디렉션됩니다. 사용자가 정체성 공급자로 인증되지 않으면 Cloudflare는 응용 프로그램에 대한 요청을받지 않습니다.

위에서 언급한 것과 같이, Cloudflare는 모든 신원 공급자 (IdPs), 기업과 소비자도 통합될 수 있습니다. 그런 다음 응용 프로그램 및 정책 수준에서 인증 할 수있는 IdPs를 선택합니다. 예를 들어, 제한된 직원 수는 액세스 할 수있는 응용 프로그램이있을 수 있습니다. 따라서 IdP만 가능합니다. 다른 응용 프로그램을 위해 계약자 또는 타사 파트너와 같은 non-employee 사용자의 더 넓은 그룹에 액세스 할 수 있습니다. GitHub 또는 LinkedIn 자격 증명을 통해 인증할 수 있습니다.

사용자가 IdP가 인증한 경우, IdP가 인증한 서명인 페이지로 표시될 것입니다. 단 하나 IdP를 가진 신청을 위해, 당신은 IdP에 사용자를 자동적으로 리디렉션할 수 있습니다. 구성 된 모든 가능한 IdP를 표시 할 응용 프로그램을 구성 할 수 있으며, 정책을 업데이트 할 필요없이 미래에 새로운 공급자를 추가 할 수 있습니다.

![Figure 3 - 조직의 다른 부분에서 직원은 동일한 응용 프로그램에 인증.](~/assets/images/reference-architecture/designing-ztna-access-policies-for-cloudflare-access/figure3.svg "Figure 3 - How employees from different parts of the organization authenticate to the same application.")

인증 후, IdP는 Cloudflare로 ID에 대한 정보를 보내려고합니다. IdP에 따라이 정보는 포함될 수 있습니다.[인증 방법 참고 자료](https://datatracker.ietf.org/doc/html/rfc8176)(amr) 값, IdP 그룹, SAML 속성 또는 OIDC는 정책에 사용될 수있는 주장.

우리의 장치 대리인을 사용할 때, 사용자는 또한 정통하고 IdPs의 주문 명부를 선물할 수 있습니다. 에이전트가 인증되면 Cloudflare에 연결할 수 있으며, 디바이스 에이전트와 관련된 기존 인증 세션을 신뢰하는 대신 인증을 건너뛰기 위해 애플리케이션을 구성할 수 있습니다.

### 회사연혁

이제 우리는이 가이드의 주요 초점에 도착 : 응용 프로그램에 대한 액세스를 정의하는 정책. 이것은 실제 작업이 접근하고있는 것을 정의하는 것입니다. 예를 들어 사용 사례를 보면, 여기에 정책 작업의 고장입니다.

![Figure 4 - ZNTA 서비스 액세스는 액세스 정책의 다양한 속성을 사용할 수 있습니다.](~/assets/images/reference-architecture/designing-ztna-access-policies-for-cloudflare-access/figure4.svg "Figure 4 - Our ZNTA service Access can use a wide variety of attributes in an access policy.")

각 신청은 다수 정책을 포함할 수 있고, 순서에서 평가됩니다. 여러 정책 — 규칙의 여러 세트와 함께 — 확실히 복잡하게 얻을 수 있기 때문에, 사용자를 제공하는 정책 테스터가 모든 정책과 규칙에 대해 평가되는 방법을 참조하십시오. 정책은 다음과 같은 요소로 구성됩니다:

#### 이름 \*

이것이 무엇인지 분명한 것 같지만, 우리는 귀하의 정책을 naming하기위한 전략을 갖는 것이 좋습니다. "모든 풀 타임 직원"또는 "Block high-risk users"와 같은 여러 응용 분야에서 유사한 정책을 만들 가능성이 있기 때문에. 모든 응용 분야에 걸쳐 동일한 naming 계획을 사용하여 응용 프로그램을 검토하고 미래에 정책의 전체 목록을 이해하기 위해 광대하게 능력을 간소화합니다.

#### - 연혁

본 방침은 사용자 또는 서비스가 정책의 기준을 일치할 때 발생하는 것을 결정합니다. 행동의 4 가지 주요 유형이 있습니다.

- **지원하다**신청에 대한 권한을 부여합니다. 로그인 페이지는 초기 액세스 요청에 사용자에 표시됩니다.
- **제품정보**denies 응용 프로그램에 액세스. 이것은 일반적으로 접근이 기본적으로 거부되기 때문에 필요하지 않습니다. 사용자는 블록 정책을 특정 정책 조건 또는 단락 정책 평가를 테스트하기위한 것입니다. 블록 정책이 허용보다 더 높을 경우, 사용자는 블록 정책을 일치, 다른 모든 정책 평가는 중단.
- **비밀번호**애플리케이션에 액세스하기 전에 트래픽에 대한 집행을 비활성화 할 수 있습니다. 예를 들어, 응용 프로그램의 특정 엔드 포인트는 인터넷에서 광범위하게 액세스 할 수 있습니다.
- **서비스 Auth**다른 서비스 또는 응용 프로그램에서 요청을 인증 할 수 있습니다.[사이트맵](/ssl/client-certificates/enable-mtls/)또는[서비스 토큰](/cloudflare-one/access-controls/service-credentials/service-tokens/). 로그인 페이지가 본 정책 기준을 충족하면 사용자 또는 서비스에 표시되지 않습니다. 이것은 다른 신청에서 그들과 같은 비 사용자 요구가, 안전한 자원에 접근할 수 있다 그래야 디자인됩니다.

:::노트북
모델 번호: Cloudflare 액세스는 기본 서비스에 의해 deny, 이는 요청이 어떤 정책 동작과 일치하지 않는 경우, 기본 동작은 "Block"입니다.
주요 특징

#### 세션 기간

세션 기간은 사용자의 인증이 성공적으로 응용 프로그램에 로그인 한 후 유효 기간을 나타냅니다. 일반적으로 세션 기간은 24 시간 동안 설정되지만 즉시 만료되는 민감한 응용 프로그램에 대한 지속 시간을 설정할 수 있습니다. 이 접근법은 핵심 Zero Trust 원칙을 준수합니다. 사용자가 처음에 적합한 장치 자세와 정체성 컨텍스트를 제시하더라도, 연속 검증은 액세스 권한이 각 새로운 요청으로 재조정됩니다. 이 방법은 초기 인증 및 승인 상태가 장시간 기간 동안 유효하다는 가정을 제거하는 것과 같은 위험 창을 크게 감소시킵니다.

#### 이름 \*

이 정책의 주요 초점입니다. 규칙은 정책이 허용하거나 denies 액세스를 허용하거나 격리 된 브라우저에서 응용 프로그램을 렌더링하는 경우 모든 속성을 정의합니다. 그들은 당신이 평가하고있는 데이터를 평가하고 싶은 속성에 필수적으로 선택기와 값으로 구성됩니다.

각 규칙은 사용자가이 정책이 영향을 미칠 것이라고 결정하는 필터입니다. 규칙의 몇몇 종류가 있습니다:

- **이름 \***&#xADDC;칙은 누구 또는 접근할 자격이 있는지 정의합니다. 사용자가 "Include" 규칙에 일치하면 액세스 할 수있는 후보가되고 정책의 다른 규칙 유형에 따라 다릅니다. 이 규칙 사용 OR 논리 — 어떤 것을 만족시키는 것은 충분합니다. 예를 들어 특정 그룹에 사용할 수있는 응용 프로그램을 만들 수 있지만 이메일 목록에 대한 계약자에 추가해야하며 사용자가 이러한 (그룹 회원 또는 유효한 이메일) 중 하나를 일치합니다. 모든 정책은 적어도 하나의 포함 항목이 있어야합니다.

- **이름 \***&#xD574;당 이용 후기에 달린 코멘트가 없습니다. 규칙과 달리, "Require" 규칙 사용 및 논리 - 모든 규칙은 충족해야합니다. 이것은 일반적으로 규칙을 포함해서 정의된 기본적인 접근 기준의 정상에 층 안전에 사용됩니다. 예를 들어, 관리자는 애플리케이션 사용 특정 MFA 메소드에 액세스하려고 할 수 있습니다.

- **이름 \***&#xADDC;칙은 다른 규칙 유형의 접근, overriding 예외를 정의합니다. 사용자가 "Exclude" 규칙을 일치하면 다른 정책 조건과 관계없이 액세스가 거부됩니다. 예를 들어, 사용자는 로그인 중에 MFA 메소드를 사용하도록 요구 사항을 충족 할 수 있지만 특정한 경우[다중 인증 (MFA) 방법](/cloudflare-one/access-controls/policies/mfa-requirements/)제외 규칙에 정의되어, 그들은 정책에 의해 차단됩니다. 또는, 사용자가 '고위험'IdP 그룹과 관련되어 있다면, 그들은 다른 모든 자세 요구 사항을 충족하는 경우에도 그 기반에 제외 될 수 있습니다.

이러한 다른 유형의 규칙을 적용하는 방법을 상상하는 유용한 방법은 곰팡이를 상상하는 것입니다. selectors는 사용자의 속성을 정의, 트래픽 또는 장치는 허용 될 정책에 포함, 차단 등. 그 목록에서 더 많은 필터를 요구하면 속성이 사용자가 Include 및 Require와 일치하는 사용자가 필터링하는 것과 관련되어야합니다.

![Figure 5 - 정책 및 규칙은 funnel에서 평가됩니다. 모든 사용자를 구성하는 규칙을 포함, 특정 요구 사항을 충족하는 규칙 및 정책 평가에서 사용자 식별 제거 규칙.](~/assets/images/reference-architecture/designing-ztna-access-policies-for-cloudflare-access/figure5.svg "Figure 5 - Policies and rules are evaluated in a funnel. With Include rules aggregating all users, Require rules mandating specific requirements and Exclude rules removing user identities from the policy evaluation.")

위의 다이어그램은 강력한 MFA를 사용하여 보안 장치에 대한 정책 "모든 직원 및 계약자"에 대한 예를 시각화합니다. 그룹 "모든 종업원" 또는 계약자는 회사 도메인의 사용자 이름과 인증이 정책에 일치합니다. 최신 OS를 가지고있는 장치를 사용하고 암호화 된 저장을 사용합니다. 그들은 MFA 요소로 인증되어야하지만 SMS는 없습니다. 또한 Cloudflare의 보안 웹 게이트웨이를 통해 응용 프로그램에 액세스해야합니다.

많은 다른 있다[selectors의 종류](/cloudflare-one/access-controls/policies/#selectors). 모든 가능한 선택자는 여기에 나열되지 않습니다, Cloudflare를 사용하여 조직의 다음 목록 특정 결과 건물 정책에 대한 일반적인 욕망을 접근하십시오. 이것은 특정 결과를 달성하는 방법을 이해하는 데 도움이됩니다.

- **Cloudflare 게이트웨이에 오는 사용자 트래픽입니까?**&#xC0AC;용자가 SWG, Cloudflare에 응용 프로그램을 접근하는 보장 게이트웨이는 피싱이나 압도적 인 도난으로 인해 무단 액세스를 방지하는 좋은 방법입니다. 또한 Cloudflare Gateway에 의해 로그인 및 필터링 된 모든 트래픽을 보장 할 수 있습니다.

  "gateway" 장치 자세 검사를 활성화하여이 제어를 구성하고 응용 프로그램 정책에서 "gateway"를 필요로 할 수 있습니다. Requiring "gateway"는 사용자가 브라우저 Isolation 또는 Cloudflare WAN 연결 사이트에서 램프를 켜거나 Cloudflare WAN 연결 사이트, 트래픽 로깅 및 필터링을 제공 할 수있는 장치 에이전트에 단독으로 의존하는 것보다 더 유연합니다. 또한 장치 에이전트를 사용할 때, 사용자가 장치 자세 검사 세트를 통과 한 준수 장치에서 오는 것을 보장 할 수 있습니다.

  게이트웨이가 지속적으로 시행됩니다.[자체 호스팅 응용](/cloudflare-one/access-controls/applications/http-apps/self-hosted-public-app/). SaaS 앱의 경우 로그인 당시에만 시행됩니다. 그러나 전용 egress IP는 Cloudflare 게이트웨이를 통해 항상 트래픽을 실행하는 탠덤에서 레버리지 할 수 있습니다.

- **사용자는 기존 그룹에 속하거나 특정 ID 속성이 있습니까?**&#x49;dP가 SCIM을 지원하는 경우, 그룹 회원 정보는 정책에서 사용할 수있는 Cloudflare로 가져올 수 있습니다. 그룹 정보는 SAML 또는 OAuth 데이터에서 인증의 일부로 전송할 수 있습니다. 실제로 OIDC 또는 SAML이 사용되고 주장이 전송되면 정책에 사용될 수 있습니다. 그래서 사용자가 SAML을 사용하여 IDP에 정해진 경우, 결과 토큰은 규칙에 그 값을 쿼리 할 수 있습니다.

- **어떤 정체 서비스는 인증을 위해 사용되었습니까?**&#x49;dP 그룹과 속성과 마찬가지로, 이 "로그인 방법" selector는 IdP 그룹과 같은 정체성 서비스를 사용하고, 액세스 정책의 특정 라인 항목보다 오히려 액세스 그룹에 더 적합합니다. 로그인 방법은 특정 정체성 공급자로 인증된 특정 사용자에게 다른 정책을 적용할 수 있습니다. 예를 들어, GitHub 또는 LinkedIn과 같은 소비자 정체성을 인증한 사용자가 하드 토큰 기반 MFA를 포함하는 인증 방법을 얻기 위해 액세스할 수 있습니다.

  이것은 원시적 인 시나리오이지만 인증을위한 여러 IdPs를 활성화해야하는 경우이 선택기를 사용하여 사용자가 특정 서비스로 인증 할 수 있습니다. 이 요구 사항의 값은 여러 계층의 보안 정책을 처리 할 때 명확하게되며 로그인에 따라 액세스의 다른 수준을 정의해야합니다.

- **개인 또는 조직 이메일**모든 정체 서비스는 이메일 주소를 제공합니다. 많은 경우 개인의 사용자 이름과 일치합니다. 이 웹 사이트는 애플 리케이션에 전념. 우리는 정품 앱과 게임을 제공 할 목적으로이 사이트를 만들었습니다. 4AppsApk 최고의 안드로이드 애플 리케이션을위한 무료 APK 파일 다운로드 서비스, 계략. 예를 들어, @company.com 이메일 주소를 사용하여 GitHub를 통해 인증된 사용자에 대한 액세스를 허용할 수 있습니다.

  이 selector의 또 다른 좋은 사용은 당신이 관리하는 경우[이메일 목록](/cloudflare-one/reusable-components/lists/)높은 위험이 있거나 특정 응용 프로그램에서 차단 된 사용자의. 사용자가 응용 프로그램에 액세스 할 수없는 하위 세트를 보장하기 위해 목록을 제외 규칙을 사용할 수 있습니다.

- **사용자 인증은 어떻게 했습니까?**&#xC815;체성 공급자가 사용자를 인증하고 Cloudflare로 다시 리디렉션하면 인증 방법에 대한 정보가 포함되어 있습니다. 이것은 전형적으로 보내집니다[인증 방법 참고 자료](https://datatracker.ietf.org/doc/html/rfc8176)데이터. 이것을 사용하면 MFA가 사용하고 어떤 유형인지 확인할 수 있습니다.

  이것은 다른 신청을 위한 credential 필요조건의 다른 수준을 정의하는 것이 유용합니다. 예를 들어, 일반 회사 응용 프로그램은 MFA가 어떻게 사용되었는지 요구할 수 있습니다. 그러나 진짜로 과민한 관리 공구는 FIDO2 기계설비 근거한 안전 열쇠를 요구할지도 모르고, 그러므로 SMS를 통해 OTP가 입증 과정의 부분으로 이용된 경우에 따라서 명시적으로 deny 접근을.

- **어떤 나라에서 오는 요청?**&#xC9C0;정된 요청에 따라 규칙을 설정할 수 있습니다. 이것은 당신이 사업을 할 특정 국가에 대한 액세스를 제한하는 데 유용 할 수있다.

- **어떤 IP 범위에서 오는 요청?**&#xC218;신 요청의 IP 범위에 따라 규칙을 설정할 수 있습니다. 이것은 기업 네트워크 IP 범위에서만 접근할 수 있었습니다.

- **목록에서 장치 또는 사용자 정보를 확인할 수 있습니까?**&#xB54C;때로, 당신은 다른 범주에 neatly 적합하지 않는 특정 장치 또는 사용자 특성에 따라 권한을 부여하거나 제한 할 수 있습니다. 현재 위치[이름 \*](/cloudflare-one/reusable-components/lists/)handy에 와서 : 계약자 이메일 목록을 정의하거나 가져올 수 있습니다, 또는 승인 된 장치 일련 번호 목록 및 액세스 정책 내에서 기준을 사용. 이 목록은 수동으로 또는 우리의 통해 업데이트될 수 있습니다[사이트맵](/api/resources/zero_trust/subresources/gateway/subresources/lists/methods/create/), 다른 장치 또는 사용자 관리 시스템과 통합 할 수 있습니다.

- **장치의 보안 자세가 적절합니까?**&#xC7A5;치 클라이언트가 액세스 요청을 만드는 네이티브 장치에서 원격 측정을 제공합니다. 장치 수준의 스캔을 수행함으로써 이것을 수행합니다. 장치의 하드 드라이브는 암호화됩니까? BitLocker 또는 FileVault 같은 기술이 활성화되어 특정 볼륨 이름을 검사 할 수 있는지 확인 할 수 있습니다. 민감한 응용 프로그램을 보호하는 경우, 또는 중요한 정보를 보유하는 무언가, 이것은 시행하는 효과적인 필요조건입니다.

- **다른 프로세스 또는 응용 프로그램에 의해 만들어진 요청은?**&#xD56D;상 실제 인간이 응용 프로그램에 액세스하려고 시도하지 않습니다. 이것은 Cloudflare를 레버리지에 유용합니다 다른 소프트웨어에 의해 APIs에 통신을 관리하는 접근. 요청은 서비스 토큰, 상호 TLS 인증서 및 SSH 인증서를 포함할 수 있으며, 자동화된 프로세스 및 기계에 대한 로그인을 가능하게 합니다. Cloudflare 내의 서비스 auth 옵션을 사용하여이 토큰 및 인증서의 저장 및 수명주기 관리를 중앙화합니다.

- **제3자 도구는 장치에 대해 뭐라고 말합니까?**&#xB9CE;은 조직은 Crowdstrike, SentinelOne 또는 Microsoft Intune와 같은 엔드포인트 보안을위한 다른 전문 도구를 사용하여 응용 프로그램 요청을 만드는 장치의 보안 자세에 대한 원격 측정을 제공합니다. 여러 UI를 탐색하기 위해 사용자를 필요로하는 것보다, Cloudflare로 이러한 도구를 통합 할 수 있습니다. API를 통해 응용 프로그램 로그인 중에 시행 될 수있는 장치 자세 속성에 대한 통찰력을 적용합니다.

:::노트북
몇몇 제3자 장치 자세 통합은 사용자 장치가 설치된 우리의 대리인이 없을 때 조차 사용될 수 있습니다. 대신, 제3자 통합은 이메일에 근거를 둔 사용자와 Cloudflare에 정보를 직접 제공합니다.

#### 추가 설정

아래는 보안을 개선하는 데 도움이되는 몇 가지 추가 응용 프로그램 설정입니다.

##### Isolate 응용

때로는 계약자 또는 파트너와 같은 덜 신뢰할 수있는 타사 사용자를위한 자체 호스팅 응용 프로그램에 대한 액세스를 관리하고 싶습니다. 당신은 응용 프로그램에 콘텐츠를 읽을 수 있도록 할 수 있지만 파일을 다운로드 할 수있는 능력, 복사 및 붙여 넣기 데이터 및 페이지를 인쇄 할 수 있습니다. 모델 번호: Cloudflare Access는 원격에서 응용 프로그램을 렌더링 할 수 있습니다[\* 이름](/cloudflare-one/access-controls/policies/isolate-application/)(사용)[원격 브라우저 고립, 또는 RBI](/cloudflare-one/remote-browser-isolation/)) 그래서 응용 프로그램은 사용자의 브라우저로 모든 콘텐츠를 전송하는 우리의 네트워크 versus에 머리없는 브라우저를 사용하여 렌더링됩니다. 이것은 Cloudflare를 허용하여 사용자가 콘텐츠와 상호 작용할 수있는 방법을 통해 제어 범위를 시행합니다.

설정은 정책 수준에서, 그래서 하나의 정책은 신뢰할 수있는 사용자를 허용 할 수 있습니다 (예 : 직원과 같은) 일반적으로 액세스 응용 프로그램에 액세스 할 수 있습니다, 브라우저 고립과 다른 정책은 계약자에 대한 RBI 서비스를 적용 할 수 있습니다.

최종 사용자에게 전달되기 전에 격리 된 브라우저에 이 설정 힘 트래픽은 Cloudflare 게이트웨이에 의해 검사되고 관리됩니다. 사용자가 할 수있는 것을 제한하려면 게이트웨이의 동반 정책을 만들 필요가 있으며 동일한 사용자를 식별하고 그 다음 시행[제품정보](/cloudflare-one/remote-browser-isolation/isolation-policies/#policy-settings)액세스 제한을 원합니다. Cloudflare의 응용 프로그램에 액세스하는 사용자의 동일한 그룹에 대한 RBI를 실행하는 게이트웨이 정책을 작성하는 것이 중요합니다. 액세스 정책이 적용됩니다. 그렇지 않으면 정책은 모든 사용자에게 브라우저 고립을 시행하기 위해 기본값입니다.

RBI를 실제로 실행할 수 있습니다. 동일한 세트의 사용자를 위한 RBI는 non-secured device를 사용하여 응용 프로그램에 액세스하려고 하는 경우. 이 경우, Cloudflare Access의 직원을위한 정책을 지속적으로 정의 할 것입니다. 그러나, 또한 Cloudflare에서 정책을 만들 게이트웨이는 동일한 응용 URL로 이동하면 응용 프로그램을 격리하는 장치 자세 검사가 실패하여 장치가 관리되지 않거나 안전하지 않습니다. 이 장치가 회사 엔드포인트 보안 클라이언트 (Crowdstrike 또는 SentinelOne for example)가 설치되어 있지 않거나 보안 검사를 실패했습니다. 우리는 아래의 사용 사례에서 이것을 보여줄 것입니다.

이 웹 사이트는 애플 리케이션에 전념. 우리는 정품 앱과 게임을 제공 할 목적으로이 사이트를 만들었습니다. 4AppsApk 최고의 안드로이드 애플 리케이션을위한 무료 APK 파일 다운로드 서비스, 계략.

##### 이름 \*

응용 프로그램의 모든 인증 이벤트를 감사하고 만장 세부 정보를 캡처 할 수 있습니다. 이 설정은 사용자 액세스의 더 잘 정의 된 감사 트레일을 작성하고 관리자가 액세스 패턴과 단정을 검토하고 분석 할 수 있습니다. 사용할 때, 사용자는 액세스 권한을 얻기 전에 간단한 설명을 제공 할 수 있습니다. 이것은 과민한 신청을 위해 특히 유용합니다 또는 특정한 시간 기간 도중, 외부 정상적인 사업 시간과 같은.

##### 임시 인증

응용 프로그램에 액세스하기 전에 지정된 authorizers에서 "temporary authentication" 승인을 얻기 위해 사용자를 요구하는 액세스 제어의 추가 레이어를 추가하십시오. 사용할 때, 사용자가 접근을 요청하는 것은 공인된 앱로버에게 알림을 트리거합니다.

### 액세스 그룹

ZTNA 정책을 정의하는 가장 중요한 부분 중 하나는 reusable 엘리먼트를 활용하기 위한 것입니다.[액세스 그룹](/cloudflare-one/access-controls/policies/groups/). 각 액세스 그룹은 사용자, 트래픽 또는 장치를 정의하는 것과 같은 규칙을 사용합니다. 이 그룹은 많은 정책을 통해 사용할 수 있습니다, deny, 우회, 또는 응용 프로그램에 대한 격리 액세스.

예를 들어, Access Group으로 한 번 "Employees"를 정의 할 수 있으며 직원을 참조하려는 모든 응용 프로그램 정책에서 사용됩니다. 이 Access Group의 업데이트는 모든 정책에 반영됩니다. 이것은 배열 된 논리 (예를 들어, Linux 장치와 사용자 및 바이러스 백신 소프트웨어 활성화)를 포함하는 좋은 방법입니다.

아래는 보안 관리자의 특성을 정의하기 위해 속성의 범위를 사용하는 "Secure Administrators"라는 Access Group의 다이어그램입니다. 다이어그램은 "Secure Administrators"내의 두 가지 다른 Access Group의 추가를 보여줍니다. 이 그룹에는 최신 Windows 또는 macOS 중 하나에서 장치가 있어야 하는 요구 사항과 함께 실행되는 장치가 포함됩니다.

## 사용 사례

이제 기본 인프라가 응용 프로그램에 대한 액세스를 확보하고 정책 시스템은 덮여있어 일반적인 사용 사례로 다이빙 할 수 있습니다.

### 신뢰할 수 있는 장치에 대한 wiki 액세스만 허용

많은 회사는 기밀 회사 정보 resides가 내부 콘텐츠 시스템의 일부 종류를 호스팅합니다. Wiki's는 직원이 누구나 쉽게 협업할 수 있도록 일반적인 유형의 응용 프로그램입니다. 그러나이 정보는 기밀이기 때문에 강력한 자격 증명을 검증하는 것이 중요합니다. 또한 보안 연결을 통해 액세스가 안전한 장치를 통해 액세스가 보장됩니다.

그러나 때때로 회사는 사용자가 비 회사 장치를 사용하고 wiki에 액세스해야합니다. 당신은이를 허용하는 정책을 설정하고자 할 수 있지만 사용자의 행동을 제한합니다. 예를 들어, 데이터를 편집하거나 복사하고 관리되지 않은 장치에 붙여넣기에서 방지합니다. 이 사용 사례는 Cloudflare를 설정하는 방법을 설명합니다. 직원에 대한 보안 액세스를 정의하는 액세스 응용 프로그램은 보안 연결을 통해 보안 된 장치에서 완전히 기능 액세스를 제공하지만 여전히 비 안전한 장치에서 제한된 액세스를 허용한다.

Access Group이 직원을 식별하고 승인 된 장치를 최신 운영 체제 버전을 실행하기 위해 생성 된 예를 살펴 보겠습니다.

#### Access Group: 보안 직원

이 액세스 그룹은 두 정책에서 사용되고, 그 유일한 목표는 "Secure Employee"가 무엇인지 확인하는 것입니다.

| 이름 \*       | 보안 직원                                         |
| :---------- | :-------------------------------------------- |
| **이름 \***   |                                               |
| Azure AD 그룹 | "Full-Time 직원"                                |
| **이름 \***   |                                               |
| Azure AD 그룹 | "보안 훈련"                                       |
| OS 버전       | "MacOS의 최신 버전", "Windows의 최신 버전", "최신 리눅스 버전" |

이것은 매우 간단한 액세스 그룹, 단지 두 그룹 선택자. 특정 디렉토리에서 그룹에 기반을 둔 회원을 확인하기 때문에 사용자는 그 디렉토리에 인증해야합니다. 또 다른 정체성 공급자로 이동하거나 전체 시간 직원을 정의하는 그룹 회원 요구 사항을 변경하면 한 번만 액세스 그룹을 변경합니다.

볼 수 있듯이, "모든 직원"은 Azure AD 그룹 "Full Time 직원", 그룹 "Completed security training"에 있다는 것을 정의합니다. 첫 번째 선택기는 Access Group의 초기 범위를 정의하고 두 번째 선택자는 특정 그룹에 있어야합니다.

이 액세스 그룹은 세 가지를 요구합니다.[장치 자세 검사](/cloudflare-one/reusable-components/posture-checks/warp-client-checks/)생성되었습니다.[OS 버전](/cloudflare-one/reusable-components/posture-checks/warp-client-checks/os-version/). 예를 들어, 자세 검사 "MacOS의 최신 버전"은 "macOS 버전은 15.1"보다 크거나 동일하며 최신 버전을 반영하여 안정적이고 안전한 (vs. 매우 최신 OS 버전)을 고려합니다. 액세스 정책에 포함되면, 여기에 설치된 논리를 시행합니다. 어떤 사용자가 'Secure Employee'로 로그인하려는 경우 이러한 요구 사항을 충족해야합니다.

| - 연혁       | 지원하다                |
| 액세스 그룹     | 포함 - 모든 직원          |
| **이름 \***  |                     |
| 이름 \*      |                     |
| 인증 방법      | MFA - 다중 요인 인증      |
| **추가 설정**  |                     |
| Isolate 신청 | 이름 \*               |

이 정책은 첫 번째와 매우 유사하지만, 최신 운영 체제에서 장치를 가지고 요구 사항을 제거하고 우리의 장치 에이전트를 사용하여. 사용자는 여전히 강력한 MFA 백업 자격 증명으로 정해진 풀 타임 직원이어야합니다.

그러나 우리는 이제 "Isolate Application"을 활성화합니다. 이것은 무엇을 의미합니까? 이 응용 프로그램에 대한 모든 요청은 이제 RBI 기술에 렌더링됩니다. RBI는 Cloudflare의 글로벌 클라우드 네트워크에서 서버에서 실행되는 헤더리스 브라우저에서 직접 로드에서 wiki UX를 방지합니다. 그런 다음 렌더링의 결과는 안전하고 효율적으로 최종 사용자의 브라우저로 전달됩니다. 이 때문에, 요청은 SWG 서비스를 통해 전송됩니다. 이는 사용자가 위키와 상호 작용할 수있는 정책을 작성할 수 있습니다.

**Gateway HTTP 정책**

| insecure 장치에서 사용자를 위한 Isolate 회사 신청 |                          |
| :---------------------------------- | :----------------------- |
| - 연혁                                | 사이트맵                     |
| **교통안내**                            |                          |
| 도메인 이름                              | 위키.mycustomerexample.com |
| **장치 Posture**                      |                          |

| **계정 설정**                           |                          |
| 복사 / 붙여넣기                           | 이름 \*                    |
| Disable 파일 다운로드                     | 이름 \*                    |
| Disable 파일 업로드                      | 이름 \*                    |
| 장애인 키보드                             | 이름 \*                    |
| Disable 인쇄                          | 이름 \*                    |

위의 예에서 SWG 정책은 회사 위키에 본사를 둔 트래픽과 일치하여 RBI (ZTNA 응용 정책과 일치)를 처리하고 위키와 모든 상호 작용을 해제합니다.

그것은 또한 우리의 장치 대리인의 존재를 위한 사용자의 장치를 검사하기 위하여 장치 자세 검사 “WARP 검사 (Mac OS)”를 추가합니다. 사용자의 장치가 설치된 대리인이 없는 경우에, 그 후에 장치 자세 체크는 일어날 수 없고 그들은 정책을 만족시키기 위하여 자동적으로 실패할 것입니다. 사용자가 장치 에이전트가 활성화되면, 그들은 자세 검사를 통과하고 전체 위키 액세스를 부여합니다. WARP는 우리의 장치 대리인을 위해 사용되는 이름입니다.

필수, insecure 장치의 직원은 "읽기 전용"모드에서 위키를 볼 수 있지만 업로드 / 다운로드 또는 복사 / 붙여 넣기 기밀 정보와 같은 추가 상호 작용에서 제한됩니다.

이 정책 접근은 몇 가지 목표를 달성:

1. 그것은 당신의 Zero Trust 보안 목표와 일치 wiki에 가득 차있는 접근을 위한 믿을 수 있는 장치의 사용을 적용합니다.
2. 개인 기기를 사용하여 직원을위한 낙하 옵션을 제공합니다. 브라우저 고립을 통해 제한된, 보안 방식으로 위키에 액세스 할 수 있습니다.
3. 기업의 보안 자세에 대한 순 긍정적 인 인 WARP를 활성화하는 직원을 집중합니다.
4. Cloudflare 액세스 정책을 Cloudflare Gateway HTTP 정책을 결합하여 달성 한 더 많은 과립 보안 제어의 힘과 유연성을 보여줍니다.

이 접근법은 wiki를 확보하고 다른 응용 프로그램을 보호하기위한 모델을 수립합니다. 조직은 하이브리드 작업 시나리오의 현실에 적응하면서 강력한 사이버 위생을 유지할 수 있습니다.

### Salesforce에 대한 보안 액세스

두 번째 사용 사례는 장치 클라이언트의 사용을 필요로하는 안전한 액세스 전략을 구현합니다. 그러나, 구현은 이전 위키 예보다 약간 더 관련이 있습니다.

특정 주소를 지정하기 전에 Cloudflare를 통해 SaaS 앱에 액세스하는 이점에 대해 알아볼 것입니다. 모든 경우 Salesforce 및 기타 주요 SaaS 제공 업체는 이미 자신의 액세스 제어, MFA 및 감사 로그를 포함하여 강력한 보안 기능을 제공합니다. 그래서 왜 일부 조직은 여전히 Cloudflare를 통해 SaaS 트래픽을 경로를 선택합니까?

여기에 중요한 이점은 IT 생태계 전체의 보안 정책 시행 중입니다. Cloudflare를 통해 Salesforce 액세스를 라우팅하면 Salesforce를 확보하지 않습니다. Zero Trust 전략을 사용하여 모든 사용자 활동에 대한 가시성을 포함하며 여러 보안 시스템을 관리하는 복잡성을 줄일 수 있습니다. 또한 단일 SaaS 애플리케이션에 액세스할 수 있는 많은 IdP를 구현할 수 있습니다.

이 사용 사례의 맥락에서 Salesforce를 보호하는 것이 중요합니다. 즉, 민감한 고객 데이터를 포함하는 것이 중요하며, 공인된 사용자에게만 액세스할 수 있습니다. 우리는 이러한 목적을 모두 커버 할 수있는 안전한 액세스 정책을 설계하려고합니다.

첫번째 단계는 구성하는 것입니다[Cloudflare Gateway의 IP 정책](/cloudflare-one/traffic-policies/egress-policies/). 게이트웨이를 통해 트래픽을 필터링한 사용자들에게 특정 IP를 구매하고 할당할 수 있습니다. 그런 다음 Salesforce에서 egress 정책에 일치하는 소스 IP로 트래픽을 허용 할 수 있습니다. 이 조합은 Salesforce에 접근을 얻는 유일한 방법은 Cloudflare를 통해 입니다.

| Egress 정책                   |                 |
| :-------------------------- | :-------------- |
| **이름 \***                   |                 |
| 사용자 그룹 이름                   | 모든 직원           |

이것은 Salesforce에 대한 액세스를 확보하는 것이 중요하지 않지만 사용 중에 콘텐츠를 적절하게 보호하는 것이 중요합니다. 다음 단계는 wiki를 위해 만든 하나와 비슷한 접근 정책을 검토하는 것입니다. 그러나이 정책은 영업 또는 임원 그룹 구성원에 대한 액세스를 제한합니다. Crowdstrike 통합을 사용하여 사용자는 회사 관리 장치에 있습니다.

이 접근법은 몇몇 이유를 위해 중요합니다:

- 잠재적으로 위험한 액세스 시도에 대한 인간의 oversight를 허용, 손상 또는 insecure 장치를 통해 무단 액세스의 가능성을 감소.
- 그것은 합법적 인 사용자에 대한 유연성을 제공합니다 응용 프로그램에 액세스 할 때 장치가 가장 높은 보안 표준을 충족하는 실패. 이 기능은 사용자가 기기에서 좋은 보안 관행을 유지하도록 권장합니다.
- 또한, 모든 사용자 트래픽이 Cloudflare를 통해 경로를 통과했기 때문에 웹 트래픽 정책을 통해 추가 보안 조치를 시행 할 수 있습니다.

| 회사 소개            | 이름 \*              |

여기, 우리는 MFA 시작 보안 자세 검사의 높은 숫자를 소개하고 있습니다. 우리는 MFA에 대한 두 가지 표현이 있습니다 : 첫 번째 것은 사용자가 MFA 방식에 정통해야합니다. SMS가 유효 인증 방법을 고려하지 않다는 두 번째 '예' 표현. 우리는 SMS가 공격자의 하나가 악용하고 빼기 때문에 이것을 합니다, 그러므로[더 적은 안전](https://sec.okta.com/articles/2020/05/sms-two-factor-authentication-worse-just-good-password)다른 MFA 방법 보다는. 결과적으로 사용자가 하드 키 또는 OTP와 같은 더 강한 자격 증명을 제공 할 때 액세스 할 수 있습니다. 이러한 엄격한 MFA 요구 사항은 자격 기반 공격의 위험을 줄일 수 있으며 잠재적 인 공격자는 사용자가 암호를 얻은 경우이 중요한 데이터베이스에 대한 무단 액세스를 얻기 위해 훨씬 더 도전합니다.

다른 자세 요소는 다음과 같습니다 :

- 최신 OS를 요구합니다.
- 사용자는 Microsoft Active Directory 도메인에 가입됩니다.
- 사용자의 장치는 명시적으로 회사 관리 장치 (관리 장치 일련 번호의 목록을 참조하여 표시).

이 결합된 자세 검사는 당신의 관리한 환경 내의 단지 최신, 회사 통제한 장치가 데이터베이스에 접근할 수 있다는 것을 보증하고, 공격 표면과 잠재적으로 타협되거나 통제되지 않는 내점에서 접근의 위험을 감소시키.

추가 설정에서, 우리는 또한 그 사용자가 데이터베이스에 액세스하기위한 목적의 justification을 입력해야합니다. 보안 팀은 접근 패턴을 분석하고 잠재적으로 의심스러운 행동을 식별 할 수 있습니다. 보안 제어의이 세트는 또한 중요한 데이터베이스에 액세스 할 수 있도록 엄격하게 규제, 기록, 그리고 단화 - 두드러지게 무단 액세스 또는 오용의 위험을 감소.

이 수준의 보호 및 가시성은 더 복잡하고 자원 집중적 인 장애, 독립 보안 솔루션으로 달성 될 것입니다. Cloudflare를 통해 보안 정책 시행을 중화하여 중요한 내부 자원에 대한 미세한 접근을 구현하는 방법을 단순화 할 수 있습니다.

### 보안 RDP 액세스

이 최종 사용 케이스 센터는 두 가지 방법으로 RDP를 통해 장치에 원격 액세스를 확보합니다. 자체 호스팅 또는 개인 IP. 두 옵션은 독특한 혜택을 제공하지만 궁극적으로 우선 순위에 올랐다 : 액세스를 단순화하는 것이 더 중요합니다, 또는 단단하게 작동을 모니터링?

우리는 자체 호스팅 옵션으로 시작합니다 - 터널 위에 프록시 포트 3389, 호스트 이름에 맵핑.

| Application 구성 |                                         |
| :------------- | :-------------------------------------- |
| 신청 이름          | 데이터베이스 서버의 RDP 서비스                      |
| 이름 \*          | rdp.databaseserver.company.internal의 경우 |

정책 정의:

| 정책 이름            | 관리자 액세스            |
| :--------------- | :----------------- |
| - 연혁             | 지원하다               |
| **이름 \***        |                    |
| 그룹 멤버            | IT 관리자             |
| **이름 \***        |                    |
| 인증 방법            | MFA - 멀티 팩터 인증     |
| 오시는 길            | 이름 \*              |
| 모델 번호: WARP      | 이름 \*              |
| 장치 자세 - 연속 번호 목록 | 회사 관리된 장치 Serial 수 |
| 외부 평가            | \[시간 증발기 URL]      |

정책 내에서, 우리는 IT 관리자를위한 새로운 액세스 그룹에 사용할 수있는이 응용 프로그램을 만들었습니다. "Require에서," 우리는 Cloudflare WARP의 사용을 구체적으로 (Cloudflare 게이트웨이만 반대하십시오). 사용자는 Cloudflare의 회사의 인스턴스에 정정되는 활동적인 장치 클라이언트와 더불어 회사 관리한 장치에, MFA는 로그인 도중 사용되어야 하고, 외부 평가를 위해 밑에 추가 선택권이 있습니다.

[외부 평가](/cloudflare-one/access-controls/policies/external-evaluation/)우리는 일부 종류의 API 엔드포인트가 있습니다.[액세스 로직](https://github.com/cloudflare/workers-access-external-auth-example)— 이 경우, 당일 액세스 시간. 이 엔드포인트에 API 호출을 만들고 Cloudflare가 API에서 온 응답을 확인하는 데 사용하는 키 정의입니다. 이것은 몇몇 이유를 위해 유용합니다:

외부 평가는 사용자가 posture 체크의 기본 설정에 의해 포함되지 않은 기준에 따라 맞춤 보안 자세 검사를 만들 수 있습니다. 이 예제의 경우, 우리는 서비스에 내장되어 있습니다[Cloudflare Workers](https://workers.cloudflare.com/).

- 업무시간 외의 터미널에 대한 액세스 제한은 시간 기반 액세스 제어 양식을 구현합니다. 이것은 잠재적인 공격자를 위한 기회의 창을 제한해서 보안의 여분 층을 추가합니다.

이제 개인 IP 응용 프로그램으로 RDP 액세스를 보안하는 방법을 배우게됩니다.

| Application 구성 |                 |
| :------------- | :-------------- |
| 신청 이름          | 사이트맵            |
| 대상 IP          | 169.254.255.254 |

이전에 언급했듯이, Cloudflare 프록시가 네트워크의 IP 범위를 프록시했기 때문에 개인 IP 애플리케이션 작업. 이 응용 프로그램의 성격은 사용자가 Cloudflare (그리고 더 구체적으로, 그들은 WARP-to-Tunnel 연결의 이점을 취할 수 없는), 그들은 비 지방 RFC 1918 주소를 도달할 수 없을 것입니다.

| 교통안내                         |                                            |
| :--------------------------- | :----------------------------------------- |
| 대상 IP                        | 169.254.255.254                            |
| 관광 명소                        | 3389                                       |
| **이름 \***                    |                                            |
| 사용자 그룹 이름                    | 서버 관리자                                     |
| **장치 Posture**               |                                            |
| Passed Device Posture 검사     | WARP 체크 (Mac OS) (파일) macOS의 최신 버전 (OS 버전) |
| **- 연혁**                     | 지원하다                                       |
| **Enforce WARP 클라이언트 세션 기간** | 60분0                                       |

응용 프로그램을 정의하는 것은 간단합니다, Cloudflare가 자동으로 IP 범위에서 채우고 RDP에 검출 된 프로토콜을 제한해야합니다. 그러나 개인 IP 응용 프로그램에 대한 규칙은 약간 다릅니다. 액세스 관리에도 불구하고 Cloudflare Gateway 메뉴의 네트워크 정책으로 나타납니다. MFA 및 외부 평가 검사와 같은 특정 옵션은 여기에 나타나지 않습니다. 그러나 이러한 속성은 사용자가 장치 클라이언트를 활성화하고 조직에 인증 할 때 확인 될 수 있습니다.

여기에서 사용할 수있는 하나의 옵션은 장치 에이전트 클라이언트 세션 기간을 강제합니다. 이것은 특정 시간 후에, 사용자는 reauthenticate에 강제될 것입니다. 이 기능은 개인 IP 응용 프로그램을 보호하는 Zero Trust 접근 방식을 취할 수 있습니다. 사용자의 자격 증명이 손상되거나 장치가 중단되지 않은 경우 잠재적 인 창이 제한됩니다. 정기적인 요구에 따라, 우리는 지속적으로 사용자의 정체성 및 허가 상태를 확인하고, 핵심 Zero Trust 원리에 맞추고, 항상 확인합니다."

Cloudflare는 Zero Trust 방법론에 있는 중요한 자원에 보호하고 감시하는 포괄적인 안전 해결책을 제공합니다.
