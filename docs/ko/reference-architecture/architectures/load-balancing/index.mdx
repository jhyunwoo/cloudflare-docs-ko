## 제품정보

모델 번호: Cloudflare Load Balancing은 유지 보수, 실패, 탄력성 및 확장성의 우려를 크게 감소하면서 글로벌 사용자 기반 응용 프로그램을 호스팅 할 수있는 SaaS입니다. Cloudflare 사용하기 Load Balancing은 다음과 같은 문제를 해결하는 조직을 허용합니다.

- 매우 큰 볼륨의 들어오는 트래픽을 처리, 특히 예상치 못한 서지 또는 스파이크 중.
- 응용 프로그램과 서비스는 사용자에게 접근 할 수 있습니다.
- 빠른 응답 시간 유지 및 모든 사용자에 대 한 최적의 성능, 특히 높은 트래픽 기간 동안.
- 교통 수요를 변경하고 인프라를 보장하는 것은 성장을 수용 할 수 있습니다.
- 응용 프로그램과 서비스는 서비스 (DDoS) 공격의 Distributed Denial에 저항합니다.

모델 번호: Cloudflare Load Balancing은 모든 네트워크 (enterprise and Internet), 클라우드 환경, 응용 프로그램 및 사용자간에 모든 연결을 확보 할 수있는 프로그래밍 가능한 클라우드 기반 서비스의 통합, 지능형 플랫폼 인 Cloudflare의 연결 클라우드에 내장되어 있습니다. 데이터 센터와 함께 가장 큰 글로벌 네트워크 중 하나입니다.<PublicStats id="data_center_cities" />상호 연결<PublicStats id="network_peers" />. 그것은 또한 많은 다른 큰 기술 회사 보다는 핵심 인터넷 교환에 있는 더 중대한 존재가 있습니다.

결과적으로 Cloudflare는 세계 인터넷 연결 인구의 \~95 %의 \~ 50m 이내에 작동합니다. 모든 Cloudflare 서비스는 모든 네트워크 위치에 걸쳐 실행하도록 설계되었습니다. 모든 요청은 경로, 검사 및 소스에 가까운 필터링되어 강력한 성능과 일관성있는 사용자 경험에서 발생합니다.

이 문서는 참고 자료 아키텍처를 통해 글로벌 및 로컬 트래픽 관리 로드 밸런싱 솔루션을 배포합니다.

## 현대 애플리케이션에서 동적 워크로드 처리

### 개념 및 용어

#### 끝점

이 문서에서는, 용어 “endpoint”는 공개 또는 개인 트래픽을 수신하고 처리하는 모든 서비스 또는 하드웨어입니다. 로드 밸런싱은 웹 서버에서 사용할 수 있으므로 용어 엔드포인트는 모든 유형의 소스, 호스트 이름, 개인 또는 공공 IP 주소, 가상 IP 주소 (VIPs), 서버 및 기타 전용 하드웨어 상자를 나타냅니다. 그것은 대중 또는 개인적인 구름에서 온프레미스 또는 호스팅될 수 있었습니다 — 그리고 제3자 짐 밸런서일 수 있었습니다.

#### 제품 정보

스티어링은 로드밸런서의 주요 함수입니다 — 취급, 전송 및 전달 요청의 프로세스는 정책의 세트에 따라입니다. 이 정책은 일반적으로 요청 URL, URL 경로, HTTP 헤더, 구성 된 무게, 우선 순위 및 endpoint 대기 시간, 응답성, 용량 및 부하를 포함하여 계정으로 많은 요소를 고려합니다.

#### 층 7

[층 7](https://www.cloudflare.com/learning/ddos/what-is-layer-7/)이름 \*[OSI 모델](https://www.cloudflare.com/learning/ddos/glossary/open-systems-interconnection-model-osi/), 또한 신청 층으로 알려져, SSH, FTP, NTP, SMTP 및 HTTP (S) reside와 같은 의정서가 어디에 있습니다. 이 문서는 7 층 또는 층 7 로드밸런서를 참조하면 HTTP (S) 기반 서비스를 의미합니다. Cloudflare 층 7 더미는 Cloudflare가 DDoS 보호, Bot 관리 같이 서비스를 적용하기 위하여 허용합니다. WAF, CDN, Load Balancing 등 고객의 웹 사이트에 성능, 가용성 및 보안 향상.

#### 층 4

층 4 의[OSI 모델](https://www.cloudflare.com/learning/ddos/glossary/open-systems-interconnection-model-osi/)— 또한 수송 층이라고 불립니다 — 2개의 장치 사이 최후 커뮤니케이션을 책임집니다. 레이어 4에서 작동되는 네트워크 서비스는 서비스 및 프로토콜의 훨씬 더 넓은 설정을 지원할 수 있습니다. Cloudflare의 퍼블릭 레이어 4 로드밸런서는 Spectrum이라는 제품에 의해 활성화되어 레이어 4 역 프록시로 작동합니다. Load balancing 외에도 Spectrum은 보호 기능을 제공합니다.[DDoS 공격](https://www.cloudflare.com/learning/ddos/what-is-a-ddos-attack/)그리고 endpoint IP 주소를 은폐할 수 있습니다.

#### SSL/TLS 오프로드

SSL(Secure Sockets Layer) 및 그 후속 TLS(Transport Layer Security)는 인터넷에 연결하기 위해 사용되는 암호화 프로토콜입니다. SSL 및 TLS offloading은 SSL/TLS 종료 또는 SSL/TLS 가속으로도 알려져 있으며, 엔드포인트의 성능에 영향을 미치지 않고 SSL/TLS 암호화 및 해독 프로세스를 처리하는 데 사용되는 기술입니다. SSL/TLS offloading은 서버 성능 향상, 인증서 관리 단순화, 리소스 기반 암호화 및 암호 해독 작업을 해제하여 확장성을 향상, endpoints가 콘텐츠 및 응용 논리를 제공하도록 최선을 다하고 있습니다.

### Load Balancers에 의해 해결 된 도전

현대 웹 사이트, 또는 그 문제에 대한 어떤 응용 프로그램, 세 가지 주요 과제를 직면:

1. **성과:**&#xC751;용 프로그램은 사용자 요청에 응답하고 적시에 입력
2. **가용성:**&#xC751;용 프로그램에 대한 가동 시간을 유지하므로 항상 사용자 요청에 응답 할 수 있습니다.
3. **확장성:**&#xC0AC;용자 행동 또는 수요에 따라 애플리케이션 리소스를 재배, 축소 또는 재구성합니다.

#### - 연혁

신청 성과는 몇몇 요인에 의해 영향을 미칠 수 있습니다, 그러나 성과 문제점의 일반적인 원인은 endpoint에 있는 사용법 또는 짐의 양입니다. endpoint는 일반적으로 compute 리소스의 무한한 금액을 제공 할 수 있습니다. 너무 많은 요청이 한 번에 도착하거나 요청 유형이 CPU / 메모리 사용 증가하면 엔드포인트가 느리게 반응하거나 전혀 응답하지 못합니다.

이러한 문제를 해결하려면 엔드포인트는 더 많은 컴퓨팅 리소스로 업그레이드 할 수 있습니다. 그러나 idle 또는 low-usage 시간 동안, 조직은 underutilized 자원을 지불합니다. 조직도 여러 엔드포인트를 배포할 수 있습니다. 그러나 그들 사이의 원활한 스티어 트래픽에, 로드 밸런싱 솔루션은 최종 사용자에게 원활한 프로세스를 만들기 위해 필요합니다.

Figure 1는 로드밸런서 없이 로드가 배포될 수 있는 방법을 보여줍니다:

![Endpoint 짐은 짐 balancer 없이 균등하게 배부되지 않습니다](~/assets/images/reference-architecture/load-balancing-reference-architecture-images/lb-ref-arch-1.svg "Figure 1: Endpoint performance can suffer without a load balancer")

Load Balancers는 조직이 여러 엔드포인트를 호스팅하고 트래픽을 끊을 수 있으므로 단일 엔드포인트가 압도되지 않습니다. Load Balancer는 모든 들어오는 요청을 처리하고 적절한 엔드포인트로 전달합니다. 클라이언트는 endpoint 가용성 또는 짐의 어떤 지식이 필요하지 않습니다 — 그것은 다만 짐 밸런서에 요구를 보내고 짐 밸런서는 나머지를 취급합니다. Figure 2는 load balancer가 endpoints를 설정한 사용자로부터 트래픽을 균등하게 배포할 수 있는 방법을 보여줍니다.

![Load Balancer는 여러 엔드포인트에 걸쳐 요청을 배포하는 데 도움이됩니다.](~/assets/images/reference-architecture/load-balancing-reference-architecture-images/lb-ref-arch-2.svg "Figure 2: Load balancers help distribute load across endpoints")

또 다른 성능 관련 문제는 클라이언트와 엔드포인트 사이의 거리를 수행해야합니다. 훨씬 더 많은 네트워크 홉을 만들거나, 더 긴 거리를 여행하는 요청은 일반적으로 더 높은 왕복 시간 (RTT)가 있습니다.

RTT는 가늠자에 중요합니다. 예를 들어 클라이언트와 엔드포인트가 미국에 위치한 경우 25ms의 RTT를 기대할 수 있습니다. 클라이언트가 20 요청이 있으면 응답이 필요합니다. 총 시간은 순차적으로 처리해야합니다 (예를 들면 시간) 500ms (20 x 25ms). 그리고 APAC 지역과 연결된 동일한 클라이언트가 RTT가 150ms로 올라갈 수 있다면, 3000ms (20 x 150ms)의 바람직한 총 로딩 시간으로 인해 발생합니다. (Certainly, HTTP / 2 및 HTTP / 3의 스트리밍 향상을 요청하면이 수학을 변경할 수 있습니다. 그러나 동적 또는 상호 작용 콘텐츠가있는 웹 사이트에서 응답의 정보는 추가 요청을 생성하는 데 사용됩니다. 예는 일반적으로 보유합니다.) 그림 3이 어떻게 일어나는지 보여줍니다.

![요청의 수를 기반으로 한 Latency 화합물](~/assets/images/reference-architecture/load-balancing-reference-architecture-images/lb-ref-arch-3.svg "Figure 3: How latency can compound and affect the total time it takes to load a resource")

로드밸런서와 같은 방법으로 트래픽을 덜 버스 엔드 포인트로 전달할 수 있습니다. 또한 지리적으로 가까운 엔드 포인트로 트래픽을 전달할 수 있으며 클라이언트의 응답된 경험에 더 많은 결과가 있습니다. 특히, 로드밸런서는 요청을 전송하는 IP 주소의 조회를 수행하고 위치를 결정하고 가장 가까운 지역 적합성 엔드 포인트를 선택하여 전송 (이 GeoDNS와 같은 DNS 솔루션에 의해 제공된 기능과 유사합니다).

#### 적용분야

서비스 가용성은 load balancer 뒤에 endpoints의 unintentional와 의도적인 가동불능시간을 둘 다 우회합니다. 몇몇 요인은 기계설비 실패, 소프트웨어 버그, 네트워크 문제점 및 ISP 또는 다른 납품업자 문제점을 포함하여 unintentional 가동불능시간에, 공헌할 수 있습니다. 가장 진보 된 조직에서도 이러한 문제는 불가피합니다.

Load balancers는 항상 endpoints의 건강을 모니터링하여 이러한 문제를 해결합니다. endpoint가 건강 검사에 반응하는 것이 느려지거나 완전히 응답하지 못하면, endpoint는 건강으로 표시됩니다. ICMP (ping) 및 TCP 연결 테스트와 같은 기본 건강 테스트를 포함하여 모니터링을위한 몇 가지 방법이 있습니다. 더 진보 된 건강 테스트는 HTTP GET 요청을 발급하고 특정 응답 코드 및 응답 체는 endpoint에서 반환됩니다. endpoint가 degraded 상태에 있는 경우에, 짐 balancer는 더 적은을 보낼 것입니다 또는 더 건강한 endpoints의 호의에 있는 그것의 방법. 엔드포인트가 다시 작동되고 로드밸런서는 건강 검사에 대한 응답을받을 수 있습니다, 엔드포인트가 작동으로 표시되고 트래픽이 한 번 더 스티어링됩니다.

Intentional 다운타임은 용량 변경, 하드웨어 또는 인프라 업그레이드 및 소프트웨어 업데이트를 포함하여 몇 가지 다른 형태로 제공됩니다. Load balancers는 이러한 유지 보수를 허용하기 위해 하나 이상의 엔드 포인트에서 트래픽을 완전히 제거합니다.

#### 제품정보

효과적인 신청 사기는 조직은 고객 또는 사용자 요구에 응하고 불필요한 청구 또는 책임을 피합니다. 교통이 증가하는 동안, 조직은 일시적으로 서비스 수행을 보장하기 위해 더 많은 엔드포인트를 배포해야합니다. 그러나, 끊임없이 당신의 최대 가능한 트래픽을 충족하기 위해 충분한 엔드포인트가 온라인에 위치하거나 AWS, GCP, 또는 Azure와 같은 클라우드 제공 업체를 통해 엔드포인트에 상관없이 비용이 많이 들 수 있습니다. 로드밸런서는 동적 증가 또는 감소를 허용하여 처리, 연결 및 endpoints에 대기 시간.

고려해야 할 다른 유형은 지리적 규모입니다. 서비스가 인기로 성장함에 따라, 엔드포인트 위치가 더 중요합니다. 최종 점보다 다른 지리적 영역에서 사용자는 느린 응답 시간을 가질 수 있으며 동일한 지역에서 사용자보다 낮은 품질의 서비스를받을 수 있습니다. 조직은 다른 지역에서 새로운 엔드포인트를 배포함으로써 트래픽을 배포하려는 방법을 결정해야 합니다. 이 도전은 글로벌 트래픽 관리 (GTM) 및 Private Network Load Balancing이라는 로드 밸런싱의 다른 레이어에 의해 충족되었습니다. 이 문서는 다음과 같은 섹션에서 세부 사항을 모두 설명합니다. 그러나 요약에서 GTM 로드밸런서는 초기 요청 (DN을 통해 전형적으로)을 처리하고 적절한 지리적 영역에서 엔드포인트로 배포되는 Private Network Load Balancer에 스티어링 트래픽을 선택합니다.

### 교통 관리의 종류

언급했듯이, 글로벌 애플리케이션 및 서비스에 대한 로드 밸런싱은 두 개의 레이어로 제공됩니다. 첫번째 층은 Global Server Load Balancing (GSLB)라고도 할 수 있는 Global Traffic Management 또는 Manager (GTM)라고 합니다. 두 번째 레이어는 Server Load Balancing (SLB)라고도 할 수 있는 Private Network Load Balancing이라고 합니다. 이 섹션은 이러한 다른 유형의 로드 밸런싱과 함께 작동하는 방법을 정의합니다.

#### 글로벌 트래픽 관리자 / 글로벌 트래픽 관리 (GTM)

글로벌 트래픽 관리자는 인터넷에서 일반적으로, 적절한 지역 또는 데이터 센터에 라우팅 요청을 담당합니다. 많은 GTM 로드밸런서는 DNS 레이어에서 작동하며, 이를 허용한다.

- IP 주소로 DNS 요청을 해결합니다.
- 클라이언트에 가까운 endpoint 또는 서비스의 IP를 제공하므로 연결할 수 있습니다.

Figure 4는 GTM 로드밸런서는 클라이언트 위치 또는 지역에 따라 데이터 센터를 선택하는 데 사용됩니다.

![글로벌 트래픽 관리 steers 트래픽은 적절한 지역 또는 데이터 센터에](~/assets/images/reference-architecture/load-balancing-reference-architecture-images/lb-ref-arch-4.svg "Figure 4: Global traffic management load balancer overview")

Global Traffic Managers는 HTTP 요청에서 읽기/변경/삭제 헤더를 포함하여 다양한 검사를 수행하고 지역 또는 지리적 위치에 따라 URL을 수정할 수 있습니다. GTM 기능은 클라우드 기반 로드밸런서(Cloudflare와 동일)에 의해 가장 잘 구현됩니다. 하드웨어 로드밸런서는 단일 물리적 위치에 존재하며, 더 많은 트래픽이 로드밸런서에서 시작되는 것을 의미하며, 최종 사용자 경험을 느리게합니다. 클라우드 기반 로드 밸런서는 다양한 지리적 위치에서 실행할 수 있으며 DNS 전용, 레이어 4 및 레이어 7 컨텍스트에 대한 실행 솔루션을 제공합니다.

#### 개인 네트워크 부하 Balancing

Private Network Load Balancing steers 트래픽 데이터 센터 또는 지리적 위치. Private Network Load Balancer는 load balancing, SSL/TLS offloading, content switching 및 기타 Application Delivery 기능을 담당할 수 있습니다. Private Network Load Balancing은 여러 엔드포인트를 통해 클라이언트 요청의 효율적인 배포를 통해 성능 향상 및 높은 가용성을 보장합니다. Private Network Load Balancers는 일반적으로 개인 네트워크 내부에 배치되며 공개적으로 또는 개인적으로 접근 가능한 리소스를로드하는 데 사용됩니다. 아래 그림 5에서 GTM 로드 밸런서는 유럽 데이터 센터를 선택하여 유럽 데이터 센터의 Private Network Load Balancer에 요청을 전달하여 적절한 엔드포인트로 스티어링합니다.

![Private Network Load Balancing은 최종 엔드포인트 또는 목적지로 스티어링을 담당합니다.](~/assets/images/reference-architecture/load-balancing-reference-architecture-images/lb-ref-arch-5.svg "Figure 5: Private Network Load Balancer overview")

Private Network Load Balancer와 그들의 엔드포인트는 일반적으로 방화벽 뒤에 앉아 있습니다. 그러나 endpoints는 개인 네트워크에 보호 될 수 있지만, Private Network Load Balancer에 대한 접근성은 배포 요구 사항에 따라 공공 또는 개인이 될 수 있습니다. Private Network Load Balancer는 총 요청, 연결, 엔드포인트 건강을 모니터링하여 요청을 적시에 응답할 수 있는 엔드포인트로 향합니다.

#### On-premises vs 클라우드 기반 로드밸런서

2개의 주요 짐 밸런서 건축술이 있습니다:

- 온프레미스 로드밸런서
  - 일반적으로 하드웨어 기반도 가상화 또는 소프트웨어 기반이 될 수 있습니다.
  - 최대 성능에 집중
- 클라우드 기반 로드밸런서
  - 공공 클라우드 인프라 구축
  - 요청의 시작점에 더 가까이 핸들 요청

각 접근법에는 장점과 단점이 있습니다. On-premises load balancers는 일반적으로 조직에 의해 완전히 통제되는 개인 네트워크의 안쪽에 존재합니다. 이 짐 밸런서는 끝점으로 collocated, 그래서 대기 시간 및 RTT 시간은 최소한이어야한다. 이러한 온-프레미스 로드밸런서는 단일 물리적 위치에 제한되는 것입니다. 다른 지역에서 트래픽을 의미하는 것은 긴 RTT 및 높은 대기 시간 응답. 또한 다른 데이터 센터를 추가하면 구매 및 모든 새로운 장비를 배포해야합니다. On-premises load balancers는 일반적으로 지리적으로 지역 또는 지역 부적절한 데이터 센터에 의해 처리되는 요청을 얻기 위해 지리적 트래픽 스티어링을 위한 클라우드 기반 로드밸런서가 필요합니다. 클라우드 기반 로드 밸런서의 장점은 선반 공간, 전력, 냉각 또는 유지 보수에 대한 우려없이 거의 모든 지리적 지역에서 작동 할 수 있으며 새로운 섀시, 모듈 또는 더 큰 네트워크 연결에 대한 우려없이 스케일 할 수 있습니다. Cloud-based load balancers는 load balancer와 endpoints 사이에 지연시간과 RTT를 증가시키며, 일반적으로 endpoints에 할당되지는 않습니다.

## 모델 번호: Cloudflare 적재 Balancing 건축과 디자인

Cloudflare는 2016년부터 클라우드 기반 GTM를 제공하고 2023년에 Private Network Load Balancing 기능을 추가했습니다. 이 섹션은 Cloudflare Load Balancing 아키텍처를 검토하고 다른 구성과 옵션으로 깊이 다이빙 할 것입니다. 먼저, Cloudflare Load Balancers가 Cloudflare의 글로벌 네트워크에서 실행하여 간단히 혜택을 이해하는 것이 중요합니다.

### Cloudflare 건축술에 있는 Inherent 이점

모델 번호: Cloudflare Load Balancing은 모든 네트워크 (enterprise and Internet), 클라우드 환경, 응용 프로그램 및 사용자 간의 모든 연결을 가능하게하는 프로그래밍 가능한 클라우드 기반 서비스의 통합, 지능형 플랫폼 인 Cloudflare의 연결 클라우드에 내장되어 있습니다. 데이터 센터와 함께 가장 큰 글로벌 네트워크 중 하나입니다.<PublicStats id="data_center_cities" />상호 연결<PublicStats id="network_peers" />. 그것은 또한 많은 다른 큰 기술 회사 보다는 핵심 인터넷 교환에 있는 더 중대한 존재가 있습니다.

결과적으로 Cloudflare는 세계 인터넷 연결 인구의 \~95 %의 \~ 50m 이내에 작동합니다. 그리고 모든 Cloudflare 서비스는 모든 네트워크 위치에 걸쳐 실행하도록 설계되어 있기 때문에, 모든 트래픽은 연결되고, 검사되고, 제일 성과 및 일관된 사용자 경험을 위한 근원에 닫히는 거릅니다.

Cloudflare의 로드 밸런싱 솔루션은 anycast 기술의 사용으로부터 혜택을 받습니다. Anycast는 Cloudflare를 통해 전 세계 모든 데이터 센터의 IP 주소를 발표하므로 트래픽은 항상 소스에 가까운 Cloudflare 데이터 센터로 이동합니다. 이것은 교통 검사, 인증 및 정책 시행은 최종 사용자에 가까운 곳으로, 일관되게 높은 품질의 경험을 선도합니다.

anycast를 사용하여 Cloudflare 네트워크는 잘 균형을 잡습니다. 네트워크의 트래픽에 급격한 증가가 있는 경우, 로드는 여러 데이터 센터를 통해 배포 될 수 있습니다. 즉, 사용자가 일관성 있고 신뢰할 수있는 연결을 유지할 수 있습니다. 또한 Cloudflare의 대형 네트워크 용량과 AI / ML 최적화 스마트 라우팅은 성능이 지속적으로 최적화되도록 도와줍니다.

대조적으로, 다른 많은 SaaS 근거한 짐 밸런싱 공급자는 단 하나 IP 주소가 단 하나 endpoint 및/또는 자료 센터와 관련있는 Unicast 여정을 이용합니다. 이 웹 사이트는 귀하가 웹 사이트를 탐색하는 동안 귀하의 경험을 향상시키기 위해 쿠키를 사용합니다. 이 쿠키들 중에서 필요에 따라 분류 된 쿠키는 웹 사이트의 기본적인 기능을 수행하는 데 필수적이므로 브라우저에 저장됩니다. 예를 들면, 성과는 신청의 끝점 옆에 사무실에서 일하는 직원을 위해 우수할지도 모릅니다, 그러나 원격 직원을 위해 빈약한 또는 해외 작업. Unicast는 또한 스케일링 트래픽 부하를 준수합니다. 단일 서비스 위치는 부하 증가 할 때 리소스를 기울여야하며 어떤 네트워크는 많은 데이터 센터와 지리를 통해 트래픽을 공유 할 수 있습니다.

그림 6은 Cloudflare 네트워크를 사용하는 방법을 보여줍니다 지리적으로 사용자가 가능한 한 빨리 자신의 리소스에 연결할 수 있습니다.

또 다른 방법 교통량은 Cloudflare 갱도의 사용에 의해 영향을 미칠 수 있습니다. 이 문서는 Cloudflare를 포함합니다 다음 섹션의 깊이에 터널. Cloudflare 때문에 터널은 특정 Cloudflare 데이터 센터에 엔드포인트를 연결하고, 그 엔드포인트에 대한 트래픽은 엔드포인트에 도달하기 위해 그 데이터 센터를 추적해야합니다. 그림 9는 Cloudflare를 통해 연결된 개인 엔드 포인트에 연결하는 방법을 보여줍니다 터널은 터널이 종료되는 데이터 센터를 통과해야 합니다.

일반적으로 GTM 및 Private Network Load Balancers는 별도의 하드웨어 또는 별도의 SaaS(GTM) 및 하드웨어 Private Network Load Balancing 구성 요소입니다. Cloudflare의 GTM 및 Private Network Load Balancing 기능은 구성과 관리를 단순화하는 단일 SaaS로 결합됩니다. GTM 로드밸런서와 스티어 트래픽을 로컬 Private Network Load Balancers에 만들 필요가 없습니다. 모든 엔드포인트는 Cloudflare에 직접 연결될 수 있고 교통은 정확한 지역, 자료 센터 및 단 하나 짐 밸런서 윤곽에서 endpoint에 steered. GTM 및 Private Network Load Balancing 기능의 개념은 지속될 것이며, Cloudflare의 구현은 단순하고 간단합니다. Figure 10 글로벌 트래픽이 어떤 지리적 영역에서 특정 엔드포인트로 끌어올릴 수 있는지 보여줍니다.

![GTM 및 Private Network Load Balancing 기능을 단일 로드밸런서 구성에 결합](~/assets/images/reference-architecture/load-balancing-reference-architecture-images/lb-ref-arch-10.svg "Figure 10: Cloudflare combines the function of GTM and Private Network Load Balancing")

### Cloudflare Load Balancer의 구조

Cloudflare Load Balancer는 종종 가상 IP (VIP)로 언급되며 엔트리 포인트로 구성됩니다. 일반적으로이 엔트리 포인트는 DNS 레코드입니다. 로드밸런서가 먼저 정의된 트래픽 스티어링 알고리즘을 적용하여 엔드포인트 풀을 선택하여 기능, 지리적 영역, 또는 지역으로 선택된 엔드포인트 그룹을 선택합니다. 짐 밸런서 윤곽에는 1개 또는 다수 엔드포인트 수영장이 있고, 각 엔드포인트 수영장은 1개 또는 많은 엔드포인트가 있을 수 있습니다. 엔드포인트 풀을 선택한 후, 로드밸런서는 엔드포인트 스티어링 알고리즘을 엔드포인트 목록에 적용하여 트래픽을 스티어링하는 엔드포인트를 선택합니다. 그림 11은 Cloudflare Load Balancer 내의 클라이언트 요청에서 기본 단계를 보여줍니다.

![Cloudflare Load Balancer 내의 단계](~/assets/images/reference-architecture/load-balancing-reference-architecture-images/lb-ref-arch-11.svg "Figure 11: The basic process flow through a Cloudflare Load Balancer")

Cloudflare Load Balancer의 정의는 세 가지 주요 구성 요소로 나뉩니다.

1. 건강 모니터: 이러한 구성 요소는 endpoints의 건강을 관찰 하 고 건강 하 고 중요 한 (건강)로 분류.
2. Endpoint Pools: 이것은 endpoints가 정의되고 어디 건강 모니터 및 endpoint Steering가 적용됩니다.
3. 로드밸런서: 이 구성 요소에서 엔드포인트 풀 및 트래픽 스티어링 정책의 목록이 적용됩니다.

다음 섹션은 Cloudflare Load Balancer 구성을 위해 사용할 수있는 옵션과 고려 사항을 자세히 설명합니다. 스티어링을 시작으로 엔드포인트 풀과 로드밸런서 구성에 활용됩니다.

### 스티어링 유형 및 방법

스티어링은 로드밸런서와 스티어링 방법의 핵심 기능으로, 로드밸런서가 참여할 때 선택될 것입니다. 로드밸런서의 관점에서 스티어링은 두 가지 주요 영역에 적용 할 수 있습니다.

첫 번째는 'traffic Steering'라고 불리며, endpoint Pool이 들어오는 요청을 처리하는 데 책임이 있습니다. 일반적으로 requester의 근접 또는 지리적 지역을 기반으로합니다. 트래픽 스티어링의 개념은 글로벌 트래픽 관리의 아이디어와 밀접하게 일치합니다.

스티어링이 적용된 두 번째 영역은 지역, 데이터 센터 또는 엔드포인트 풀이 선택되었습니다. 이 시점에서, 로드밸런서는 'endpoint Steering'라고 불리는 요청이나 연결을 처리하는 단일 엔드포인트를 선택해야 합니다. 이러한 수준 모두에서 스티어링 방법을 적용하여 로드밸런서를 배치하는 고객의 특정 요구에 맞게 수행됩니다. 선택할 수있는 여러 가지 알고리즘이 있지만 모든 알고리즘은 스티어링 유형에 적용되지 않습니다.

아래는 모든 스티어링 방법 Cloudflare의 심층적인 검토입니다. 이 섹션의 끝에, 알고리즘이 사용 사례에 적용 가능한 이해에 도움이 될 수있는 빠른 참고 자료 테이블이 있습니다.

#### 교통 조타

트래픽 스티어링은 엔드포인트 풀이라고도 불리는 엔드포인트 그룹을 선택합니다. 트래픽 스티어링의 가장 일반적인 사용은 적어도 늦은 응답 시간, 지리적 지역, 또는 물리적 위치에 따라 엔드포인트 풀을 선택할 수 있습니다. 트래픽 스티어링은 글로벌 트래픽 관리에 밀접하고 엔드포인트에 트래픽을 지시하는 초기 단계 역할을 합니다.

#### Endpoint 핸들

Endpoint Steering는 endpoint가 요청 또는 연결을 수신하는 선택에 책임집니다. Endpoint 조타는 무작위로 endpoint를 선정할 수 있습니다, 이전에 선택된 endpoint ( session affinity가 활성화되는 경우에), 또는 그것은 요구 또는 연결을 위한 적어도 이용된, 가장 빠른 응답, endpoint를 선정하기 위하여 사용될 수 있습니다. Endpoint Steering는 Private Network Load Balancing과 긴밀히 관련되어 있으며, 요청 또는 연결의 최종 목적지를 선택할 수 있습니다.

#### 공급 능력

Weighted Steering는 endpoint Pools와 endpoints의 차이를 고려하여 로드밸런서에서 요청을 처리할 수 있습니다. 엔드포인트 무게, 모든 엔드포인트에 필요한 필드는 특정 스티어링 방법이 선택될 때만 사용됩니다. 마찬가지로 endpoint Pool weight는 특정 스티어링 방법이 선택될 때만 필요합니다. 오시는 길[조타 선택권 개요](#steering-options-overview)무게가 적용될 때 빠른 참고 자료를 위한 단면도.

무게는 endpoint 풀 또는 endpoint 선택의 랜섬에 영향을 미칩니다. 무게는 역사적인 자료 또는 현재 연결 정보를 고려하지 않습니다. 즉, 무게는 더 짧은 시간 프레임에 분포에 차이가 있을 수 있습니다. 그러나 더 긴 기간 동안 시간과 상당한 트래픽을 가진 유통은 구성에 적용되는 원하는 무게를 더 밀접하게 닮을 것입니다. 세션 친화도는 초기 연결 후 무게 설정과 동일한 엔드포인트 풀 또는 엔드포인트에 후속 요청을 지시하는 것이 중요합니다. Figure 12는 동일한 용량과 확률을 가진 두 개의 엔드포인트 풀에 대한 무게 예제를 보여줍니다.

![선택한 동일한 확률로 endpoint 풀의 쌍](~/assets/images/reference-architecture/load-balancing-reference-architecture-images/lb-ref-arch-12.svg "Figure 12: A pair of endpoint pools with equal capacity")

Least Outstanding Request Steering와 같은 특정 알고리즘은 개방된 요청과 연결의 수를 고려합니다. 무게는 endpoints 또는 endpoint 수영장이 개방된 요청이나 연결의 더 큰 수를 처리 할 수 있는지 결정하는 데 사용됩니다. 필수, 무게는 선택된 스티어링 방법과 관계없이 엔드포인트 또는 엔드포인트 풀의 용량을 정의합니다.

무게는 0.00와 1.00 사이 어떤 수로 정의됩니다. 엔드포인트 풀의 총 중량 또는 엔드포인트 풀 내의 엔드포인트가 동일하지 않는 것이 중요합니다. 대신, 무게는 함께 추가 될 것입니다, 그리고 그 다음 개별 중량 값은 선택한 그 엔드 포인트의 확률을 얻을 수 그 합계로 나뉩니다.

무게 비율 방정식: (endpoint weight) ÷ (풀의 모든 무게의 여름) = (% 트래픽의 endpoint)

아래는 트래픽을 배포하는 데 사용되는 중량을 이해하는 데 도움이되는 다이어그램의 예입니다. 이러한 예에서 목표가 동일한 용량 또는 계산 리소스를 가진 모든 엔드포인트의 트래픽을 균등하게 배포하는 것이 가정됩니다.[이름 \*](#random-steering)트래픽 스티어링은 3개의 엔드포인트 풀에 걸쳐 트래픽 분배를 설명하는 데 사용됩니다.

예제 1:

- 정의 된 세 가지 엔드 포인트 풀이 있습니다. 모든 무게 1
- 각 엔드포인트 풀은 선택한 33%의 확률이

1: (1) ÷ (1 + 1 + 1) = (.3333) (또는 33.33%)

![세 개의 엔드 포인트 풀 세트 모두 동등한 확률](~/assets/images/reference-architecture/load-balancing-reference-architecture-images/lb-ref-arch-13.svg "Figure 13: Three endpoint pools with equal weight")

이 예에서, 그것은 간단한 1 엔드 포인트 풀의 각에 대한 모든 무게 값. 그러나 0.01과 1.00 사이의 모든 숫자가 동일한 숫자가 모든 3개의 엔드포인트 풀에서 사용되었기 때문에 사용될 수 있다는 것을 주목해야 합니다. 예를 들어, 모든 3 풀을 .1 또는 심지어 .7로 설정하면 각 풀이 트래픽을받을 수 있도록 동일한 확률로 표시됩니다.

무게의 합이 확률을 계산하기 위해 사용되기 때문에 조직은 이러한 입력을 쉽게 이해하기 위해 모든 값을 사용할 수 있습니다. 다음 예제에서 각 엔드포인트가 동일한 용량을 가지고 있기 때문에, .1 무게의 값은 각 엔드포인트로 할당되며, 이러한 값의 합은 엔드포인트 풀의 무게로 사용됩니다.

예제 2

- 정의된 3개의 엔드포인트 풀이 있습니다
- 각 엔드포인트 풀에는 다양한 엔드포인트가 있지만, 모든 엔드포인트에는 동일한 용량이 있습니다.
- endpoints에서 하중을 균등하게 배포하려면 각 엔드포인트 풀은 다른 확률이 필요합니다.

![엔드포인트의 다른 숫자로 3개의 엔드포인트 풀](~/assets/images/reference-architecture/load-balancing-reference-architecture-images/lb-ref-arch-14.svg "Figure 14: Illustrates how to use weight to balance load across endpoint pools with different capacity")

.4의 무게를 위한 예 수학: (.4) ÷ (.4 + .5 + .6) = (.2667) (또는 26.67%)

.5의 무게를 위한 예 수학: (.5) ÷ (.4 + .5 + .6) = (.3333) (또는 33.33%)

.6의 무게를 위한 예 수학: (.6) ÷ (.4 + .5 + .6) = (.4000) (또는 40.00%)

끝점은 모두 동일한 용량이 없습니다. 다음 예에서 엔드포인트 풀의 엔드포인트 중 하나는 다른 두 개의 엔드포인트 풀에서 엔드포인트의 용량을 두 번 가지고 있습니다.

예제 3

- 정의된 3개의 엔드포인트 풀이 있습니다
- 엔드포인트 풀 1에는 엔드포인트 풀 2 및 엔드포인트 풀 3에 비해 용량을 두 배로 늘리는 엔드포인트가 있습니다.
- 목표는 엔드포인트 풀 1에 대한 트래픽의 양을 두 배로 배치하는 것입니다
- 엔드포인트 풀 1에는 4개의 엔드포인트가 있습니다 그러나 두 배 수용량과 더불어, 각 엔드포인트의 무게는 endpoint 수영장을 위한 .8의 합계를 위해 .2에 평가될 것입니다

![다른 용량의 엔드포인트와 엔드포인트의 다른 숫자로 3개의 엔드포인트 풀](~/assets/images/reference-architecture/load-balancing-reference-architecture-images/lb-ref-arch-15.svg "Figure 15: Using weight to balance load across endpoint pools with different capacities and endpoints")

.8의 무게를 위한 예 수학: (.4) ÷ (.8 + .5 + .6) = (.4211) (또는 42.11%)

.5의 무게를 위한 예 수학: (.5) ÷ (.8 + .5 + .6) = (.2632) (또는 26.32%)

.6의 무게를 위한 예 수학: (.6) ÷ (.8 + .5 + .6) = (.3157) (또는 31.57%)

마지막 예에서, 엔드포인트 풀 1의 4개의 엔드포인트가 다른 엔드포인트의 용량을 두 배로, 계산은 근본적으로 4개의 엔드포인트가 있는 것처럼 endpoint 풀 1을 대우합니다. 그러므로, .8 대신 .4의 무게 값은 예 2.로 표시됩니다.

이 세 가지 간단한 예제는 엔드포인트 풀 또는 엔드포인트를 통해 하중을 배포하는 데 사용할 수있는 방법을 설명합니다. 동일한 계산은 endpoint 풀 내에서 endpoints에 적용된 중량에 사용됩니다. 그러나 다른 스티어링 방법 내에서 무게를 사용하는 영향은 다음과 같습니다.

무게는 1개의 엔드포인트 풀이 다른 엔드포인트 풀 보다는 더 많은 리소스가 있을지도 모르거나 엔드포인트 풀 안에 endpoints가 동등한 수용량이 없을 때 가장 유용합니다. 무게는 모든 리소스가 똑같게 자신의 능력을 부여하는 데 도움이됩니다.

#### 핸들링 방법

##### 오프 - 실패

오프 - 실패는 트래픽 스티어링 정책의 가장 기본입니다. 종점 풀의 순서를 직접 트래픽을 선택하기위한 우선 순위 목록으로 사용합니다. 목록의 첫 번째 풀이 건강하고 트래픽을받을 수 있다면 선택한 풀입니다. 오프 이후 - 실패는 엔드포인트 스티어링에 사용할 수 없습니다, 다른 스티어링 방법은 엔드포인트를 선택하기 위해 사용됩니다. 오프 - 실패는 일반적으로 활성 / 수동 장애 시나리오에서 사용되며, 기본 데이터 센터 또는 엔드 포인트 그룹은 트래픽을 처리하는 데 사용되며 실패 조건 하에서만 트래픽은 백업 엔드 포인트 풀에 스티어링됩니다.

##### 연락처

랜덤 스티어링은 트래픽 스티어링과 엔드포인트 스티어링을 모두 사용할 수 있습니다. 로드밸런서 구성과 엔드포인트 풀 안에 정의된 무게를 기반으로 한 리소스의 랜덤 스프레드 트래픽. 각 엔드포인트 풀에 대한 로드밸런서에서 설정된 무게 값은 엔드포인트 풀 내에서 엔드포인트 당 무게 값과 다를 수 있습니다. 예를 들어, 로드밸런서 구성 내에서, 트래픽의 70 %는 두 개의 엔드포인트 풀 중 하나에 전송 될 수 있으며, 그 엔드포인트 풀 내에서 트래픽은 4 개의 엔드포인트를 통해 균등하게 배포 될 수 있습니다. 이전 섹션,[공급 능력](#weighted-steering), 무게가 사용되는 방법 및 endpoint 풀 또는 endpoint의 선택을 결정하는 계산의 상세한 설명을 제공합니다.

##### Hash 핸들

Hash Steering는 엔드포인트 무게와 요청의 소스 IP 주소를 사용하여 엔드포인트 스티어링 알고리즘입니다. 결과는 동일한 IP 주소에서 모든 요청이 항상 동일한 엔드포인트에 스티어링됩니다. endpoints의 순서를 바꾸거나 endpoints를 추가하거나 제거하는 것이 중요합니다. endpoint Pool의 endpoints는 해시 알고리즘을 사용할 때 다른 결과가 발생할 수 있습니다.

##### Geo 조타

Geo Steering는 특정 국가 또는 지리적 지역에 엔드포인트 풀을 묶는 엔터프라이즈 플랜 고객에게 제공하는 트래픽 스티어링 알고리즘입니다. 이 옵션은 스티어링 트래픽에 의해 성능 개선에 유용 할 수 있습니다. 또한 특정 지역의 리소스에 대한 사용자의 스티어링 요청에 의해 법 및 규정 준수 또는 특정 규제 요구 사항을 충족하도록 설계 된 리소스에 대한 지원.

##### 스티어링

Dynamic Steering는 둥근 여행 시간 (RTT) 프로파일을 생성하는 엔터프라이즈 플랜 고객에게 사용할 수있는 트래픽 스티어링 알고리즘입니다. RTT 값은 각 시간마다 건강 조사 요청을 수집하고 endpoint에서 모니터 요청에 응답을 기반으로합니다. 요청이 만들어지면 Cloudflare는 RTT 데이터와 RTT 값으로 풀을 검사합니다. 지역 또는 지역 센터의 풀에 대한 기존 RTT 데이터가없는 경우 Cloudflare는 실패 주문의 풀에 트래픽을 지시합니다. 동적 스티어링을 실행할 때 엔드포인트 풀에 대한 첫 번째 시간을 설정하면 Cloudflare가 그 풀에 RTT 프로필을 빌드합니다. 동적 스티어링은 가장 낮은 RTT 엔드포인트 풀을 선택하여 결정적인 공정과 단독으로 집중하는 지리적 경계를 사용하지 않습니다.

##### Proximity 핸들

Proximity Steering는 요청에 따라 가장 가까운 물리적 데이터 센터에 대한 스티어링 트래픽을 엔터프라이즈 플랜 고객에게 제공하는 트래픽 스티어링 알고리즘입니다.

Cloudflare는 다음과 같은 방법을 사용하여 requester의 물리적 위치를 결정합니다.

1. [EDNS 클라이언트 서브넷](https://developers.google.com/speed/public-dns/docs/ecs)DNS 요청에서 제공되는 정보
2. 해결자의 위치 정보 Cloudflare에 도달
3. Cloudflare 데이터 센터의 GPS 위치 요청 처리

Proximity Steering는 모든 엔드포인트 풀에 GPS 좌표를 제공해야하며, Cloudflare를 허용하여 요청 IP, DNS 해결자 또는 Cloudflare 데이터 센터를 기반으로 가장 가까운 엔드포인트 풀을 계산합니다.

##### Least 뛰어난 요청 핸들링 (LORS)

Least 걸출한 요구 조타 (LORS)는 기업 계획 고객에게 유효하 통행과 내점 조타를 위해 사용될 수 있습니다.

LORS는 스티어링에 영향을 미치는 HTTP 요청의 수를 사용하고 Cloudflare Layer 7 proxied Cloudflare Load Balancers와 함께 사용될 때만 기능적입니다. LORS가 로드밸런서의 다른 유형에 할당된 경우, 그 동작은 임의의 스티어링과 동일합니다. LORS는 무게와 함께 열린 요청의 카운트를 사용하여 스티어링 결정에 사용되는 새로운 변형 된 무게를 만듭니다.

LORS에 대한 동등한 변형 무게:

- 무게 / (count + 1) = transformedWeight

무작위 무게 계산을 위한 Reminder:

- 무게 / (총 중량) = 선택한 확률

다음은 LORS의 예입니다.

- 풀 A에는 0.4의 무게가 있습니다.
- 풀 B의 무게가 0.6
- Pool A에는 3개의 열려있는 요구가 있습니다
- 풀 B는 0개의 열려있는 요구가 있습니다
- 관련 방적
  - 무게 / (count + 1) = transformedWeight
- 풀 A의 변형 된 무게 : 0.4 / (3 + 1) = 0.1
- 풀 B의 변형 된 무게 : 0.6 / (0 + 1) = 0.6
- 관련 방적
  - 무게 / (총 중량) = 선택한 확률
- 풀 A의 확률로 향하는: 0.1 / (0.1+0.6) = .1429 (14.29%)
- 풀 B의 확률로 향하는: 0.6 / (0.1+0.6) = .8571 (85.71%)

이 예에서 다음 연결에는 풀 A와 85.71%의 확률이 14.29%의 확률이 있습니다. 풀 B. 트래픽이 풀 B로 스티어링 될 가능성이 있지만 여전히 풀 A에 스티어링 할 수 있습니다. 더 가벼운 짐 상태를 가진 상황에서, 조타 결과에 더 많은 변화가 있을 것입니다, 이는 정확하게 형성된 무게 일치할지도 모릅니다. 그러나 부하 증가로 실제 스티어링 결과가 구성 된 무게와 밀접하게 일치합니다.

non-L7 proxied load balancers가 LORS와 함께 사용될 때, 열려있는 요구 조사 정보는 유효하지 않습니다. 결과적으로, denominator는 항상 1 일 것입니다. 1개의 숫자를 분할하기 때문에 numerator를 변경하지 않으며, 이 경우에, numerator는 무게, 조타 결정은 무게에서만 할 것입니다. 위에서 설명한 임의 방법에서 이 결과.

LORS는 endpoint 풀 또는 엔드포인트가 동시 요청에서 스파이크로 쉽게 압도되는 경우에 가장 잘 사용됩니다. 지연, 지리적 정렬, 또는 기타 메트릭과 같은 요인에 대한 endpoint 건강에 대한 응용 프로그램에 잘 적합합니다. 이것은 특히 유용합니다 일부 또는 모든 요청이 endpoint에 무거운 부하를 넣고 응답을 생성하는 데 중요한 시간을 가지고.

### 건강 모니터

건강 모니터는 endpoints의 건강을 한 번 결정합니다. Health monitors는 endpoints에 연결 시도인 probes를 생성합니다. 건강 모니터는 endpoint 건강을 기록하는 조사에 응답을 사용합니다. Health monitors는 서비스 유형, 경로 및 포트와 같은 고급 기능을 포함 하는 템플릿으로 제공, 타임아웃, 그리고 프로토콜 특정 설정에 대 한 Endpoint 건강. 건강 모니터 템플릿은 엔드포인트 풀에 적용되며, 유사한 서비스를 호스팅하는 엔드포인트가 포함되어 있습니다. 건강 모니터가 엔드포인트 풀에 부착되면 엔드포인트 주소는 건강 모니터 프로브의 목적지로 사용됩니다. 단일 건강 모니터는 많은 엔드포인트 풀에서 사용할 수 있으며, 건강 모니터는 계정 수준의 개체이며 동일한 Cloudflare 계정 내에서 여러 영역에서 활용할 수 있습니다.

기본적으로, 건강 모니터 프로브는 엔드포인트 주소로 직접 전송되며, 전체 레이어 7 스택을 우회합니다. 이것은 load balancer를 통해서 endpoint에 실제적인 교통이 건강 감시자 조사 보다는 다른 처리를 받을 것이라는 점을 의미합니다. 구성에 따라, 실제 연결 또는 요청이 실패하더라도 건강 상태 모니터링 보고서에 결과 할 수 있습니다.

Simulate Zone 기능은 건강 모니터 프로브가 실제 요청으로 동일한 길을 따라 전체 레이어 7 스택을 통과합니다. 이것은 건강 감시자가 네트워크를 통해서 정확한 동일한 경로 및 다른 층 7 과정을 통해 endpoint에 도달하.

Simulate Zone 기능은 특정 기능이 활성화될 때 건강 감시자를 위해 요구됩니다[인증된 원본 풀 (AOP)](/ssl/origin-configuration/authenticated-origin-pull/), 프로브가 근원에 있는 입증을 위한 적당한 mTLS 증명서로 제공되지 않는 경우에 실패한 곳에. Simulate Zone은 건강 모니터 프로브가 제공한 동일한 경로를 보장합니다.[Argo 스마트 여정](/argo-smart-routing/)그리고 같은[전용 CDN Egress IPs](/smart-shield/configuration/dedicated-egress-ips/)조직의 레버리지[Smart Shield 고급](/smart-shield/get-started/#packages-and-availability)Cloudflare가 엔드포인트에 도달하는 가장자리 IP 주소를 제한하기 위해.

### 엔드포인트 및 엔드포인트 풀

Endpoints는 Load Balancer가 모든 정책을 적용한 후 연결 및 요청을 처리하는 실제 서버입니다. 엔드포인트는 물리적 서버, 가상 머신, 서버리스 애플리케이션이 될 수 있습니다. 그들은 사용자 또는 클라이언트에서 요청 또는 연결을 처리 할 수 있기 때문에, 그들은 endpoint로 간주 될 수 있습니다. 정의의 여러 가지 방법이 있으며 Cloudflare에 엔드 포인트를 연결하고 다음 섹션 세부 사항이 있습니다.

#### 연결 엔드 포인트 Cloudflare

Cloudflare Tunnel은 조직이 방화벽 구성을 단순화하고, 복잡성을 줄이며, 보안을 강화하고, 자산을 Cloudflare 네트워크에 더 쉽게 연결할 수 있게 해 주는 아웃바운드 연결입니다. 이러한 터널을 생성하는 실행 파일은 `cloudflared`이며, 이 문서와 이후 다이어그램에서도 이 이름으로 참조될 수 있습니다.

##### Cloudflare proxied, DNS, IP 및 비 Cloudflare endpoints

위의 "HTTP(S) Load Balancing"섹션에서 언급했듯이, Load balancing은 요청이 엔드포인트로 전송되기 전에 매우 마지막 프로세스 실행입니다. 그러나 경우에, 끝점이 Cloudflare의 가장자리를 통해 proxied 경우에, 짐 밸런서 후에, 요구는 층 7 더미를 다시 통과하지 않고 endpoint에 직접 전달됩니다. 이것은 endpoint는 unprotected 또는 uncached, 그러나 의미하지 않습니다. 로드밸런서 자체로 인해 그 모든 보호가 엔드포인트보다 오히려 로드밸런서에 제공됩니다. endpoint를 가진 어떤 직접적인 커뮤니케이션은 아직도 Cloudflare의 층 7 더미로 proxied 대우될 수 있습니다, 그러나 endpoint 장소와 통신은 모두 짐 밸런서의 앞에 처리, endpoint 아닙니다. 그림 19는 Cloudflare 층 7 더미가 엔드 포인트 (s)와 관련하여 배치되는 곳의 차이를 보여줍니다.

![Load balancing은 endpoint에 파견하기 전에 마지막 과정입니다.](~/assets/images/reference-architecture/load-balancing-reference-architecture-images/lb-ref-arch-19.svg "Figure 19: Differences in the Layer 7 paths between load balancer and endpoint")

endpoint의 유형이 endpoint 풀의 일부로 정의 될 때 로드밸런서 관점에서 매우 몇 가지 차이가 있습니다. 트래픽 및 엔드포인트 스티어링 정책 및 로드밸런서 규칙이 적용되면 Cloudflare 로드밸런싱 서비스는 들어오는 요청이나 연결을 전달하는 L7 스택을 지시합니다. 이 요청은 endpoint에 직접 전송됩니다. 끝점에 연결의 유형에 따라 다른 경로가있을 수 있습니다. Argo Smart Routing 또는 Tunnel-connected endpoints와 같은 특징은 다른 Cloudflare 데이터 센터에 종결되어 Cloudflare 가장자리에서 요청을 전송하는 것보다 트래픽을 가로 질러 내립니다. 그러나 경로에 관계없이로드 밸런싱은 스택에서 마지막 프로세스이며 트래픽이 추가 처리를받지 못한다는 것을 의미합니다. 따라서 endpoint에 연결이 Cloudflare에서 endpoint에 경로를 변경할 수 있지만, 처리 또는 처리는 endpoint가 선택되면 변경하지 않습니다.

##### Cloudflare 갱도

모델 번호: Cloudflare 터널은 조직이 방화벽 구성을 단순화하고 복잡성을 줄이고 보안을 강화하고 Cloudflare 네트워크에 자산을 쉽게 결합 할 수있는 아웃 바운드 연결입니다. 이 터널을 생성하는 실행은 구름이라고 불립니다 그리고 이 문서에서 참고 자료d 일 수 있고 따르는 도표.

Cloudflare Tunnel (cloudflared)는 엔드포인트 또는 엔드포인트에 IP 연결이 가능한 서버에서 직접 설치할 수 있습니다. 그리고 Cloudflare에 연결이 Cloudflare 갱도가 Cloudflare에 설치되었기 때문에, 필요로 하는 유일한 접근은 Cloudflare에 outbound 접근입니다. 단일 Cloudflare 터널은 두 가지 다른 방법 중 하나에 하나 또는 많은 다른 엔드 포인트에 트래픽을 수송 할 수 있습니다, endpoint에 결과가 완전히 개인적으로 접근 할 수있는 엔드 포인트를 유지하고 하나.

모델 번호: Cloudflare 터널은 Cloudflare에 연결해야하는 엔드포인트 또는 엔드포인트에 레이어 3 (IP) 연결과 함께 엔드포인트 자체 또는 어떤 서버에서 설치할 수 있습니다. 별도의 Cloudflared에 대한 결정은 endpoint(s)을 격리하고 네트워크 수준의 연결성 및 엔드포인트를 관리하거나 서버가 분리 된 역할 또는 책임이있는 건축 단순성을위한 분리 된 팀의 성능을 보장하기 위해 제한된 여러 가지 이유를 위해 만들 수 있습니다.

![다중 엔드포인트에 대한 단일 클라우드 인스턴스 터널 트래픽](~/assets/images/reference-architecture/load-balancing-reference-architecture-images/lb-ref-arch-20.svg "Figure 20: A shared cloudflared deployed on a separate server tunnels traffic for multiple endpoints")

단일 클라우드 인스턴스는 4 개의 다른 터널, 두 개의 다른 Cloudflare 데이터 센터에 두 개의 터널을 만들 것입니다. 이 모델은 높은 가용성을 보장하고 개별 연결 실패의 위험을 감소시킵니다. 단일 연결, 서버 또는 데이터 센터가 오프라인으로 진행되는 경우 엔드포인트는 사용할 수 있습니다. 모델 번호: Cloudflare 터널은 또한 조직이 Cloudflared의 추가 인스턴스를 배포 할 수 있도록, 가용성과 실패 시나리오에 대한. 이 독특한 인스턴스는 복제를 호출합니다. 각 복제는 끝점(s)에 대한 추가적인 포인트로 봉사하는 4개의 새로운 연결을 설치합니다. 복제의 각각은 동일한 터널로 점합니다. 이것은 네트워크가 클라우드를 실행하는 단일 호스트에서 남아 있다는 것을 보장합니다. 디자인에 의하여, 복제는 교통 조타 (random, hash, 또는 둥근 robin)의 어떤 수준을 제안하지 않습니다.

###### 공유 hostname

공개 엔드포인트 방식에서는 조직이 엔드포인트에서 실행 중인 특정 서비스나 포트를 가리키는 터널을 정의할 수 있습니다. 터널은 엔드포인트 자체나, 엔드포인트에 IP 연결이 가능한 서버에서 종료될 수 있습니다. 이 공개 hostname 방식을 사용하려면 터널을 통해 접근할 각 서비스를 터널 구성에 정의해야 합니다. 구성되면 `d74b3a46-f3a3-4596-9049-da7e72c876f5`와 같은 고유한 터널 ID가 생성되고, 이 터널 ID는 Cloudflare 소유 도메인인 `cfargotunnel.com` 아래의 고유한 공개 hostname으로 만들어집니다. 그 결과 해당 서비스로 직접 연결되는 DNS A 레코드가 생성됩니다. 예를 들어 `d74b3a46-f3a3-4596-9049-da7e72c876f5.cfargotunnel.com` 같은 형태입니다. 이 hostname은 공개되어 있지만, 해당 Cloudflare Tunnel 구성을 소유한 계정을 통해 전달되는 트래픽만 사용할 수 있습니다. 다른 계정은 이 DNS 주소로 직접 접근하거나 트래픽을 보낼 수 없습니다. 또한 `cfargotunnel.com` hostname을 소유한 계정 외부에서 만든 DNS CNAME 레코드로는 해당 Cloudflare Tunnel을 통해 트래픽을 보낼 수 없습니다.

대시보드를 통해 구성될 때, Cloudflare는 cfargotunnel.com hostname을 뜻하는 DNS 영역에서 CNAME 레코드를 자동으로 생성합니다. 예를 들어, myTunnelService.example.com의 CNAME 레코드는 d74b3a46-f3a3-4596-9049-da7e72c876f5.cfargotunnel.com의 레코드를 점하기 위해 만들 수 있습니다. CNAME 레코드로 사용 및 관리의 용이가 목적에 대해 훨씬 더 제안되고 고객 DNS 영역에 속합니다.

또 다른 옵션은 호스트 실행 클라우드에 이러한 터널 및 서비스를 만드는 것입니다. 이것은 호출[로컬 관리 터널](/cloudflare-one/networks/connectors/cloudflare-tunnel/do-more-with-tunnels/local-management/). 로컬 관리 터널과 작업할 때, CNAME 입력은 자동으로 생성되지 않습니다. 그러나 조직은 터널 및 서비스가 정의된 후이 수동으로 구성해야 합니다.

로드 밸런서 관점에서 이러한 터널을 엔드포인트로 어떻게 사용할 수 있는지 이해하는 것은 매우 중요합니다. 엔드포인트는 `cfargotunnel.com` hostname을 사용해서만 정의할 수 있습니다. `cfargotunnel.com` 주소를 가리키는 공개 CNAME 레코드를 사용하면 제대로 동작하지 않으며 지원되지도 않습니다. 이는 특히 포트 80 또는 443에서 동작하지 않는 엔드포인트 서비스에서 중요합니다. Cloudflare Load Balancer는 기본적으로 엔드포인트에서 실행 중인 서비스에 접근할 때 이 두 포트를 사용합니다. 조직에 다른 포트에서 실행되는 서비스가 있다면, 해당 포트에 도달할 수 있도록 [catch-all rule](/cloudflare-one/networks/connectors/cloudflare-tunnel/do-more-with-tunnels/local-management/configuration-file/#how-traffic-is-matched)이 포함된 Cloudflare Tunnel을 구성해야 합니다. 이렇게 하면 Cloudflare Tunnel이 엔드포인트의 원하는 포트로 연결을 프록시하는 동안, Cloudflare Load Balancer는 포트 443을 통해 그 서비스에 접근할 수 있습니다.

###### 개인 IP

두 번째 방법은 개인 서브넷입니다. 이 방법은 조직이 개인 IP 주소와 Cloudflare 글로벌 네트워크 내에서 개인 가상 네트워크를 만들 수있는 서브넷 마스크를 정의 할 수 있습니다. Zero Trust 정책을 통해 액세스 할 수있는 조직 내에서 개인 서브넷 방법을 허용하지 않습니다.

이 서브넷은 Cloudflare 내부의 가상 네트워크에 추가하여 사용자가 액세스 할 수있는 방법을 제어 할 수 있습니다. 이 서브넷은 32비트 마스크(단일 IP 주소, i.e., 10.0.0.1/32)를 사용하여 원하는 서브넷 또는 라우팅을 정의할 수 있습니다. 허용되는 서브넷은 클라우드화 프로세스를 실행하는 호스트에 존재하지 않습니다. 필요한 모든 계층 3 또는 IP 연결 호스트 실행 클라우드와 Cloudflare 터널에 도달 할 수 있는 서브넷 사이입니다.

##### 이름 \*

개별 엔드포인트는 엔드포인트 풀 내에서 정의되며, 엔드포인트 풀은 풀당 하나 이상의 엔드포인트를 허용한다.

- 더 보기*endpoint 이름*주로 참고 자료, 보고, 분석에 사용됩니다; 그것은 짐 밸런서 또는 엔드포인트 풀의 기능에 영향을 미치지 않습니다.
- 더 보기*endpoint 주소*, 그러나, load balancer가 요청 또는 연결을 처리하는 데 사용할 수있는 리소스를 정의합니다.
  - 엔드포인트 풀 내의 엔드포인트는 포트 80 또는 443에 접근해야 합니다. 엔드포인트가 포트 80 또는 443에 듣지 않는 경우 프록시 서비스 또는 네트워크 포트 포워딩 장치가 엔드포인트 앞의 포트 80 또는 443 포트에 배치되어야합니다. 이는 서비스가 실제로 듣는 포트입니다.
  - endpoints의 매핑 포트에 대한 또 다른 방법 80 또는 443은 엔드포인트 서비스에 연결[Cloudflare 갱도](#cloudflare-tunnel), 그리고 그 프로세스를 통해 만든 hostname을 endpoint 주소로 사용합니다. 이것은 443 포트에 의도 된 엔드 포인트 포트를 자동으로지도합니다.

*Endpoint 주소*다음과 같은 방법으로 정의 할 수 있습니다 :

- 공공 IP 주소
- Cloudflare-proxied 공개적으로 도달 가능한 hostname
- 공개적으로 눈에 띄는 non-Cloudflare hostname
- 개인, 비공개 가상 네트워크의 선택과 routable IP 주소

##### Host 헤더 수정

Endpoint Pools는 endpoint에 요청을 파견하기 전에 호스트 헤더를 수정할 수 있습니다. 이 구성은 HTTP(S) 레이어 7 로드밸런서에만 적용됩니다 (개인 IP 및 스펙트럼을 포함한 레이어 4 로드밸런서와 함께 사용할 때 무시됩니다).

요청이 HTTP (S) 기반 인 레이어 7 로드 밸런서 내에서 Host header는 단일 엔드 포인트로 요청되는 엔드포인트를 말합니다. 여러 웹 도메인을 호스팅 할 수 있습니다. 엔드포인트가 웹 도메인을 호스트하도록 특별히 구성되면, 해당 호스트 헤더 (i.e., 호스트 헤더)에 요청된 리소스를 호스팅하지 않는 경우 리소스에 대한 요청으로 실패 응답을 전달할 수 없습니다.

- 사용자가 도달하려고`www.example.com`. load balancer는 hostname로 구성될 것입니다`www.example.com`모든 요청을 수신합니다.

##### 짐 헛간

[짐 헛간](/load-balancing/additional-options/load-shedding/)- 관리자가 풀에서 엔드포인트에 대해 보호하는 실시간 응답[건강하다](/load-balancing/understand-basics/health-details/)— 또한 endpoint 풀에 구성.

Load shedding 설정은 관리자가 건강하게하지 않고 endpoint 풀을 적극적으로 보호하려고하지 않는 한 활성화되지 않습니다. 그것은 활성화, 예를 들어, 여전히 요청에 응답하는 엔드 포인트가 증가 된 CPU 또는 메모리 사용, 증가 된 응답 시간, 또는 때때로 모든 응답 실패.

endpoint 풀의 건강이 degrade로 시작될 때, 짐 shedding는 1개의 endpoint 수영장에서 다른 것에 기존하는 짐의 일부를 직접 도울 수 있습니다.

엔드포인트 풀의 건강에 따라, 단순히 헛간 또는 새로운 요청을 리디렉션하고 엔드포인트 풀에서 연결하기에 충분할 수 있습니다. 이 정책은 트래픽에 적용되며, 이러한 새로운 연결은 아직 선택된 엔드포인트 풀 또는 엔드포인트가 없었기 때문에 세션 친화 규칙에 적용되지 않습니다 (그리고, 따라서 최종 사용자 경험에 잠재적으로 영향을 미치지 않습니다).

로드로 인해 endpoint 풀 접근이 중요하지 않은 오류가 발생하면 다음 옵션이 추가 세션 친화 트래픽을 흘러 내릴 수 있습니다. 세션 친화도를 통해 엔드포인트 풀에 바인딩된 요청과 연결을 리디렉션하기 시작합니다. 그러나이 프로세스가 궁극적으로 사용자의 엔드포인트를 변경할 수 있기 때문에 최종 사용자의 경험에 영향을 미칠 수 있습니다. 궁극적으로, 영향은 균형 잡힌 응용 프로그램에 의해 결정되며, 얼마나 많은 연결 컨텍스트가 endpoints 사이에서 공유됩니다.

##### 층 7 HTTP (S) 로드 균형

첫째, 가장 일반적인 모델은**HTTP (S) 기반 층 7 proxied 로드 밸런서**. 이 짐 밸런서는 Cloudflare의 가장자리에 존재하고 대중적으로 도달 가능합니다. 다른 기능 중, 이 모델 지원[웹소켓](/network/websockets/)클라이언트와 엔드포인트 사이의 연결을 열고 두 사이에 데이터를 전달할 수 있습니다.

이 동일한 층 7 안전 더미는 또한 WAF의 디도스 보호, Bot 관리, Zero Trust를 제공하고, 이 공중 짐 밸런서를 접근하는 다른 서비스는 필요에 따라 정정되고 허가한 사용자에게 제한될 수 있습니다. (필수)[공급 능력](#protecting-and-securing-load-balancers)더 많은 정보를 위해.)

이 층 7 더미에서는, 짐 밸런싱은 조직의 공중 직면 웹 자산의 성과, 신뢰성 및 도달성을 더 개량할 수 있습니다. 이 로드밸런서의 엔드포인트는 공공 클라우드, 개인 클라우드, 온프레미스 또는 동일한 로드밸런서 내에서 이러한 모든 조합에 배포될 수 있습니다. (필수)[연결 엔드 포인트 Cloudflare](#connecting-endpoints-to-cloudflare)endpoints를 Cloudflare의 가장자리 네트워크에 연결하는 방법에 대한 자세한 내용은.

![계층 7 로드 균형 요청 흐름 두 가지 유형의 엔드 포인트](~/assets/images/reference-architecture/load-balancing-reference-architecture-images/lb-ref-arch-23-ALT.svg "Figure 23: How Cloudflare’s Layer 7 load balancers can steer traffic to both public and private endpoints")

위의 그림 23에서 설명 된대로 레이어 7 스택의 로드 밸런싱 구성 요소는 최종 지점을 향해 이동으로 요청에서 마지막 프로세스 실행입니다. 이것은 성과 증가에 큰 긍정적인 충격이 있고 endpoints에 짐을 감소시킬 수 있습니다.

예를 들어, 캐싱은 엔드포인트에 도달하고 로드밸런서에 참여하지 않고 응답 할 수 있습니다. 또한 WAF, DDoS 보호 및 Bot 관리는 합법적인 트래픽을 위해 더 많은 용량을 떠나는 공격 트래픽 altogether를 제거 할 수 있습니다.

요청이 로드밸런서 프로세스에 도달하면, 요청은 항상 선택한 엔드포인트에 직접 전송됩니다. 이것은 끝점이 Cloudflare를 통해 proxied 경우에 조차, 요구는 endpoint에 직접 보내지고 더 가공하지 않습니다.

load balancer가 endpoint를 선택한 후 맞춤형 처리를 위해 load balancer의 Custom Rules가 적용됩니다. (이것은 세부 사항에서 덮여있다.[로드밸런서](#load-balancers)아래에 단면도).

**Layer 7 HTTP(S) 로드밸런서에 대한 중요 노트:**

- Layer 7 HTTP(S) 로드밸런서 모두 공개 및 개인 엔드포인트 지원
- Layer 7 HTTP(S) 로드밸런서는 HTTP(S) 및 WebSocket 트래픽만 지원합니다.
- Zero 신뢰 정책은 Layer 7 HTTP(S) 로드밸런서에 적용할 수 있습니다.

##### DNS 전용 로드 밸런싱

Cloudflare의 DNS 유일한 짐 밸런서는 unproxied 짐 밸런서입니다. 이것은 자원을위한 초기 DNS 요청 만 의미 - 실제 트래픽이 아닙니다 - Cloudflare 가장자리를 통과합니다. 따라서, Cloudflare IP에 해결하는 DNS 요청 대신에 그림 7, Cloudflare에서 이전에 본 것과 같이 층 7 더미를 통해서 움직이는 것은 DNS 전용 짐 밸런서를 위한 DNS 요구를, 적용합니다 모든 적합한 짐 밸런싱 정책을, 그 후에 직접 도달하기 위하여 요구한 클라이언트에 IP 주소를 돌려보냅니다.

클라이언트와 엔드포인트 사이의 모든 트래픽은 Cloudflare의 레이어 7 스택을 통해 두 개간에 직접 이동할 수 있기 때문에, IP 트래픽의 모든 유형은 DNS 전용 로드 밸런서에 의해 지원될 수 있습니다.

![오렌지 클라우드 아이콘은 proxied Layer 7 Cloudflare Load Balancer를 나타냅니다.](~/assets/images/reference-architecture/load-balancing-reference-architecture-images/lb-ref-arch-24.png "Figure 24: A proxied load balancer configuration")

![회색 클라우드 아이콘은 unproxied (DNS-only) 로드밸런서를 나타냅니다.](~/assets/images/reference-architecture/load-balancing-reference-architecture-images/lb-ref-arch-25.png "Figure 25: An unproxied (DNS-only) load balancer configuration")

심지어 Cloudflare는 이러한 유형의 로드밸런서 연결을 프록시하지 않습니다, 건강 모니터 서비스는 여전히 풀의 모든 엔드포인트에 건강 모니터링. 엔드포인트의 건강 또는 가용성을 기반으로 Cloudflare DNS 전용 로드 밸런서는 DNS 응답에 적용 가능한 엔드포인트를 추가하거나 제거하여 트래픽이 건강한 엔드포인트로 자극됩니다.

![DNS 전용 로드밸런서만 Cloudflare를 사용하여 DNS 요청에 응답합니다.](~/assets/images/reference-architecture/load-balancing-reference-architecture-images/lb-ref-arch-26.svg "Figure 26: How Cloudflare’s DNS-only load balancer functions")

DNS 전용 로드밸런서는 트래픽 스티어링을 통해 엔드포인트 풀을 선택한 후, 하나 또는 많은 IP 주소는 DNS 응답으로 돌아올 수 있습니다.

DNS 응답 내에서 하나 또는 많은 IP 주소를 보내는 결정은 선택한 엔드포인트 풀 내에서 엔드포인트에 할당된 무게를 기반으로 합니다.

- 모든 무게가 모든 엔드포인트와 동일하면, 모든 엔드포인트의 모든 IP 주소는 DNS 응답으로 반환됩니다.
- 적어도 하나의 엔드포인트가 엔드포인트 풀 내에서 독특한 무게로 지정되면, 단 하나 IP 주소만 엔드포인트 풀에서 선택한 엔드포인트 스티어링 방법에 관계없이 DNS 응답으로 반환됩니다.

이 조직은 모든 엔드포인트를 인식하고 로컬 실패를 수행 할 수있는 응용 프로그램을 허용 할 수있는 유연성을 제공하거나 Cloudflare를 허용하여 응용 프로그램에 대한 단일 IP를 제공합니다.

Figure 27는 엔드포인트 풀 내에서 정의된 무게가 DNS 전용 로드밸런서가 어떻게 반응할 수 있는지 보여줍니다.

![DNS 전용 로드 밸런서는 DNS 요청에 응답할 수 있습니다 하나 또는 많은 IP 주소](~/assets/images/reference-architecture/load-balancing-reference-architecture-images/lb-ref-arch-27.svg "Figure 27: How weight affects the DNS response from a DNS-only load balancer")

DNS 전용 로드 밸런서에는 몇 가지 제한이 있습니다.

- load balancer no longer hides the endpoint’s IP address from the client as it is sent back to the client directly.
- 그들은 이전 모델에 언급 된 내장 층 7 스택 서비스가 없습니다. 즉, DNS 전용 로드밸런서는 캐싱, WAF, DDoS 보호 또는 Zero Trust 지원을 포함하지 않습니다.
- 세션 친화는 제한됩니다.`ip_cookie`, endpoint deterministically를 선택 하 고 다음 모든 후속 요청에 대 한 클라이언트 IP 주소에 종료 지도.
- 마지막으로, 연결은 DNS를 위한 로드밸런서를 통해서 proxied 때문에, 특정 스티어링 방법은 작동하지 않을 것입니다. 예를 들어,[계정 만들기](#least-outstanding-requests-steering-lors)Cloudflare가 엔드 포인트에 연결의 인식이되지 않기 때문에 작동하지 않을 것입니다. 이 스티어링 방법은 무작위로 무게를 달아 줄 것입니다.

추가 스티어링 방법에 대한 자세한 내용은 참조하시기 바랍니다[제품 정보](#steering)이름 \*

DNS 전용 로드밸런서를 사용할 때 클라이언트 및 해결자 DNS 캐시 고려 사항이 있습니다. 캐시 수명은 DNS 서버가 요청을 응답하여 결정됩니다. 더 보기[(TTL)에 시간](https://www.cloudflare.com/learning/cdn/glossary/time-to-live-ttl/)값은 DNS 요청자가 얼마나 긴 응답이 클라이언트가 새로운 DNS 요청을 보내면 대상이 변경되었는지 확인할 수 있습니다. TTL은 초로 계산됩니다. 예를 들어, TTL 값은 1 시간의 TTL 값입니다. 그러나 표준 DNS TTL 값은 일반적으로 12 또는 24 시간 또는 43200 및 86400입니다.

DNS 전용 로드밸런서의 TTL은 30(초)로 설정됩니다. 이것은 endpoint 건강 변화 또는 endpoints가 추가되거나 삭제되는 것을 보증합니다. DNS 전용 로드 밸런서는 가능한 가장 정확한 목록을 제공하기 위해 더 자주 정복됩니다.

**DNS 전용 로드밸런서에 대한 중요한 노트:**

- DNS 전용 로드밸런서만 공개 엔드포인트 지원
- DNS 전용 로드 밸런서는 프록시 트래픽이 아닙니다. — 같은 것과 같이, endpoint에 연결되지 않습니다.
- DNS 전용 로드밸런서만 IP 주소 또는 IP 주소 설정으로 DNS 요청에 응답

##### Spectrum Load 밸런싱

Cloudflare는 또한 다른 진입 방법을 통해 제안합니다[스펙트럼](/spectrum/)제품.

레이어 7 스택만 지원된 HTTP(S) 및 WebSockets, Spectrum은 TCP- 또는 UDP 기반 프로토콜에 대한 지원을 제공합니다. Spectrum을 사용하여 Cloudflare Load Balancer는 TCP 및 UDP 프로토콜이 존재하는 레이어 4에서 트래픽의 진입으로 작동합니다. 수송을 위한 TCP 또는 UDP를 이용하는 어떤 서비스는 SSH, FTP, NTP, SMTP 및 더 많은 것을 포함하여 Cloudflare 짐 밸런서도 스펙트럼을 활용할 수 있습니다.

서비스 및 프로토콜의 폭을 줄이면, 제공되는 치료는 층 7 HTTP (S) 스택과 함께 제공되는 것보다 더 일반화됩니다. 예를 들면, Cloudflare Spectrum은 TLS/SSL offloading, DDoS 보호, IP 액세스 목록, Argo Smart Routing 및 세션 persistence와 같은 기능을 지원합니다.

![Spectrum 기반 로드 밸런싱은 공공 엔드포인트를 지원합니다.](~/assets/images/reference-architecture/load-balancing-reference-architecture-images/lb-ref-arch-28-ALT.svg "Figure 28: Spectrum Layer 4 load balancers support both TCP and UDP protocols")

Cloudflare 층 4 스펙트럼 짐 밸런서는 공개적으로 접근 가능합니다. 이 로드 밸런싱 리소스에 액세스하면 Spectrum 구성을 사용하여 관리 할 수 있습니다.*IP 접근 규칙,*&#x57;AF 구성의 일부로 정의 할 수 있지만 특정 IP 주소, 하위넷, 국가, 또는 특정 IP 주소에 대한 "allow"또는 "block"작성 규칙에 제한됩니다[국경 게이트웨이 프로토콜 (BGP)](https://www.cloudflare.com/learning/security/glossary/what-is-bgp/)자율 시스템 번호 (ASN).

대중적이기 위하여는, 스펙트럼 짐 밸런서는 항상 proxied. 이전에 표시된 프록시 설정(Figures 24 및 25)은 Spectrum이 로드밸런서의 진입 경로로 구성될 때 무시됩니다. 스펙트럼 근거한 짐 밸런서를 위한 모든 교통은 항상 Cloudflare 가장자리를 통과할 것입니다.

**Spectrum Load Balancers에 대한 중요한 노트:**

- Spectrum Load Balancers는 공공 및 민간 엔드포인트 모두 지원
- Spectrum Load Balancers는 레이어 7 HTTP(S) 로드밸런서로 처음 생성됩니다. Spectrum Application은 Load Balancer endpoint type으로 만들어졌으며 이미 생성된 Load Balancer가 선택되었습니다.
- Spectrum load balancers는 항상 load balancer 구성에 프록시 설정과 상관없이
- 종점에 스펙트럼을 통해 인터넷에서 진입 포트를 변경할 수있는 능력이 없습니다. 즉, 트래픽이 포트 22에서 스펙트럼에 들어있는 경우 엔드포인트에 22 포트에 스티어링됩니다.
- Spectrum Load Balancers는 해시 엔드포인트 스티어링 방법을 사용하여 세션 친화성만 지원합니다.
- Spectrum Load Balancers는 사용자 정의 규칙을 지원하지 않습니다.

##### 세션 친화

세션 친화도, 세션 지속 또는 끈적한 세션으로도 알려진 세션은 첫 번째 요청 또는 연결 후 모든 후속 요청에 대해 동일한 엔드포인트에 연결되는 클라이언트를 유지합니다. 이것은 세션 데이터를 공유하지 않는 응용 프로그램에 대한 중요한 기능일 수 있습니다. — endpoints 사이 웹 애플리케이션과 사용자의 상호 작용의 맥락. 예를 들어, 새로운 엔드포인트가 클라이언트 세션의 중간에 선택되고 세션에 대한 정보 (예를 들어 사용자의 쇼핑 카트의 내용) 손실 된 경우, 해당 응용 프로그램에 대한 사용자 경험은 가난한 것.

Cloudflare는 세션 친화성을 가능하게하기위한 세 가지 방법을 제공합니다.

1. **Cloudflare 쿠키에 의해 (cookie):**&#x70;roxied load balancer에 대한 첫 번째 요청에, 쿠키가 생성되고, 요청을 종료하는 인코딩 정보는 전달됩니다. 특정 요청 (같은 클라이언트가 동일한 로드밸런서에 의해)는 최종점이 건강하게 남아있는대로 쿠키 및 b)의 지속 시간이 쿠키 및 b)의 지속되는 최종점에 전송됩니다. 쿠키가 만료되거나 종료된 경우 새로운 엔드포인트가 계산되고 사용됩니다.
2. **Cloudflare 쿠키 및 클라이언트 IP 삭제 (ip cookie)에 의하여:**&#xC774; 쿠키는 위와 유사하며, 쿠키는 클라이언트 IP 주소를 기반으로 생성됩니다. 이 경우, 같은 IP 주소에서 요청은 항상 같은 엔드포인트를 향해 스티어링됩니다) 최종점이 건강하게 남아있는대로 쿠키 및 b의 지속 시간이 지남에 따라. 쿠키가 만료되거나 종료된 경우 새로운 엔드포인트가 계산되고 사용됩니다.
3. **HTTP 헤더에 의해 (헤더):**&#x70;roxied load balancer에 대한 첫 번째 요청에서 세션 키는 구성 된 HTTP 헤더를 기반으로 생성됩니다. 같은 헤더를 가진 로드밸런서에 대한 간접적 요청은 같은 엔드포인트로 전송됩니다. 세션이 세션의 지속 시간 (TTL) 초 또는 엔드 포인트가 건강하지 않다면 새로운 엔드 포인트가 계산되고 사용됩니다.

이 세 세션 친화 옵션은 레이어 7 HTTP (S) 로드 밸런서에만 적용됩니다. Session affinity는 TTL을 필요로 하며, 긴 로드밸런서가 특정 엔드포인트에 대한 후속 요청을 경로를 결정합니다. 기본 TTL은 82,800 초 (23 시간)이지만 1,800 초 (30 분)에서 604,800 초까지 설정할 수 있습니다.

쿠키 기반 세션 친화, 만료 타이머는 결코 재설정되지 않습니다, 타이머는 세션의 시작에서 계산하는 의미 - idle 또는 활성 세션에 관계없이. HTTP 헤더 기반 세션 친화는 매번 만료 타이머를 재설정합니다.

##### Endpoint 배수

Endpoint 배수는 세션 친화의 subfeature입니다. 새로운 세션이 동일한 엔드포인트에 생성되지 않는 동안, 새로운 세션을 허용하지 않는 동안 세션을 완전히 종료할 수 있습니다. Endpoint draining은 유지 보수에 유용합니다. 관리자가 arbitrarily 또는 abruptly가 엔드포인트에서 모든 활성 세션을 제거하기 위해 사용자 세션을 차단할 필요가 없습니다.

endpoint drain TTL은 endpoints가 강제적으로 종료되기 전에 활성 세션을 유지하도록 허용되는 시간의 양입니다. endpoint drain TTL이 설정되면 endpoint draining은 endpoint Pool 내의 endpoint (또는 Multiple endpoints)를 비활성화하여 시작됩니다. 아래 이미지에서 볼 때 관리자는 load balancer UI에서 endpoint 도면 작업에 남아있는 시간을 모니터링 할 수 있습니다.

![웹 사용자 인터페이스에서 프로세스에서 Endpoint 배수](~/assets/images/reference-architecture/load-balancing-reference-architecture-images/lb-ref-arch-30.png "Figure 30: Endpoint draining occurring within a Cloudflare Load Balancer")

Endpoint draining은 세션 affinity 없이 세션 affinity에만 적용되며, 이후 요청 또는 연결은 동일한 엔드포인트로 스티어링할 수 없습니다. 따라서, endpoint를 비활성화하는 것은 사용자 경험에 영향을 미치지 않습니다.

##### Zero-downtime 장애

Zero-downtime failedover는 일시적인 네트워크 문제 중 엔드포인트 풀 내의 트래픽을 자동으로 전송합니다.<Render file="zero-downtime-failover-retry-on-error" product="fundamentals" />이 응답 코드는 endpoint에서 반환되지 않습니다, 하지만 요청에서 upstream Cloudflare 서비스에 의해 조직의 endpoints.

Zero-downtime 장애는 가동의 3개의 형태가 있습니다:

1. **없음 (오프):**&#xC2E4;패가 발생하지 않으며 사용자는 오류 메시지 또는 가난한 사용자 경험을받을 수 있습니다.
2. **일시:**&#xD2B8;래픽은 endpointal endpoint가 다시 사용할 때까지 다른 endpoint(s)로 전송됩니다.
3. **끈끈한:**&#xC138;션 친화 쿠키는 업데이트되고 이후 요청이 필요한 새로운 엔드포인트로 전송됩니다. session affinity가 HTTP 헤더 모드를 사용할 때 지원되지 않습니다.

## 제품정보

Cloudflare 글로벌 anycast 네트워크는 부하 균형을위한 강력한 플랫폼입니다. Cloudflare에 있는 짐 균형을 잡는 윤곽은 안으로 접근 가능합니다<PublicStats id="data_center_cities" />전 세계는 거의 무제한 용량과 대역폭을 가지고 있습니다.

이 로드밸런서는 Cloudflare Load Balancers를 사용하여 GTM 및 Private Network Load Balancing을 수행 할 수있는 엔드포인트를 포함하여 인터넷 연결 인구의 약 95 %의 약 50ms 내에서 작동합니다. Cloudflare는 이제 두 가지 명백한 부하 균형 개념을 단일 부하 균형으로 결합합니다. 이것은 조직이 지리적으로 관련 데이터 센터에 스티어 트래픽을 활성화 할 수 있도록 다음 요청을 처리하기 위해 적절한 엔드포인트를 선택하십시오.

Cloudflare로 터널, 엔드 포인트는 개인 네트워크 내에서 찾을 수 있으며 여전히 Cloudflare 로드 밸런스러에 의해 사용됩니다. Cloudflare는 공공 레이어 7 로드밸런서를 제공합니다. HTTP (S) 및 WebSockets뿐만 아니라 TCP 또는 UDP 트래픽을 제거 할 수있는 공공 레이어 4 로드밸런서를 지원합니다. 즉, Cloudflare는 모든 조직 및 사용자에 부하 밸런싱 서비스를 제공 할 수 있음을 의미합니다. 위치, 사용 사례 또는 기존 구성에 상관없이.
