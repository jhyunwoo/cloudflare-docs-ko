## 제품정보

시간이 지남에 따라 급속하게 진화 애플리케이션 보안 및 성능 산업, 회사는 여러 공급 업체를 배포하기 위해 왔습니다 서비스를 제공합니다. 때때로 고객은 규제 / 회사 규정 준수, 탄력성, 성능, 또는 비용의 이유에 대한 여러 공급 업체를 사용하고 있습니다.

몇몇 고객은 이 문서에서 토론된 각종 이유를 위한 다vendor 해결책을 실행하는 것을 봅니다, 다vendor 배치는 다수 대시보드s 및 윤곽 및 가파른 학습 곡선 때문에 추가 복잡성, 더 높은 가동 비용을 소개할 수 있습니다. 또한, 여러 공급 업체에서 지원되는 기능의 기본을 설정하려고하는 동안 고객은 공급 업체의 최신 기능 / 혁신을 활용하지 않고 최소한의 일반적인 디노미네이터 설정이 끝날 수 있습니다. 고객은 목표와 요구 사항을 신중하게 고려해야하며, 모든 이해 관계자와 무게를 다벤더 배포로 진행하기 전에.

이 문서는 몇몇 고객이 다수 이중 납품업자 접근을 배치하고 Cloudflare가 그런 해결책으로 통합될 수 있는 이유를 시험합니다. 특히, 이 문서는 애플리케이션 보안 및 성능에 대한 멀티벤더 접근 방법을 설명합니다. 이 문서는 건축가 및 보안 및 성능에 대한 멀티 벤더 클라우드 기반 솔루션을 사용하여 관심있는 사람들을 대상으로합니다.

## 클라우드 기반 보안 및 성능 제공 업체

멀티 벤더 보안 및 성능 솔루션에 대해 논의하기 전에 클라우드 기반 솔루션이 일반 및 트래픽이 그들을 통해 어떻게 전달되는지 알아내는 것이 중요합니다.

Cloudflare와 같은 클라우드 기반 보안 및 성능 제공 업체는 역 프록시로 작동합니다. 역 프록시는 웹 서버 앞에 앉아서 클라이언트 요청을 전달하는 서버입니다. 역 프록시는 일반적으로 보안, 성능 및 신뢰성을 높일 수 있도록 합니다.

![Figure 1: 서버의 클라이언트 요청](~/assets/images/reference-architecture/multi-vendor-architecture-images/Figure_1.png "Figure 1")

정상적인 트래픽은 역 프록시없이 클라이언트가 DNS 조회 요청을 전송하고, 원래 IP 주소를 수신하고, 원래 서버 (s)에 직접 communicating. 이것은 그림 1에서 시각화됩니다.

역 프록시가 도입되면 클라이언트는 여전히 DNS 조회에 DNS 조회 요청을 보냅니다. 이는 DNS 조회의 첫 번째 중지입니다. 이 경우, DNS 해결자는 클라이언트와 클라이언트에 납품업자의 역 프록시 IP 주소를 반환하고 그 후에 공급자의 역 프록시에 요청을 만듭니다. 클라우드 기반 프록시 솔루션은 이제 추가 보안, 성능 및 신뢰성 서비스를 제공 할 수 있습니다.[사이트맵](https://www.cloudflare.com/cdn/), [모델 번호: WAF](https://www.cloudflare.com/waf/), [DDoS 공격](https://www.cloudflare.com/ddos/), [모델 번호: API Shield](https://www.cloudflare.com/products/api-shield/), [Bot 관리](https://www.cloudflare.com/products/bot-management/)보안 정책에 따라 결정하기 전에 기능 등, 클라이언트 요청을 각각의 Origin 서버(s)로 전달하는지 여부. 이것은 그림 2.에서 시각화됩니다.

일부 경우에, 역 프록시를 제공하는 공급 업체는 DNS 서비스를 제공합니다; 이것은 아래 그림 3에서 시각화됩니다. 이것은 단일 대시보드에서 모든 서비스를 관리하고 운영 단순성을 위해 도움이 될 수 있습니다.

## Cloudflare의 역 프록시 아키텍처 및 솔루션

Cloudflare는 전 세계 프록시 아키텍처를 제공합니다.[anycast 네트워크](https://www.cloudflare.com/learning/cdn/glossary/anycast-network/)각각의 보안, 성능 및 신뢰성 서비스를 제공합니다. Anycast는 수신 요청이 동일한 IP 주소 공간을 광고하는 다양한 위치 또는 'nodes' 광고로 경로를 전달할 수있는 네트워크 주소 및 라우팅 방법입니다. Cloudflare는 anycast와 믿을 수 있는 감사, 뿐 아니라 그것의 세계적인 존재입니다[전세계 수백 도시](https://www.cloudflare.com/network/). Cloudflare는 또한 모든 중요한 ISP, 클라우드 공급자 및 기업을 포함하여 12,000개의 네트워크에, 그리고 세계 인터넷 연결 인구의 95%에서 \~50 ms 내의 직접 연결됩니다.

Cloudflare는 모든 Cloudflare 데이터 센터의 모든 서버에서 모든 서비스가 실행되는 하나의 글로벌 네트워크를 보유하고 있습니다. Cloudflare 네트워크는 anycast를 사용하므로 클라이언트에 가장 가까운 데이터 센터가 요청에 응답합니다. 이로 인해 Cloudflare 네트워크 전반에 트래픽이 더 넓게 분산되어, 지연 시간은 줄어들고 네트워크 복원력, 가용성, 보안은 향상됩니다.

[Cloudflare의 글로벌 anycast 네트워크](https://www.cloudflare.com/network/)뒤에 오는 이점을 제공합니다:

- 수신 트래픽은 요청을 효율적으로 처리 할 수있는 용량으로 가장 가까운 데이터 센터로 이동합니다.
- 가용성과 중복은 inherently 제공됩니다. 여러 노드가 동일한 IP 주소를 광고하기 때문에, 하나의 노드가 실패한 경우, 요청은 가까운 근접에 다른 노드로 전환됩니다.
- anycast는 여러 데이터 센터를 통해 트래픽을 배포하기 때문에 Cloudflare의 네트워크를 통해 트래픽의 전반적인 배포를 증가시키고 요청으로 압도적으로되는 모든 위치를 방지합니다. 이런 이유로, anycast 네트워크는 DDoS 공격에 매우 의존합니다.

![그림 4: Cloudflare는 글로벌 anycast 네트워크를 통해 DNS 및 보안 / 성능 서비스를 제공](~/assets/images/reference-architecture/multi-vendor-architecture-images/Figure_4.png "Figure 4")

## Cloudflare 온보딩 옵션

이 섹션은 Cloudflare 온보드 옵션의 간단한 개요를 제공합니다. 멀티벤더 솔루션에 대한 세부 사항을 찾고 이전에 이해하기 위해 유용합니다. onboarding의 방법은 멀티 벤더 솔루션이 배포 / 구성하는 방법에 대한 차이를 허용합니다. 이미 Cloudflare 내장 옵션에 익숙한 경우 멀티벤더 솔루션에 대해 다음 섹션으로 이동할 수 있습니다.

Cloudflare는 쉽게 내장하고 안전, 성과 및 신뢰성 서비스를 소모하는 다수 선택권을 제공합니다. 프록시 설정을 통해 제공되는 클라우드 솔루션의 장점 중 하나는 온보딩이 용이하며, 이는 주로 프록시를 통해 클라이언트 요청을 경로로 DNS 구성을 포함합니다. 그러나 DNS 구성으로 온보드 내에서도 Cloudflare는 여러 옵션과 유연성을 제공합니다.

핵심 요구 사항은, 트래픽은 Cloudflare를 통해 proxied되어야 합니다; 이것은 또한 Cloudflare를 통해 proxied 때문에 ‘orange-clouded’로 불립니다. 대시보드 내에서 특정 DNS 항목에 대한 상태를 볼 수 있습니다 ‘Proxied’ 그리고 그림 5 아래에 표시된 오렌지 클라우드 아이콘.

![그림 5 : Cloudflare 사이트 프록시 트래픽으로 구성 https://api2.cf-tme.com](~/assets/images/reference-architecture/multi-vendor-architecture-images/Figure_5.png "Figure 5")

Cloudflare를 통해 프록시 트래픽에 대한 몇 가지 방법이 있으며 사용되는 방법은 고객 요구 사항에 따라 달라집니다.

**1. 가득 차있는 DNS 체제 - 1 차적인 DNS 공급자로 Cloudflare**

Cloudflare는 1 차적인 DNS 공급자로 구성되고 기록은 Cloudflare를 통해 프록시 교통에 형성됩니다. 프록시가 DNS 레코드에서 활성화되면 응답은 Cloudflare anycast IP 주소가 Cloudflare 프록시가 될 수 있습니다.

**2. 두 번째 DNS override와 두 번째 DNS 설정**

Cloudflare는 이차 공급자로 구성되고 모든 DNS 기록은 1 차적인 공급자에서 옮겨집니다. Cloudflare는 칭한 특징을 제공합니다[두 번째 DNS override](/dns/zone-setups/zone-transfers/cloudflare-as-secondary/proxy-traffic/)Cloudflare 이차 네임서버에서 제공하는 응답을 보장 할 수 있습니다. 이를 통해 고객은 DNS 제공업체 간의 자동으로 동기화할 수 있는 레버리지 영역을 활용할 수 있습니다. 또한 Cloudflare DNS에서 레코드를 업데이트 할 수있는 유연성을 제공하여 Cloudflare와 같은 다른 서비스 제공 업체에 특정 트래픽을 리디렉션합니다. 이 경우 응답은 Cloudflare anycast IP 주소가 Cloudflare를 프록시로 허용됩니다.

**3. 부분/CNAME 설정**

이 설정에서 Cloudflare는 권위있는 DNS 공급자가 아니며 고객은 외부 DNS 레코드를 관리합니다.

CNAME 설정으로 변환하면 호스트 이름을 결국 Cloudflare IP로 해결합니다. 이것은 고객이 현재 DNS 설정을 변경하고 싶지 않을 때 유용하지만 여전히 다른 Cloudflare 서비스를 사용하고 싶습니다.

고객의 현재 DNS 공급자가 Cloudflare의 [CNAME Flattening](/dns/cname-flattening/)처럼 zone apex(일명 "root domain" 또는 "naked domain")에서 CNAME을 지원하지 않는다면, Cloudflare에서 Static IP를 구매한 뒤 공급자 DNS에 해당 Static IP를 가리키는 A 레코드를 만들어야 합니다. 그리고 Cloudflare에서는 zone apex가 origin을 가리키도록 A 레코드를 생성할 수 있습니다.

Cloudflare 서비스를 사용하는 많은 고객은 관리 및 운영 단순성을위한 단일 UI의 단순성과 함께 크로스 제품 통합 및 혁신을 활용하고 CDN 및 WAF와 같은 여러 Cloudflare 서비스를 사용합니다. 권장하지 않지만 CNAME을 통해 Cloudflare를 통해 DNS를 전달하기 위해 DNS를 설정하여 다른 CDN 제공 업체와 Cloudflare와 같은 보안 서비스를 사용할 수 있으며 캐시 규칙을 통해 Cloudflare 캐싱을 비활성화합니다.

## 왜 멀티벤더인가?

일반적으로 고객은 규제 / 회사 준수, 탄력성, 성능 및 비용의 이유에 대한 멀티 벤더 접근 방식을 선택합니다.

### 규제/회사 준수

일부 고객은 모든 보안, 성능 및 신뢰성 서비스에 대한 단일 공급업체에 의존하지 않는 규제 / 회사 정책을 준수해야 할 수 있습니다. 이 회사는 특정 공급 업체 아웃소싱 / 조직 및 / 또는 증가 된 공급 업체 가격 / 비용에 대한 mitigate에 레버리지를 위해 특정 벤더 아웃소싱 위험의 회사 정책의 이유를 위해 수행 할 수 있습니다. 이 정책에 대한 준수를 위해 멀티 벤더 전략이 필요합니다.

### 책임감

단일 공급 업체가 모든 보안 및 성능 서비스에 사용될 때, 이것은 실패의 단일 지점으로 인식 될 수있다. 이 모든 중요한 체계에 있는 신뢰성을 개량하기 위하여 규제 압력에 의해 몰릴 수 있습니다, 단일 납품업자의 장기 신뢰성을 가진 인큐베이트 납품업자와 경험있는 정전.

### - 연혁

많은 경우 단일 공급 업체는 매우 잘 연결 될 수 있으며 특정 지역 내에서 예상 수준의 성능을 제공하지만 다른 지역에서 더 적은; 이것은 투자, 제한된 자원, 지리적 인 이유 등 여러 가지 이유로 인해 발생할 수 있습니다. 많은 고객은 성능이 중요한 애플리케이션과 미디어에서 속도를 완전히 최적화하고 그 데이터를 기반으로 가장 최적의 공급 업체에 대한 실시간 성능 모니터링과 결합 된 멀티 벤더 접근 방식을 구현함으로써 노력합니다.

### 제품정보

특정 공급 업체의 성능과 마찬가지로 콘텐츠, 일 시간 및 위치에 따라 달라질 수 있으므로 특정 공급 업체를 통해 특정 트래픽을 전송할 수 있습니다. 일반적으로 이러한 이점은 높은 볼륨 미디어 트래픽과 같은 매우 특정 사용 사례에서 멀티 벤더 전략을 구동 볼 수 있습니다, 내장 및 여러 공급 업체를 관리하는 비용으로 일반적으로 특정 틈새 사용 케이스 밖에 monetary 및 리소스 비용을 증가. 또한 멀티 벤더 접근 방식을 채택하면 벤더의 유연성과 협상 능력을 제공하는 단일 공급자와 함께 공급 업체 잠금을 피하는 데 도움이됩니다.

## Multi-vendor 솔루션

모든 멀티 벤더 아키텍처는 여러 구성 요소를 포함 할 것입니다 조직은 비즈니스 및 기술 측면에 모두 구현하기 전에 결정해야합니다. 또한, Cloudflare의 강점과 독특한 차별화자를 맞추기 위해 설정을 최적화하는 데 도움이되는 몇 가지가 있습니다.

기능 설정 및 배달 방법론 최적화. Cloudflare는 우리의 serverless compute 서비스를 통해 쉽게 전달된 관례 특징과 더불어 대부분의 중요한 납품업자를 가진 특징 parity를 제안할 수 있습니다. 납품 방법론을 위해, Cloudflare의 anycast 건축술은 Cloudflare 제안하는 각 서비스를 전달할 수 있다는 것을 각 서버에서 독특합니다, 활동/활동적인 접근을 위한 최선 후보자를 만들기.

레버리지 Cloudflare의 API 및 신속한 배포 기능 가능. Cloudflare는 모든 기능 API를 첫째로 제안하고, 구성은 일반적으로 몇몇 초에서 눈에 보입니다, 이것은 긴 배치 시간을 기다리지 않고 프로그래밍 방식으로 유행에 있는 변화를 시험하고 배치하기 위하여 팀을 위해 쉬운 만듭니다.

"stacked" 접근을 피하십시오. 이것은 다른 납품업자의 뒤에 요구 교류에서 Cloudflare를 두는 것을 피합니다. 우리는 종종 선형 패션의 각 층을 통해 동일한 트래픽을 실행하여 깊이의 방어를 제공 희망으로 공급 업체를 겹쳐 쌓이는 것을 고려합니다. 이론에서이 실행 될 수있는 두 개의 공급업체의 정책에 대해 허용하고, 하나의 공급 업체에 의해 잡지 않는 나쁜 트래픽은 다음으로 잘 잡습니다. 이 설정이 매우 다르면 우리가 연습을 볼 수 있습니다. 주요 단점은 Cloudflare의 위협 인텔리전스가 Bot Management, Rate Limiting, DDoS 완화 및 IP 평판 데이터베이스와 같은 다양한 Cloudflare의 위협 인텔리전스 구동 서비스의 손실입니다. 이것은 또한 트래픽이 두 개의 네트워크를 통과해야하기 때문에 성능 측면에서 매우 초래합니다. 각각 자신의 처리 및 연결 오버 헤드가 원래로 돌아가기 전에. 또한, 작업, 관리 및 지원에 불필요한 복잡성을 만듭니다.

스택 된 접근법에 대한 하나의 주의는 특정 지점 솔루션에 대한 특정 사례로, 특히 봇 관리 솔루션 및 API 게이트웨이와 같은 다른 앞에 하나의 공급 업체 솔루션을 배치 할 수 있습니다, 특히 새로운 공급 업체 / 공급 업체를 향해 마이그레이션 할 때. 이러한 시나리오에서 각 솔루션이 요구 흐름에 떨어지는 것을 이해하는 것이 중요합니다.

Cloudflare 및 많은 공급자는 가용성의 고차를 유지하고 강력한 결함 관대한 건축술은, 몇몇 고객은 의존성과 실패의 각각 단 하나 납품업자 점을 감소시키기 위하여 더 욕망이 있습니다. 이 웹 사이트는 애플 리케이션에 전념. 우리는 정품 앱과 게임을 제공 할 목적으로이 사이트를 만들었습니다. 4AppsApk 최고의 안드로이드 애플 리케이션을위한 무료 APK 파일 다운로드 서비스, 계략. 고객은 DNS 제공 업체, 네트워크 및 소스 연결에 대한 중복을 제거하는 방법을 고려해야합니다. 단일 공급 업체 / 구성 요소 오류 캐스케이드의 위험을 제거하기 위해.

특정 업체는 공급 업체 및 비즈니스 케이스에 따라 다를 수 있지만, 멀티 벤더 배포에 대한 기술적 고려 사항은 세 가지 영역으로 양동이 될 수 있습니다. 논리, 구성 관리 및 기원 연결.

### 로그아웃

멀티 벤더 전략을 찾고있을 때해야 할 첫 번째 및 가능성이 가장 중요한 결정은 각 공급자에게 트래픽을 전달하는 방법입니다. 이것은 사업 논리 둘 다 다 다 국경 전략을 몰고 질문에 있는 각 납품업자의 기술적인 기능에 달려 있습니다. 각 공급자에 교통은 현재 상태에 따라 DNS 및 교대를 이용하고 사업의 필요. Cloudflare는 권위있는 DNS 공급자, 이차 DNS 공급자, 또는 지역을 위한 non-Cloudflare DNS (CNAME) 체제로 윤곽을 지원할 수 있습니다.

![Figure 6: 클라이언트 요청은 멀티벤더 설정에서 Origin 서버(s)로 경로를 지정합니다.](~/assets/images/reference-architecture/multi-vendor-architecture-images/Figure_6.png "Figure 6")

DNS 기반 로드 밸런싱 및 건강 검사는 여기에 레버리지 될 수 있으므로 클라이언트 요청에 도메인/사이트는 건강한 기원 서버(s)에서 배포됩니다. DNS 공급자는 서버와 DNS의 건강 모니터링은 해당 IP와 라운드로빈 접근을 사용하여 클라이언트 요청에 응답합니다.

멀티 벤더 DNS 접근법이 DNS 수준 탄력성에 대해 원하는 경우, 다양한 구성은 다른 공급업체로부터 여러 권위있는 네임서버로 가능합니다. 이 문서의 'Multi-vendor DNS 설정 옵션' 섹션을 참고하여 추가 세부 정보를 제공합니다. 여기에서 키는 여러 공급자의 일관된 구성을 보장합니다. DNS 설정/ 구성에 따라, 이 일관성은 지역 전송과 같은 다른 접근 방식을 사용하여 해결 될 수 있습니다, Terraform 또는 OctoDNS와 같은 도구를 통해 자동화, 스크립트를 통해 모니터링/자동화, 또는 수동 구성.

### 제품 설명

많은 공급 업체가 유사한 최종 사용자 경험을 제공 할 수 있지만, 구성 및 관리는 성공적인 구현의 비용을 구동하는 공급자 사이에서 크게 다를 수 있습니다. 궁극적으로 사업은 각 납품업자의 구성 논리에 익숙해야하며 그 사이에 지도하는 시스템을 개발한다. 가능한 경우, 관리 단순성, 자동화 지원 및 신속한 배포를 최적화하여 비용 및 관리 오버 헤드를 최소화할 수 있는 공급업체를 찾습니다.

모든 공급업체의 제품 기능에 대한 API 지원은 여기에 중요한 것입니다. 일관된 구성을 유지하는 것은 특정 멀티 벤더 DNS 설정에서 라우팅뿐만 아니라 WAF, API 보안 등과 같은 모든 해당 서비스의 일관성을 유지하기위한 것이 중요합니다. 트래픽은 제공 업체 중 하나에 전달 될 수 있습니다. Terraform 또는 custom scripted Automation 도구와 같은 자동화 도구는 이 일관성을 유지하려면 API를 활용합니다.

### 연결성

해야 하는 또 다른 중요한 결정은 각 공급자가 조직에 다시 연결 하는 방법 이다. 이것은 공급업체의 역량과 조직의 기술 및 보안 요구 사항에 크게 의존합니다.

클라이언트는 인터넷을 통해 요청을 만들고 요청은 공급업체의 클라우드에 해당 공급업체의 프록시 서비스에 경로를 지정합니다. 대부분의 기본 시나리오에서 프록시는 인터넷에서 기원으로 트래픽을 우회합니다. 이것은 기본 설정입니다.

고객은 보안 또는 추가 성능 혜택을 원하면 암호화 된 터널과 같은 공급 업체가 제공하는 연결 옵션을 활용하여 고객 데이터 센터에서 직접 Cloudflare 데이터 센터를 통해 Cloudflare 데이터 센터에 연결하여 고객의 장비에서 Cloudflare에 직접 연결할 수 있습니다. Vendors는 인터넷을 통해 가장 빠른 경로를 전달하는 가속된 라우팅 기능을 제공 할 수도 있습니다.

Cloudflare는 스마트 루팅과 함께 모든 연결 옵션을 제공합니다. 이 연결 옵션은 이 문서의 'Cloudflare 연결 옵션' 섹션에서 더 자세히 설명됩니다.

routing 앞에, 이 예는 두 공급자의 외부에 살고 있는 권위있는 DNS를 보여주고 그들 사이 균형을 적재합니다. 이 DNS 공급자는 다른 제3자 공급자에 호스팅되거나 살 수 있었습니다. 교통은 각 공급자에게 대응하여 쿼리에 대응합니다.`www.example.com`공급자 특정한 CNAME 기록 또는 apex 도메인 트래픽을 위한 정체되는 IP로. 이 트래픽 분할을 달성하기 위해 타사 DNS 제공 업체는 트래픽을로드 할 수있는 몇 가지 능력을 가지고해야합니다. 대부분의 주요 DNS 제공 업체는 복잡성 및 구성성의 다양한 각도로 DNS 기반 부하 균형을 수행 할 수있는 메커니즘이 있습니다. 이것은 간단한 케이스에 있는 기록 사이 둥근 강도를 의미할 수 있고, 또는 클라이언트 위치에 근거를 둔 응답, 건강 체크 자료 및 더 많은 것을 변화할 수 있었습니다.

![그림 9: Cloudflare 및 DNS를 위한 다른 공급자 및 다른 공급자를 가진 다vendor 체제](~/assets/images/reference-architecture/multi-vendor-architecture-images/Figure_9.png "Figure 9")

권위있는 DNS 공급자에 따라 트래픽은 2 개 또는 동적으로 분할 될 수 있습니다. 종종 고객은 Thousandeyes 또는 Catchpoint와 같은 제 3 자 모니터링 서비스에서 sourced 성능 / 가용성 데이터로 DNS 라우팅을 알리고 그 데이터를 기반으로 DNS 응답을 조정할 수 있습니다. 세 번째 파티 모니터링 서비스는 종종 실시간 성능에 따라 전체 HTTP 요청/response 메트릭을 캡처하는 데 사용됩니다. 트래픽은 쉽게 승인 된 DNS를 업데이트하여 공급자로부터 멀리 이동할 수 있으며, TTL 레코드를 기다리십시오.

제3자 서비스가 엔드 투 엔드 애플리케이션 성능 메트릭을 찾고 있다는 것을 알고 중요한 것은 DNS 응답 시간 또는 DNS 해결사에 의해 사용되는 제한된 데이터가 아닙니다. DNS 레코드는 올바른 보안 공급 업체의 프록시를 반영하기 위해 성능 데이터를 기반으로 업데이트됩니다.

두 공급자의 구성은 관리자가 동기화하여 각 공급자의 API로 호출하는 Terraform을 통해 변경 사항을 밀어줍니다. Cloudflare가 모든 기능에 대한 전체 API 지원을 가지고있는 동안, 이것은 모든 공급자의 경우가 될 수 없습니다.

1개의 외부 DNS 공급자만 이용되고 있는 경우에, 그것은 DNS 공급자가 정전의 단 하나 점을 창조합니다. 이 위험을 완화하는 방법은 멀티 벤더 DNS 솔루션을 구현하는 것입니다. 이것은 더 자세히 논의됩니다.[멀티벤더 DNS 옵션](#multi-vendor-dns-setup-options)이 문서의 섹션.

평행한 접근의 또 다른 도전은 공급자의 sync에 있는 윤곽을 일관된 최종 사용자 경험을 전달하기 위하여 지킵니다. 이것은 관리자가 두 공급업체의 구성 관리와 익숙해야하며 기능 패리티가 달성 될 수 있는지 이해합니다.

DNS, 모든 보안 및 성능 서비스 및 해당 정책이 적용된 보안 및 성능 서비스 제공 업체에 한 번 트래픽이 전달되고 트래픽은 고객의 방화벽이 각 공급자에 의해 지정된 IP를 허용하는 근원으로 인터넷 뒤로 전달됩니다.

### Multi-vendor Active-active 보안과 같은 공급자로부터 멀티벤더 DNS

아래 예제는 DNS 제공 업체가 보안 프록시 공급 업체이며 DNS 레코드는 영역 전송을 통해 동기화에 보관됩니다. 멀티벤더 DNS 솔루션은 선호하고 가장 탄력적인 솔루션으로 권장됩니다.

여기에 다른 DNS 공급 업체와 사이에서 가능한 다른 설정은 각각의 장점 / 단점이있는이 문서의 '멀티 벤더 DNS 설정'섹션에서 더 자세히 논의됩니다.

이 예에서, 여러 권위있는 DNS 제공 업체가 1 차이며 다른 하나는 이차입니다. 이차 DNS 및 각 표준의 사용 당, 영역은 쉽게 동기화되는 다른 공급자 사이에서 DNS 구성을 허용한다.

이 모델에서 두 제공 업체 (같은 호스트에 대한)에 대한 요청을 점하기 위해, 이차로 설정된 공급 업체는 프록시를 통해 갈 예정된 레코드를 덮을 수 있어야합니다. 이차로 기록을 덮는 능력 없이, 모든 차적인 기록의 목적지는 정체되는 남아 있고 전반적인 체제의 융통성 그리고 탄력을 감소시킬 것입니다; Cloudflare는 이 기능을 가진 제공합니다[두 번째 DNS override](/dns/zone-setups/zone-transfers/cloudflare-as-secondary/proxy-traffic/). 예를 들면, Cloudflare와 같은 공급자가 이차로 설치되는 경우에, Cloudflare는 지역 이동을 통해 1 차에서 그(것)들을 자동적으로 동기화한 DNS가 있고, 그것의 자신의 프록시/서비스에 점에 기록하기 위하여 보조 DNS override를 사용할 수 있습니다.

DNS 기반 로드 밸런싱은 여기에 필요하지 않습니다, 그것은 각 공급자에 가지고 도움이 그래서 요청은 여러 공급 업체를 통해 상당히 분할 될 수 있습니다, 그렇지 않으면 트래픽 분할 클라이언트의 해결자 네임 서버 선택에 의해 크게 언급된다.

![그림 10: Cloudflare와 다른 납품업자와 동일한 공급자에게서 다vendor DNS를 가진 다vendor 체제.](~/assets/images/reference-architecture/multi-vendor-architecture-images/Figure_10.png "Figure 10")

권위있는 DNS 제공 업체에서 각 공급 업체는 NS 레코드를 나열하고 클라이언트는 해결자를 기준으로 nameserver를 선택합니다. 해결자는 요청시 저자명서의 전체 세트를 받게됩니다. 대부분의 해결사에 의해 사용되는 논리는 일반적으로 계정 해상도 시간뿐만 아니라 가용성에 걸립니다. 이 시나리오에서, 해결자는 이미 성능/availability 데이터를 기반으로 하는 네임 서버의 결정에 사용됩니다.

일반적으로 DNS 해커가 이미 사용되는 네임서버와 관련된 쿼리와 응답을 볼 수 있다는 것을 주목하는 것이 중요합니다. 예를 들어, nameserver는 고객에 대한 공급 업체가 이미 공인 DNS 및 해결사에 대한 다른 사이트에서 사용할 수 있습니다 이미 성능 데이터의 강력한 역사적인 기반이 즉시 레버리지를 시작할 수 있습니다.

이 예제에서는 주기적인 영역 전송을 통해 동기화된 레코드를 볼 수 있습니다. Cloudflare는 나가는 지역 이동 둘 다 지원할 수 있습니다. 트래픽은 공급자 특정 CNAME 레코드 또는 정적 IP로 각 프록시로 지시됩니다.

DNS 측의 구성은 다를 수 있습니다; 다른 옵션은 다음 섹션에서 더 자세히 논의됩니다. DNS는 1 차적으로 행동하는 1개의 공급자로 설치될 수 있고 이차로 다른 행동. DNS 제공 업체는 기본적으로 모든 DNS 구성이 수행되고 이차 DNS는 영역 전송을 통해 구성 복사를받습니다.

일부 DNS 제공 업체와 같은[모델 번호: Cloudflare](/dns/zone-setups/zone-transfers/cloudflare-as-secondary/proxy-traffic/)이차 DNS가 A 및 AAAA 레코드를 덮을 수 있는 기능을 제공합니다. 이를 통해 A/AAAA 레코드를 작성할 수 있습니다. 이 경우 두 번째 DNS 공급자는 동일한 호스트 이름에 대한 기본보다 다른 응답을 제공 할 것입니다. 즉, 네임서버가 클라이언트의 해결사 쿼리에 따라 요청은 공급업체의 해당 네트워크로 전달됩니다. 이 유연성과 감소된 복잡성을 통해 트래픽 스티어링을 위한 클라이언트 해결자에 의존하고 네임서버가 느리거나 접근할 수 없는 경우 실패합니다. 이 제공된 비용의 직접 제어 및 예측 가능성에 어떤 공급자 클라이언트 선택.

다른 변형은 특정 공급자를 통해 호스팅되는 특정 응용 프로그램 / 호스트 이름이 있습니다. 즉, 위의 예에서, 기본 및 보조 DNS 서버 모두`www.example.com`공급자가 초기 DNS 쿼리를 해결하지 않고 Cloudflare 주소로 매핑되었습니다.

## Multi-vendor DNS 설정 옵션

중요한 여정은 DNS에 의해 결정됩니다. 논의 된대로 다중 구성이 가능합니다. 아래는 보안 솔루션 제공업체인 두 개의 DNS 제공업체를 사용하고 있습니다.

**1. 2개의 권위 - 1개의 1 차 및 1 차**

이 설정은 1 차 및 2 차 공급자로 한 공급자를 설정할 수 있습니다. 이차 DNS의 목적은 기본과 이차의 구성과 동기화되는 멀티-DNS 솔루션을 지원하는 것입니다.

이 설정에서 두 DNS 제공 업체는 권한이지만 하나의 주요이며 진실의 소스이며 DNS 구성 변경 / 업데이트가 이루어집니다. 1 차에 구성 변경/업데이트는 공급자에 의해 관리되는 지역 이동을 통해 이차 DNS 공급자에 동기화됩니다. 두 공급자의 DNS는 DNS 쿼리에 응답합니다.

이 배포 모델과의 장점과 주요 사용 사례는 여러 공급자를 통해 DNS를 동기화하는 표준을 사용하고이 이유를 위해 생성되었으며 DNS 공급자는 지역 전송을 담당합니다. 이 옵션은 공급자 간의 DNS 동기화 유지에 대한 단순성을 제공합니다.

때때로 고객은 다음과 같은 다른 옵션을 사용할 수 있습니다 :

- 기록 관리 및 지역 전송 파이프라인이 다운될 때 DNS 레코드를 업데이트하는 필요조건.
- DNS 동기화 및 desiring에 대한 제 3 자 / 승인에 의존하지 마십시오.
- 이 옵션을 제외한 특정 제한/규제가 있습니다.

이 설정은 동기화를 유지하기위한 보조 DNS 및 공급자에 의해 제공되는 단순성을 원하는 고객에게 권장됩니다.

프로 :

- 표준 (AXFR, IXFR)을 사용하여 DNS 동기화를 유지하고 Zone Transfer를 통해 자동으로 수행하십시오.
- DNS 공급자로서의 단순성은 DNS 동기화를 담당합니다.

단점 :

- 기록 관리 및 영역 전송 파이프라인이 다운되면 DNS 레코드가 업데이트 될 수 없습니다.
- 몇몇 고객은 DNS sync를 위한 납품업자/3rd 당에 rely 원하지 않으며 더 통제와 융통성을 욕구합니다.

**2. 2개의 권위 - 둘 다 1 차**

일부 고객은 기록 관리 및 지역 전송 파이프라인이 다운될 때 DNS 레코드를 업데이트할 수 있는 추가 보증을 가질 수도 있습니다. 그들은 또한 DNS 동기화 및 더 많은 제어를 원하는 세 번째 파티 / 승인에 의존 할 수 없습니다. 이 경우 두 DNS 제공 업체는 기본으로 사용될 수 있습니다.

이 설정에서 각 DNS 공급자는 권한 및 기본입니다. DNS에 대한 이차 DNS 및 변경/업데이트가 제공되지 않습니다. 또한 DNS 제공 업체 모두 DNS 쿼리에 응답합니다.

공급자 간의 DNS 구성의 동기화는 중요하며, 이 설정에서 이제 두 공급자에서 동기화되는 DNS를 유지하기 위해 고객의 책임이 됩니다. 고객은 일반적으로 OctoDNS, Terraform 등과 같은 자동화 도구와 동기화하거나 공급업체의 API를 활용할 수 있는 맞춤형 자동화를 통해 이루어집니다.

이 설정은 기록 관리 및 영역 전송 파이프라인이 DNS 동기화를 통해 더 많은 제어를 원하는 고객 및/또는 DNS 레코드를 지원 하는 가장 유연한 및 탄력 옵션을 원하는 고객에 대 한 권장.

프로 :

- 제어 비행기가 한 공급자에 다운되면 DNS 레코드는 여전히 다른 곳에서 업데이트 될 수 있습니다.
- DNS 동기화를 위한 DNS 공급자에 더 많은 통제 및 reliance.

단점 :

- 공급자 synced 사이 DNS를 유지하는 더 복잡성.
- 고객은 공급업체 API를 통해 자동화된 자동화 도구를 통해 수행될 수 있는 DNS 동기화를 책임집니다.

**3. 1개 이상 허가 - 숨겨지은 1 차 및 다수 이차**

숨겨진 기본 설정에서 사용자는 모든 영역 파일을 저장하고 변경할 수 없는 1차 서버를 설치하고 쿼리를 수신하고 해결하기 위해 1차 서버를 활성화합니다. 초급의 대부분이 권한이지만, 그것은 할 필요가 없습니다. 이 옵션에서, 1 차는 레지스트라로 나열되지 않습니다. 1 차는 쿼리에 응답하지 않으며 주요 목적은 진실의 단일 소스입니다.

이차 서버는 기본적으로 1 차 서버의 기능을 충족하지만 숨겨진 설정은 사용자가 원래 IP를 숨기고 공격으로부터 보호 할 수 있습니다. 또한, 1 차는 DNS 서비스를 방해하지 않고 유지 보수를 위해 오프라인으로 촬영 할 수 있습니다.

이 설정은 동기화를 유지하기위한 보조 DNS 및 공급자에 의해 제공되는 단순성을 원하는 고객에게 권장됩니다. 이 해결책은 또한 더 적은 충격으로 1 차적인 따로따로 가지고 가는 융통성을 제공합니다.

프로 :

- 고객이 인프라에 DNS 레코드 관리를 유지하고 Zone Transfer를 통해 DNS 동기화를 자동으로 유지하도록 표준을 사용합니다.
- 1 차는 진실의 근원과 DNS 기록을 유지하고 정비 /administration를 위해 따로따로 가지고 갈 수 있습니다.

단점 :

- 기록 관리 및 영역 전송 파이프라인이 다운되면 DNS 레코드가 업데이트 될 수 없습니다.
- 일부 고객은 DNS 동기화 및 더 많은 컨트롤을 원하는 업체 / 3rd 파티에 의존하지 않습니다.

그림 11는 평행한에 있는 Cloudflare와 다른 공급자 둘 다의 맞은편에 윤곽을 관리하는 전형적인 본을 묘사합니다. 이 예제에서는 동일한 워크로드가 제공 업체를 통해 분할되고 관리자 팀은 API를 통해 구성을 업데이트하고 있습니다. 이것은 또한 내부 CI/CD 파이프라인에 연결될 수 있습니다. 모든 Cloudflare 기능은 API를 통해 형성되고 API를 통해 첫째로 배달될 수 있습니다. 이 다이어그램은 전자 메일, webhook 또는 PagerDuty를 통해 전달 될 수있는 일반적인 SIEM 및 기본 경고 기능으로 전송되는 로그를 묘사합니다. 성능, 보안 또는 관리 기준에 따라 경고합니다.

다양한 사용자 정의 옵션 Cloudflare 제공 (Ruleset Engine, native features, WorkerCustoms), Cloudflare는 시장에서 다른 주요 공급 업체와 기능 패리티를 만날 수 있지만 이러한 기능은 동일한 방식으로 구성 할 수 없다는 것을 보장하지 않습니다. Cloudflare 계정 팀과 긴밀하게 협력하는 것은 Cloudflare와 작업 흐름을 정렬하기 위해 작업 및 모범 사례의 주요 차이를 이해하는 데 중요합니다.

## 연결 옵션

각 공급자가 근원 (s)에 연결하고 안전, 성과 및 탄력에 있는 무역 떨어져 제안하는 방법을 고려하기 위하여 그것을 제안하는 다 이득을 위해 중요합니다. Cloudflare는 대부분의 사용 케이스에 적합하고 잡종 고객 환경을 적합하기 위하여 신청 (hostname/DNS 기록) granularity 당 평행한에서 배치될 수 있는 몇몇 선택권을 제안합니다.

### 인터넷 (과태)

대부분의 기본 시나리오에서 프록시는 인터넷을 통해 트래픽을 전달합니다. 이는 모든 공급업체의 기본 설정입니다. 이 설정에서 클라이언트와 기원은 각 ISP를 통해 인터넷에 직접 연결됩니다. 요청은 클라이언트에서 공급 업체 프록시 (DNS 구성을 통해)에 인터넷을 통해 전달됩니다. 프록시는 인터넷을 통해 고객의 원산지로 요청합니다.

아래 다이어그램은 Cloudflare 네트워크를 통해 요청 흐름으로 인한 기본 연결성을 설명합니다. 요청이 proxied DNS 레코드를 표시하고 원산지에 도달 할 필요가있을 때, Cloudflare는 Cloudflare 소유 주소의 세트에서 인터넷에서 네트워크를 통해 트래픽을 보낼 것입니다.

![그림 12: Cloudflare에서 인터넷을 통해 근원 서버 (s)에 연결](~/assets/images/reference-architecture/multi-vendor-architecture-images/Figure_12.png "Figure 12")

선택적으로, 고객은 또한 레버리지를 선택할 수 있습니다[전용 CDN Egress IPs](/smart-shield/configuration/dedicated-egress-ips/)Cloudflare가 당신의 근원에 다시 연결하기 위하여 이용된다는 고객의 특정한 IPs를 할당하는 . 우리는 이 네트워크에서 트래픽을 허용하는 것이 좋습니다. 원래 측면 방화벽에서 IP 차단 외에도 "Full (Strict)" SSL 설정 또는 mTLS auth를 통해 트래픽의 추가 검증을 강력하게 권장합니다. 모든 트래픽이 고객의 구성 영역을 통과하는 요청에서 소스됩니다.

Cloudflare는 또한 지원합니다[자신의 IP를 가져 오기 (BYOIP)](/byoip/). BYOIP가 형성될 때, Cloudflare 세계적인 네트워크는 고객의 자신의 IP 접두사 및 접두사는 각각 Cloudflare로 사용될 수 있습니다 층 7 서비스.

### 개인 연결 - 터널 또는 VPN

또 다른 옵션은 추가 보안을 위해 인터넷에 개인 터널 / 연결이 있습니다. 일부 공급 업체는 암호화되거나 암호화 될 수있는 터널 또는 VPN을 통해 개인 연결성을 제공합니다. 이러한 다양한 복잡성 / 관리 및 연결성을 허용하기 위해 추가 보안 / 방화벽 업데이트가 필요합니다. 전통적인 VPN 설정은 원래의 중앙 공급 업체 위치를 통해 제한됩니다.

Cloudflare 제안[Cloudflare 갱도](/cloudflare-one/networks/connectors/cloudflare-tunnel/)당신의 근원 (s)와 Cloudflare의 네트워크 사이에서 암호화된 갱도를 제공하는 Tunneling 소프트웨어입니다. 또한, Cloudflare는 글로벌 네트워크에서 anycast를 레버리지 때문에, 근원 (s)는 클라이언트와 같이, 가까운 Cloudflare 자료 센터 (s)에 연결합니다.

터널을 실행할 때, 인프라의 경량 데몬, 클라우드, 원래 서버와 Cloudflare 네트워크 사이에 4개의 아웃바운드 전용 연결을 설정한다. 이 4개의 연결은 강력한 탄력성을 제공하는 적어도 2개의 명백한 자료 센터의 맞은편에 4개의 다른 서버로 퍼집니다. 원래 서버와 Cloudflare 네트워크 사이의 탄력을 증가하는 많은 클라우드 인스턴스를 설치할 수 있습니다.

Cloudflared는 당신의 근원 웹 서버 (s)와 Cloudflare의 가장 가까운 자료 센터 (s) 사이에서 암호화된 갱도를, 모든 공중 상행한 항구 열기 없이 만듭니다. 이 기능은 방화벽에 필요한 보안 변경이 없습니다. 이 솔루션은 또한 공격에 취약 할 수있는 방화벽 구성의 위험을 낮춥니다.

방화벽 및 보안 자세는 방화벽을 통해 모든 Origin 서버 포트 및 프로토콜을 잠금하여 경화됩니다. 한 번 Cloudflare 터널은 배치 및 해당 보안 적용, HTTP / S 포트의 모든 요청은 볼륨 디도스 공격을 포함하여 삭제됩니다. Data breach 시도는 transit 또는 brute force login 공격에 데이터의 스누핑과 같은 완전히 차단됩니다.

![그림 13: Cloudflare에서 Cloudflare를 통해 근원 서버 (s)에 연결 관련 제품](~/assets/images/reference-architecture/multi-vendor-architecture-images/Figure_13.png "Figure 13")

위 도표는 Cloudflare 갱도를 통해서 연결성 모형을 설명합니다. 참고,이 옵션은 공용 IP 주소없이 Cloudflare에 리소스를 연결하는 안전한 방법을 제공합니다. 모델: Cloudflare 터널은 HTTP 웹 서버, SSH 서버, 원격 데스크톱 및 Cloudflare에 안전하게 다른 프로토콜을 연결할 수 있습니다.

### 직접 연결

대부분의 공급 업체는 네트워크에 직접 연결 옵션을 제공합니다. 직접 연결은 공공 인터넷을 사용하여 보안, 신뢰성 및 성능 혜택을 제공합니다. 이 직접 연결은 피어링 시설, 인터넷 교환 (IX) 인터넷 서비스 제공 업체 (ISP) 및 인터넷 네트워크가 서로 상호 연결하거나 공급업체 파트너를 통해 할 수 있습니다.

![그림 14: Cloudflare에서 Cloudflare 네트워크 상호 연결 (CNI)를 통해 본래 서버 (s)에 연결성](~/assets/images/reference-architecture/multi-vendor-architecture-images/Figure_14.png "Figure 14")

위의 다이어그램은 소스 연결을 통해 설명합니다.[Cloudflare 네트워크 상호 연결 (CNI)](https://blog.cloudflare.com/cloudflare-network-interconnect/)Cloudflare와 직접 네트워크 인프라를 연결하고 그 직접 링크에서만 통신 할 수 있습니다. CNI는 Cloudflare와 직접 상호 연결 분지 및 본부 위치를 허용합니다. 고객은 Cloudflare를 3가지 방법으로 상호 연결할 수 있습니다: 개인 네트워크 상호 연결 (PNI)에 유효한[Cloudflare 피어링 시설](https://www.peeringdb.com/net/4224)IX를 통해[많은 글로벌 거래소 Cloudflare 참여](https://bgp.he.net/AS13335#_ix), 또는 우리의 것[Interconnection 플랫폼 파트너](https://blog.cloudflare.com/cloudflare-network-interconnect-partner-program).

Cloudflare의 글로벌 네트워크는 인프라 및 직원이 어디에 상관없이 네트워크에 쉽게 연결할 수 있습니다.

## 추가 라우팅 및 보안 옵션

대부분의 납품업자는 또한 근원과 communicating 때 강화된/optimized 여정 및 추가 보안 기능을 위한 추가 기능을 제공합니다. 성능과 보안 기능 측면에서 예상되는 경우 해당 공급업체 문서로 확인해야 합니다.

Cloudflare 제안[Argo 스마트 여정](/argo-smart-routing/)Cloudflare 네트워크를 통해 최적화된 루트를 찾고 사용 하 여 사용자에 게 응답을 더 빨리 전달 하 고 인증 된 원본 풀 (mTLS) 당신의 기원 서버에 요청을 보장 하기 위해 Cloudflare 네트워크

### Argo 스마트 여정

Argo Smart Routing은 Cloudflare 네트워크를 통해 최적화된 루트를 찾아 사용자가 더 빠르게 응답할 수 있는 서비스입니다.

Argo Smart Routing는 초당 28 백만 HTTP 요청을 라우팅에서 실시간 데이터 및 네트워크 인텔리전스를 고려하여 트래픽을 가속화합니다. 그것은 가장 빠르고 신뢰할 수있는 네트워크 경로가 Cloudflare 네트워크에서 원래 서버로 추적됩니다. 평균적으로 Argo Smart Routing 계정은 웹 자산의 30 % 빠른 성능입니다.

또한 Cloudflare CDN은 Argo Tiered Cache를 위한 최고의 상위 계층 데이터 센터를 결정하기 위해 Argo Smart Routing을 활용합니다. Argo Smart Routing은 Cloudflare 네트워크를 통해 가장 빠른 경로가 항상 상위 계층 데이터 센터 및 소스 서버 사이에서 촬영됩니다. Argo Smart Routing없이, 상위 계층 데이터 센터 간의 통신은 여전히 인터넷의 문제 주위에 지능적으로 소스의 가용성을 보장합니다. Argo Smart Routing에 대한 자세한 정보는 CDN에 리레이트되어 있습니다.[Cloudflare CDN 참고 자료 회사연혁](/reference-architecture/architectures/cdn/).

### 인증된 원본 풀 (mTLS)

Authenticated Origin Pulls는 Cloudflare 네트워크에서 소스 서버에 요청을 보장하는 데 도움을 줍니다.[한국어](/ssl/origin-configuration/ssl-modes/full/)또는[풀 (strict)](/ssl/origin-configuration/ssl-modes/full-strict/)SSL/TLS 암호화 모드 Cloudflare 제공.

이 인증은 특히 중요합니다.[Cloudflare 웹 응용 프로그램 방화벽 (WAF)](/waf/). WAF와 함께, 당신은 당신의 근원 서버에서 응답을 받기 전에 모든 교통이 평가된다는 것을 확인할 수 있습니다.

도메인을 원하는 경우[한국어](https://en.wikipedia.org/wiki/Federal_Information_Processing_Standards)준수, 당신은 자신의 인증서를 업로드해야합니다. 이 옵션은 모두 사용할 수 있습니다[지역 수준](/ssl/origin-configuration/authenticated-origin-pull/set-up/zone-level/)·[이름 \*](/ssl/origin-configuration/authenticated-origin-pull/set-up/per-hostname/)인증된 원본 풀.
