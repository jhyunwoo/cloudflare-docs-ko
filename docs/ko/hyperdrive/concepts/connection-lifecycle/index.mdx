Workers, HyperdriveXQ의 연결 작업에 대해 자세히 알아보세요.

Cloudflare의 네트워크 내에서 데이터베이스에 연결 풀을 유지함으로써 HyperdriveXQ는 쿼리를 보낼 수 있기 전에 데이터베이스에 7 라운드 스트립을 줄입니다. TCP Handhake (1x), TLS 협상 (3x) 및 데이터베이스 인증 (3x).

## 연결이 관리되는 방법

Cloudflare에서 데이터베이스 클라이언트를 사용할 때 작업자, 연결 수명주기는 전통적인 서버 환경에서 다르게 작동합니다. 여기에 무슨 일이:

![Hyperdrive 연결](~/assets/images/hyperdrive/configuration/hyperdrive-connection-lifecycle.svg)

Hyperdrive 없이, 각 노동자 invocation는 당신의 근원 데이타베이스에 새로운 연결을 직접 설치해야 할 것입니다. 이 연결 설정 프로세스는 TCP Handhake, TLS 협상 및 데이터베이스 인증을 완료하기 위해 인터넷 전역의 여러 라운드 스트립을 필요로합니다. 즉, 7x 왕복이며 쿼리가 실행되기 전에 대기 시간을 추가 할 수 있습니다.

Hyperdrive는 연결 설정을 두 개의 부품으로 분할하여이 문제를 해결합니다. 빠른 가장자리 연결과 데이터베이스에 최적화 된 경로.

1. **가장자리에 연결 설정**: 작업자 코드의 데이터베이스 드라이버는 Hyperdrive 인스턴스에 연결됩니다. 이 가장자리에서 발생, 당신의 노동자와 공동으로, 연결 만들기 매우 빠른. 이것은 당신이 Hyperdrive의 특별한 연결 끈을 사용하는 이유입니다.

2. **지구의 단일 왕복**: 인증이 이미 가장자리에서 완료되었기 때문에, Hyperdrive는 연결 설정 중 발생한 여러 왕복 대신 데이터베이스에 대한 단일 라운드 여행을 필요로합니다.

3. **Pool의 기존 연결**: Hyperdrive는 데이터베이스에 닫히는 풀에서 기존의 연결을 사용합니다.

4. **사용 가능한 연결이 없는 경우, 새로 만들기**: 필요한 경우, 새로운 연결은 데이터베이스에 가까운 지역에서 새로운 연결을 설정의 지연을 줄이기 위해 만들어집니다.

5. **자주 묻는 질문**: 귀하의 쿼리는 데이터베이스에 대해 실행되며 결과는 Hyperdrive를 통해 작업자에게 반환됩니다.

6. **연결 눈물**: 작업자가 요청을 처리 할 때, 작업자의 데이터베이스 클라이언트 연결은 자동으로 수집됩니다. 그러나, Hyperdrive는 수영장에서 열린 당신의 근원 데이타베이스에 연결을 유지하고, 다음 노동자 invocation에 의해 재사용될 준비합니다. 즉, 요청은 여전히 빠른 가장자리 연결 설정을 수행하지만 데이터베이스 근처의 Hyperdrive의 풀에서 기존 연결 중 하나를 재사용합니다.

:::참조

Cloudflare Worker, Worker 내의 데이터베이스 클라이언트 연결은 단일 발명품의 기간 동안만 살아있다. Hyperdrive로, 각 invocation에 새로운 클라이언트를 창조하는 것은 Hyperdrive가 당신을 위한 underlying 데이타베이스 연결을 유지하고, 최선 위치에 풀고 가늠자를 확대하기 위하여 WorkersXQ를 통해 공유하기 때문에 빠르고 추천됩니다.

:::

## 고객 연결 청소

요청을 처리 할 때 작업자는 데이터베이스 클라이언트가 자동으로 수집되어 Hyperdrive에 대한 가장자리 연결이 정리됩니다. Hyperdrive는 재사용을 위한 수영장에서 열리는 당신의 근원 데이타베이스에 underlying 연결을 지킵니다.

당신은**아니다.**&#xC804;화 번호`client.end()`, `sql.end()`, `connection.end()`(또는 이와 유사한) 데이터베이스 클라이언트를 정리합니다. Workers-to-HyperdriveXQ 연결은 요청 또는 직업 끝을 포함하여, 자동적으로 청소됩니다[작업 흐름](/workflows/)또는[Queue 소비자](/queues/)완료, 또는 때[튼튼한 목표](/durable-objects/)hibernates 또는 idle 때 evicted입니다.

```ts
import { Client } from "pg";

export default {
	async fetch(request, env, ctx): Promise<Response> {
		const client = new Client({
			connectionString: env.HYPERDRIVE.connectionString,
		});
		await client.connect();

		const result = await client.query("SELECT * FROM pg_tables");

		//client.end()를 호출할 필요가 없습니다. — Hyperdrive는 자동으로 청소합니다.
		//요청이 종료될 때 클라이언트 연결까지. 이름 *
		//당신의 근원 데이타베이스에 풀 연결은 재사용을 위해 열려 있습니다.
		return Response.json(result.rows);
	},
} satisfies ExportedHandler<Env>;
```

:::note\[커버 내부 데이터베이스 클라이언트]

항상 귀하의 요청 핸들러 내부 데이터베이스 클라이언트를 작성해야합니다 (`fetch`, `queue`, 그리고 이와 유사한), 글로벌 범위에. Workers는 허용하지 않습니다[요청에 따라 I/O](/workers/runtime-apis/bindings/#making-changes-to-bindings), 그리고 Hyperdrive의 분배된 연결은 이미 연결 시작 latency를 위해 해결합니다. 드라이버 레벨 풀 사용 (예 :`new Pool()`또는`createPool()`) 글로벌 스크립트 범위에서 실패 쿼리 및 하드 오류 결과로 stale 연결로 당신을 떠날 것입니다.

:::

글로벌 범위에서 데이터베이스 클라이언트 또는 연결 풀을 만들지 마십시오. 대신, 각 핸들러 invocation 내부의 새로운 클라이언트를 만듭니다 — Hyperdrive의 연결 풀은 이것은 빠릅니다:

<TypeScriptExample filename="index.ts">
  ```ts
  import { Client } from "pg";

  //✓ Bad: 클라이언트는 요청에 따라 글로벌 범위의 persists에서 만든.
  //Workers는 요청에 따라 I/O를 허용하지 않습니다, 그래서 이 클라이언트
  //stale과 후속 쿼리가 어려운 오류를 발생시킵니다.
  const globalClient = new Client({
  	connectionString: env.HYPERDRIVE.connectionString,
  });
  await globalClient.connect();

  export default {
  	async fetch(request, env, ctx): Promise<Response> {
  		//✅ 좋은: 클라이언트는 이 요구에 배열된 핸들러 안쪽에 창조했습니다.
  		//Hyperdrive는 당신의 근원 데이타베이스에 완전하게 연결,
  		//그래서 요청에 의하여 새로운 클라이언트를 창조하는 것은 빠르고 믿을 수 있습니다.
  		const client = new Client({
  			connectionString: env.HYPERDRIVE.connectionString,
  		});
  		await client.connect();

  		const result = await client.query("SELECT * FROM pg_tables");
  		return Response.json(result.rows);
  	},
  } satisfies ExportedHandler<Env>;
  ```
</TypeScriptExample>

## 연결 lifecycle 고려사항

### Durable Objects와 지속적인 연결

일반 Workers와는 달리,[모델 번호: Durable Objects](/durable-objects/)여러 요청에 따라 상태를 유지할 수 있습니다. 데이터베이스 클라이언트가 튼튼한 개체에서 열리면 연결은 Hyperdrive의 연결 풀에서 할당됩니다. 오래 살아남은 Durable Objects는 많은 목표가 연결이 동시에 열리는 경우에 유효한 연결을 배기할 수 있습니다.

:::카트로션

Durable Objects의 지속적인 데이터베이스 연결을 유지 할 때주의하십시오. 각 개방 연결은 Hyperdrive의 연결 풀에서 리소스를 소비하며 다른 응용 프로그램의 부품을 영향을 줄 수 있습니다. 사용중인 경우의 연결, 연결 타임아웃을 사용, 그리고 데이터베이스 연결을 유지 Durable ObjectsXQ의 번호를 제한.

:::

### 긴 실행 거래

Hyperdrive는에서 작동합니다[거래 풀 모드](/hyperdrive/concepts/how-hyperdrive-works/#pooling-mode), 연결이 거래 기간 동안 개최되는 곳. 여러 쿼리를 포함하는 긴 실행 거래는 Hyperdrive의 사용 가능한 연결이 완료 될 때까지 풀에서 연결을 보유하기 때문에 더 빨리.

:::가격

가능한 한 짧은 거래 유지. 트랜잭션 내에서 필수 쿼리만 수행하고 트랜잭션 블록 내부의 non-database 작업 (외부 API 호출 또는 복잡한 계산과 같은)을 포함하여 피합니다.

:::

더 알아보기[제한 사항](/hyperdrive/platform/limits/)Workers 계획에 근거를 둔 당신의 Hyperdrive 윤곽을 위해 얼마나 많은 연결이 유효한지 이해하십시오.
