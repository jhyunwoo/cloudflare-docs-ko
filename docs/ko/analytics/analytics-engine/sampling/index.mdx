Workers Analytics Engine은 매우 많은 양의 데이터를 기록하고 빠르게 조회할 수 있도록, 적은 비용 또는 무료로 제공되도록 설계되어 있습니다. 대량의 데이터를 합리적인 비용으로 기록할 수 있도록 Workers Analytics Engine은 가중 적응형 [샘플링](https://en.wikipedia.org/wiki/Sampling_\(statistics\))을 사용합니다.

샘플링을 사용할 때는 데이터셋에 대한 질문에 답하기 위해 모든 데이터 포인트가 하나도 빠짐없이 필요하지는 않습니다. 충분히 큰 데이터셋에서는 [필요한 표본 크기](https://select-statistics.co.uk/blog/importance-effect-sample-size/)가 원래 모집단의 크기에 좌우되지 않습니다. 필요한 표본 크기는 측정값의 분산, 분석하려는 하위 그룹의 크기, 추정값에 요구되는 정확도에 따라 달라집니다.

Analytics Engine에서 이것이 의미하는 바는, 매우 큰 데이터셋을 훨씬 적은 수의 관측치로 압축하면서도 대부분의 쿼리에 대해 매우 높은 정확도로 답할 수 있다는 점입니다. 덕분에 사용량이 매우 높고 카디널리티가 무한한 경우에도 낮고 예측 가능한 가격으로 분석 서비스를 제공할 수 있습니다.

샘플링은 큰 흐름에서 다음과 같이 동작합니다.

1. 쓰기 시점에 하나의 인덱스로 데이터 포인트가 너무 빠르게 기록되면 샘플링합니다.
2. 조회 시점에 쿼리가 너무 복잡하면 다시 샘플링합니다.

## 샘플링이 동작하는 방식

Cloudflare의 데이터 샘플링은 Google Maps 같은 온라인 지도 서비스가 서로 다른 확대 수준에서 지도를 렌더링하는 방식과 비슷합니다. 대륙 전체의 위성 이미지를 볼 때 지도 서비스는 사용자 화면 크기와 인터넷 속도에 맞는 크기의 이미지를 제공합니다.

![왼쪽 이미지는 OpenStreetMap의 위성 화면입니다. 오른쪽은 같은 이미지를 확대했습니다. 두 이미지에서 각 픽셀은 같은 면적을 나타내지만, 오른쪽 이미지에는 픽셀이 훨씬 적습니다.](~/assets/images/analytics/zoom-less-pixels.png)

지도 위의 각 픽셀은 몇 제곱킬로미터처럼 큰 영역을 나타냅니다. 사용자가 스크린샷을 확대하면 결과 이미지는 흐릿해집니다. 대신 지도 서비스는 사용자가 특정 도시를 확대하면 더 높은 해상도의 이미지를 선택합니다. 전체 픽셀 수는 비교적 일정하지만, 각 픽셀이 나타내는 영역은 몇 제곱미터처럼 더 작아집니다.

![이제 오른쪽 이미지는 훨씬 더 높은 해상도를 가집니다. 각 픽셀은 훨씬 더 작은 영역을 나타내지만, 두 이미지의 총 픽셀 수는 대략 같습니다.](~/assets/images/analytics/zoom-more-pixels.png)

핵심은 지도의 품질이 해상도나 픽셀당 표현 면적에만 달려 있지 않다는 점입니다. 최종 화면을 렌더링하는 데 사용된 총 픽셀 수가 품질을 결정합니다.

지도 서비스의 해상도 처리 방식과 Cloudflare Analytics가 적응형 샘플로 분석을 제공하는 방식은 다음과 같이 유사합니다.

* **데이터 저장 방식**:
  * **지도 서비스**: 서로 다른 해상도로 이미지를 저장합니다.
  * **Cloudflare Analytics**: 서로 다른 샘플 비율로 이벤트를 저장합니다.
* **사용자에게 데이터를 표시하는 방식**:
  * **지도 서비스**: 화면 크기가 같다면 선택한 영역의 크기와 상관없이 총 픽셀 수는 거의 일정합니다.
  * **Cloudflare Analytics**: 데이터셋 크기나 선택한 시간 길이와 관계없이 각 쿼리마다 비슷한 수의 이벤트를 읽습니다.
* **해상도를 선택하는 방식**:
  * **지도 서비스**: 각 픽셀이 나타내는 면적은 렌더링하는 지도 범위에 따라 달라집니다. 더 축소된 지도일수록 각 픽셀이 더 넓은 면적을 나타냅니다.
  * **Cloudflare Analytics**: 결과에 포함되는 각 이벤트의 샘플 간격은 기반 데이터셋의 크기와 선택한 시간 범위에 따라 달라집니다. 큰 데이터셋이나 긴 기간에 대한 쿼리에서는 샘플링된 이벤트 하나가 비슷한 여러 이벤트를 대표할 수 있습니다.

## 샘플링된 데이터를 읽는 방법

효율적으로 쿼리를 작성하고 데이터를 분석하려면 먼저 Workers Analytics Engine에서 샘플링된 데이터가 어떻게 읽히는지 이해하는 것이 좋습니다.

Workers Analytics Engine에서는 모든 이벤트에 `_sample_interval` 필드가 기록됩니다. 샘플 간격은 샘플 비율의 역수입니다. 예를 들어 1%(0.01)의 샘플 비율이 적용되면 `sample_interval`은 `100`으로 설정됩니다.

지도 예시에 빗대어 단순하게 말하면, 샘플 간격은 주어진 샘플링된 데이터 포인트(픽셀)가 대표하는 "샘플링되지 않은 데이터 포인트 수"(킬로미터 또는 미터 수)를 의미합니다.

샘플 간격은 Workers Analytics Engine에 저장된 각 개별 행에 연결된 속성입니다. 공정한 샘플링 구현 방식 때문에 샘플 간격은 행마다 달라질 수 있습니다. 따라서 데이터를 조회할 때는 샘플 간격 필드를 고려해야 합니다. 쿼리 결과에 상수 샘플링 계수를 단순히 곱하는 것만으로는 충분하지 않습니다.

다음은 샘플링된 데이터에 대해 자주 사용하는 쿼리를 표현하는 예시입니다.

| 사용 사례                         | 샘플링 미적용 예시         | 샘플링 적용 예시                                     |
| -------------------------------- | -------------------------- | ---------------------------------------------------- |
| 데이터셋의 이벤트 수 세기        | `count()`                  | `sum(_sample_interval)`                              |
| 양 합계 계산, 예: 바이트 수      | `sum(bytes)`               | `sum(bytes * _sample_interval)`                      |
| 평균 계산                        | `avg(bytes)`               | `sum(bytes * _sample_interval) / sum(_sample_interval)` |
| 분위수 계산                      | `quantile(0.50)(bytes)`    | `quantileExactWeighted(0.50)(bytes, _sample_interval)` |

앞서 지도 비유에서 언급했듯 결과의 정확도는 샘플 간격 자체로 결정되지 않습니다. 샘플 간격이 크더라도 정밀한 결과를 얻을 수 있습니다. 정확도는 쿼리된 전체 데이터 포인트 수와 그 분포에 달려 있습니다.

## 데이터가 샘플링되는 방식

각 이벤트의 샘플 간격을 결정하기 위해서는, 대부분의 분석에 정확한 결과로 분석해야 하는 중요한 하위 그룹이 있다는 점을 먼저 알아야 합니다. 예를 들어 사용자 사용량이나 특정 호스트 이름에 대한 트래픽을 분석하고 싶을 수 있습니다. Analytics Engine 사용자는 이벤트를 기록할 때 `index` 필드를 채워 이런 그룹을 정의할 수 있습니다. 이를 통해 지정된 그룹 내에서 더 정밀하고 집중된 분석이 가능해집니다.

다음으로 주목할 점은, 이런 인덱스 값마다 기록되는 이벤트 수가 매우 다를 가능성이 높다는 것입니다. 실제로 대부분의 웹 서비스 사용량은 [파레토 분포](https://en.wikipedia.org/wiki/Pareto_distribution)를 따르며, 상위 소수 사용자가 전체 사용량의 대부분을 차지합니다. 파레토 분포는 흔하며 대략 다음과 같습니다.

![이 그래픽에서 각 막대는 사용자를 나타내고, 막대 높이는 총 사용량을 나타냅니다.](~/assets/images/analytics/total-usage.png)

이 데이터의 1% 단순 무작위 표본을 뽑아 전체 모집단에 적용하면, 대형 고객은 정확하게 추적할 수 있을지 모르지만 소규모 고객이 무엇을 하고 있는지는 보이지 않게 됩니다.

![위와 같은 그래픽이지만, 이번에는 데이터의 1% 표본을 기반으로 합니다.](~/assets/images/analytics/sample-data.png)

큰 막대는 거의 변하지 않아 여전히 꽤 정확해 보입니다. 하지만 더 작은 고객을 분석할수록 결과는 [양자화](https://en.wikipedia.org/wiki/Quantization_\(signal_processing\))되어 심지어 완전히 0으로 반올림될 수도 있습니다.

이는 큰 모집단에서는 1% 또는 그보다 더 작은 표본만으로도 충분할 수 있지만, 작은 모집단에서는 정확한 결과를 얻기 위해 더 큰 비율의 이벤트를 저장해야 할 수 있음을 보여줍니다.

이를 위해 공정 샘플링(equitable sampling)이라는 기법을 사용합니다. 즉, 각 고유 인덱스 값마다 저장하는 이벤트 수를 비슷하게 맞춥니다. 비교적 드문 인덱스 값에 대해서는 `writeDataPoint()`로 받은 모든 데이터 포인트를 기록할 수 있습니다. 하지만 하나의 인덱스 값으로 매우 많은 데이터 포인트를 기록하면 샘플링이 시작됩니다.

다음은 같은 분포에 (시뮬레이션된) 공정 샘플링을 적용한 모습입니다.

![이 그래픽은 같은 모집단에 공정 샘플링을 적용한 모습입니다.](~/assets/images/analytics/equitable-sampling.png)

이 그래픽은 첫 번째 그래프와 매우 비슷해 보일 수 있습니다. 하지만 전체적으로 `<10%`의 데이터만 저장해도 됩니다. 실제 샘플 비율은 큰 시리즈일수록 `10%`보다 훨씬 낮고(즉 더 큰 샘플 간격을 저장), 작은 시리즈일수록 더 높습니다.

위의 지도 비유를 다시 떠올려 보세요. 지도에 표시되는 면적과 관계없이 전체 픽셀 수는 일정하게 유지됩니다. 마찬가지로 여기서도 각 인덱스 값마다 비슷한 수의 데이터 포인트를 저장하려고 합니다. 다만 지도에서 픽셀 하나가 나타내는 면적이 표시 범위에 따라 달라지듯, 여기서는 저장된 데이터 포인트 하나가 대표하는 데이터 양이 해당 인덱스의 전체 데이터 수에 따라 달라집니다.

## 읽기 시점의 Adaptive Bit Rate Sampling

공정 샘플링은 특정 시간 프레임 안에서 각 인덱스에 대해 동일한 양의 데이터를 유지하도록 보장합니다. 하지만 쿼리는 목표로 하는 시간 범위가 크게 다를 수 있습니다. 어떤 쿼리는 10분치 데이터 스냅샷만 필요할 수 있고, 어떤 쿼리는 10주에 걸친 데이터를 분석해야 할 수도 있습니다. 이는 10,000배 더 긴 기간입니다.

이 문제를 해결하기 위해 [adaptive bit rate](https://blog.cloudflare.com/explaining-cloudflares-abr-analytics/) (ABR) 방식을 사용합니다. ABR에서는 더 긴 시간 범위를 다루는 쿼리가 더 큰 샘플 간격의 데이터를 읽어 정해진 시간 제한 안에서 완료되도록 합니다. 쉽게 말해, 지도 비유에서 화면 크기나 대역폭이 고정 자원인 것처럼 쿼리를 완료하는 시간도 고정 자원입니다. 따라서 관련 데이터 양과 상관없이, 쿼리에 응답하기 위해 스캔하는 전체 행 수를 제한해야 합니다. 이는 공정성을 보장하기 위한 것으로, 기반 데이터셋의 크기와 무관하게 모든 쿼리가 사용 가능한 계산 시간의 동등한 몫을 받도록 합니다.

이를 위해 공정 샘플링된 데이터에서 파생된 여러 해상도(예: 100%, 10%, 1%)로 데이터를 저장합니다. 쿼리 시점에는 쿼리 복잡도에 따라 읽기에 가장 적합한 데이터 해상도를 선택합니다. 쿼리 복잡도는 읽어야 할 행 수와 쿼리가 N초 안에 완료될 확률로 결정됩니다. 이렇게 적절한 해상도를 동적으로 선택해 쿼리 성능을 최적화하고 할당된 시간 예산 안에 머물게 합니다.

ABR의 큰 장점은 데이터 크기나 기간과 관계없이 고정된 쿼리 예산 안에서 일관되게 결과를 제공할 수 있다는 점입니다. 이는 대규모 데이터셋에서 시간 초과, 오류 또는 높은 비용에 시달리는 다른 시스템과 구별되는 특징입니다.

## 인덱스 선택 방법

샘플링된 데이터로 정확한 결과를 얻으려면 인덱스로 사용할 적절한 값을 선택해야 합니다. 인덱스는 사용자가 데이터를 조회하고 보는 방식과 일치해야 합니다. 예를 들어 사용자가 특정 디바이스나 호스트 이름 기준으로 데이터를 자주 본다면, 해당 속성을 인덱스에 포함하는 것이 좋습니다.

인덱스를 고를 때 고려해야 할 속성은 다음과 같습니다.

* 모든 인덱스 값 전체에 걸쳐 데이터셋 전체의 요약 통계를 정확하게 얻기
* 인덱스의 고유 값 수를 정확하게 계산하기
* 특정 인덱스 값 내부의 요약 통계(예: count, sum)를 정확하게 얻기
* 인덱스에 없는 특정 필드의 `Top N` 값을 보기
* 대부분의 필드로 필터링하기
* 분위수 같은 다른 집계 수행하기

고려해야 할 제약과 트레이드오프는 다음과 같습니다.

* 인덱스에 없는 필드의 고유 개수를 정확하게 구하지 못할 수 있습니다.
  * 예를 들어 `hostname`으로 인덱싱했다면 고유 URL 수를 세지 못할 수 있습니다.
* 인덱스에 없는 필드의 매우 드문 값을 관측하지 못할 수 있습니다.
  * 예를 들어 host로 인덱싱했고 고유 URL이 수백만 개인 경우, 특정 hostname의 특정 URL은 관측되지 않을 수 있습니다.
* 여러 인덱스를 한 번에 가로지르는 정확한 쿼리를 수행하지 못할 수 있습니다.
  * 예를 들어 한 번에 하나의 host(또는 전체 host)만 쿼리해야 정확한 결과를 기대할 수 있습니다.
* 특정 개별 레코드를 반드시 가져올 수 있다고 보장할 수는 없습니다.
* 정확한 이벤트 시퀀스를 재구성할 수도 없습니다.

대부분의 사용 사례에서는 모든 행에 UUID 같은 고유 인덱스 값을 기록하는 것은 권장되지 않습니다. 이렇게 하면 개별 데이터 포인트를 매우 빠르게 가져올 수 있지만, 집계나 시계열을 위한 대부분의 쿼리는 느려집니다.

[Sampling](/analytics/faq/wae-faqs/#sampling)에 대한 일반적인 질문은 Workers Analytics Engine FAQ를 참고하세요.
